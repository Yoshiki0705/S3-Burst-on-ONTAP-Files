# 検証環境と本番の差分（このテンプレートを本番の型として使わない理由）

[`environments/aws-origin/template.yaml`](../../environments/aws-origin/template.yaml) は
**測るための環境**です。`Environment` パラメータに `prod` を入れていないのは意図的で、
**測定に都合のよい選択が、本番では逆になる箇所がいくつもある**ためです。

このページはその差分を並べます。**「こう設定してください」とは書きません** —
このリポジトリが実測しているのは検証構成側であって、本番構成側ではないからです。
**決める項目と、決めるときに要る材料を示すところまで**が範囲です。

## このテンプレートが測定のために選んでいること

| 箇所 | このテンプレート | 測定のためにそうしている理由 | 本番で再考する点 |
|---|---|---|---|
| 配置 | `SINGLE_AZ_1`、1 サブネット | **AZ をまたぐ遅延が数値に入らない。** ファイルシステムと計測ホストを同じサブネットに置ける | 可用性要件。Multi-AZ は AWS の選択肢としてあるが、**このリポジトリでは未測定**（費用も遅延特性も別）|
| 自動バックアップ | `AutomaticBackupRetentionDays` を 0 に落として測る | バックアップのスナップショットが上書き前のブロックを保持し、**容量が 100% になって書き込みが 8 分の 1 に落ちる**。`rm` では戻らない | 保持期間と復旧目標。**0 のまま本番に出すと復旧手段がない** |
| スナップショット | `SnapshotPolicy` を `none` に | 同じ理由。削除したデータも参照され続ける | 世代保護の要件。ランサムウェア対策を含めるかで別の設計になる |
| インライン効率化 | 測定前に無効化 | **圧縮・重複排除がペイロードを吸収し、購入した上限を超えた値が返る** | 容量効率。**有効化は本番では通常の選択**で、そのとき性能値は変わる |
| SSD IOPS | 既定の `AUTOMATIC`（1 GiB あたり 3） | 既定構成の数値を出すため | 読み取り要求。**上げると読み取りが 4 倍級で変わる**（実測 4.04〜4.86 倍）。$0.0204/IOPS-月、**下げるには 6 時間のクールダウン** |
| 検証ホスト | 同一スタックに t3.small を 1 台 | ONTAP 側の操作に VPC 内のホストが必要 | 本番の踏み台・運用ホストの方針。**このホストは受信ルールを持たず Session Manager 専用** |
| fsxadmin の鍵 | Secrets Manager、サービス管理鍵 | **CMK は削除に 7〜30 日の待機が入り、当日中に消せる性質を壊す** | 鍵管理の要件。**鍵ポリシー自体が統制対象なら CMK** |
| S3 側の権限 | `HostS3ResourceArns` などが `*` | アクセスポイントも S3 Files もこのスタックの適用時点で存在しない | **作成後に ARN へ絞る。** 3 つは別ステートメントで、1 つを絞っても他に届かない |
| 不可逆機能 | SnapLock・スナップショットロックを一切有効化しない | **有効化するとボリューム・SVM・ファイルシステム全体が保持期間中削除できない** | 改ざん防止の要件。**保持期間を名指しで決めてから**有効化する。姉妹リポジトリで 128 MiB の監査ログボリュームがファイルシステム全体を 6 か月削除不能にした |
| 書き込み経路 | Origin の S3 Access Point に集約 | 経路を 1 つに保つと、測った数値の出どころが一意になる | Cache 側で書くかどうか。write-back は ONTAP 9.15.1 以降で、**S3 経由の書き込みと競合するとキャッシュの未書き戻しデータが破棄される** |

## 本番で決める項目の一覧

**このリポジトリが判断材料を持っているものと、持っていないものを分けて書きます。**

| 項目 | このリポジトリにある材料 | 段階 |
|---|---|---|
| 配布プロトコル（NFS / SMB）と security style | Origin 作成前に決める理由と、継承の実測 | **検証済み**（[最初に決めること](design-first-decisions.md)） |
| Cache 側の指定値 | **消費側が見る性能は Cache 側の指定値で決まる。** Origin を上げても Cache は上がらない（実測、2026-09-18） | **検証済み**（[実測](verification/throughput-iops-concurrency.md#origin-を-2048-mbps-に上げたときの向きの逆転2026-09-18)） |
| Origin 側の指定値と SSD IOPS | 読み取りの倍率と、その天井が未特定であること | **検証済み**（倍率）／**未解明**（天井） |
| 鮮度の見込み | S3 で書いたものがファイルから見えるまでの実測 | **検証済み**（[可視性](verification/s3ap-nfs-visibility.md)） |
| ピアリングの設計 | このリポジトリは作らない。必要なポートと順序 | **文書化済み**（[配布側](deployment/onprem-terraform.md)） |
| Multi-AZ での性能と費用 | **無い** | **未測定** |
| オンプレミス ONTAP を Cache にした場合 | **無い**（主経路だが未検証） | **未検証**（[検証状況](verification-status.md)） |
| バックアップ・スナップショット設計 | 測定を壊す側の知見のみ。**復旧目標からの設計は範囲外** | **範囲外** |
| 監視・アラート設計 | CloudWatch のどの指標が何を示すかの実測はある | **部分的** |
| 権限モデルの統制 | **2 層（AWS 側とファイルシステム側）で、単一の根拠にはならない** | **検証済みの制約**（[構成の形](architecture.md)） |

## 検証の数値をそのまま本番に持ち込めない理由

**測定条件が本番条件と違うことが、数値の出方に直接出ます。**

- **インライン効率化を切って測っています。** 有効にした本番では、同じワークロードの
  ディスク側の動きが変わります。**効率化を入れたうえでの数値はこのリポジトリにありません。**
- **スナップショットもバックアップも無い状態で測っています。** 世代が積もる本番では
  容量の使われ方が違います。
- **単一クライアント・単一 AZ です。** 台数を増やしたときの上限は
  「各クライアントが読む領域が重なるかどうか」で 5.5 倍動きました。**本番の同時実行の形を
  そのまま測らないと、この差は埋まりません。**
- **すべて ap-northeast-1 の値です。** 単価も、リージョン合計のスループット枠
  （既定 10,240 MB/s）も、リージョンで変わります。

**引用のときに落とせない条件は 9 項目あります。**
[測る前に読む性能の期待値](performance-expectations.md#引用のときに落とさないこと)に一覧があります。

## このリポジトリが答えを持たない範囲

**書いていないことを、書いていないと分かる形にしておきます。**

- **可用性設計**（Multi-AZ、フェイルオーバ時の挙動、RPO / RTO の設計）
- **バックアップと復旧の設計**（保持期間、復旧手順の検証、DR サイト）
- **監査・コンプライアンス対応の判断**。ここにあるのは設計上の考慮点で、
  **法務・コンプライアンス上の判断ではありません**
- **本番運用の手順**（変更管理、権限の棚卸し、インシデント対応）
- **容量計画**（成長率からのサイジング）

**これらが必要な場合、このリポジトリは出発点であって到達点ではありません。**
判断に使えるのは、**測った箇所とその条件**、および**踏んだ失敗とその症状**です。
