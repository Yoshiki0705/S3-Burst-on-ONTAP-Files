# 検証記録 — Amazon S3 Files の `StorageBytes` 増分と作業セット比の 1 回の観測

<!-- ontap-version-exempt-file: this record measures Amazon S3 Files standalone; ONTAP is not
     involved in the quantity measured here. -->

**この記録は Amazon S3 Files 単体を 1 回だけ観測した結果である。** 一般化しない。環境を変えた
ときに同じ比になるかは測っていない。測ったのは、既定の取り込みしきい値以下のオブジェクトを
作業セットの一部だけ読んだとき、高性能ストレージの課金次元である `StorageBytes` がどれだけ
増えたか、という 1 点である。

**`StorageBytes` はデータとメタデータの合計であって、アクティブ割合そのものの測定ではない。**
高性能ストレージに載ったバイト数には、読まれたオブジェクトのデータに加えてメタデータが
含まれる。したがって下の比（読んだバイトに対する増分の倍率）は、アクティブ割合の近似ではあるが、
アクティブ割合を直接測った値ではない。読み方はこの区別を保ったまま使うこと。

この観測は、[FinOps の費用構造](../reference/comparison/finops-s3-vs-s3ap.md)の感度節が置く
「S3 Files 高性能ストレージはアクティブ 100%（保存量の全量をアクティブとして計上）」という
**仮置き・未測定**の前提に対して得た最初の実測だが、**この 1 回の観測では既定値 100% を
下げる変更はしない。** 1 回の観測で、かつ `StorageBytes` がアクティブ割合の直接測定ではないため、
モデルの既定を動かす根拠には足りない（下げるには環境を変えた反復と、保管の請求の時間積分での確定が要る）。

## 検証環境

| 項目 | 値 |
|---|---|
| 計測日 | 2026-10-17 |
| リージョン | ap-northeast-1 |
| データセット | 64 KiB × 200 ディレクトリ × 1,000 ファイル（1 ファイルシステムあたり 200,000 ファイル） |
| 取り込みしきい値 | 既定（`sizeLessThan 131072`）。64 KiB は取り込み対象 |
| 作業セット | 5% と 20% の 2 条件 |
| トリガ | FS-A は `ON_DIRECTORY_FIRST_ACCESS`、FS-B は `ON_FILE_ACCESS` |
| ベースライン | 読み取り前の `StorageBytes` 2,086,912 B |
| メトリクス取得元 | CloudWatch `AWS/S3/Files` の `StorageBytes`、`ImportFailures`、トリガ段階の増分 |
| ファイルシステム ID / アカウント ID | この記録では伏せる（公開物のため。プレースホルダも置かない） |

## 観測結果

### 読んだバイトに対する `StorageBytes` 増分 1.094 倍

作業セットを読んだあと、`StorageBytes` の増分は読んだバイト数の **1.094 倍**だった。これは
保存量の全体に対して、作業セット 5% のとき **5.47%**、20% のとき **21.89%** にあたる。

| 作業セット | `StorageBytes` 増分 ÷ 読んだバイト | 保存量全体に対する比 |
|---|---|---|
| 5% | 1.094 倍 | 5.47% |
| 20% | 1.094 倍 | 21.89% |

**1.094 倍の 0.094 分がデータ以外（メタデータ等）である。** 増分がデータ読み取り量を上回るのは、
`StorageBytes` がデータとメタデータの合計だからで、アクティブ割合が 100% を超えるという意味
ではない。

### トリガ差による段階 4 の増分の違い

同一データセットに対し、トリガ設定だけを変えた 2 ファイルシステムで、段階 4 の `StorageBytes`
増分が分かれた。

| ファイルシステム | トリガ | 段階 4 の `StorageBytes` 増分 |
|---|---|---|
| FS-A | `ON_DIRECTORY_FIRST_ACCESS` | +71.7 MB |
| FS-B | `ON_FILE_ACCESS` | +10.3 MB |

**`ON_DIRECTORY_FIRST_ACCESS` は、ディレクトリを最初にたどったときに配下の対象ファイルを
まとめて取り込む。** そのため読んだファイル数より多くのバイトが高性能ストレージに載り、段階 4 の
増分が `ON_FILE_ACCESS` より大きくなった。どちらの向きが課金上安いかは、作業セットと
アクセスパターンで変わる設計判断であり、この 1 回の観測から一般化しない。

### コントロールと `ImportFailures`

**コントロールは成立した。** ベースライン 2,086,912 B は読み取り前の値で、増分はこの基準からの
差として取った。

**`ImportFailures` が 1 ファイルシステムあたり約 200,000 件出た。** データセットのファイル数と
同じ桁だが、**原因は調査していない。** 失敗したインポートが `StorageBytes` 増分に与える影響も
切り分けていない。この件はこの記録では未解決として残す。

## 課金側の突き合わせと残る未確認

**請求の数量は 2026-10-19 に Cost Explorer で確認した。** 結果は
[請求数量と CloudWatch 指標の突き合わせ](s3files-billing-reconciled.md)にある。この測定（M-A）では、
読み取りの請求数量（`APN1-Files-Read` 3.246 GiB）が CloudWatch の `DataReadBytes` と
`MetadataReadBytes` の合計（約 3.23 GiB）に比 約 0.995 で一致した。書き込みの請求数量
（`APN1-Files-Write` 5.258 GiB）は、`StorageBytes` の最大値から読み取り前のベースラインを引いた
取り込み量の見積りの約 0.97 で、CloudWatch の書き込み指標には取り込み分が出ない。
保管（`APN1-Files-TimedStorage-ByteHrs`）は時間積分していない。

**請求額は確認していない。** Cost Explorer の値は `Estimated: true` で、クレジットで相殺されて
正味 0 だった。上の比を金額に読み替えない。

次は引き続き未確認である。

- 保管の請求が `StorageBytes` の時間積分に一致するか（桁が合うことまで）
- 約 200,000 件の `ImportFailures` が請求の数量に与える影響（書き込みの数量が `StorageBytes` の
  増分に近いので、失敗した取り込みが大きく課金されている形跡はないが、切り分けていない）
- FS-B で `DataReadBytes` が CloudWatch に出なかった理由（請求の数量とは整合する）

## 読み取れること

**作業セットの一部だけを読んだとき、高性能ストレージに載るのは読んだ分におおむね比例する**
（この 1 回の観測では、読んだバイトの 1.094 倍）。ただし 3 つの留保が付く。(1) 1 回の観測であり、
環境を変えた反復をしていない。(2) `StorageBytes` はデータとメタデータの合計で、アクティブ割合の
直接測定ではない。(3) 読み取りと書き込みの請求数量は確認したが、保管の請求は時間積分で突き合わせておらず、
請求額は確認していない。これらが解けるまで、感度節の既定値（アクティブ 100%）は
下げない。
