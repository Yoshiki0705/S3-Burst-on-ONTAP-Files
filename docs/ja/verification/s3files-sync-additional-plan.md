# S3 Files のファイルからバケットへの反映の追加測定計画

<!-- ontap-version-exempt-file: this is a measurement plan for Amazon S3 Files standalone, not a
     record of what was measured, and not about ONTAP. -->

**この文書に測定値はない。** Amazon S3 Files の「ファイルに書いてから S3 API で読めるまで」の
反映を、1 つの代表値ではなく条件ごとに分けて測るための計画を書く。実行後に結果を別の記録として
追加する。

既に測った反映の速さと意味論は[実測記録](s3files-measured.md)にある。そこでは、ファイル → S3 の
p50 63,769.3 ms（約 60 秒の窓、30 回すべて 63.8〜66.3 秒）、S3 → ファイルの p50 1,533.1 ms、
エクスポート側は CloudWatch `ExportAge` peak 66.06 秒がクライアント側 max 66.33 秒と 0.27 秒差で
一致、インポート側は `ImportAge` peak 62.80 秒がクライアント側 max 14.36 秒と一致しない、までを
記録している。**この計画はその続きで、最大反映時間と、反映を遅らせうる条件を分けて測る。**

パターン記号は **SY** で、既存の S / A / D / E / E1 / E2 / F / G と重ならない。

## この計画が答えないこと

- **最大反映時間の保証値ではない。** 実測はインポート側で 2 系統が一致せず、公式資料にも最大
  反映時間の記載を見つけられていない。この計画は上限値を主張せず、条件ごとの分布を出す。
- **スループットや IOPS ではない。** それは[ファイルシステム性能の測定計画](s3files-throughput-matrix-plan.md)の役割。
- **反映の速さの再測ではない。** 既に測った代表値（[実測記録](s3files-measured.md)）は再測しない。
  この計画が足すのは、代表値の背後にある条件分けである。

## なぜ測るか — 代表値 1 つでは分けられない条件

[実測記録](s3files-measured.md)の反映は、同一ファイルへ書いて書き込みを止め、無書き込み待機が
成立してからエクスポートされる 1 本の経路しか測っていない。本文の反映は 4 段（(a) 書き込み完了・
永続化、(b) 無書き込みの待機、(c) エクスポート開始、(d) S3 API から見える）に分かれるが、
各段の長さと、段を遅らせうる条件（待機が成立しない連続追記、別ファイルの更新による順番待ち、
同時更新による競合）は分けて測っていない。

| 分けたい条件 | いまの状態 |
|---|---|
| 無書き込み待機が成立しない間、エクスポートが遅れ続けるか | **未測定**（書き込みを止めてからの 1 経路のみ） |
| 更新停止から (d) までの分布 | **一部**（p50 と max のみ。待機成立の時刻を分離していない） |
| 別ファイルの更新が走っている最中の対象ファイルの反映 | **未測定**（単一ファイルのみ） |
| 同時更新と競合・lost+found の発生条件 | **一部**（窓の内側 5 秒の競合のみ。窓の外は未測定） |

## 測定パターン

| ID | 何を動かすか | 何を固定するか | 何を確かめるか | 経路確認（CloudWatch） | 判定基準 |
|---|---|---|---|---|---|
| **SY-1** | 連続追記の継続時間（無書き込み待機を成立させない）。1 ファイルへ一定間隔で追記し続ける | ファイルサイズ、追記間隔、ホスト、マウント条件 | 待機が成立しない間、エクスポートが遅れ続けるか。追記を止めた後に初めて (c) が始まるか | `ExportAge` が追記中は進まず、追記停止後に立ち上がるか | 追記中は S3 側に新バージョンが出ず、停止後に出る。`ExportAge` の立ち上がりが停止時刻と一致 |
| **SY-2** | 更新停止後の待機成立から (d) までの時間 | 追記間隔を 0（単発書き込み）、サイズ、ホスト | 待機成立の時刻を分離した上での (c)→(d) の分布 | `ExportAge` の立ち上がり時刻を (c)、クライアント側の `GetObject` 成功を (d) とする | n=30 で p50 / p90 / max を出し、既存の 63.8〜66.3 秒と整合するか |
| **SY-3** | 別ファイルの更新が走っている最中に、対象ファイルを 1 回更新する | 対象ファイルのサイズ、背景更新のレート、ホスト | 背景の更新が対象ファイルの反映を遅らせるか（順番待ち） | `PendingExports` の滞留と、対象ファイルの `ExportAge` を分けて見る | 背景更新ありと背景更新なしで、対象ファイルの (c)→(d) に差が出るか。差があれば順番待ちの証拠 |
| **SY-4** | 同一ファイルの同時更新（ファイル側と S3 API 側）。更新の時間差を窓の内外で振る | キー、サイズ、ホスト | 競合の勝者と lost+found 退避の発生条件。窓の内と外で変わるか | `LostAndFoundFiles` の件数と、退避ディレクトリのエントリ数を突き合わせる | 退避件数（ファイルシステム側）と `LostAndFoundFiles`（サービス側）が一致。窓の内外で勝者が変わるかを記録 |

**SY-4 は[実測記録](s3files-measured.md)の競合測定の続きである。** 既存は窓の内側（5 秒後）の
競合 3 回のみで、`.s3files-lost+found-<file-system-id>` へ 0 → 3 の退避を観測し、
`LostAndFoundFiles` peak 3.00 と一致した。**この計画は、競合の時間差を窓の外にも振り、
勝者と退避の条件が変わるかを測る。**

## 合意済みの設計判断

**測ってから決めると出た数値に都合のよい形を選べるので、先に確定させる。**

| 論点 | 確定した形 | 理由 |
|---|---|---|
| 代表値 | **定常窓の中央値・窓長・同一条件 2 回の幅。最大単独で語らない** | 最大単独は最も再現しない。既存の反映測定でもこの規律を使った |
| 経路の確認 | **クライアント側の時刻だけでなく CloudWatch（`ExportAge` / `ImportAge` / `LostAndFoundFiles` / `PendingExports`）と突き合わせる** | 既存測定で `ExportAge` と `ImportAge` の一致・不一致が切り分けの決め手になった |
| 最大反映時間 | **上限値として報告しない。条件ごとの分布として報告する** | 公式資料に記載を見つけられておらず、インポート側は 2 系統が一致しない |
| 待機成立の時刻 | **書き込み停止の時刻を記録し、(c) を `ExportAge` の立ち上がりで分離する** | 既存測定は (a)→(d) の全体しか分離していない |

## 必要な環境

**未デプロイである。** S3 Files の作成・マウント・破棄の手順は
[S3 Files 検証環境セットアップ](../deployment/aws-s3files-compare.md)にあり、以下はこの計画に
固有の要件である。いずれも課金される。

| 要素 | 条件 | 理由 |
|---|---|---|
| S3 Files ファイルシステム | 汎用バケット全体、バージョニング必須、SSE-S3 か SSE-KMS | S3 Files の前提（[セットアップ](../deployment/aws-s3files-compare.md#前提条件)） |
| ホストロールの CloudWatch 権限 | `logs:CreateLogGroup` / `CreateLogStream` / `PutLogEvents`、`cloudwatch:PutMetricData` | 無いとマウントが無言でハングする（[マウントの落とし穴](s3files-mount-pitfalls.md)） |
| botocore | dnf で導入（`pip3` 不可） | 無いと `access denied` かメトリクス不可（同上） |
| 時刻同期 | クライアントの NTP が合っていること | クライアント側の時刻と CloudWatch の時刻を突き合わせるため |
| 退避の可視化 | `s3files:ClientRootAccess`（SY-4 の観測時のみ、一時付与） | `.s3files-lost+found-*` は `0700 root:root` で、アクセスポイント経由では見えない（[実測記録](s3files-measured.md)） |

## 記録する項目

**1 つ欠けると引用できない。** 一覧は[性能検証の考慮点](../reference/performance-testing-guide.md#記録に必ず添える項目)にあり、
この計画に固有のものは次のとおり。

- 測定日、リージョン、S3 Files の取り込みしきい値と保持窓、暗号化方式、NFS バージョン
- マウントの**実効オプション**（`findmnt` の出力。`actimeo` でなく `acregmin` を見る）
- 書き込みの時刻（停止時刻を含む）、追記間隔、背景更新のレート、競合の時間差
- クライアント側の p50 / p90 / max と、CloudWatch の `ExportAge` / `ImportAge` / `LostAndFoundFiles` / `PendingExports`
- 退避件数（ファイルシステム側）と `LostAndFoundFiles`（サービス側）の突き合わせ結果

## 不可逆操作と破棄の順序

**この計画に不可逆な機能（S3 Object Lock、保持設定、Vault Lock）は入れない。** 入れる場合は
保持値を名指しした明示の指示が要る（AGENTS.md の不可逆操作の節）。S3 Files 固有の破棄順は
[ファイルシステム性能の測定計画](s3files-throughput-matrix-plan.md#不可逆操作と破棄の順序)と同じで、
エクスポート待ちが捌けるのを `ExportAge` で確認してからファイルシステムを削除し、バケットは最後に
バージョンごと空にして消す。**成功レスポンスは成功の証拠ではない。** 削除は戻り値でなく一覧 API の
件数で判定する。
