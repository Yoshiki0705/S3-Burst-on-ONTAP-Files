# S3 Files と本構成の比較検証

## TL;DR

**両方とも実測値です。** 左はこのリポジトリの構成（2026-08-09）、右は S3 Files（2026-09-01）。
どちらも同一ホスト・単一クロック・64 B・並列度 1・n=30 で測っています。

| # | 方向 | 本構成（実測） | S3 Files（実測） |
|---|---|---|---|
| 1 | ファイル書き込み → S3 API で読み取り | p50 44 ms | **p50 63,769 ms** |
| 2 | ファイル書き込み → ファイル読み取り（拠点へ） | p50 6 ms | 該当なし（機構を持たない） |
| 3 | S3 API 書き込み → 拠点のファイル読み取り | **p50 8 ms** | **p50 1,533 ms**（同一ストレージ内） |
| 4 | S3 API 書き込み → 同一ストレージのファイル読み取り | p50 3 ms | p50 1,533 ms |

**桁が違いますが、これは優劣ではなく設計点の違いです。** S3 Files はファイル側の書き込みを
約 60 秒まとめてから S3 へ出す設計で、その代わりに移行が不要でバケットが正本のまま残ります。

LT で言えること 3 つ。

1. **同じ要求に対する 2 つの設計点であり、速い遅いの話ではありません。** 本構成は
   ファイルプロトコル側への反映を p50 8 ms で実測（方向 3、64 B、並列度 1、
   [全方向比較](cross-protocol-directions.md)）。S3 Files は同方向が p50 1,533 ms、
   逆方向が p50 63,769 ms でした（[実測記録](s3files-measured.md)）。
   後者は仕様どおりで、**約 60 秒のバッチング窓が実在し分布も狭い**ことを確認しています
   （30 回すべて 63.8〜66.3 秒）。統合の単純さと移行の不要さがその対価です。
2. **どちらも方向で非対称ですが、非対称の幅が違います。**
   本構成は S3 → ファイル 8 ms、ファイル → S3 44 ms で 5 倍。S3 Files は
   1,533 ms 対 63,769 ms で 42 倍でした。**片方の数値をもう片方の代わりに使えません。**
   S3 Files のエクスポート側は CloudWatch の `ExportAge`（peak 66.06 秒）と
   クライアント側の max（66.33 秒）が 0.27 秒差で一致しており、2 系統で裏付けています。
3. **前提条件の形が違います。** 本構成は収集層に ONTAP 9.17.1 以降を要求します。
   S3 Files はバケットに S3 バージョニングを要求し、利用側を AWS 上の Linux に限定します
   （NFSv4.1 と 4.2 のみ、SMB と NFSv3 は対象外）。**どちらも「前提なし」ではありません。**

> **数値の扱い**: 左側の数値はすべてこのリポジトリの実測で、環境は下記のとおりです。
> 右側は[計測スクリプト](../../../scripts/measure_s3files_visibility.py)を実機で走らせた
> あとに入ります。実測前に見込み値を入れると、後から出典を辿れない数値が残ります。

### サイズしきい値による読み取り遅延（S3 Files のみ）

S3 Files は既定 128 KiB 未満を高性能ストレージへ取り込み、1 MiB 以上の読み取りは
バケットから直接ストリームします。しきい値の両側で遅延が変わるはずですが、
**この構成には対応する機構がないので、比較表ではなく S3 Files 単独の表になります。**

| オブジェクトサイズ | 経路（ドキュメント記載） | p50 | p90 | max | n |
|---|---|---|---|---|---|
| 64 KiB（しきい値未満） | 高性能ストレージ | 12.6 ms | 13.7 ms | 14.2 ms | 30 |
| 4 MiB（1 MiB 以上） | バケットから直接ストリーム | 48.0 ms | 63.5 ms | 66.2 ms | 30 |

**この 3.8 倍はサイズ差と経路差が混ざった値です。** 経路だけを切り出す測定を別途行いました。
**オブジェクトサイズを 64 KiB に固定して取り込みしきい値だけを動かすと、
高性能ストレージ上 p50 10.8 ms 対 バケット直読 p50 55.0 ms で約 5.1 倍**でした
（[実測記録](s3files-measured.md)）。経路の効果は混ざった値より大きく、
4 MiB の 48.0 ms は 64 KiB の直読 55.0 ms に近いので、**支配しているのはサイズではなく経路**です。

CSV の列は `プロトコル, マウント方法, p50, p90, max, n, 計測日` で、
[計測スクリプト](../../../scripts/measure_s3files_visibility.py)の `--csv` が
この順で出力します。上の表に貼れる形にしてあります。

## 設計点の違い

| 観点 | S3 Files | 本構成（S3 AP で収集 → FlexCache で配布） |
|---|---|---|
| 正本 | S3 バケット 1 つ。オブジェクトとファイルが同じバケットを指す | FSx for ONTAP の Origin ボリューム |
| 移行 | 不要。既存バケットにファイルシステムを付ける | 収集の受け口を S3 Access Point に寄せる設計が前提 |
| 実装基盤 | Amazon EFS | ONTAP の FlexCache |
| 書き込み経路 | S3 API とファイルの両方から書ける | 収集は S3 Access Point 経由で Origin に集約 |
| 反映（S3 → ファイル） | **p50 1,533 ms**（実測） | **p50 8 ms**（実測、方向 3） |
| 反映（ファイル → S3） | **p50 63,769 ms**（実測。約 60 秒の窓は実在） | p50 44 ms（実測、方向 1） |
| 読み出し側プロトコル | NFSv4.1 / 4.2 のみ | NFS と SMB |
| 読み出し側の設置場所 | AWS 上の EC2 / Lambda / EKS / ECS | 拠点のオンプレミス ONTAP を含む |
| 前提条件 | バケットに S3 バージョニング必須、SSE-S3 か SSE-KMS | 収集層に ONTAP 9.17.1 以降 |
| 部分的な配置 | アクティブな作業セットのみ高性能ストレージに載る | Cache は疎で、読まれた分だけ保持 |
| ロック | advisory のみ。mandatory locking は非対応 | ONTAP のファイルロック |
| データ管理機能 | S3 の機能群（バージョニング、ライフサイクル、イベント通知） | ONTAP の Snapshot、FlexClone、SnapMirror |
| 対象外のデータ | Glacier 系と Intelligent-Tiering のアーカイブ層はファイルから読めない | S3 のイベント通知、ライフサイクル、バージョニング |

**発想が近い部分があります。** どちらもアクティブな作業セットだけを低遅延の層に置き、
全量を複製しません。違うのは、その層がどこにあり、誰が正本かです。

## 選び方

判断軸は 3 つで、順番に見ると分岐します。

| # | 問い | S3 Files に寄る | 本構成に寄る |
|---|---|---|---|
| 1 | 読み出し側はどこにいて、何を話すか | AWS 上の Linux で、NFSv4.1 以降を話せる | 拠点にあり、NFSv3 か SMB で固定されている |
| 2 | ファイルに書いたものを S3 側でいつ見たいか | 分オーダーで足りる | 秒未満から数十ミリ秒で見たい |
| 3 | 正本をどちらに置くか | S3。S3 の機能群を使い続けたい | ONTAP。Snapshot や SnapMirror を前提にしている |

**1 で「拠点・NFSv3・SMB」に当たった時点で S3 Files は選択肢から外れます。**
対応プロトコルの制約なので、他の軸で埋め合わせられません。逆に 1 を満たし、
2 が分オーダーで足りるなら、統合の単純さと固定費の差は S3 Files 側の利点です
（費用の比較は[FinOps の費用構造](../reference/comparison/finops-s3-vs-s3ap.md)）。

判断のフローチャートは[選び方](../reference/decision-trees/choosing-this-architecture.md)、
代償の一覧は[代替案との比較](../reference/comparison/alternatives.md)にあります。

### `nconnect` 非対応が持つ意味

上の表の「`nconnect` 非対応」は、実測してから重みが変わった 1 行です。

Linux の NFS マウントは既定でサーバーごとに TCP 接続を 1 本しか張り、VPC 内の単一フローは
5 Gbps 付近で止まります。FSx for ONTAP 側でストリーム数を 1 / 4 / 8 と振った読み取りは
588.1 / 589.9 / 589.7 MB/s で**ストリーム数にまったく反応せず**、`nconnect=16` を付けると同じ
測定が 2000 MB/s 級になりました（[実測記録](throughput-iops-concurrency.md#2048-mbps-段でのコールドリード4-回測って-3-回捨てた)）。

**S3 Files ではこの操作ができません。** ドキュメントが `nconnect` を非対応として明記しています。

| | 単一フローの上限を外す手段 |
|---|---|
| FSx for ONTAP の NFS | `nconnect` を指定する。**無料** |
| S3 Files のファイル経路 | **なし**（`nconnect` 非対応） |

**測ったので、「だから遅い」ではないことが分かりました。** ストリーム数を 16 まで上げた結果です。

| ストリーム数 | S3 Files 読み取り |
|---|---|
| 1 | 67.9 |
| 4 | 264.3 |
| 8 | **451.3** |
| 16 | 404.8 / 450.0 |

単位 MB/s、c5n.2xlarge、非圧縮、O_DIRECT。**8 ストリームで約 450 MB/s に達し、16 では伸びません。**
450 MB/s は 3.6 Gbps なので、**単一フローの上限（約 5 Gbps）には当たっていません。**

**止めているのはローカルのプロキシです。** 16 ストリームの読み取り中の CPU が
`efs-proxy` に 67.3% + 18.1% + 14.9%（8 vCPU）でした。そして構造がマウントオプションに出ています。

```text
127.0.0.1:/ nfs4 rw,vers=4.2,rsize=1048576,wsize=1048576,proto=tcp,port=20812,addr=127.0.0.1
```

**マウントの相手は 127.0.0.1、つまり同じホストの `efs-proxy` です。** サービスではありません。
`nconnect` はマウントの接続数を増やすオプションなので、**増えるのはローカルプロセスへの接続で、
`efs-proxy` とサービスの間には届きません。** FSx for ONTAP のマウントは相手がファイルシステム
自身なので、そこが構造的に違います。

**そして `nconnect` を指定するとマウントはハングしました**（90 秒でタイムアウト）。拒否でも
黙殺でもありません。**未対応のオプションを試すときは `timeout` を付けてください。**

設計上言えることは次のとおりです。**FSx for ONTAP 側には並列度を上げずにスループットを上げる
無料の手段があり（`nconnect`、実測 4.95 倍）、S3 Files 側にはありません。** ただし
**S3 Files が止まる位置は単一フロー上限ではなくローカルプロキシの CPU なので、対処はホストを
太くする方向であって、マウントオプションではありません。**

| 双方が同じファイルを変更したときの挙動 | **実測済み。** バケット側が正本になり、ファイル側は lost and found へ移る（3/3、`LostAndFoundFiles` peak 3.00 で裏付け） |

## 実測値を先に書かない理由

見込み値を入れておいて後で直す運用は、このリポジトリでは一度失敗しています。
NFS → S3 AP 方向の p50 を 873 ms として公開し、あとで 44 ms に訂正しました。
差の大部分は CLI のプロセス起動コストで、ストレージの反映遅延ではありませんでした
（[訂正の経緯](cross-protocol-directions.md)）。

**測定方法が数値の桁を変えます。** だから S3 Files 側も同一手法で測るまで空欄にしていました。
2026-09-01 に測り、埋めました。同時に、クライアント側の値を CloudWatch の `ExportAge` と
突き合わせています。エクスポート側は 0.27 秒差で一致し、**インポート側は一致しません**
（クライアント max 14.36 秒 対 `ImportAge` peak 62.80 秒）。
一致しなかったことも結果として[実測記録](s3files-measured.md)に残しています。

## スループットの比較を 1 つの列にしない理由

スループットは[別の記録](throughput-iops-concurrency.md)で同一ホストから測りました。ここに
要点だけ置きます。**表を横に並べるときは上限の種別を必ず併記してください。**

| 経路 | FSx for ONTAP S3 Access Point | Amazon S3 |
|---|---|---|
| 上限の性質 | **購入した** throughput capacity | **購入していない**弾性 |
| 書き込み（8 MiB、並列 16） | 129.5 MB/s（128 MBps の段） | 757.9 MB/s |
| 読み取り（8 MiB、並列 16） | 579.3 MB/s | 647.0 MB/s |
| 503（全点） | 0 件 | 0 件 |

書き込みの差は速度差ではなく、購入した段と弾性の差です。**読み取りは 12% 差でほぼ並びます。**
そして FSx for ONTAP 側の読み取り 579.3 MB/s は、購入した 128 MBps の 4.5 倍です。**書き込みの段を
読み取りの見積りに使うと外します。**

ファイル経路では S3 Files 側の単一ストリームが 46.5 MB/s、8 ストリームで 369.6 MB/s です。
**後にストリーム数を 16 まで伸ばし、頭打ちの位置を約 450 MB/s と特定しました**（[下記](#nconnect-非対応が持つ意味)）。
369.6 は頭打ちではなく、そこで止めた値でした。
経路に `efs-proxy --tls` が入るため単一ストリームが遅く、並列で伸びます。**転送中の暗号化が
既定で入る構成の代価**であり、欠陥ではありません。

FSx for ONTAP 側のファイル経路の読み取りは、当初 1126.0 MB/s と書いて撤回し、その後
warm と cold を分けて決着しました。**warm 1164.1 MB/s、cold 751.0 MB/s（比 1.55x）。**
経緯は[実測記録](throughput-iops-concurrency.md#ファイル経路の読み取り-1130-mbs-が安定した値でないこと決着済み)にあります。

> **この warm 1164.1 と cold 751.0 は、後から 2 つとも取り下げました。** どちらも `/dev/zero` を
> 書いたファイルの読み取りで、ONTAP はゼロブロックをディスクに行かずに返します。同じ段・同じ
> 介在量でデータだけを非圧縮に変えると **warm 297.8 対 cold 297.2、比 1.00** になり、
> **warm と cold の差は存在しませんでした**（[詳細](throughput-iops-concurrency.md#b--128-mbps-段の-warm-と-cold-の一致非圧縮)）。
> 「1130 MB/s はこのファイルシステムの読み取り性能ではない」という結論は残りますが、理由は
> 「warm なキャッシュを測っていた」ではなく**「読み取り性能を測っていなかった」**でした。

## 上限の種別が違うことが動作として出る箇所

**同じ設定を 1 台から、次に 2 台から同時に実行すると、2 つの上限は逆向きに振る舞います。**

| 対象 | 1 台 | 2 台の合計 | 1 台あたり |
|---|---|---|---|
| FSx for ONTAP S3 AP 読み取り | 585.3 | **592.5** | 半減 |
| Amazon S3 読み取り | 649.3 | **1308.9** | ほぼ不変 |

単位 MB/s、8 MiB、並列度 16。

FSx for ONTAP 側は購入した容量を分け合うので、クライアントを増やしても合計は増えません。
Amazon S3 側は合計が 2.02 倍になり、1 台あたりは変わりません。**単一ホストで見えていた
649 MB/s は S3 の上限ではなく、クライアント側の上限でした。**

選び方への含意は具体的です。**読み手が多い構成では、FSx for ONTAP 側は容量計画を
ファイルシステム単位で行い、Amazon S3 側はクライアント側の帯域で行います。** どちらが速いかでは
なく、増やし方が逆だという違いです。
