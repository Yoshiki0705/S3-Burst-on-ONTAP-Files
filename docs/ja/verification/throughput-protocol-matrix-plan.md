# プロトコル別スループットの測定計画

**この文書に測定値はない。** 何をどう測るか、そのために何が必要か、そして既存の測定では答えに
ならない理由を書く。実行後に別の記録として結果を追加する。

可否（どの組み合わせがマウントできるか）は
[プロトコル別の可否](protocol-matrix-efs-vs-ontap.md)にある。**可否を先に読むこと。** 非対応の
組み合わせは測定の前に落ちる。

## 測定パターン

| ID | 対象 | 書き込み | 読み取り | 何を確かめるか |
|---|---|---|---|---|
| **A-1** | FSx for ONTAP Origin ボリューム | S3 API | **S3 API** | 同一データを同じ経路で読んだ値 |
| **A-2** | 同じボリューム、同じデータ | S3 API | **NFS / SMB** | 経路を変えるだけで読み取りがどう変わるか |
| **D** | Amazon EFS | NFSv4.0 / NFSv4.1 | 同じ | EFS のプロトコル別 |
| **E** | FSx for ONTAP **第二世代** | SMB / NFSv3 / NFSv4.0 / NFSv4.1 / NFSv4.2 | 同じ | FSx for ONTAP のプロトコル別 |
| **E1** | FSx for ONTAP 第一世代 | NFSv4.1 | 同じ | 世代差。プロトコルを固定して比べる |

**A-1 と A-2 は同じデータに対して行う。** 書き込みを 1 回だけ実施し、そのあと読み取りの経路を
変える。書き直すと、比較しているものがデータの配置差を含んでしまう。

**D と E を同じ列に並べられるのは NFSv4.0 と NFSv4.1 だけである。** 他は E のみの行になる。

### プロトコル別の測定を第二世代で行う理由

**プロトコル差を見るには、プロトコル差より上に余裕が必要である。** 第一世代 Single-AZ の読み取りは
2,048 MBps で、そこに複数のプロトコルを当てると、どれもファイルシステムの上限を報告して差が
出ない。差が無かったのか、差が上限に隠れたのかを区別できない。第二世代の 6,144 MBps は、
プロトコル差が上限に達する前に現れる余地を作るために選ぶ。

**もう 1 つは、SMB がディレクトリへの外向き通信を必要とすることである。** AD に参加した SVM は
Kerberos と LDAP、そして ONTAP が行う win から unix への name-mapping 参照のためにドメイン
コントローラへ到達する必要がある。第一世代のファイルシステムはこの環境が作ったものではなく、
そのセキュリティグループを書き換えることは共有リソースへの変更になる。第二世代側なら、規則は
この環境のテンプレートの中で完結する。

**世代差は E1 として別に測る。** プロトコルを NFSv4.1 に固定して第一世代と第二世代を並べる。
プロトコル別（E）と世代差（E1）を 1 つの表に混ぜると、変わったのがプロトコルなのか世代なのかが
言えなくなる。

**SMB 用の SVM は NFS 用の SVM と同じファイルシステムに置く。** 2 つは別の識別子だが、
**スループットキャパシティは共有する。** 同時に測ると 1 つの 6,144 MBps を分け合うことになるので、
**片方ずつ測り、どちらを止めていたかを記録する。**

費用の内訳は[検証パターンごとの費用構造](../reference/comparison/finops-performance-test-patterns.md)にある。

## 既存の測定でこの比較が成立していない理由

A-1 と A-2 に相当する数値は[既存の記録](throughput-iops-concurrency.md)にあるが、**比較として
成立していない。** 3 つの理由がある。

1. **ペイロードが違う。** S3 API 読み取りの 579.3 MB/s は圧縮可能なテストデータでの測定である。
   同じ記録の中で、読み取りは圧縮可能データだと公称上限の 4 倍で返ることが分かっている。
2. **形が違う。** S3 API 側は 8 MiB オブジェクトの並列 64、NFS 側は 8 ストリームの逐次で、
   1 リクエストの大きさと並列の作り方が揃っていない。
3. **同一データではない。** それぞれの経路で別に書いたデータを読んでいる。

したがって「S3 API で読むと NFS より速い / 遅い」は、この記録からは言えない。

## 使うツール

### ファイルプロトコル側 — auto_vdbench

[auto_vdbench](https://github.com/shuichi-taketani/auto_vdbench) は Oracle VDBENCH を駆動して
IOPS とレイテンシを測り、グラフと CSV / Excel にまとめる。IOPS を振りながらレイテンシの変化を
追えるので、**「頭打ちがどこか」ではなく「どのレイテンシまでなら何 IOPS 出るか」が出る。**
ONTAP 側の統計収集にも対応する。

**このツールはマウントされたパスに対して動く。** S3 API のワークロードは生成できない。

### オブジェクト側 — 既存スクリプト

A-1 の S3 API 読み取りには、このリポジトリの `scripts/measure_s3_throughput.py` を使う。
**auto_vdbench と同じ数字にはならないので、2 つを同じ表に並べるときは測定器が違うことを添える。**

| 測る対象 | ツール | 出る単位 |
|---|---|---|
| NFS / SMB | auto_vdbench（VDBENCH） | IOPS、レイテンシ、スループット |
| S3 API | `scripts/measure_s3_throughput.py` | スループット、req/s、p50 |

## 必要な環境

**未デプロイである。** テンプレートと実行順序は
[測定環境](../../../environments/perf-matrix/README.md)にあり、以下はそれが作るもの、および
手で用意するものである。いずれも課金される。

| 要素 | 条件 | 理由 |
|---|---|---|
| FSx for ONTAP 第二世代 | SINGLE_AZ_2、6,144 MBps ×1 HA ペア、SSD 2,048 GiB | E と、E1 の第二世代側。SSD は 900 GiB のボリューム 2 つ（NFS 用と SMB 用）を置くため |
| FSx for ONTAP 第一世代 | 既存、2,048 MBps へ引き上げ | A と E1。新規には作らない |
| Amazon EFS | 1 ファイルシステム、Elastic と Provisioned の 2 モード | D の対象。**モードで上限が 20 倍違う** |
| Linux クライアント | c5n.9xlarge ×1、c5n.2xlarge ×8 | 帯域が保証値のインスタンスでないと、頭打ちの原因を切り分けられない |
| **Windows クライアント** | c5n.9xlarge、ドメイン参加済み | SMB 測定用。EFS は Windows からマウントできないので E のみ。Linux 側と同じインスタンス型にする |
| **AWS Managed Microsoft AD** | Standard、**2 AZ に 2 サブネット**（サービス要件） | SMB 測定用。SVM と Windows クライアントを参加させる |
| **SMB 用の SVM** | NTFS セキュリティスタイル、AD 参加済み | NFS 用 SVM とは別に立てる（理由は下） |
| VDBENCH | Oracle のサイトから取得（ライセンス同意が必要） | auto_vdbench の前提 |
| Java | VDBENCH の実行に必要 | 同上 |

**この環境に既存の AD は無い。** 既存 SVM 2 つは `MEAS.FSXN.LOCAL` に参加した記録を持つが、
**その記録の DNS アドレスに ENI が存在せず、アカウントに Managed AD も無い。** SVM が `CREATED` を
返すのは参加時の設定が残っているだけで、いま参加できることを意味しない。**SMB を測るには
ディレクトリを新設する。**

### SMB 用の SVM を分ける理由

**CIFS を有効にした SVM では、ONTAP がファイルシステム操作の一部で win から unix への
name-mapping 参照を行う。** この参照は到達可能なドメインコントローラを必要とする。NFS 用の SVM を
参加させると、**この行程が NFS の測定値すべての経路に入る**。NFS の数値が NFS の数値でなくなり、
ディレクトリ側の不調がストレージ側の結果として現れる。SVM を 2 つに分けると、2 つのプロトコル
経路は互いに独立する。

### SMB の測定値に添える条件

| 項目 | 理由 |
|---|---|
| **ドメインコントローラがどの AZ にあるか** | Managed AD は 2 AZ を要求する。DC は認証と name-mapping の経路には乗る（データ経路には乗らない）ので、AZ を跨ぐ分の遅延が SMB の値に含まれる |
| **マウントに使ったアカウント** | `Domain Admins` のメンバーは権限評価の一部を迂回する。代表的な値が要るなら非特権アカウントを作る |
| **ボリュームのセキュリティスタイル** | NTFS を選んだ。参照される権限モデルが変わる |
| **SMB のダイアレクト** | 2.0 / 3.0 / 3.1.1 のどれで接続が成立したか |

**リードキャッシュの扱いを先に決めること。** FSx for ONTAP にはインメモリと NVMe の 2 層があり、
容量を超えない読み取りはディスクに到達しない。**2 層の合計を確実に超える量**を読むか、
`system node external-cache` で状態を確認したうえで結果を読む。詳細は
[スループットの実測記録](throughput-iops-concurrency.md)にある。

**インライン効率化はデータを書く前に切る。** 書いた後では、バックグラウンド処理が終わるまで
`PATCH` が拒否される。

**EFS はマウント方法でクライアント 1 台あたりの上限が変わる。** Elastic かつ
`amazon-efs-utils` 2.0 以降（または EFS CSI ドライバ）で 1,500 MiBps、**素の `mount -t nfs` では
500 MiBps** である。**どちらでマウントしたかを記録する。** ファイルシステム単位の 61,440 MiBps に
近づけるにはクライアントを並べる必要があり、1 台の測定値をファイルシステムの上限として読むと
外す。

## 測定条件（両ツールで揃えるもの)

| 項目 | 値 |
|---|---|
| テストデータ | 非圧縮（`dedup-ratio 1`、`compression-ratio 1`） |
| ブロックサイズ | 4 KiB / 64 KiB / 1 MiB / 8 MiB |
| 読み書き比 | 100% read、100% write、70/30 |
| アクセスパターン | 逐次、ランダム |
| マウントオプション | 実効値を記録する（指定値ではなく） |
| 繰り返し | 同一条件を 2 回以上。差が 1% を超えたら条件の理解を疑う |

**指定したマウントオプションではなく、実際に効いている値を記録する。** `rsize` / `wsize` は
1048576 を要求しても 65536 で成立することがあり、その場合マウントは成功する。

## 結果の書き方

- **可否と性能を同じ列に並べない。** 非対応は空欄でも 0 でもなく「非対応」と書く。
- **数値には環境を併記する**（測定日、リージョン、ONTAP バージョン、スループットキャパシティ、
  プロトコル、マウント実効オプション、ブロックサイズ、並列度、繰り返し回数）。
- **測定器が違う値を並べるときは、そのことを書く。** VDBENCH の IOPS と S3 の req/s は
  同じものを数えていない。
- **未測定は「できない」と書かない。**
