# 検証記録 — スループット / IOPS / 並列度の実測（S3 Access Point と Amazon S3）

同一のクライアント・同一のコード・同一の時計で、2 つの書き込み先を測った記録です。

- **FSx for ONTAP S3 Access Point**（この構成の収集層）
- **Amazon S3 バケット**（S3 Files が前段に置かれたバケット）

**この 2 つのスループットは 1 つの列に並べてはいけません。** 前者の上限は購入した
throughput capacity であり、後者は購入していない弾性です。同じ列に置くと「S3 が 5.9 倍速い」と
読めますが、それは購入と弾性の差であって速度の差ではありません。以下の表は必ず上限の種別を
併記しています。

<!-- allow:conflation -->
また、**S3 API の経路は S3 Files を通っていません**。S3 Files が前段に置かれたバケットも通常の
バケットなので、S3 API で測ったのは「FSx for ONTAP S3 Access Point と Amazon S3 の比較」です。
ファイル経路はこれとは別の機構なので、別に測りました（後半の節）。

## 測定環境

| 項目 | 値 |
|---|---|
| 測定日 | 2026-09-01（UTC） |
| リージョン | ap-northeast-1、単一 AZ（ap-northeast-1a / apne1-az4） |
| 計測ホスト | c5n.9xlarge、36 vCPU、Amazon Linux 2023、kernel 6.18.44 |
| Python | 3.12.14、boto3 1.43.85（既定の python3 は 3.9 で `datetime.UTC` を持たない） |
| FSx for ONTAP | SINGLE_AZ_1、SSD 1024 GiB、SSD IOPS 3072（AUTOMATIC）、専用に新規作成 |
| throughput capacity | 128 MBps（既存の可視性記録と同じ段）、および 2048 MBps |
| ONTAP バージョン | `DescribeFileSystems` は `null` を返した（既知。ONTAP 側から読む必要がある） |
| S3 Access Point | NetworkOrigin=VPC、FileSystemIdentity=UNIX/root、S3 Gateway エンドポイント経由 |
| S3 Files | ファイルシステム 1 つ、バケット全体、`sizeLessThan: 131072` は既定のまま |
| リトライ | **無効**（`max_attempts=0`）。503 を数えるため |

### 計測ホストに c5n.9xlarge を選んだ理由

**「Up to」表記のインスタンスでは、詰まったのがストレージかクライアントかを切り分けられません。**
ネットワークが先に飽和した場合、出てくる数値は EC2 のネットワーククレジットの測定値であって、
出力のどこにもそう書かれません。

| インスタンス | 価格/h | ネットワーク | この検証での判定 |
|---|---|---|---|
| c5n.xlarge | $0.272 | **Up to** 25 Gbps | 128 MBps 段（1.02 Gbps）には十分。上位段では切り分け不能 |
| c5n.4xlarge | $1.088 | **Up to** 25 Gbps | 2048 MBps（16.4 Gbps）に対して保証値がない |
| **c5n.9xlarge** | **$2.448** | **50 Gbps（保証値）** | 採用 |

価格は ap-northeast-1、Linux、オンデマンド、2026-08-01 適用（AWS Price List API から取得）。

c5n.9xlarge は「Up to」が付かない最小の c5n です。50 Gbps は 2048 MBps 段の 16.4 Gbps も、
S3 Files が単一クライアントへ公表する 3 GiB/s（24 Gbps）も上回ります。36 vCPU は並列度 64 の
TLS ストリームが CPU 側の制約にならない担保です。安くはないので、測定は短く保っています。

## 手法

| 決めたこと | 理由 |
|---|---|
| リトライ無効 | 既定では botocore が 503 を内部で再送し、絞られた状態が「遅い」に見える |
| 固定の実時間（各点 30 秒） | 固定個数だと遅い点は単に長くかかるだけで、待ち行列が数値に出ない |
| コネクションプール = 並列度 | botocore の既定は 10。並列度 64 では 54 スレッドがプールで待ち、それが遅延として出る |
| ウォームアップ 5 秒を破棄 | 最初のリクエストがプール全体の TLS ハンドシェイクを払う |
| 読みと書きを別フェーズ | 読みが自分の書きと競合しないようにする |
| インスタンス種別を IMDS から記録 | クライアントが上限だった可能性を後から否定できるようにする |
| パーセンタイルは nearest-rank | 既存の測定スクリプトと同じ定義 |

書き込みは各点の直後にオブジェクトを削除しています。2048 MBps 段の 30 秒は約 61 GB になり、
8 点で約 490 GB になるためです。

### 書き込みが購入した段で止まることの確認

FSx for ONTAP 側の書き込みは 1 MiB で 131.2 MB/s、8 MiB で 129.5 MB/s で止まりました。購入した
throughput capacity は 128 MBps です。並列度を 16 から 64 に上げても増えず（129.5 → 127.5）、
503 は 0 件なので、**これはリクエストレートの絞りではなく帯域の上限**です。

### 読み取りが購入した段を超えることの確認

同じ 128 MBps のファイルシステムで、読み取りは 579.3 MB/s に達しました。購入した段の 4.5 倍です。
throughput capacity は読み取りの上限としては効いていません。

### 1 リクエストあたりの固定費の差

並列度 1、1 MiB での p50 は FSx for ONTAP 書き込み 363.7 ms、S3 書き込み 50.1 ms です。8 MiB でも FSx for ONTAP は
331.5 ms なので、**サイズではなくリクエストあたり約 330 ms の固定費**が支配しています。
FSx for ONTAP 側の S3 API 経路でスループットを出すには並列度が必要で、単一ストリームでは出ません。

読み取りは逆に近く、8 MiB 並列度 1 の p50 は FSx for ONTAP 89.9 ms、S3 96.4 ms でほぼ同じです。

## ファイル経路の結果

同じホストから、両方を NFS でマウントして 1 GiB/ストリームの逐次 IO を測りました。
**両方向で O_DIRECT を使っています。** 使わないと最初の読みがクライアントのページキャッシュから
返り、96 GiB のインスタンスではそれがストレージの数値に見えます。

| ストリーム | FSx for ONTAP 書き込み | FSx for ONTAP 読み取り | S3 Files 書き込み | S3 Files 読み取り |
|---|---|---|---|---|
| 1 | 142.6 | 1126.0 † | 29.1 | 46.5 |
| 4 | 129.5 | 1131.6 † | 120.8 | 182.6 |
| 8 | 129.6 | 1130.8 † | 248.2 | 369.6 |

単位 MB/s。**† は撤回した値です。** 段を上げると同じ測定が半分になったため、この列は
このファイルシステムの読み取り性能として引用できません。理由は
[下の節](#ファイル経路の読み取り-1130-mbs-が安定した値でないこと決着済み)にあります。

### マウントの非対称性

**この 2 つは同じ形でマウントされていません。** 揃えようとして揃いませんでした。

| 項目 | FSx for ONTAP | S3 Files |
|---|---|---|
| プロトコル | NFS 4.1（直接） | NFS 4.2（`127.0.0.1:20589` 経由） |
| 経路上の追加要素 | なし | `efs-proxy --tls`（amazon-efs-utils 3.3.1） |
| 転送中の暗号化 | なし（この測定では） | あり（プロキシが TLS） |
| rsize/wsize | 65536 | 1048576 |

S3 Files 側の単一ストリームが 29.1 MB/s と低く、ストリーム数に比例して伸びるのは、
ローカルプロキシが 1 本のストリームを直列化するためと整合します。これは欠陥ではなく、
既定で転送中の暗号化が入る構成の代価です。

### rsize/wsize が 65536 で止まることの確認

1048576 を明示して要求しても、NFSv4.1 と NFSv3 の両方で 65536 になりました。**要求は黙って
引き下げられ、マウントは成功します。** 最初の測定ではこれを「自分のチューニング漏れ」だと
考えましたが、明示的に確かめた結果、この環境での上限でした。

```text
nfsvers=4.1 requested 1048576 -> got: vers=4.1 rsize=65536 wsize=65536
nfsvers=3   requested 1048576 -> got: vers=3   rsize=65536 wsize=65536
```

### ファイル経路の読み取り 1130 MB/s が安定した値でないこと（決着済み）

**結論から書きます。あれはキャッシュでした。** 2026-09-01 に専用のファイルシステムで測り直し、
warm と cold を分離しました。

| 読み方 | スループット | 備考 |
|---|---|---|
| warm（書いた直後に読む） | **1164.1 MB/s** | 撤回した 1130 MB/s とほぼ同じ |
| cold（16 GB キャッシュに対して 24 GiB を介在させた後） | **751.0 MB/s** | 比 **1.55x** |

> **この節の数値は 2 段階で訂正しました。読む前に訂正を見てください。**
>
> 1. **cold 751.0 を「768 MBps/TiB の 97.8%」と読んだ解釈は取り下げ。** この測定は `/dev/zero` を
>    書いたファイルを読んでおり、ONTAP はゼロブロックをディスクに行かずに返します。751.0 と 768 が
>    近いのは偶然です。
> 2. **warm 1164.1 と cold 751.0 という 2 つの数値そのものを取り下げ。** 同じ段・同じ介在量で
>    データだけを非圧縮に変えると **warm 297.8 対 cold 297.2、比 1.00** になりました。
>    **warm と cold の差は存在しません。**
>
> 「1130 MB/s はこのファイルシステムの読み取り性能ではない」という結論は残ります。ただし理由は
> 「warm なキャッシュを測っていた」ではなく、**「ゼロブロックがストレージに行かないので、
> 読み取り性能を測っていなかった」**でした。詳細は
> [B の節](#b--128-mbps-段の-warm-と-cold-の一致非圧縮)。以下の記述は、その訂正の前に
> 書かれたものとして読んでください。

以下は、そこに至るまでに間違えた過程の記録です。同じ設計ミスを避けるために残します。

まず、8 GiB の別データを挟んで読み直しても 1.2 GB/s のままでした。ここまでは「素朴に温かい
だけではない」ことの証拠です。

```text
書き込み直後の再読み込み : 1.1 GB copied, 0.903998 s, 1.2 GB/s
8 GiB を挟んだ後の再読み込み: 1.1 GB copied, 0.911372 s, 1.2 GB/s
```

ところが同じファイルシステムで throughput capacity を 2048 MBps に上げると、同じ測定が
589.7 MB/s になりました。**段を上げて読み取りが半分になる説明はつきません。** したがって
1130 MB/s は、このファイルシステムの読み取り性能として引用できません。

**まず、8 GiB の追い出しテストは原理的に足りていませんでした。** 公式の性能仕様を後から読むと、
段ごとのキャッシュ量は次のとおりです（ap-northeast-1、第一世代 Single-AZ）。

| 段 | インメモリキャッシュ | NVMe 読み取りキャッシュ |
|---|---|---|
| 128 MBps | 16 GB | なし |
| 2048 MBps | 256 GB | **あり**（2 GBps 以上の Single-AZ 1 に付く） |

**128 MBps の段でインメモリキャッシュは 16 GB です。** 8 GiB を挟んでも、1 GiB のファイルは
追い出せません。テストの設計が間違っていました。

当時 3 つの候補を挙げ、そのうち 2 つを後日の測定で処理しました。

| 当時の候補 | 現在の状態 |
|---|---|
| 1130 MB/s はキャッシュから返っていた | **当時は確定としたが、後に理由ごと差し替えた。** 非圧縮では warm 297.8 対 cold 297.2 で差がない。1130 が出たのはキャッシュから返っていたからではなく、**ゼロブロックがストレージに行かないから** |
| throughput capacity の変更でハードウェアが移った | **不要になった。** 下記のとおり再現しません |
| 2048 MBps で付く NVMe キャッシュが大きい IO で不利に働いた | **否定。** 無効化しても変わりません |

**段を上げると読み取りが半分になる現象は再現しませんでした。** 新しいファイルシステムで同じ
段変更（128 → 2048 MBps）を行い、同じ測定をした結果は warm 1164.1 → 1154.8 MB/s で、ほぼ同じ
です。最初に観測した 589.7 MB/s は再現していません。**1 回の観測を性質として扱わないという
規律が、ここでは正しく働きました。**

NVMe キャッシュ説の検証は[別の節](#nvme-読み取りキャッシュの有無と影響)にあります。

**教訓は測定設計の側にあります。** 「8 GiB では保証できない」と caveat に書いてあったものが
実際に外れました。しかも公式の性能仕様に段ごとのキャッシュ量が載っており、**測る前に読めば
足りないと分かる話でした。**

| 段 | インメモリキャッシュ | NVMe 読み取りキャッシュ |
|---|---|---|
| 128 MBps | 16 GB | なし（ONTAP 側でも 0 件） |
| 2048 MBps | 256 GB | **あり**（実測で確認、下記） |

コールドリードを測るには、段ごとのインメモリキャッシュ量を超える介在 IO が必要です。当時の
環境では 2048 MBps の段で測れませんでした。キャッシュが 256 GB でボリュームが 200 GiB なので、
追い出すだけの介在 IO を置く場所がありません。**この制約はボリュームを 400 GiB で作り直して
解消し、[次の節](#2048-mbps-段でのコールドリード4-回測って-3-回捨てた)で測っています。**

## 購入した段に合わせた測定（2048 MBps）

同じファイルシステムの throughput capacity を 128 MBps から 2048 MBps に上げ（オンラインの
更新、**24 分**かかりました）、同じ測定を繰り返しました。段が書き込みを律速していたのかを
因果として確かめるためです。

### S3 API 経路

| 測定点 | 128 MBps | 2048 MBps | 倍率 |
|---|---|---|---|
| 書き込み 8 MiB 並列 16 | 129.5 | **403.7** | 3.1x |
| 書き込み 8 MiB 並列 64 | 127.5 | **497.1** | 3.9x |
| 書き込み 1 MiB 並列 64 | 131.2 | **288.3** | 2.2x |
| 読み取り 8 MiB 並列 16 | 579.3 | 654.8 | 1.13x |
| 読み取り 8 MiB 並列 64 | 573.5 | 581.0 | 1.01x |

単位 MB/s。503 は 2048 MBps 側も全点 0 件。

**書き込みは段に追随し、読み取りはしません。** これで「128 MBps で書き込みが止まったのは
購入した段が理由」が観察から因果になりました。同時に「読み取りは段に縛られない」も裏が取れ、
読み取りは 128 の時点ですでに段の 4.5 倍だったので、上げても伸び代がありません。

### 2048 MBps で 497.1 MB/s だったことの説明

**当初これを「段の 24%」と書きましたが、その分母が誤りです。** 公式の性能表を読むと、
2048 MBps の段では購入した段は書き込みの上限になっていません。ap-northeast-1 の
第一世代 Single-AZ に効く上限は 3 つあり、実際の上限はその最小値です。

| 上限 | 値 | 出どころ |
|---|---|---|
| 購入した throughput capacity（ディスクスループット） | 2,048 MBps | [性能仕様](https://docs.aws.amazon.com/fsx/latest/ONTAPGuide/performance.html) |
| 既定の SSD IOPS から来るディスクスループット | **768 MBps**（768 MBps/TiB × 1 TiB、`AUTOMATIC` のとき） | 同上 |
| HA ペアあたりの**書き込み**上限 | **750 MBps**（読み取りは 2,048） | 同上 |

このファイルシステムは SSD 1024 GiB = 1 TiB なので、この時点では **768 MBps と書き込み側の
750 MBps が効きます。** 実測 497.1 MB/s は 750 の 66% です。

> **2 行目の名前を後から直しました。** 当初「SSD 容量から来るディスクスループット」と書き、
> 容量で決まる固定の天井として扱っていました。実際には SSD IOPS のプロビジョニング量で決まり、
> **`USER_PROVISIONED` で IOPS を上げると 768 MBps ごと上がります。**
> [4 回目のコールドリード](#4-回目-ssd-iops-だけの引き上げ)で 280 GiB の読み取りが 286.1 から
> 2042.1 MB/s になったのがその実測です（別日の再測では 2667.2 MB/s）。**ただし速い側は
> キャッシュから返っていたため、上がった機構は未特定です。** 費用の判断に使うときはこの限定を外せません。

段ごとに何が効いていたかを整理すると次のようになります。

| 段 | 効いた上限 | 実測 | 上限に対する割合 |
|---|---|---|---|
| 128 MBps | 購入した段（128） | 129.5 MB/s | **101%** |
| 2048 MBps | 書き込み上限（750） | 497.1 MB/s | 66% |

**128 MBps では段をちょうど使い切っています。** 2048 MBps では段が上限から外れ、別の 2 つが
上限になりました。

残りの 34% を何が使っているかは特定していません。公式表から候補が 2 つ挙がります。

- **書き込みは読み取りの 2 倍のネットワーク帯域を使います。** セカンダリのファイルサーバーへ
  複製されるため、1 回の書き込みが 2 倍のネットワークスループットになる、と明記されています。
- **1 リクエストあたり約 330 ms の固定費**（この記録の上の節）。並列度 64 で p50 が 1054.9 ms
  まで伸びているので、並列度を上げてもリクエスト数が伸びません。

**設計上の含意はこちらの方が重要です。** throughput capacity だけを上げても、SSD IOPS が
既定（`AUTOMATIC` = 3 IOPS/GiB）のままならディスクスループットは 768 MBps/TiB で止まります。
2,048 MBps 分のディスクスループットを使うには、SSD 容量を 2.67 TiB 以上にするか、
**SSD IOPS を明示的にプロビジョニングします。** 後者を実測した結果が
[4 回目のコールドリード](#4-回目-ssd-iops-だけの引き上げ)で、40,000 IOPS にすると 286.1 から
2042.1 MB/s になりました。**段は唯一のレバーではありません。**

> **この 2042.1 を「段の 2,048 MBps の 99.7%」と読んだ解釈は取り下げています。** 別日の再測で
> **2667.2 MB/s**（+30.6%）になり、同じ 2,048 を 30% 超えました。上限にちょうど当たったのは
> 偶然です（[再測](#i--280-gib-の読み取りの再現の不成立とキャッシュ由来の大半)）。**上げると伸びることは再現しますが、
> どこで止まるかはこの測定では特定できていません。**

## 小さいオブジェクトの IOPS

スループットではなくリクエストレートを測ります。4 KiB と 64 KiB、並列度 1/16/64/256、各点 20 秒、
S3 Access Point 経由。**SSD IOPS 3,072（AUTOMATIC、1 TiB）に到達するかを見る測定です。**

| 並列度 | 4 KiB 書き込み | 4 KiB 読み取り | 64 KiB 書き込み | 64 KiB 読み取り |
|---|---|---|---|---|
| 1 | 4.0 | 21.8 | 5.4 | 23.0 |
| 16 | 153.9 | 330.3 | 171.2 | 336.1 |
| 64 | **415.3** | **630.3** | **415.9** | 567.7 |
| 256 | 420.8 | 594.0 | 404.4 | 571.9 |

単位 req/s。503 は全 16 点で 0 件。

**SSD IOPS 3,072 には届きません。** 書き込みは約 420 req/s、読み取りは約 600 req/s で頭打ちに
なり、**サイズをほぼ問いません**（4 KiB と 64 KiB で書き込みが 415.3 と 415.9）。並列度を 64 から
256 に上げても増えず、読み取りはむしろ下がります。

**律速しているのは S3 Access Point のリクエスト経路で、ストレージの IOPS ではありません。**
到達したのは公称値の 14%（書き込み）から 20%（読み取り）です。サイズを問わないという性質は、
1 リクエストあたりの固定費が支配していることと整合します。

設計上の含意: **小さいオブジェクトを大量に扱うワークロードで、SSD IOPS を増やしても S3 経由の
リクエストレートは上がりません。** SSD IOPS の追加プロビジョニング（$0.0204/IOPS-Mo）を検討する
前に、経路がどちらで詰まっているかを確認してください。

> **この判定は後日、実際に IOPS を上げて確かめました。** 段を 16 倍・SSD IOPS を 13 倍
> （3,072 → 40,000）にしても、**6 点すべてで req/s は増えず、書き込みは 25% 下がりました。**
> 40,000 IOPS に対して出ているのは 279〜605 req/s、つまり **0.7〜1.5%** です。
> 詳細は [D の節](#d--段と-iops-を上げても増えない小オブジェクトのリクエストレート)。

## NVMe 読み取りキャッシュの有無と影響

公式ドキュメントの 2 か所が食い違っていました。ap-northeast-1 を含む「その他のリージョン」の
性能仕様表には NVMe キャッシュの列が**ありません**。一方でデプロイタイプの節は
「2022-11-28 以降に作成され、2 GBps 以上の Single-AZ 1 には NVMe 読み取りキャッシュが付く」と
書いています。**ONTAP に直接聞いて決着させました。**

```text
128 MBps  : system node external-cache -> 0 records
2048 MBps : node FsxId...-01  is_enabled: true  is_hya_enabled: true
            node FsxId...-02  is_enabled: true  is_hya_enabled: true
```

**2048 MBps では実在し、有効です。** デプロイタイプの節の記述が正しく、リージョン別の表は
この列を落としています。

そのうえで、**無効化しても測定値は変わりませんでした。**

| 状態 | 書き込み | 読み取り |
|---|---|---|
| 出荷時（有効） | 763.1 | 1154.8 |
| `external-cache modify -is-enabled false` | 768.0 | 1152.9 |

単位 MB/s、8 GiB、8 ストリーム、O_DIRECT。差は 0.6% と 0.2% で、実行ごとのばらつきの範囲です。

**「NVMe キャッシュが大きい IO で不利に働く」という仮説は否定されました。** AWS がその注記を
第二世代に限定しているのは正しく、第一世代のこの構成には当てはまりません。

> **この 4 つの絶対値は、ディスク側の上限と比べないでください。** ゼロ埋めデータでの測定です。
> **有効・無効の差が 1% 未満という結論は成立します**（同じ潰れ方をした 2 つの相対比なので）。
> 非圧縮データでの NVMe キャッシュの寄与は別に測っており、280 GiB の読み取りで
> **1.09 倍**でした（[4 回目](#4-回目-ssd-iops-だけの引き上げ)）。8 GiB を 1152.9 で読めたのは
> インメモリキャッシュに収まるからで、キャッシュに入らない大きさでは値が変わります。

### 書き込み 768.0 MB/s が意味すること（解釈を取り下げ）

この測定の副産物として、NFS 経由の書き込みが 768.0 MB/s に達しました。当初これを
「SSD 容量から来るディスクスループット 768 MBps/TiB とちょうど一致し、上限を使い切っている」と
読みました。**この解釈は取り下げます。**

理由は 2 つあり、どちらもペイロードにあります。

- **NFS 側は `/dev/zero` を書いていました。** ONTAP はゼロブロックを認識し、ディスクに
  書かずに済ませます。この 768.0 は取り込み経路の数値で、ディスク側の上限と比べる対象では
  ありません。
- **S3 側も圧縮可能なペイロードでした。** 測定スクリプトは 1 バイトを繰り返した本体
  （`b"t" * size`）を送っており、インライン圧縮が潰し、同一オブジェクトどうしをインライン
  重複排除がさらに潰します。ボリュームのインライン効率化は測定中ずっと有効でした。

つまり **768 と 497 は「別種の潰れ方をした 2 つの数値」で、比を取る前提が成立していません。**
どちらもディスクに届いていないので、768 MBps という上限に対する割合という読み方もできません。

同じ量を、両経路とも非圧縮ペイロード・インライン効率化オフ・同じ SSD IOPS で測り直した結果が
[差の 41% がどこへ行くか](#差の-41-がどこへ行くか同じカウンタで両経路を測る)にあります。

**この節が残っている理由。** ペイロードの選択が測定の妥当性を決める、という一般的な話は
測る前に言えたはずのことです。実際には、ディスクスループットの上限と数字が一致したことを
「上限に当たっている」の証拠として読み、そこで止まりました。**数値が期待した上限と一致した
ときこそ、それが偶然でないことを別の経路で確かめる必要がありました。**

## 2048 MBps 段でのコールドリード（4 回測って 3 回捨てた）

キャッシュから返らない読み取りが、この段でどこまで出るかを測ります。ボリュームを 400 GiB で
作り、インメモリキャッシュ 256 GB を超える 280 GiB の介在 IO を置きました。

**4 回測って、最初の 3 回を捨てました。** 捨てた理由が測定手法の教材としては本体より重要なので、
順に残します。

| 回 | 変えたこと | 出た数値 | 捨てた理由 |
|---|---|---|---|
| 1 | 既定マウント、1 ストリーム | warm 617.6 / cold 562.3 | クライアント側の上限に当たっていた |
| 2 | `nconnect=16` | warm 3064.7 / cold 3048.2 | 読み取りがディスクに届いていなかった |
| 3 | 非圧縮データ、効率化オフ | 280 GiB を 286.1 | 有効。ただし SSD IOPS が律速 |
| 4 | SSD IOPS 3,072 → 40,000 | 280 GiB を **2042.1** | 有効 |

### 1 回目: ストリーム数を増やしても動かない数値

warm 617.6 に対し cold 562.3、比 1.10x。「差がない」と読みかけました。しかし同じマウントで
ストリーム数を振った別の測定が、すでに次の値を出していました。

| ストリーム数 | 読み取り |
|---|---|
| 1 | 588.1 MB/s |
| 4 | 589.9 MB/s |
| 8 | 589.7 MB/s |

**ストリーム数を 8 倍にしても動きません。** 応答しているのはファイルシステムではなく
クライアントです。590 MB/s は 4.7 Gbps で、これは VPC 内の単一フローの上限に相当し、Linux の
NFS マウントは既定でサーバーごとに TCP 接続を 1 本しか張りません。warm と cold の両方が同じ
天井に座っていたので、**この測定には差を検出する力が最初からありませんでした。**

### 2 回目: 上限の 4 倍で返ってきた読み取り

`nconnect=16` を付けると 3064.7 MB/s になりました。ここで止まらずに済んだのは、**出た数値が
物理的にありえなかった**からです。

- ファイルシステムの段は 2048 MBps
- SSD は 1024 GiB なので、既定のディスクスループットは 768 MBps

**280 GiB の介在読み取りも同じ 3067.3 MB/s で返りました。** 256 GB のキャッシュに入らない
280 GiB が上限の 4 倍で返るはずはありません。原因はテストデータで、全バイトが `/dev/zero`
由来でした。ONTAP はゼロブロックを再構成して返します。

このボリュームの `space_savings` を後から見ると **重複排除で 67%** と出ており、圧縮可能な
ペイロードが実際に潰されていたことが裏から確認できます。

### 3 回目: 非圧縮データにしたら 286.1 MB/s

AES-CTR でゼロストリームを暗号化して 1 GiB の非圧縮ブロックを作り（`/dev/urandom` より桁違いに
速い）、ボリュームのインライン効率化（圧縮・重複排除・コンパクション）を切って測り直しました。
gzip で 100.0% になることを毎回確認しています。

| 測定点 | 値 | 読み方 |
|---|---|---|
| warm 16 GiB、8 ストリーム | 2863.1 / 2965.5 MB/s | 256 GB のインメモリキャッシュから返る |
| **280 GiB（キャッシュに入らない）** | **286.1 MB/s** | ディスクから返る |
| 560 GiB の介在後に 16 GiB を再読み | 1478.5 MB/s | まだ一部が常駐している |

2 つ、想定と違いました。

**286.1 は既定のディスクスループット 768 MBps の 37% しかありません。** 286.1 MB/s を
IOPS 3,072 で割ると 1 IO あたり約 93 KiB です。これは**スループットではなく IOPS で律速された
シーケンシャル読み取りの形**です。このファイルシステムは `DiskIopsConfiguration` が
`AUTOMATIC` で、値はちょうど 3,072（1 TiB × 3,072 IOPS/TiB）でした。

**560 GiB を通したのに 16 GiB のファイルが 1478.5 MB/s で返りました。** 追い出しきれていません。
この 16 GiB は warm 測定で 2 回読んでおり、介在データは 1 回しか読んでいないので、読み取り回数を
見る追い出し方針なら残ります。**「キャッシュ量より多く流せば追い出せる」は成り立ちません。**
キャッシュに入らない大きさを一度に読む方が、コールドリードの測定としては素直です。

### 4 回目: SSD IOPS だけの引き上げ

仮説が IOPS 律速なら、SSD IOPS だけを上げれば動くはずです。`AUTOMATIC` 3,072 から
`USER_PROVISIONED` 40,000 へ変更し（オンライン更新、`UPDATED_OPTIMIZING` が **18 分**）、
他は一切変えずに同じ 280 GiB を測りました。

| SSD IOPS | NVMe 読み取りキャッシュ | 280 GiB の読み取り | 段の 2,048 MBps に対して |
|---|---|---|---|
| 3,072（AUTOMATIC） | 無効 | 286.1 MB/s | 14% |
| **40,000** | 無効 | **2042.1 MB/s** | **99.7%** |
| 40,000 | 有効・1 回目 | 2086.3 MB/s | 102% |
| 40,000 | 有効・2 回目 | **2232.0 MB/s** | 109% |

**SSD IOPS を上げただけで 7.14 倍になりました。** そして 2042.1 は 2,048 MBps の 99.7% です。

> **この「99.7%」は偶然でした。取り下げます。** 同じ手順を別日に繰り返すと **2667.2 MB/s**、
> つまり同じ 2,048 を 30% 超えます。超えられる理由は CloudWatch で分かりました。**読み取った
> バイトの 98.5〜99.9% はディスクに行っていません。** 280 GiB はこの段のインメモリキャッシュ
> 256 GB（= 238 GiB）より **18% 大きいだけ**で、「キャッシュに入らない」というラベルが
> 甘すぎました。**7.14 倍という観測は残りますが、その機構は「ディスク経路が速くなった」では
> 説明できません。** 詳細は [I の節](#i--280-gib-の読み取りの再現の不成立とキャッシュ由来の大半)。

**「768 MBps/TiB がディスクスループットの上限」という読み方は誤りでした。** 公式ドキュメントは
実際には次のように書いています。

> 達成できるディスクスループットと IOPS の上限は、次のうち小さい方です。
>
> - throughput capacity から決まる、ファイルサーバー側のディスク性能
> - **プロビジョニングした SSD IOPS の数から決まるディスク性能**

768 MBps/TiB と 3,072 IOPS/TiB は「既定で SSD ストレージが提供する水準」で、容量から来る固定の
天井ではありません。**SSD IOPS を明示的にプロビジョニングすると、その水準ごと上がります。**
実測はこの読み方と整合し、上限はファイルサーバー側の 2,048 MBps に移りました。

同じ 40,000 IOPS で書き込みも測っています。

| 測定点 | 値 | 効いている上限 |
|---|---|---|
| NFS 書き込み 280 GiB、8 ストリーム、非圧縮 | **712.4 MB/s** | HA ペアあたりの書き込み上限 750 MBps の **95%** |

**NVMe 読み取りキャッシュは 9% でした**（2042.1 → 2232.0）。2 回目が段のディスクスループットを
超えているのは、NVMe から返る分がディスク経路を通らないためです。この段でのこのキャッシュは、
[128 MBps 段での否定](#nvme-読み取りキャッシュの有無と影響)と合わせて「あるが支配的ではない」
という位置づけになります。

### 設計上の含意

| 変えるもの | 280 GiB の読み取りに効くか | 備考 |
|---|---|---|
| SSD IOPS を既定から上げる | **7.14 倍** | いちばん効いた。$0.0204/IOPS-Mo の課金対象 |
| `nconnect` を付ける | 590 → 2000 MB/s 級 | クライアント側。**無料** |
| NVMe 読み取りキャッシュ | 1.09 倍 | 段に付随し、選べない |
| throughput capacity の段 | 上限としては効く | ただし SSD IOPS が下で詰まっていると届かない |

**段を上げる前に、SSD IOPS とクライアントのマウントを確認してください。** この環境では
その 2 つで 7 倍動き、どちらも段の変更より安価です。

## 差の 41% がどこへ行くか（同じカウンタで両経路を測る）

S3 Access Point 経路が NFS より遅い、その差の行き先を特定します。**前提を 4 つ揃えました。**

| 揃えたもの | 値 |
|---|---|
| ペイロード | 両経路とも非圧縮（S3 側は `--body random`、NFS 側は AES-CTR ブロック） |
| ボリュームのインライン効率化 | 圧縮・重複排除・コンパクションをすべてオフ |
| SSD IOPS | 40,000（`USER_PROVISIONED`） |
| 測定器 | **どちらも ONTAP のボリュームカウンタ**（クライアント側の計測ではない） |

同じカウンタで測るのが要点です。クライアント側の計測はプロトコルごとに数え方が違いますが、
ボリュームカウンタは両方を同じ単位で見ます。

| 経路 | 書き込み | ボリュームの書き込み ops/s | 1 IO の平均サイズ | 1 IO の平均サービス時間 |
|---|---|---|---|---|
| S3 Access Point、8 MiB、並列 64 | **414.0 MB/s** | 49.3 | **8,192 KiB** | **1,010,221 µs** |
| NFS 4.1、`nconnect=16`、8 ストリーム | **702.1 MB/s** | 10,712.8 | 64 KiB | 5,201 µs |

30 秒窓を 3 つ取り、いずれも 697.9 / 702.1 / 702.7 と安定しています。

**S3 Access Point 経路は NFS の 59.0% でした。差は 41% です。** 以前記録した 35%（497 対 768）は、
別種に潰れた 2 つの数値を比べたものだったので置き換えます。

**行き先はボリュームに届く IO の形にあります。**

- S3 経路は 1 オブジェクトを **8 MiB の単一書き込み IO** としてボリュームに渡し、その 1 回の
  サービス時間が **約 1.01 秒**です。並列 64 に対して実際に進むのは毎秒 49.3 回で、
  **同時に 50 本程度しかボリュームに入っていません。**
- NFS 経路は **64 KiB の IO を毎秒 10,700 回**流し、1 回のサービス時間は 5.2 ms です。

つまり **S3 経路の律速は「大きな IO を少数、長い時間かけて」という形そのもの**で、NFS 経路の
「小さな IO を大量にパイプライン化する」形と非対称です。上の
[1 リクエストあたり約 330 ms](#1-リクエストあたりの固定費の差) と、
[並列度を上げても IOPS が伸びないこと](#小さいオブジェクトの-iops)は、同じ性質の別の断面です。

### ここで止まる理由

ONTAP のノード CPU まで見れば「ONTAP 自体が飽和しているのか」を言えます。**この環境では
見られませんでした。**

```text
GET /api/cluster/nodes?fields=name,statistics   -> {"records": [], "num_records": 0}
GET /api/private/cli/system/node/utilization    -> API not found
GET /api/private/cli/statistics/show-periodic   -> API not found
GET /api/private/cli/system/node?fields=node,health -> 2 records（CPU の列はない）
```

**FSx for ONTAP の `fsxadmin` 資格情報では、ノードレベルの統計に到達できません。** ボリューム
単位のカウンタは取れますが、ノードの CPU は取れません。したがって「S3 変換の費用が ONTAP の中に
あるのか、AWS 側の S3 変換層にあるのか」は、**この境界より内側には踏み込めません。**

これは根本原因ではなく境界です。観測できた範囲では、差は IO の形とボリュームに入る同時数で
説明がつきます。

> **この境界は後日 1 段動かしました。「観測不能」を撤回します。** ONTAP REST では取れませんが、
> **CloudWatch の `AWS/FSx` には `CPUUtilization` があります。** <!-- allow:naming CloudWatch の名前空間名そのもの -->実測すると **S3 Access Point
> 経由で 417 MB/s のとき CPU 21〜24%、NFS で 800 MB/s のときも 18〜23%** でした。
> **同じ CPU で 2 倍のスループットが出ているので、ONTAP はどちらでも飽和していません。**
> 代価は ONTAP の中ではなく上流の S3 変換にあります。詳細は
> [H の節](#h--cloudwatch-から分かる-ontap-の飽和)。

## 測定を無効にしうる 4 つの既定値

この回で 3 回測り直したのは、いずれも**既定値が測定対象をすり替えていた**ためです。同じ形の
測定をする人が同じ順で踏むはずなので、まとめて残します。

| 既定値 | 何が起きるか | 気づき方 | 対処 |
|---|---|---|---|
| Linux NFS の TCP 接続は 1 本 | 約 590 MB/s（4.7 Gbps）で止まり、**ストリーム数に反応しない** | 1 / 4 / 8 ストリームで値が動かない | `nconnect=16` |
| `dd if=/dev/zero` | ゼロブロックはディスクに行かず、**上限の 4 倍で返る** | 公称上限を超える | 非圧縮データ（AES-CTR で生成） |
| ボリュームのインライン効率化が有効 | 同一・圧縮可能ペイロードが潰れ、**保存も読み出しもされない** | `space_savings.dedupe_percent` が高い | 測定中だけオフ（下記の注意あり） |
| `DiskIopsConfiguration: AUTOMATIC` | 3 IOPS/GiB で **IOPS 律速**になり、スループット上限に届かない | MB/s ÷ IOPS が IO サイズとして不自然に小さい | `USER_PROVISIONED` |
| **キャッシュ量を「少し」超えた読み取り** | キャッシュから返る割合が支配し、**ディスク経路を測っていない** | `DataReadBytes` に対する `DiskReadBytes` が数 % 以下 | キャッシュの **2 倍以上**を一度に読む |

**5 つめは後から足しました。** 「256 GB のキャッシュに対して 280 GiB を読めばキャッシュ外だ」と
考えていましたが、256 GB は **238 GiB** なので 18% 超えただけで、**実測では読んだバイトの
98.5〜99.9% がディスクに行っていませんでした。** CloudWatch の `DiskReadBytes` と
`DataReadBytes` を比べれば分かります。**「キャッシュを超えた」と「キャッシュから来ない」は
別のことです。**

**共通しているのは「もっともらしい数値が出る」ことです。** 590 も 3064 も 286 も 2042 も、それ自体は
異常に見えません。異常だと分かったのは、**公称上限と突き合わせたとき**と、**別の日に測り直した
とき**でした。

- 590 は「ストリーム数に反応しない」ことで露見しました。**1 点だけ測っていたら分かりません。**
- 3064 は「上限の 4 倍」で露見しました。**上限を先に調べていなければ通していました。**
- 286 は「上限の 37%」で露見しました。**低すぎる値も、高すぎる値と同じくらい疑う対象です。**

測定値は必ず**公称上限に対する割合として**書き、割合が 100% を大きく外れたら数値ではなく
測定を疑ってください。

**そして上限にきれいに当たった数値ほど、別の日に測り直してください。** 「2042.1 は段の 99.7%」は
2 週間ではなく 1 日で崩れました。同一環境・同一条件の再現性は **0.2% 以内**（下記）なので、
**再測で 30% 動いたなら、それは測定のばらつきではなく、条件の理解が違っています。**

### 片道になりうるインライン効率化

測定のためにボリュームのインライン効率化を切りましたが、**戻せませんでした。** 経路を 2 つ
試して、どちらも拒否されます。

```text
PATCH /api/private/cli/volume/efficiency  {"inline_compression": true}
-> "specifying the \"-inline-compression\" parameter when the \"compression\" parameter
    is not specified, are not supported for the volumes with auto adaptive compression."

PATCH /api/private/cli/volume/efficiency  {"compression": false, "inline_compression": true}
-> "Disabling compression and enabling inline compression simultaneously cannot be done."

PATCH /api/storage/volumes/{uuid}  {"efficiency": {"compression": "inline"}}
-> "Cannot change the efficiency policy from \"auto\" because there is an active \"auto\"
    background efficiency operation on the volume."
```

出荷時の状態は `compression: false, inline_compression: true` です。**その組み合わせを
private CLI 経由で復元する引数の組はありません。** 3 番目の documented endpoint は
バックグラウンドの効率化処理が走っている間はポリシー変更を拒否します。

> **後日確認し、この節の見出しを撤回します。片道ではありません。** 効率化処理が `idle` に
> なってから documented endpoint を 2 回叩けば、出荷時の状態に戻ります。手順は
> [E の節](#e--インライン圧縮の可逆性と片道の撤回)。**待つことが条件でした。**

`inline_dedupe` と `data_compaction` は 1 つずつなら戻せました。

> **注意点が 2 つあります。** 1 つは、**捨てて構わないボリュームでのみ切ること。** もう 1 つは、
> このとき最初の復元処理が**エラーを返していたのに気づかなかった**ことです。復元の PATCH を
> `>/dev/null` に流し、直後に状態を確認していませんでした。次の回の冒頭で
> `inline_compression: false` を見て初めて分かりました。**成功レスポンスは成功の証拠ではなく、
> 見ていないレスポンスは何の証拠でもありません。**

## FlexCache 経由の読み取り

配布層そのものの測定です。**AWS が文書化している 3 つの構成のうち
「FSx for ONTAP → FSx for ONTAP」**で行いました。専用のファイルシステムを 2 つ作り、
cluster peering と SVM peering を張り、FlexCache ボリュームを作成しています。

| 読み方 | スループット |

| FlexCache 初回読み取り（origin から充填しながら） | 558.7 |
| FlexCache 2 回目（キャッシュに常駐） | 616.0 |
| origin を直接読む（対照、warm） | 1158.9 |

**初回と 2 回目の差は 10% しかありません**（558.7 対 616.0）。FlexCache は疎に充填されるので
初回は origin から引くことになりますが、この構成ではその代価が小さいという結果です。

対照との比較は**どの対照を採るかで変わります**。

- origin の warm 読み取り 1158.9 に対して FlexCache 常駐は **53%**
- origin の cold 読み取り 751.0（[上記](#ファイル経路の読み取り-1130-mbs-が安定した値でないこと決着済み)）に対して **82%**

> **この節の数値と結論を取り下げます。両方を非圧縮で測り直すと逆になりました。**
> FlexCache 常駐 **882.7〜907.1** に対して origin 直読み **383.3**、つまり
> **FlexCache が 2.31 倍速い**です。初回充填の代価も 10% ではなく **2.88 倍**でした。
> 理由は cache が別のファイルシステムで、自分の段と自分のメモリを持つことです。詳細は

**同一 AZ・同一 VPC での測定です。** 実際のトポロジは cache 側がオンプレミスや別リージョンに
あることを想定しており、その場合は経路の遅延が加わります。**この数値は上限側の目安であって、
WAN を挟んだ構成の予測ではありません。**

### S3 API で書いたオブジェクトが FlexCache 側から見えること

origin ボリュームに S3 Access Point 経由で `PutObject` し、5 秒後に cache 側のマウントで
`ls` しました。**両方に出ています。**

```text

```

これはこの構成の中核の動作（S3 で収集し、ファイルで配布する）が FSx for ONTAP どうしの FlexCache で

## 複数クライアントでの集約

**この節が、上限の種別を分けて書くべき理由をもっとも直接に示します。** 同じ設定
（8 MiB、並列度 16、20 秒）を、1 台から、次に 2 台から同時に実行しました。

| 対象 | 1 台 | 2 台の合計 | 1 台あたりの変化 |
|---|---|---|---|
| FSx for ONTAP S3 AP 書き込み | 128.0 | **129.6**（65.7 + 63.9） | **半減** |
| FSx for ONTAP S3 AP 読み取り | 585.3 | **592.5**（278.9 + 313.6） | **半減** |
| Amazon S3 書き込み | 776.2 | **1528.7**（773.2 + 755.5） | ほぼ不変 |
| Amazon S3 読み取り | 649.3 | **1308.9**（642.2 + 666.7） | ほぼ不変 |

単位 MB/s。503 は全点 0 件。

**2 つの上限は種類が違うことが、ここで動作として出ます。**

- **FSx for ONTAP 側は共有された上限です。** クライアントを増やしても合計が増えず（128.0 →
  129.6、585.3 → 592.5）、1 台あたりが半分になります。購入した容量を分け合う挙動です。
- **Amazon S3 側は 1 台あたりの上限でした。** 合計が 1.97 倍（書き込み）と 2.02 倍（読み取り）に
  なり、1 台あたりは変わりません。**単一ホストで見えていた 649〜776 MB/s は S3 の上限ではなく、
  クライアント側の上限だったということです。**

設計上の含意: **FSx for ONTAP 側はクライアントを増やしても総量が増えないため、容量計画は
ファイルシステム単位で行います。** Amazon S3 側はクライアントを増やせば総量が増えるため、
容量計画はクライアント側の帯域で行います。**同じ「MB/s」という単位で並べても、増やし方が
逆です。**

## リージョンを跨いだ FlexCache（読み手が遠い場合）

上の FlexCache 測定は同一 AZ で、経路の遅延がありませんでした。**実際のトポロジは cache 側が
遠くにあることを想定しているので、リージョンを跨いで測り直しました。**

| 項目 | 値 |
|---|---|
| origin | ap-northeast-1（東京）、128 MBps |
| cache | **ap-northeast-3（大阪）**、128 MBps |
| 接続 | リージョン間 VPC ピアリング |
| 測定した往復 | **connect 9.7 ms**（東京のホスト → 大阪の管理エンドポイント）対 0.2 ms（東京内） |
| 読み手 | 大阪のホスト（c5n.2xlarge） |

**オンプレミスではありません。** リージョン間の 9.7 ms は、都市間のデータセンター接続の代役と
しては妥当ですが、長距離 WAN や実際のオンプレミス回線とは違います。

### 大阪から読んだ結果

8 GiB、O_DIRECT。**対照は「東京の origin をピアリング越しに直接読む」形です。**

| 読み方 | 8 ストリーム | **1 ストリーム** |
|---|---|---|
| 大阪の FlexCache（初回、経路越しに充填） | 509.4 | — |
| 大阪の FlexCache（常駐、ローカル） | **612.5** | **602.0** |
| 大阪の FlexCache（3 回目、常駐の再確認） | 611.7 | — |
| 東京の origin を経路越しに直接（対照） | 450.3 | **101.5** |

単位 MB/s。

**1 ストリームで 5.9 倍の差が出ます**（602.0 対 101.5）。8 ストリームでは 1.36 倍
（612.5 対 450.3）にとどまります。**並列度が遅延を隠すので、差が出るのは並列度が低いときです。**

これが FlexCache を置く判断の分かれ目になります。

- **多重度の高いバッチ**なら、経路越しの直読みでも 450.3 MB/s 出ます。FlexCache の利得は 1.36 倍で、
  キャッシュ側の SSD 費用に見合うかは要件次第です
- **1 本ずつ順に読む処理**（対話的な参照、単一プロセスのパイプライン）では 101.5 MB/s しか出ず、
  FlexCache が 6 倍近く効きます

**初回と常駐の差は 509.4 対 612.5 で 20% です。** 疎な充填の代価は、リージョンを跨いでも
小さいままでした。2 回目と 3 回目が 612.5 と 611.7 で一致しており、再現しています。

### B — 128 MBps 段の warm と cold の一致（非圧縮）

この記録は長いあいだ「warm 1164.1 MB/s、cold 751.0 MB/s、比 1.55x」を載せてきました。同じ段・
同じ介在量（16 GB のキャッシュに対して 24 GiB）で、**データだけを非圧縮に変えて測り直した結果**が
次です。

| 測定点 | ゼロ埋め（旧） | 非圧縮（新） |
|---|---|---|
| 書き込み 8 ストリーム | 129.6 | **133.4**（段 128 の 104%） |
| read warm | **1164.1** | **297.8 / 317.1** |
| read cold（24 GiB 介在後） | **751.0** | **297.2** |
| warm ÷ cold | **1.55** | **1.00** |
| 24 GiB を一度に読む（キャッシュ超） | 未測定 | 304.5 |

**warm と cold の差が消えました。** 4 点（297.8 / 317.1 / 297.2 / 304.5）はすべて同じ範囲に入り、
キャッシュに載っているかどうかで動きません。

読み方はこうなります。**この段で読み取りを止めているのはキャッシュの有無ではありません。**
128 MBps の段のディスクスループットはベースライン 128 MBps・バースト 600 MBps なので、
実測 297〜317 はバースト側の途中に当たります。warm でも cold でも同じところで止まるのは、
**どちらもこのバースト許容量で律速されているから**と整合します。

**そして「1130 MB/s はキャッシュだった」という結論も、言い方を変える必要があります。**
1164.1 が出たのはインメモリキャッシュから返っていたからではなく、**ゼロブロックがそもそも
ストレージに行かないから**でした。この記録が「warm は 1164」と書いていた数値は、
warm という状態を測ったものではありません。

### C — origin より速い FlexCache と、前回の「53%」の逆転

前回は FlexCache 常駐 616.0 に対して origin 直読み 1158.9 で、**「FlexCache は origin の 53%」**
と書きました。両方を非圧縮で測り直すと逆になります。

| 測定点 | ゼロ埋め（旧） | 非圧縮（新） |
|---|---|---|
| FlexCache 初回（充填しながら） | 558.7 | **306.8** |
| FlexCache 2 回目（常駐） | 616.0 | **882.7** |
| FlexCache 3 回目（常駐） | 未測定 | **907.1** |
| origin を直接読む（対照、warm） | 1158.9 | **383.3** |
| 常駐 ÷ origin 直読み | **0.53** | **2.31** |

**FlexCache 常駐は origin 直読みの 2.31 倍です。** 理由は構成にあります。cache は**別の
ファイルシステム**で、自分の段・自分のメモリ・自分のバースト許容量を持ちます。cache から読むと
origin 側の上限が一切かかりません。ゼロ埋めのときは origin が 1158.9 で返せたので cache が
遅く見えただけで、**実データでは origin の方が先に詰まります。**

充填の代価も逆でした。**初回 306.8 に対して常駐 882.7 で、2.88 倍**です。前回「初回と 2 回目の
差は 10% しかない」と書いたのは、ゼロ埋めでは充填が実質何も運んでいなかったためです。

**配布層としての読み方が変わります。** FlexCache は「origin の性能を分けてもらう仕組み」では
なく、**読み取り側に別の容量を足す仕組み**です。10% だと思っていた初回の代価は 2.9 倍なので、
一度も読まれていないデータを最初に読む経路は、この差を見込んで設計してください。

### A — ペイロードによる書き込みスループットの変化幅（5% 未満）

この記録は直前の版で「圧縮可能なテストデータは書き込みスループットを少なくとも 17% 高く
見せた」と書いていました。**測ったら違いました。**

2048 MBps 段・SSD IOPS 40,000・インライン効率化は出荷時（有効）のまま、**ペイロードだけを
振った結果**です。

| 経路 | `fill`（1 バイト反復） | 非圧縮 | 差 |

**書き込みではペイロードはほとんど効きません。** 読み取りでは 4 倍の違いを生んだのと対照的で、
これは筋が通ります。**書き込みはクライアントが実際にバイトを送るので、潰れるのは着地する側だけ
です。読み取りは、潰れていれば返す前に再構成できます。**

つまり **17% 以上という下限は撤回します。** では 497.1 と 415 の差はどこから来たのか。この 2 つは
SSD IOPS（3,072 対 40,000）とファイルシステムの個体、そして**測定時間（30 秒対 60〜90 秒）**が
違います。**特定できていません。** ただし下の再現性の数値から、これが測定ノイズではないことは
言えます。

### 同一条件の再現性は 0.2% 以内でした（意図しない対照）

上の表が 2 回ずつあるのは偶然です。**インライン効率化をオフにする PATCH が拒否された**ため、
「オフで測る」つもりの 4 点が「オンでもう一度測る」になりました。

```text
Failed to modify efficiency configuration for volume "origin_vol":
Compression cannot be disabled while an efficiency operation is in progress on the volume.
```

書き込んだ直後はバックグラウンドの効率化処理が走っており、`efficiency.op_state` は 6 分待っても
`active` のままでした。**効率化を切るなら、データを書く前に切ってください。**

結果として得られた 4 組の複製は次のとおりです。

| 測定点 | 1 回目 | 2 回目 | 差 |
|---|---|---|---|
| S3 AP、`fill` | 417.1 | 417.0 | 0.02% |
| S3 AP、非圧縮 | 415.1 | 415.7 | 0.14% |
| NFS、`fill` | 808.6 | 808.4 | 0.02% |
| NFS、非圧縮 | 772.0 | 771.1 | 0.12% |

**同一環境・同一条件なら 0.2% 以内で再現します。** これは有用な基準線です。**この記録に載って
いる数値の差が 1% を超えていれば、それは実行ごとのばらつきではありません。** 逆に、環境を
またいだ 497.1 対 415（16%）は、ばらつきでは説明できない何かです。

### E — インライン圧縮の可逆性と、「片道」の撤回

| ストリーム数 | 読み取り | 書き込み |
|---|---|---|

| 2 | 132.6 | — |
| 4 | 264.3 | 140.5 |
| 8 | **451.3** | 281.0 |
| 16 | **404.8 / 450.0** | 531.8 |

単位 MB/s、c5n.2xlarge、非圧縮、1 GiB/ストリーム、O_DIRECT。**読み取りは 8 ストリームで
約 450 MB/s に達し、16 では伸びません。** 450 MB/s は 3.6 Gbps で、**単一フローの上限

**効いているのはローカルのプロキシです。** 16 ストリームの読み取り中の CPU が答えます。

```text

67.3 efs-proxy
18.1 efs-proxy
14.9 efs-proxy      （vCPU は 8）
```

そして構造がマウントオプションに出ています。

```text
127.0.0.1:/ nfs4 rw,vers=4.2,rsize=1048576,wsize=1048576,proto=tcp,port=20812,addr=127.0.0.1
```

**マウントの相手は 127.0.0.1、つまり同じホストの `efs-proxy` です。** サービスではありません。
`nconnect` はこのマウントの接続数を増やすオプションなので、**増えるのはローカルプロセスへの

```text

-> 90 秒でタイムアウト（timeout(1) で打ち切り）
```

最初の測定はこれで丸ごと失われました。**未対応のオプションを試すときは `timeout` を付けて
ください。**

## 読み取れること

1. **書き込みスループットは購入した throughput capacity に追随します。** 128 MBps の段で
   129.5 MB/s、2048 MBps の段で 497.1 MB/s。503 は両方の段で 0 件。段を変えて追随したので、
   これは相関ではなく因果です。
2. **ただし段が上限であり続けるわけではありません。** 128 MBps では段が上限でしたが、
   2048 MBps では**既定の SSD IOPS から来る 768 MBps/TiB と、HA ペアあたりの書き込み上限
   750 MBps**が先に効きます（どちらも公式の性能表にあります）。**throughput capacity だけを
   上げても、SSD IOPS が既定のままならディスクスループットの上限は動きません。**
3. **いちばん確実に効いたレバーはクライアント側のマウントです。無料です。** 既定の NFS マウントは
   TCP 接続を 1 本しか張らないため、ストリーム数を 1 から 8 に増やしても止まったままです。
   2 つのファイルシステムで、別の日に測って **588.1 / 589.9 / 589.7** と
   **613.1 / 618.7 / 618.7**。`nconnect=16` を付けると同じ測定が **3062.8 MB/s（4.95 倍）**に
   なります。**この所見だけは 2 回独立に再現しました。**
4. **SSD IOPS を既定から上げると 280 GiB の読み取りが 7.14 倍になりました。ただし機構は
   未特定です。** `AUTOMATIC` 3,072 → `USER_PROVISIONED` 40,000 で 286.1 → 2042.1 MB/s。
   **当初これを「段のディスクスループット 2,048 MBps の 99.7%」と読みましたが、再測で 2667.2 に
   なり、その一致は偶然でした。** さらに CloudWatch を見ると、速い側の読み取りは
   **バイトの 98.5〜99.9% がディスクに行っていません。** 280 GiB はこの段のキャッシュ 238 GiB を
   18% 超えただけなので、**「ディスク経路が速くなった」では説明できません。**
   768 MBps/TiB が容量ではなく IOPS の水準で決まるという読み方自体は公式表と整合します。
5. **S3 Access Point 経路は NFS の 59.0% です**（414.0 対 702.1 MB/s、両経路とも非圧縮
   ペイロード・効率化オフ・同じ ONTAP ボリュームカウンタで測定）。差はボリュームに届く IO の
   形にあり、S3 経路は 8 MiB の単一 IO を約 1.01 秒かけて毎秒 49.3 回、NFS 経路は 64 KiB の IO を
   5.2 ms で毎秒 10,700 回流します。
6. **読み取りは段に縛られません。** 128 MBps のファイルシステムで S3 API 経由 579.3 MB/s は
   段の 4.5 倍で、段を 16 倍にしても 654.8 MB/s（1.13 倍）しか動きません。**書き込みの段を
   読み取りの見積りに使うと外します。**
7. **S3 API 経路で FSx for ONTAP 側は 1 リクエストあたり約 330 ms の固定費を払います。**
   単一ストリームの書き込みは 21.8 MB/s（8 MiB）に留まり、並列度 16 で段の上限に届きます。
   収集側を設計するとき、**直列に 1 つずつ PUT する実装は買った段を使い切れません。**
   Amazon S3 側の同じ点は 50.1 ms なので、この固定費は S3 Access Point 経路のものです。
8. **ファイル経路の S3 Files は単一ストリームが遅く、並列で伸び、約 450 MB/s で止まります。**
   読み取りは 8 ストリームで 451.3 MB/s、16 ストリームでも伸びません。**450 MB/s は 3.6 Gbps で、
   単一フローの上限（約 5 Gbps）の下です。** 止めているのはローカルの `efs-proxy` で、
   16 ストリーム時の CPU は 67.3% + 18.1% + 14.9%（8 vCPU）。マウントの相手が **127.0.0.1**、
   つまり同じホストのプロセスなので、`nconnect` は構造上この区間に届きません
   （指定するとマウントはハングします）。
9. **Amazon S3 は 8 台まで折れません。** 1 → 8 台で書き込み 8.23 倍、読み取り 8.04 倍、
   1 台あたりは不変。8 台合計 4783.2 MB/s = 38.3 Gbps。**FSx for ONTAP 側は同じラダーで
   4 台 1.01 倍**で、この非対称は台数を増やしても縮まりません。
10. **同一環境・同一条件の再現性は 0.2% 以内です。** 4 組の複製が
   417.1/417.0、415.1/415.7、808.6/808.4、772.0/771.1。**この記録の数値の差が 1% を超えていれば、
   実行ごとのばらつきではありません。**
11. **ONTAP は飽和していません。** S3 Access Point 経由で 417 MB/s のとき CPU 21〜24%、
   NFS で 800 MB/s のときも 18〜23%。**同じ CPU で 2 倍のスループットが出ているので、
   経路差の代価は ONTAP の中ではなく上流の S3 変換にあります。**
12. **書き込みではペイロードの圧縮性はほとんど効きません**（S3 で 0.5%、NFS で 4.7%）。
   **読み取りでは 4 倍変わります。** 書き込みはクライアントが実際にバイトを送るのに対し、
   読み取りは潰れていれば返す前に再構成できるためです。
13. **どちらの経路でも 503 は 1 件も出ませんでした。** ここで見た上限はすべて帯域側です。
14. **S3 API の経路は S3 Files を通っていません。** これは推論ではなく計測で裏が取れています。
   S3 API で 149.6 GB を動かしたあと、S3 Files の `DataWriteBytes` と `DataReadBytes` は
   ファイル経路の 13.96 GB しか計上していませんでした。

- **FlexCache の非圧縮測定を 2048 MBps 段で。** C は両側 128 MBps 段での測定です。origin を
  2048 に上げると origin 直読みが 2000 MB/s 級になるので、**「FlexCache が 2.31 倍速い」が
  段によって逆転する可能性があります。** 未測定です。
- **Amazon S3 のラダーが折れる位置。** 8 台・38.3 Gbps でまだ線形です。**ホストごとに別
  プレフィックスを使ったので、プレフィックスあたりのリクエスト上限は試していません。**
- **S3 Files の `efs-proxy` を増やしたときの上限。** 約 450 MB/s で止まる原因はこのプロセスの
  CPU だと判定しましたが、**マウントを複数に分けて proxy を増やす構成は試していません。**
- **NVMe 読み取りキャッシュ節の絶対値の非圧縮での対応。** 763.1〜1154.8 はゼロ埋めでの測定です。
  **「有効・無効の差が 1% 未満」という結論は同じ潰れ方どうしの比較なので成立し、非圧縮での
  寄与 1.09 倍も 2 回再現しました**が、絶対値はディスク側の上限と比べられません。
- **ランダム IO、ブロックサイズの掃引、曲線の膝。** 逐次のみ、1 MiB ブロックのみです。
  FSx for ONTAP については[公開されている fio 実測](https://zenn.dev/edash_tech_blog/articles/4ece2a554ecb27)（2026-04、東京リージョン）があります。
- **時間帯差。** 日次の再現性は 2 日ぶんで見ましたが、時間帯を変えた測定はしていません。

## 再現手順

```bash
# 1. 専用の FSx for ONTAP と計測ホスト
aws cloudformation create-stack --stack-name <name> \
  --template-body file://environments/aws-origin/template.yaml \
  --parameters ParameterKey=HostInstanceType,ParameterValue=c5n.9xlarge \
               ParameterKey=ThroughputCapacityMBps,ParameterValue=128 \
               ParameterKey=HostS3DataAccess,ParameterValue=true \
               ParameterKey=OriginVolumeSizeMB,ParameterValue=204800 \
               ... \
  --capabilities CAPABILITY_IAM

# 2. origin ボリュームに S3 Access Point を付ける
aws cloudformation create-stack --stack-name <name>-ap \
  --template-body file://patterns/collect/s3-access-point-attachment/template.yaml \
  --parameters ParameterKey=VolumeId,ParameterValue=<fsvol-...> ...

# 3. S3 Files 側
aws cloudformation create-stack --stack-name <name>-s3files \
  --template-body file://environments/s3files-compare/template.yaml \
  --parameters ParameterKey=MeasurementHostSecurityGroupId,ParameterValue=<host sg> ... \
  --capabilities CAPABILITY_IAM

# 4. S3 API 経路（計測ホスト上で）
python3.12 scripts/measure_s3_throughput.py \
  --target-name "FSx for ONTAP S3 Access Point" --target-kind provisioned \
  --bucket <access point ARN> --addressing-style path \
  --ceiling-note "128 MBps provisioned" \
  --sizes 1048576,8388608 --concurrency 1,4,16,64 --duration 30 \
  --output fsx.json --csv fsx.csv

# 5. ファイル経路（計測ホスト上で）
sudo bash scripts/measure_nfs_throughput.sh /mnt/fsx-origin "FSx for ONTAP NFS 4.1" 1 1 4 8
sudo bash scripts/measure_nfs_throughput.sh /mnt/s3files   "S3 Files mount"        1 1 4 8
```

`--target-kind` は必須です。省略できないようにしてあるのは、上限の種別を書かずに数値だけを
残せてしまうと、後からその表が誤読されるためです。

### コールドリードと経路差を測るとき

上の手順のままではこの 2 つは測れません。**4 か所を明示的に変えます。**

```bash
# a. クライアントの単一フロー上限を外す。既定のマウントでは約 590 MB/s で止まる
sudo mount -t nfs -o nfsvers=4.1,nconnect=16 <svm>:/origin_vol /mnt/origin

# b. 非圧縮のテストデータを作る。/dev/urandom より桁違いに速い
openssl enc -aes-256-ctr -pass pass:<any> -nosalt -in /dev/zero \
  | dd of=/tmp/rand1g bs=1M count=1024 iflag=fullblock
# 確認: gzip して 99% 以上でなければ非圧縮ではない
head -c 100000000 /tmp/rand1g | gzip -1 -c | wc -c

# c. ボリュームのインライン効率化を切る（捨てて構わないボリュームでのみ）
curl -k -u fsxadmin:<pw> -X PATCH -H 'Content-Type: application/json' \
  -d '{"inline_compression":false,"inline_dedupe":false,"data_compaction":false,"compression":false}' \
  "https://management.<fs-id>.fsx.<region>.amazonaws.com/api/private/cli/volume/efficiency?vserver=*&volume=origin_vol"

# d. SSD IOPS を既定から上げる。UPDATED_OPTIMIZING が 18 分ほど続く
aws fsx update-file-system --file-system-id <fs-id> \
  --ontap-configuration '{"DiskIopsConfiguration":{"Mode":"USER_PROVISIONED","Iops":40000}}'

# S3 側は非圧縮ペイロードを指定する。既定の fill は 1 バイトの繰り返しで、効率化に潰される
python3.12 scripts/measure_s3_throughput.py --body random \
  --target-name "S3 Access Point" --target-kind provisioned \
  --bucket <access point ARN> --addressing-style path \
  --ceiling-note "2048 MBps step, 40000 SSD IOPS, inline efficiency off" \
  --sizes 8388608 --concurrency 64 --duration 90 --phases write
```

**キャッシュに入らない大きさを一度に読むのが、いちばん確実なコールドリードです。** 介在 IO で
追い出す方法は、読み取り回数の多いファイルが残るため保証になりません（[3 回目](#3-回目-非圧縮データにしたら-2861-mbs)）。

**経路差は ONTAP のボリュームカウンタで測ってください。** クライアント側の計測はプロトコルごとに
数え方が違います。

```bash
curl -k -u fsxadmin:<pw> \
  "https://management.<fs-id>.fsx.<region>.amazonaws.com/api/storage/volumes?name=origin_vol&fields=name,statistics"
# throughput_raw / iops_raw / latency_raw はいずれも累積値。2 点の差を取る
```

### ONTAP が飽和しているかを見るとき

**ONTAP REST では見られません。** `fsxadmin` では `/api/cluster/nodes?fields=statistics` が 0 件を
返し、`/api/private/cli/system/node/utilization` と `statistics/show-periodic` は `API not found`
です。**CloudWatch を使ってください。**

```bash
# まずこのファイルシステムに何が出ているかを数える（33 個ありました）
aws cloudwatch list-metrics --namespace AWS/FSx `# allow:naming CloudWatch の名前空間名` \
  --dimensions Name=FileSystemId,Value=<fs-id> --query 'Metrics[].MetricName' --output json

# 負荷の窓を 1 分値で取る。CPU が低いまま経路差が出るなら、代価は ONTAP の外側にある
aws cloudwatch get-metric-statistics --metric-name CPUUtilization \
  --namespace AWS/FSx `# allow:naming CloudWatch の名前空間名` \
  --dimensions Name=FileSystemId,Value=<fs-id> \
  --start-time <ISO8601> --end-time <ISO8601> --period 60 --statistics Average \
  --query 'sort_by(Datapoints,&Timestamp)[].[Timestamp,Average]' --output text
```

**そして読み取りがディスクから来ているかは `DiskReadBytes` ÷ `DataReadBytes` で確かめてください。**
この比が数 % 以下なら、その測定はディスク経路ではなくキャッシュを測っています。**「キャッシュ量を
超える大きさを読んだ」だけでは足りません。**

| 見たいこと | メトリクス |
|---|---|
| ONTAP が飽和しているか | `CPUUtilization` |
| 読み取りがディスクから来ているか | `DiskReadBytes` を `DataReadBytes` で割る |
| 律速がネットワークか | `NetworkThroughputUtilization` |
| 律速がディスクスループットか | `FileServerDiskThroughputUtilization` |
| 律速が SSD IOPS か | `DiskIopsUtilization` |

## 後片付け

FlexCache を作っていればキャッシュ側を先に解放します。

```bash
# S3 Files 側はバージョンと削除マーカーまで消す。versioning が必須なので aws s3 rm では足りない
VPC_ID=... SUBNET_ID=... environments/s3files-compare/runbook.sh destroy
aws cloudformation delete-stack --stack-name <name>-ap
aws cloudformation delete-stack --stack-name <name>
# 消えたことは delete の戻り値ではなく list で数えて確認する
aws fsx describe-file-systems --query 'length(FileSystems)'
```

### FlexCache を作った回で詰まった 2 点

**FlexCache ボリュームは汎用のボリューム削除では消えません。**

```text
DELETE /api/storage/volumes/{uuid}
-> Cannot delete volume "cache_vol" ... because it is a FlexCache volume.
   Use the "volume flexcache delete -vserver ... -volume ..." command
DELETE /api/storage/flexcache/flexcaches/{uuid}   <- こちらを使う
```

**これが済むまで SVM ピア削除が無言でブロックされます。** 実際には「SVM ピアが 1 件のまま
10 回待っても減らない」という症状で現れ、原因が FlexCache 側にあるとは書かれません。SVM ピアが
残るので、続くクラスタピア削除も
`SVM peering relationships exist with the cluster` で拒否されます。**3 段が連鎖して、いちばん
下の原因だけがメッセージに出ません。**

もう 1 点は CloudFormation 側です。

```text
Cannot delete storage virtual machine while it has non-root volumes: fsvol-xxxxxxxx
```

**CloudFormation の外で作ったボリュームは、スタック削除がそれを知りません。** ONTAP REST で
FlexCache の親として作ったボリュームがこれに当たります。**手で消してから再実行します。**

### リージョンを跨いだ回で、スタックの外に残るもの

CloudFormation が管理しないので、**手で消さないと残ります。**

| 残るもの | 消し忘れると |
|---|---|
| ホストロールに足したインラインポリシー | **ロール削除が失敗し、スタック削除ごと止まります** |
| 相手リージョンからの CIDR ベースの SG ルール | SG が「依存オブジェクトあり」で消えません |
| VPC ピアリングと、その両側に足した経路 | 経路が blackhole として残ります。**既存 VPC に足した経路は特に忘れやすい** |
