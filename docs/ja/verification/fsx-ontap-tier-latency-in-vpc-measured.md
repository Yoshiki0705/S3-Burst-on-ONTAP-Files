# 検証記録 — FSx for ONTAP の S3 Access Points における SSD と capacity pool の `GetObject` 遅延（VPC 内、Single-AZ と Multi-AZ 第 1 世代）

**この記録は、Amazon FSx for NetApp ONTAP（以下、FSx for ONTAP）の S3 Access Points で、SSD に載るボリューム（階層化ポリシー NONE）と、
データが capacity pool にあるボリューム（階層化ポリシー ALL）を、同じ VPC の EC2 から交互に読んだときの `GetObject` の遅延を、
2 つのファイルシステム、1 日、1 回の実行で観測した結果である。** 一般化しない。測定したクライアントは VPC 内の EC2 だけで、
オンプレミスのクライアントは測っていない。

**ALL ボリュームの読みが capacity pool に届いたバッチだけを、capacity pool の遅延として読む。** ALL のデータは capacity pool にあったが、
ボリューム別の `CapacityPoolReadOperations` が 0 回だったバッチ（1 MiB と 64 KiB の大半）では、ALL の読みは capacity pool を通っていない。
そのバッチの ALL と SSD の差は ±10 ms 程度で、capacity pool の遅延ではない。どのバッチが届いたかは
[操作数の記録](fsx-ontap-cpool-read-operations-measured.md)にあり、この記録はその分類をそのまま使う。

**SSD 側の 4 MiB は、バッチによって中央値が開き、2 峰になるバッチがあった。** そのため差の符号や大きさは、n = 30 の 1 バッチずつでは安定しない。
原因は調べていない。

## 検証環境

| 項目 | Single-AZ | Multi-AZ 第 1 世代 |
|---|---|---|

| リージョン | ap-northeast-1 | ap-northeast-1 |

| スループットキャパシティ / SSD | 128 MBps / 1024 GiB（IOPS は自動の 3,072） | 同じ |
| ONTAP | 9.19.1P3 | 9.19.1P3 |
| ボリューム | 階層化ポリシー ALL と NONE の各 1 つ。UNIX、StorageEfficiency 無効、スナップショットポリシーなし | 同じ |
| S3 Access Points | ボリュームごとに 1 つ（UNIX ユーザー `root`、Internet オリジン）。アクセスポイント形式の ARN で呼んだ | 同じ |
| クライアント | EC2 c5n.xlarge 1 台、ap-northeast-1a（SSD 側のファイルシステムと同じ AZ）、S3 ゲートウェイ型 VPC エンドポイント経由 | クライアント A: 優先 AZ（1a）。クライアント C: スタンバイ AZ（1c）。どちらも c5n.xlarge |
| クライアントのソフト | Amazon Linux 2023、Python 3.12.14、boto3 1.43.115、botocore 1.43.115、s3transfer 0.19.3 | 同じ |
| 読み方 | 1 オブジェクト 1 回の `GetObject`。読んだことのない新しいオブジェクトだけ。並列度 1。マウントなし（S3 API のみ） | 同じ |
| 遅延の計測 | クライアントの `get_object` 呼び出しから本体を全部読み終えるまでを `perf_counter` で計測（ミリ秒） | 同じ |
| アカウント ID / リソース ID | この記録では伏せる（公開物のため。プレースホルダも置かない） | 同じ |

## 方法

1 バッチは新しい 30 オブジェクトで、ALL と NONE のオブジェクトを 1 個ずつ交互に読む（ALL 側 30 回、NONE 側 30 回）。バッチごとに先頭のボリュームを入れ替えた。
「差」は、同じ位置のオブジェクト対の ALL − NONE の中央値（括弧内は 10 と 90 パーセンタイル）である。バッチ単位（n = 30）の p95 と p99 は最大値に近く、裾の値としては読まない。

- Single-AZ: 4 MiB、1 MiB、64 KiB を各 2 バッチ（計 6）と、補足 2 バッチ（1 MiB と 4 MiB）。ALL だけを読む別のバッチ 9 個が同じファイルシステムにある
- Multi-AZ のクライアント A（優先 AZ）: 4 MiB、1 MiB、64 KiB を各 4 バッチ（計 12）と、補足 3 バッチ（1 MiB を 2、64 KiB を 1）
- Multi-AZ のクライアント C（スタンバイ AZ）: 4 MiB、1 MiB、64 KiB を各 1 バッチ

補足は、1 MiB と 4 MiB が capacity pool に届かなかった原因の切り分けのために、新しいオブジェクトを書き足して読んだバッチである。読みの失敗は全バッチで 0 だった。

### SSD 側の 4 MiB の中央値の開き

同じ AZ のクライアントで測った SSD ボリュームの 4 MiB は、バッチの p50 が次のように開いた。

| ファイルシステム | バッチ（NONE の p50、ms） | 範囲 |
|---|---|---|
| Single-AZ | m3-4m-b1 118.3、m3-4m-b2 75.0、s4m-int 85.2 | 75.0〜118.3 |
| Multi-AZ 優先 AZ | p-4m-b1 137.6、p-4m-b2 122.1、p-4m-b3 139.8、p-4m-b4 152.1 | 122.1〜152.1 |
| Multi-AZ スタンバイ AZ（クライアント C、1 バッチ） | c-4m-b1 333.0 | 範囲の外 |

同じ AZ のクライアントの 7 バッチ（各 n = 30）で 75.0〜152.1 ms と開いた。2 峰になるバッチは、Single-AZ の m3-4m-b2、Multi-AZ の p-4m-b2、クライアント C の 4 MiB に出た。
原因は調べていない。先頭ボリュームの順序とは対応していない（p-4m-b2 と p-4m-b4 は NONE が先で、200 ms 超は 14 回と 1 回）。

## 言えること

- この環境（FSx for ONTAP 第 1 世代 Multi-AZ、ONTAP 9.19.1P3、128 MBps、SSD 1024 GiB、優先 AZ の c5n.xlarge、S3 Access Points）で、capacity pool に届いた 4 MiB の `GetObject` は、
  ALL ボリュームが SSD ボリュームより、差の中央値で +110.4 ms 遅かった（4 バッチ、120 対。バッチごとに +104.5〜+122.4 ms）
- Single-AZ の同じ条件では、届いた 4 MiB の 1 バッチで +122.4 ms だった。同じ桁の範囲にあるが、ファイルシステムが別で、Single-AZ 側は 1 バッチなので、差があるともないとも言えない
- スタンバイ AZ のクライアントで、1 MiB が capacity pool に届いた 1 バッチは、ALL が SSD より +52.3 ms 遅かった。Single-AZ で 1 MiB が届いた補足の 1 バッチは +57.7 ms だった
- 届かなかったバッチでは、ALL と SSD の差の中央値が −10.1〜+7.8 ms にとどまった。ALL のデータが capacity pool にあっても、読みが capacity pool に届かない場合がある

## 言えないこと

- オンプレミスのクライアントからの遅延。この測定は VPC 内の EC2 だけで、AWS 外のクライアントからの結果は載せていない
- 優先 AZ とスタンバイ AZ のクライアントの差。C は各サイズ 1 バッチで、4 MiB の SSD 側が 2 峰
- Multi-AZ と Single-AZ の遅延の高低。別のファイルシステム、別の時間帯、別のバッチ数で測った
- 1 MiB と 64 KiB の capacity pool の遅延の差を、繰り返しのある値として。1 MiB で届いたのは 2 バッチ（Single-AZ の補足 1、Multi-AZ のスタンバイ AZ 1）、64 KiB で届いたバッチはない
- SSD の 4 MiB の 2 峰の原因
- 請求されるリクエスト数との対応（[操作数の記録](fsx-ontap-cpool-read-operations-measured.md)を参照）
- 他の ONTAP バージョン、他のスループットキャパシティ、Multi-AZ 第 2 世代、日をまたぐ再現、複数クライアントの並列読み
- 優先 AZ のフェイルオーバー時の遅延。フェイルオーバーは意図的には起こしておらず、測定中に自然に起きたかは確認していない

## 費用と撤去

主な費目は FSx for ONTAP と EC2 の稼働時間で、金額はこの記録に書かない（請求側の確定値を確認していないため）。稼働時間と撤去の手順、
索引にだけ残った項目の観測は[操作数の記録](fsx-ontap-cpool-read-operations-measured.md#費用と撤去)にある。両ファイルシステムの撤去後、
サービスごとの describe と list で 0 件または `NotFound` を確認した。
