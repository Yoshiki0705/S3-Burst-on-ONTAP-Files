# 検証記録 — Amazon S3 Files の相互可視性と同期の実測

**この記録は Amazon S3 Files 単体の測定です。** この構成（S3 Access Point で収集し FlexCache で
配布する形）との比較は[比較検証](s3files-vs-flexcache.md)にあります。
測定手法はこのリポジトリの既存測定に揃えていますが、**マウントオプションは揃いません**。
その差は下の環境表に併記しています。

この記録で測ったのは**反映の速さと意味論**です。スループットと IOPS は別の記録
（[スループット / IOPS / 並列度の実測](throughput-iops-concurrency.md)）にあります。そちらでは
同一ホストから S3 Access Point と Amazon S3 を並べ、並列度を掃引しています。
ランダム IO とブロックサイズの掃引は依然として測っていません。FSx for ONTAP については
公開されている実測があり、再測定に見合う独自性がないためです
（[e-dash による fio 実測](https://zenn.dev/edash_tech_blog/articles/4ece2a554ecb27)、2026-04、
東京リージョン）。

|---|---|---|---|---|---|

| 4 MiB | バケットから直接 | 48.0 ms | 63.5 ms | 66.2 ms | 30 |

## サービス側メトリクスとの対照

**クライアント側の測定を、サービス自身が報告する値と突き合わせました。** 同じ現象を独立した
2 系統で測っており、片方の誤りに気づける形にするためです。CloudWatch の名前空間は
`AWS/S3/Files`、ディメンションは `FileSystemId` です。

| 指標 | サービス側（CloudWatch） | クライアント側（この測定） | 一致 |
|---|---|---|---|
| エクスポート（ファイル → S3） | `ExportAge` mean 56.93 秒 / peak **66.06 秒** | 方向 2 p50 63.77 秒 / max **66.33 秒** | **peak が 0.27 秒差** |
| インポート（S3 → ファイル） | `ImportAge` mean 2.29 秒 / peak 62.80 秒 | 方向 1 p50 1.53 秒 / max 14.36 秒 | mean は近い。**peak は一致しない** |

**エクスポート側は 2 系統が一致します。** 「約 60 秒まとめてからコピーする」という
ドキュメントの記載が、両側から裏付けられました。分布も狭く、30 回すべてが 63.8〜66.3 秒に入ります。

**インポート側の peak は一致しません。** `ImportAge` の peak 62.80 秒に対し、クライアント側で
観測した最大は 14.36 秒でした。`ImportAge` は測定対象外の変更も含むゲージであり、
測定の反復と 1 対 1 に対応していない可能性があります。**どちらが正しいかは判定していません。**
インポート方向を代表値で語るなら、クライアント側の p50 1.53 秒を条件つきで使い、
上限側は未確定として扱ってください。

| その他の指標 | 観測値 | 読み方 |
|---|---|---|
| `PendingExports` | peak 2 | エクスポート待ちの滞留なし。毎秒 800 ファイルの上限には遠い |
| `LostAndFoundFiles` | 0 | 競合は発生していない（同時変更を測っていないため当然） |
| `Inodes` | peak 98 | 測定で作ったファイル数と整合 |
| `StorageBytes` | peak 1,003,520 B | 高性能ストレージに載った量。課金対象の次元 |

## コストの実測

**推定ではなく、課金対象のバイト数を CloudWatch から取って単価を掛けたものです。**
単価は[FinOps の費用構造](../reference/comparison/finops-s3-vs-s3ap.md)に記録済みの
ap-northeast-1 の値（2026-08-01 適用）です。

| 次元 | 実測量 | 単価 | 金額 |
|---|---|---|---|
| 書き込み（`DataWriteBytes` + `MetadataWriteBytes`） | 0.002430 GiB | $0.07 / GB | $0.000170 |
| 読み取り（`DataReadBytes` + `MetadataReadBytes`） | 0.021324 GiB | $0.04 / GB | $0.000853 |
| 高性能ストレージ | peak 0.000935 GiB × 0.92 時間 | $0.36 / GB-Mo | $0.000000 |
| **S3 Files 小計** | | | **$0.001023** |

S3 Standard のストレージと S3 リクエスト、EC2 は別枠で、この表には入っていません。

> **メタデータ読み取りがデータ読み取りの約 10 倍です。** `MetadataReadBytes` 20,718,960 B に対し
> `DataReadBytes` 2,177,076 B でした。`actimeo=0` で属性キャッシュを切っているため、
> すべての `stat` がサーバへ行きます。測定条件としては正しいものですが、**この設定を本番に
> 持ち込むと読み取り課金の内訳が変わります。** 鮮度と課金のどちらを取るかという設計判断になります。

## 読み取れること

**エクスポートの約 60 秒は実在し、分布が狭い。** 30 回すべてが 63.8〜66.3 秒でした。
ファイル側に書いたものを S3 側で見たいなら、この窓を設計に織り込む必要があります。
「速くなることもある」という性質のものではありません。

**インポートは秒オーダーで、ばらつきが大きい。** p50 1.53 秒に対し max 14.36 秒です。
p90 が 2.04 秒なので、遅いのは一部の試行に限られます。

**しきい値の両側で読み取り遅延が約 3.8 倍違います。** 64 KiB が p50 12.6 ms、
4 MiB が p50 48.0 ms でした。ただし**これはサイズ差と経路差が混ざった値です。**
同一サイズで経路だけを変えた測定はしていないため、差の要因を分離できていません。

**マウント内で完結する読み書きは 10.7 ms です。** 同期を待たない経路で、NFS の往復に相当します。

## 落とし穴

実際に構築して初めて分かったもので、公開ドキュメントに記載を見つけられなかったものを含みます。

| # | 事象 | 内容 |
|---|---|---|
| 1 | `actimeo=0` は効くが文字列は出ない | カーネルが `acregmin` / `acregmax` / `acdirmin` / `acdirmax` に展開する。`findmnt` の出力を `actimeo` で検索すると、**正しく設定された環境で偽陰性**になる |
| 2 | FSTYPE は `s3files` ではなく `nfs4` | マウントヘルパーがローカルの TLS プロキシ経由でつなぐため、source は `127.0.0.1:/`、port は高位のランダムポートになる。`tls` は NFS オプションとして現れない |
| 3 | **S3 API で書いたオブジェクトは `root:root` で現れる** | ファイルは 0644、ディレクトリは 0755。アクセスポイントで非 root にマップした利用側は、**S3 で作られたディレクトリに書き込めません**。読み取りは 0644 なので通ります |
| 4 | `ClientRootAccess` なしでは root でも書けない | スコープを絞った IAM（`ClientMount` + `ClientWrite`）だけでは、マウントルートで root の `mkdir` すら拒否されます。アクセスポイントに POSIX ユーザーを持たせるのが解で、root はその uid にマップされます |
| 5 | アクセスポイントの root ディレクトリ分だけキーがずれる | root を `/measure` にすると、バケットキー `measure/a/b` はマウント上で `<mount>/a/b` に見えます。**マウントパスとキーを同一視した測定コードは、動いている方向をポーリングし続けます。**失敗がエラーではなくタイムアウトなので、サービスが遅いのと区別できません |
| 6 | 既定の `python3` は 3.9 | Amazon Linux 2023 の `python3` は 3.9 で、`datetime.UTC`（3.11 以降）を使うスクリプトは動きません。`dnf install python3.12` が必要です |
| 7 | botocore は `pip3` では入らない | `dnf install python3-botocore` を使います。無くてもマウントは成功しますが、`mount.log` に `Failed to import botocore` が記録され、CloudWatch メトリクスが使えません |
| 8 | 信頼ポリシーのプリンシパル | `elasticfilesystem.amazonaws.com` が正しい（公式記載どおり）。**対照:** サービスが EventBridge ルール `DO-NOT-DELETE-S3-Files-*` を `ManagedBy: elasticfilesystem.amazonaws.com` で作成したことを確認しています。作成 API が成功したことは根拠になりません |
| 9 | `lost+found` は最初から存在する | `.s3files-lost+found-<file-system-id>`、`0700 root:root`。競合時に作られるのではありません |
| 10 | **エクスポート待ちがあるとファイルシステムを削除できない** | `delete-file-system` が `ConflictException: has data pending export to S3` を返します。`--force-delete` で強制できますが、未エクスポートのデータは失われます |
| 11 | **`PendingExports` は削除可否のゲートに使えない** | 上記の拒否が起きた時点で `PendingExports` は 0 を報告していました。`ExportAge` は 5 秒を示しており、こちらの方が実態に近いようです。**メトリクスで削除可能と判断しないこと** |
| 12 | **ファイルシステムが付いているバケットは削除できない** | `BucketHasS3FileSystemAttached` を返します。したがって破棄の順序はバケットが最後ではなく、**ファイルシステムを先に消してからバケット**です |

作成に要した時間も記録します。ファイルシステムは**初回ポーリングで既に `available`**、
マウントターゲットは **77 秒**、アクセスポイントは即時でした。公開されている実測記事は
ファイルシステムに「数分〜十数分」と記録しており、**一致しません。**
1 回しか作っていないので、どちらが代表的かは判定していません。

## 意味論の測定（削除・上書き・マルチパート・競合・経路）

**2026-09-01 の追加測定です。** 同一のファイルシステム・同一のホスト・同一のマウント条件で、
最初の測定が「読み取れないこと」に挙げていた項目を埋めました。7 つの問いすべてに、
同一実行内で成立しなければならない対照を付けています。

### 反映の速さ（削除と上書き）

| 問い | p50 | n | タイムアウト |
|---|---|---|---|
| S3 `DeleteObject` → マウントから消えるまで | 1,524.9 ms | 10 | 0 |
| マウント上で `unlink` → `HeadObject` が 404 になるまで | 64,941.5 ms | 10 | 0 |
| S3 `PutObject` で上書き → マウントが新内容を返すまで | 1,632.1 ms | 10 | 0 |
| マウント上で書き換え → `GetObject` が新内容を返すまで | 64,975.9 ms | 10 | 0 |

**削除と上書きは、新規作成と同じ桁です。** どちらの方向も、新規作成で測った値
（S3 → ファイル p50 1,533 ms、ファイル → S3 p50 63,769 ms）とほぼ一致します。
**エクスポート方向は操作の種類によらず約 60 秒の窓に支配されます。**

上書きは**内容一致で判定しています**（サイズではなく）。中途半端な内容が見えた試行は
1 件もありませんでした。

**2 回の書き込みは 2 バージョンになりました。** 全 10 キーで `list-object-versions` が 2 件を返します。
バッチング窓は連続した書き込みを 1 バージョンにまとめる仕組みですが、この測定では 2 回の書き込みが
分オーダーで離れているため、まとまらないのが期待値です。

### マルチパートアップロード中の可視性

| 時点 | ファイル側 | 観測 |
|---|---|---|
| パート 1 アップロード後、`CompleteMultipartUpload` 前（20 秒待機） | **見えない** | 3/3 |
| `CompleteMultipartUpload` 後（**対照**） | 見える | 3/3 |

**この構成と同じ挙動です。** 本構成でも `CompleteMultipartUpload` まで NFS 側に現れません
（[FlexCache 検証記録](flexcache-s3ap-visibility.md)）。中途半端なオブジェクトを読む心配は、
どちらの設計でも不要です。対照を置いているので、「見えない」がパスの間違いでないことも示せます。

### 競合したときの挙動

ファイル側に書き、**エクスポート窓の内側**（5 秒後）に同じキーを S3 API で上書きしました。

| 問い | 結果 | 観測 |
|---|---|---|
| どちらが正本になるか | **バケット側が勝つ** | 3/3 が S3 の内容に収束 |
| ファイル側のバージョンはどうなるか | **lost and found へ移される** | ディレクトリのエントリが 0 → 3 |

**独立した裏付け:** CloudWatch の `LostAndFoundFiles` が peak 3.00 を記録しており、
3 回の競合と一致します。ファイルシステム側から数えた 3 件と、サービス側が報告した 3 件が
別経路で一致しています。

`.s3files-lost+found-<file-system-id>` はファイルシステムのルートにあり、`0700 root:root` です。
**アクセスポイントでサブディレクトリを root にしている場合は見えません。** 読むには
`s3files:ClientRootAccess` が必要で、この観測のためだけに一時的に付与しました
（計測本体はアクセスポイント経由のままです）。

### サイズ差と経路差の分離

最初の測定は 64 KiB と 4 MiB を比べており、**サイズと経路が同時に変わっていました。**
ここでは `PutSynchronizationConfiguration` で取り込みしきい値だけを動かし、
**オブジェクトサイズを 64 KiB に固定**しています。

| 経路 | しきい値 | p50 | p90 | n |
|---|---|---|---|---|
| 高性能ストレージに載っている | 131,072 B（64 KiB < しきい値） | **10.8 ms** | 11.1 ms | 30 |
| バケットから直接 | 1,024 B（64 KiB > しきい値） | **55.0 ms** | 65.3 ms | 30 |

**経路だけで約 5.1 倍です。** サイズを固定しているので、この差は経路に帰属します。
混ざった状態で見えていた 3.8 倍より**大きい**ことに注意してください。

**4 MiB の p50 48.0 ms は、64 KiB をバケットから直接読んだ 55.0 ms に近い値です。**
両方ともバケットから配信される経路であり、**支配しているのはサイズではなく経路**だと読めます。
ただしこれは 2 つの測定の突き合わせであり、サイズを振って経路を固定した測定はしていません。

測定後にしきい値が既定値へ戻ったことを、出力ではなく API で確認しています
（`latestVersionNumber` 3、`sizeLessThan` 131072、`trigger` `ON_DIRECTORY_FIRST_ACCESS`、`daysAfterLastAccess` 30）。

|---|---|---|
| 書き込み | 0.001579 GiB | $0.000111 |
| 読み取り | 0.022816 GiB | $0.000913 |

## 読み取れないこと

| 問い | この測定では答えられない理由 |
|---|---|
| スループットと IOPS | 並列度 1、逐次 1 件ずつ。測る構成ではない。**このリポジトリでは測らない方針**で、公開実測（[e-dash](https://zenn.dev/edash_tech_blog/articles/4ece2a554ecb27)）を参照する |
| 並列度を上げたときの挙動 | 並列度 1 のみ。スループット側の問いなので上記の方針に含まれる |
| 大量の小ファイル | 逐次 30 件。毎秒 2,400 オブジェクトの取り込み上限には遠い |
| インポート側の上限値 | クライアント側 max 14.36 秒と `ImportAge` peak 62.80 秒が一致しない。2 系統が一致しないため上限として使わない |
| サイズを振って経路を固定した測定 | 経路を振ってサイズを固定した測定はした。逆はしていない |
| 別リージョン | ap-northeast-1 のみ |
| Lambda / ECS / EKS からのマウント | EC2 のみ。対応コンピュートには含まれるが確かめていない |
| KMS カスタマー管理キーでの挙動 | SSE-S3 のみ |
| 競合が窓の外で起きた場合 | 5 秒後（窓の内側）のみ。窓を越えてからの競合は測っていない |

## 再現手順

環境の作成と破棄は[S3 Files 検証環境セットアップ](../deployment/aws-s3files-compare.md)にあります。
計測そのものは次のとおりです。

1. アクセスポイントを作り、POSIX uid/gid と root ディレクトリを指定する
2. `mount -t s3files -o accesspoint=<id>,actimeo=0 <fs-id>:/ /mnt/s3files`
3. `findmnt` で**実効オプションを確認する**。`actimeo` ではなく `acregmin=0` を見る
4. ホストに Python 3.12 と boto3 を入れる（既定の 3.9 では動かない）
5. `scripts/measure_s3files_visibility.py` を `--key-prefix` 付きで実行する。
   アクセスポイントの root ディレクトリを指定した場合、その値を渡さないと全方向が
   タイムアウトする
6. 実行後に CloudWatch の `AWS/S3/Files` を実行窓で集計し、クライアント側の値と突き合わせる
7. 環境情報（上の表の全項目）を数値と一緒に記録する

```bash
python3.12 scripts/measure_s3files_visibility.py \
  --file-system-id fs-0123456789abcdef0 \
  --bucket <bucket> \
  --mount-point /mnt/s3files \
  --key-prefix measure/ \
  --iterations 30 --timeout 300 --poll-interval 0.5 \
  --output result.json --csv result.csv
```

方向 2 は 1 回あたり 60 秒以上かかるため、30 回で 35 分前後を見てください。

| S3 Files ファイルシステム / マウントターゲット / アクセスポイント | **削除済み** |
| バケット | **削除済み**（バージョン全削除後） |
| IAM ロール 2 つ（同期用・ホスト用） | **削除済み** |
| セキュリティグループ 2 つ | **削除済み** |
| 計測ホスト（EC2） | **削除済み** |
| サービスが作った EventBridge ルール | **残っていない**（`DO-NOT-DELETE-S3-Files-*` を 0 件と確認） |
| 既存の共有リソース | **一切変更していない**（既存 SG への規則追加もしていない） |

破棄後に残存 0 件を個別に確認しています。`delete-*` API の戻り値ではなく、
一覧 API の件数で判定しました。**この判定が実際に取りこぼしを捕まえています。**
最初に書いた破棄スクリプトは固定の `sleep` とエラー抑制を使っており、
すべての手順が成功したように見えたままファイルシステムとバケットが残りました。
気づけたのは最後の件数確認だけです。スクリプトは状態遷移を待つ形に直しました
（[`runbook.sh`](../../../environments/s3files-compare/runbook.sh)）。
