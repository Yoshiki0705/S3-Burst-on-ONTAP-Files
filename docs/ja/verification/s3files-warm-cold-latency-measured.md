# 検証記録 — Amazon S3 Files の 64 KiB 読み取りにおけるコールドとウォームの遅延の 1 回の観測

<!-- ontap-version-exempt-file: this record measures Amazon S3 Files standalone; ONTAP is not
     involved in the quantity measured here. -->

**この記録は Amazon S3 Files 単体を、1 クライアント、1 日、1 回の実行で観測した結果である。** 一般化しない。
測ったのは、64 KiB のファイルを初めて読むときの遅延（コールド）、2 分後に同じファイルを読み直したときの遅延
（ウォーム）、同じオブジェクトを S3 から直接取得したときの遅延の 3 点である。

**コールドの経路は区別できていない。** 読みが高性能ストレージを通ったかを `DataReadBytes` で見たが、
このメトリクスはコールドとウォームで同じ値（1 読み取りあたり 65,972 B）を示し、2 つを区別しなかった。したがって
コールドの 230.22 ms を「バケットから直接読んだ遅延」とも「取り込み後の高性能ストレージから読んだ遅延」とも書かない。
経路の区別は、S3 Files の [clean な warm / cold 比較が未完了](s3files-throughput-measured.md)という状態から
進んでいない。この記録が足すのは、別の設計で測った遅延の値と、経路を区別できなかったという結果である。

## 検証環境

| 項目 | 値 |
|---|---|
| 計測日 | 2026-10-19（1 日、1 回の実行） |
| リージョン / AZ | ap-northeast-1 / ap-northeast-1a |
| クライアント | EC2 c5n.9xlarge 1 台、Amazon Linux 2023（kernel 6.18.54-121.166.amzn2023）、パブリックサブネット、S3 ゲートウェイ型 VPC エンドポイントあり |
| S3 Files | ファイルシステム 1 つ、アクセスポイントなし（ルートをマウント）、マウントターゲット 1 つ（クライアントと同一 AZ） |
| 取り込みしきい値 | 既定。128 KiB は文書上の既定値として記録したもので、API の出力にしきい値のフィールドがなく、API では確認していない |
| マウント | `mount -t s3files <fs>:/ /mnt/s3m2`、オプション指定なし。実効は `vers=4.2,rsize=wsize=1048576,hard,noresvport,proto=tcp,timeo=600,retrans=2,sec=sys`、`127.0.0.1` の efs-proxy（TLS）経由 |
| `nconnect` | 渡していない（実効オプションに現れない） |
| クライアントのソフト | amazon-efs-utils 3.3.3、読み取りの計測は Python（`perf_counter`）、基準の GET は boto3 |
| データ | 64 KiB の乱数オブジェクト 401 個。マウントの前に S3 API で書き、1 ファイルずつ別のディレクトリに置いた |
| 読み取りの前処理 | 毎回、読む直前に `drop_caches=3`（クライアントのページキャッシュと dentry を捨てる。計測の外） |
| 並列度 | 1（逐次） |
| 高性能ストレージの容量、スループットキャパシティ、階層化ポリシー | S3 Files に該当する設定はない（FSx for ONTAP の項目ではない） |
| ファイルシステム ID / アカウント ID | この記録では伏せる（公開物のため。プレースホルダも置かない） |

## 方法

1 周は、コールド 30 個、2 分後にウォーム（同じ 30 個）、さらに 2 分後に S3 直接 GET（同じ 30 個）の順に読む。
1 バッチは 1 分間に収め、バッチの間に空の 1 分を置いた。6 周を 2 セット（a、b。オブジェクトは別）行い、
各経路 12 バッチ、n = 360 読み取りになる。読み取りは `open` → 全読み → `close` を 1 回の計測とし、
ディレクトリは一覧していない。

追加として、同じディレクトリに置いた 40 個（フラット配置）をコールド 1 バッチ、ウォーム 1 バッチで読み、
マウント直後の最初の 1 個（パイロット）も読んだ。

## 結果

### 遅延の分布

単位はミリ秒、1 読み取りあたり。

| 経路 | セット | n | p50 | p95 | p99 | 最小 | 最大 |
|---|---|---|---|---|---|---|---|
| コールド（マウント経由、初回読み） | a | 180 | 239.29 | 353.80 | 469.73 | 225.68 | 959.97 |
| | b | 180 | 229.58 | 342.20 | 568.32 | 225.73 | 684.30 |
| | 合計 | 360 | 230.22 | 350.89 | 512.79 | 225.68 | 959.97 |
| ウォーム（マウント経由、2 分後） | a | 180 | 18.61 | 19.81 | 20.57 | 17.32 | 21.71 |
| | b | 180 | 18.82 | 19.91 | 20.14 | 17.30 | 20.34 |
| | 合計 | 360 | 18.71 | 19.89 | 20.23 | 17.30 | 21.71 |
| S3 直接 GET（boto3） | a | 180 | 46.64 | 70.86 | 80.51 | 19.34 | 102.33 |
| | b | 180 | 50.06 | 69.04 | 91.63 | 22.84 | 97.95 |
| | 合計 | 360 | 47.93 | 69.86 | 90.69 | 19.34 | 102.33 |

- コールドの最小（225.68 ms）がウォームの最大（21.71 ms）より大きく、2 つの分布は重ならない。p50 の比は 12.3 倍
- 同じオブジェクトで対にした差（コールド − ウォーム、n = 360 対）の中央値は 211.8 ms、最小は 206.5 ms で、360 対のすべてが正
- 2 セットで同じ向きだった。a と b の p50 の差は、コールドが 9.7 ms、ウォームが 0.2 ms
- コールドの内訳は、235 ms 未満が 209 個、235〜260 ms が 83 個、260〜300 ms が 1 個、300〜400 ms が 54 個、400 ms 以上が 13 個。
  300 ms 以上の 67 個のうち 23 個は、a の 1 周目に集中した（a の 1 周目の中央値は 346.9 ms）。
  ほかの 11 バッチの中央値は 227.8〜240.6 ms
- S3 直接 GET の p50（47.93 ms）はウォーム（18.71 ms）より遅かった。S3 への往復、TLS、署名、boto3 の処理の
  どれがどれだけを占めるかは切り分けていない。直接 GET は基準として置いたもので、経路の比較としては読まない

### 1 回ずつの追加観測

次の 3 点は、それぞれ 1 回の観測で、一般化しない。

| 観測 | 値 | 読み方 |
|---|---|---|
| マウント直後の最初の 1 個（パイロット、n = 1） | コールド 7,732.623 ms。続くウォームが 17.013 ms と 4.931 ms | 本測定の 360 個とは別に扱う。初回の接続や認証の立ち上げを含むと推測するが、未確認 |
| 同じディレクトリの 40 個（コールド 1 バッチ） | 1 個目が 438.9 ms、残り 39 個の中央値が 13.12 ms（先頭 5 個: 438.9、16.4、13.6、13.4、13.7 ms） | 1 個目だけが遅い。理由は未確認。ディレクトリへの最初のアクセスで同じディレクトリの小さいファイルが先に取り込まれる、という説明が考えられるが、この測定で確かめておらず仮説にとどまる |
| 同じ 40 個のウォーム | 中央値 13.04 ms | `drop_caches` 後の再読みで 13 ms 前後。`MetadataReadBytes` は 1 ファイルあたり 5 操作立っているが、操作の種類は取っておらず、13 ms の内訳は未取得 |

ウォームの 18.71 ms は、毎回 `drop_caches` をかけた後の値である。パイロットの 3 回目は `drop_caches` 後でも 4.931 ms で（n = 1）、
18.71 ms が `drop_caches` 後のウォームの下限なのか、読みの順序や回数で下がる値なのかは、このデータでは決まらない。
キャッシュを温存した読みは測っていない。

### 経路の確認に使った CloudWatch の値

`AWS/S3/Files` の 1 分周期の値を、バッチの分に帰属させた。

| バッチ | `DataReadBytes`（Sum） | `MetadataReadBytes`（Sum） |
|---|---|---|
| コールド 12 バッチ | すべて 1,979,160 B（65,972 B × 30） | 1,105,920 B（270 操作 × 4 KiB）が 9 バッチ、1,114,112 B（272 操作）が 3 バッチ |
| ウォーム 12 バッチ | すべて 1,979,160 B | 1,105,920 B が 10 バッチ、1,114,112 B が 2 バッチ |
| S3 直接 GET 12 バッチ | データポイントなし | 背景の 4,096 B または 12,288 B のみ |
| フラット 40 個のコールド | 2,638,880 B（65,972 B × 40） | 819,200 B（200 操作、1 ファイルあたり 5 操作） |
| フラット 40 個のウォーム | 2,638,880 B | 819,200 B |

## 対照の合否

| 対照 | 期待 | 観測 | 判定 |
|---|---|---|---|
| S3 直接 GET が `DataReadBytes` を増やさない | 直接 GET の 12 バッチの分に立たない | 12 バッチともデータポイントなし | 成立 |
| マウント経由の読み取りが `DataReadBytes` を増やす | コールドとウォームの各バッチに立つ | 24 バッチすべてで 1,979,160 B。フラットの 2 バッチは 2,638,880 B。測定期間の合計 52,777,600 B は 24 × 1,979,160 + 2 × 2,638,880 と一致 | 成立 |
| `DataReadBytes` でコールドとウォームを区別できる | コールドは経路が違うなら値が違う | どちらも 1 読み取りあたり 65,972 B で同一 | **不成立**（このメトリクスは 2 つを区別しない） |
| 読みのない窓で `DataReadBytes` が立たない | 窓にデータポイントなし | 前後 2 つの窓とも `DataReadBytes` はデータポイントなし。窓の始点と終点は生データに記録されておらず、境界は確認できない | 成立（窓の境界は確認できない） |
| 取り込みがどのバッチで起きたかを帰属できる | 読んだバッチの分に `Inodes` と `StorageBytes` の増分 | 周期が 15 分で、バッチへの帰属はできない | **不成立**（分解能が足りない） |
| 取り込みが書き込みとして計上される | `DataWriteBytes` と `ImportFailures` の有無が見える | 測定期間を通じて `DataWriteBytes` と `ImportFailures` はデータポイントなし。`PendingExports` の最大値は 5 点とも 0。`MetadataWriteBytes` は 12:13Z（マウント直後の分）の 12,288 B のみ | **想定と不一致**（理由は未確認） |
| クライアント側のメトリクスとログ | 出力される | ホストのロールに `cloudwatch:PutMetricData` と `logs:CreateLogGroup` がなく、一部しか出なかった。マウントは成功した | 欠落（実際に使われる名前空間は未確認） |

`DataReadBytes` が 2 つを区別しなかったため、コールドの経路（バケットから直接読んで返したのか、取り込み後に高性能ストレージから返したのか）は
この測定の結果から確かめられない。

### 取り込みの進行

15 分周期の `Inodes` と `StorageBytes`（最大値）は、測定中に単調に増えた。

| 時刻（JST、15 分バケット） | `Inodes` | `StorageBytes` |
|---|---|---|
| 21:45 | 193 | 7,567,360 B |
| 22:00 | 313 | 12,482,560 B |
| 22:15 | 499 | 19,916,800 B |
| 22:30 | 619 | 24,832,000 B |
| 22:45 | 779 | 32,614,400 B |

読んだオブジェクトは 401 個すべてで、読まなかったオブジェクトが取り込まれたかは、この実験からは言えない。
周期が粗く、どのバッチで増えたかの帰属もできていない。

## 言えること

- この環境（c5n.9xlarge、ap-northeast-1a、既定のマウントオプション、1 クライアント、並列度 1、64 KiB）で、ディレクトリごとに初めて読むファイルの
  p50 は 230.22 ms、2 分後に同じファイルを読み直したときの p50 は 18.71 ms だった（各 n = 360）。分布は重ならず、2 セットで同じ向きだった
- コールドの下限は 225.68 ms で、360 個のうち 260 ms 未満が 292 個（81%）だった
- 同じディレクトリの 40 個では、1 個目だけが 438.9 ms で、残り 39 個の中央値は 13.12 ms だった（1 回の観測）。
  コールド読みの測定には、ファイルごとにディレクトリを分ける設計が要る

## 言えないこと

- コールドの 230 ms が「バケットからの直接読み」の遅延であること。`DataReadBytes` はコールドでもウォームと同じ値で、経路を区別しない
- [S3 Files のファイルシステム性能の記録](s3files-throughput-measured.md)にある「新規の 64 KiB をしきい値 1024 の状態で読んだ 4.05 ms（バケット直読）」との整合。
  この測定は別のインスタンス、別のディレクトリ構成で、`drop_caches` 付き、しきい値は既定であり、条件が違う。4.05 ms と 230.22 ms の差の原因は、このデータからは特定できない
- 64 KiB 以外のサイズ、並列読み取り、`nconnect` の効果、他のインスタンス型、他の AZ、他のリージョン、日をまたいだ再現
- 取り込みのタイミング。ウォームがコールドの 2 分後に約 12 倍速かったことは、2 分以内にデータが高性能ストレージ側に入ったことと整合するが、取り込みの時刻の直接証拠ではない
- マウント時の efs-proxy のログには `ReadBypass enabled` と、プロキシ側のキャッシュが有効という記述（`server_cache_enabled=true, local_cache_enabled=true`）の両方が出ていた。
  ReadBypass がコールドの経路にどう効いたか、プロキシ側のキャッシュがウォームの値にどの程度効いたかは、どちらも切り分けていない
- 請求。この測定は遅延だけを見ており、S3 Files の読み取り課金との対応は見ていない

## 証拠の段階

| 主張 | 段階 | 根拠 |
|---|---|---|
| 64 KiB の初回読みの p50 が 230.22 ms、2 分後の再読みの p50 が 18.71 ms | 検証済み（1 環境、1 日、1 回の実行） | 名前を付けた環境（ap-northeast-1、c5n.9xlarge、並列度 1）での 360 読み取りずつ。2 セットで同じ向き |
| コールドの経路がバケット直読か、取り込み後の高性能ストレージか | 未確認 | `DataReadBytes` が 2 つを区別しなかった |
| 同じディレクトリの 1 個目だけが遅い | 検証済み（1 回の観測） | 40 個のコールド 1 バッチ。理由は仮説 |
| 取り込みのタイミング | 未確認 | 15 分周期でバッチへ帰属できない |
| 請求への影響 | 確認していない | 遅延のみを測った |

## 費用と撤去

主な費目は EC2 の稼働時間（約 1.75 時間）で、金額はこの記録に書かない。

撤去は、EC2 の終了、マウントターゲットとファイルシステムの削除（強制フラグなし）、バケットの全バージョン削除と
バケットの削除の順に行った。サービスごとの describe と list を 74 回呼び、全クラスで 0 件または `NotFound` を確認した。
Resource Groups Tagging API は、撤去の約 18 分後まで削除済みリソースの ARN を 4 件返し続け、
約 14 時間後の再確認で 0 件になった（消えた時刻は不明）。これは検索索引の観測であって、
課金の有無についての主張ではない。削除できない残存物として、CloudWatch の名前空間 `efs-utils/S3Files` と `AWS/S3/Files` のメトリクスが保持期限まで残る。
