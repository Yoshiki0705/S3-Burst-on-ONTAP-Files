# 検証記録 — FSx for ONTAP の S3 Access Points で capacity pool のデータを読んだときの `CapacityPoolReadOperations`

**この記録は、Amazon FSx for NetApp ONTAP（以下、FSx for ONTAP）の S3 Access Points で、階層化ポリシー ALL のボリューム
（データは capacity pool にある）のオブジェクトを 1 回 `GetObject` したとき、ボリューム別の CloudWatch
`CapacityPoolReadOperations` が何回立ったかを、2 つのファイルシステム、1 日、1 回の実行で観測した結果である。**
一般化しない。

**この数は CloudWatch の操作数であって、請求されるリクエスト数ではない。** 両者の対応は確認していない。
FinOps モデルは capacity pool の読み取りを 1 回の `GetObject` につき 1 件として算入しており、
この記録の値（4 MiB で 1 個あたり 29.37〜36.73 回）はモデルの既定を変えない。モデルの 1 件に対し、観測した操作数は
4 MiB で約 36 回（Single-AZ、ALL だけ）だが、その差が請求に現れるかは未確認である。

**読みが capacity pool に届かないバッチがあった。** ALL ボリュームのデータは capacity pool にあるのに、
操作数が 0 回のバッチが、1 MiB で 13 バッチ中 7 バッチ、64 KiB で 10 バッチ中 10 バッチ、4 MiB で 12 バッチ中 1 バッチあった（下の「到達の分類」）。
原因は調べていない。

## 方法

1 バッチは新しい 30 オブジェクトの読み取りである。ボリューム別の `CapacityPoolReadOperations`（1 分値の Sum）を、
バッチを開始した分から、終了した分の次の分までの窓で足した。読み方は 2 通りある。

- ALL だけを読む（Single-AZ の M2 相当）: ALL ボリュームのオブジェクトを 30 個続けて読む
- ALL と NONE を 1 個ずつ交互に読む（Single-AZ の M3-a 相当と、Multi-AZ の全バッチ）: バッチごとに先頭を入れ替える

Single-AZ は 17 バッチ（ALL だけ 9、交互 8）、Multi-AZ は 18 バッチ（すべて交互）である。サイズは 4 MiB、1 MiB、64 KiB の 3 種類。
Single-AZ の 3 バッチ（`s1m-seq`、`s1m-int`、`s4m-int`）と Multi-AZ の 3 バッチ（`s-1m-b1`、`s-1m-b2`、`s-64k-b1`）は、
1 MiB や 4 MiB が届かなかった原因の切り分けのために、新しいオブジェクトを書き足して追加した補足である。
バッチは 4 分刻みで走らせ、バッチの間に 2 分の空白を置いた。読みの失敗は全バッチで 0 だった。

### 前提の確認: データが capacity pool にあること

ALL ボリュームの `StorageUsed`（`StorageTier=StandardCapacityPool`）の 1 分値で確認した。

- Single-AZ: 888,733,696 B に最初に達した 1 分値は 05:39Z（書き込みの終了の約 2 分後）で、書いた論理サイズ（421 個）と一致した。以降 5 点連続で同値。
  読み取りの間も変わらず、SSD への戻りは見られなかった。補足の 90 個は 1,077,477,376 B に 06:59Z に達した
- Multi-AZ: 796,327,936 B に最初に達した 1 分値は 12:28Z で、書いた論理サイズ（451 個）と一致した。以降 5 点連続で同値。
  補足の 90 個は 861,208,576 B に 13:30Z に達した
- NONE ボリュームの `StandardCapacityPool` は、どちらのファイルシステムでも 0 のまま

### 到達の分類

2 つのファイルシステムを合わせた 35 バッチ（補足 6 バッチを含む）を、サイズごとに数えた。

| サイズ | 届いた | 一部だけ・ほぼ届かず | 届かなかった | 計 |
|---|---|---|---|---|
| 4 MiB | 10 | 1（m3-4m-b2、9.00 回/個） | 1（s4m-int） | 12 |
| 1 MiB | 5 | 1（s-1m-b1、4 回） | 7 | 13 |
| 64 KiB | 0 | 0 | 10 | 10 |

「届いた」は窓の操作数が 30 個に対して十分にあるバッチ、「届かなかった」は窓の操作数が 0 のバッチである。
補足を含めない数え方にすると、各行の数は変わる。

Single-AZ の再集計では、ALL だけを読んだ 1 MiB と 4 MiB の 7 バッチはすべて届き、交互に読んだ 1 MiB と 4 MiB の 6 バッチは完全に届いたのが 2 バッチだけだった。
ただし書き込みの時期、サイズ、スロットの時刻も同時に違うので、読み方が原因だとは言えない。Multi-AZ には ALL だけを読むバッチがなく、この偏りは検証できていない。

**届かなかった理由は特定していない。** 書き込みから最初の読みまでの経過時間では説明できていない（Single-AZ は 20.8〜72.8 分後の 14 バッチと、補足の書き込みの 8.6〜16.6 分後の 3 バッチ。
4 MiB は書き込みの 16.6 分後の `s4m-int` が届かず、20.8 分後の `m2-4m-b1` が届いた。1 MiB は 68.8 分後の `m2-1m-b2` が届き、44.8 分後の `m3-1m-b1` と 60.8 分後の `m3-1m-b2` が届かなかった。
Multi-AZ の A の 1 MiB 主 4 バッチは書き込みの 14.5、26.5、38.5、50.5 分後で、いずれも届かなかった。C の 3 バッチは 81.5〜89.5 分後で、A の範囲の外にあり、経過時間が長いほど届きやすいとも読まない）。
書き込みの順序、読みの順序でも説明できていない。

### 測定窓の外の操作数

測定窓の外にも `CapacityPoolReadOperations` が立った。いずれも 1 操作あたり 4,096 B で、書き込み（PutObject）の時間帯だった。

| ファイルシステム | 窓の外の操作数 | 時間帯 |
|---|---|---|
| Single-AZ | 256 回（25、150、36 回と 18、27 回） | 05:36〜05:38Z と 06:58〜06:59Z |
| Multi-AZ | 205 回（27、101、50、11 回と 1、15 回） | 12:25〜12:28Z と 13:29〜13:30Z |

Single-AZ の ONTAP の `get` の増分も、書き込み前から最初のバッチまでで 211 回（864,256 B）あり、CloudWatch と一致した。
書き込み時に 4 KiB の GET が立つことは確認したが、原因（階層化の処理か、書き込みの検証か）は調べていない。
期間全体の合計は Single-AZ が 6,701 回（測定窓 6,445 回 + 窓の外 256 回）、Multi-AZ が 5,249 回（測定窓 5,044 回 + 窓の外 205 回）。

## 言えること

- この環境（FSx for ONTAP 第 1 世代、ONTAP 9.19.1P3、128 MBps、SSD 1024 GiB、同一 VPC の c5n.xlarge、S3 Access Points）で、ALL ボリュームだけを読んだ
  Single-AZ の 4 バッチでは、4 MiB の `GetObject` 1 回あたり CloudWatch の `CapacityPoolReadOperations` が 34.67〜36.73 回立った（各 30 個）
- 同じ条件で、1 MiB は 7.13 回と 7.63 回、64 KiB は 0 回だった（各 2 バッチ）
- 交互に読んだバッチでは、同じサイズでも 0 回になる場合があった。Single-AZ の 4 MiB は 34.20、9.00、0 回、1 MiB は 0、0、6.53 回。
  Multi-AZ の優先 AZ の 4 MiB は 29.37〜34.53 回、1 MiB は 5 バッチのうち 4 バッチが 0 回で 1 バッチが 0.13 回
- 64 KiB は、読み方、ファイルシステム、クライアントの AZ によらず、10 バッチすべてで 0 回だった。サイズ以外の理由は切り分けていない

## 言えないこと

- 請求されるリクエスト数。CloudWatch の操作数との対応は確認していない。Cost Explorer の `APN1-Requests.SAZ_2N:CPoolStdRd` は、
  Single-AZ の測定日の分を日付の終わる前に 1 回だけ引いた（日次、アカウント全体、`Estimated: true`、数量 698）。
  アカウントには測定対象とは別の FSx for ONTAP のファイルシステムが 2 つあり、集計も完了していないので、測定窓の合計（6,445 回）との比較には使えない。Multi-AZ の分は取得していない
- 操作数が、ONTAP のバージョン、スループットキャパシティ、クライアントの場所で変わらないこと
- 1 MiB と 64 KiB の capacity pool の遅延。届いた 1 MiB は Single-AZ の補足 1 バッチと Multi-AZ のスタンバイ AZ の 1 バッチ（と ALL だけの 3 バッチ）に限り、64 KiB は 0 / 10 である
- 届かない原因（キャッシュ、ONTAP の読み取り経路の別、クライアントの AZ、そのほか）
- 日をまたぐ再現、複数クライアントの並列読み、他の ONTAP バージョン、Multi-AZ 第 2 世代
- オンプレミスのクライアントからの操作数

### この repository の別の記録との関係

[S3 Files のファイルシステム性能の記録](s3files-throughput-measured.md)の S-5 は、cold の窓の読み取り 33 回で `CapacityPoolReadOperations` が 0 回で、回数が出なかった。
同じ記録は、隣接リポジトリの測定（別の日、VPC 外の Lambda からの読み取り）で、1 オブジェクトあたり 1 MiB が約 5.4〜5.6 回、5 MiB が約 29.8〜33.2 回、64 KiB が 0 回だったことも引いている。
この記録の値（1 MiB が 6.43〜7.63 回、4 MiB が 29.37〜36.73 回、64 KiB が 0 回）は近い範囲にあるが、クライアントの場所、日、サイズの構成が違うので、
再確認や反証としては読まない。操作数が立つ場合と立たない場合があった点は、隣接リポジトリの測定と同じ型の観測である。

## FinOps モデルとの関係

この記録はモデルの数値を変えない。モデルの既定は capacity pool の読み取りを 1 回の `GetObject` につき 1 件としており、
観測した 4 MiB の約 36 回（Single-AZ、ALL だけ）はそのままモデルに入れない。請求の件数との対応が決まるまで、観測値は観測値として扱う。

## 費用と撤去

主な費目は FSx for ONTAP と EC2 の稼働時間で、金額はこの記録に書かない（請求側の確定値を確認していないため）。
Single-AZ の稼働は約 2.64 時間（ファイルシステム）と約 1.97 時間（EC2）、Multi-AZ のファイルシステムは約 3.33 時間だった。
Multi-AZ の測定では、AWS 認証の失効（約 21 分。作成記録の空きからの推定）の間もファイルシステムが `AVAILABLE` のまま稼働し続けた。

撤去は、EC2 の終了、S3 Access Points の削除、ボリュームの削除（最終バックアップなし。`BypassSnaplockEnterpriseRetention` は渡していない）、SVM の削除、
ファイルシステムの削除の順に行った。強制フラグは使っておらず、WORM 系の機能も使っていない。サービスごとの describe と list を Single-AZ で 88 回、Multi-AZ で 97 回呼び、
全クラスで 0 件または `NotFound` を確認した。Multi-AZ の撤去中、アクセスポイントが 0 件になるまで待つ手順が、CLI のページ分割で数値が 2 行返ったため約 3 分終了しなかった。
アクセスポイントは削除済みで、手動で止めてボリュームの削除から再開した。

Resource Groups Tagging API は、削除済みリソースの ARN を返し続けた（Single-AZ の撤去の約 2 時間後に 3 件、約 8.8 時間後に SVM の 1 件。Multi-AZ の確認時に 9 件）。
ID を指定した確認では、いずれも `NotFound` または `terminated` だった。これは検索索引の観測であって、課金の有無についての主張ではない。
削除できない残存物として、CloudWatch `AWS/FSx` のメトリクスが保持期限まで残る。 <!-- allow:naming CloudWatch の名前空間名そのもの -->

## この記録の限界

操作数は CloudWatch の 1 分値と、ONTAP のノード別カウンタ（Multi-AZ のクライアント C の分を除く）から取った。
請求側の値、Multi-AZ の専用の長い対照窓、スタンバイ AZ の複数バッチは持っていない。
