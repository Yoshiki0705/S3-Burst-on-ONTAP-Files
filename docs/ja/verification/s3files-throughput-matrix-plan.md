# S3 Files のファイルシステム性能の測定計画

<!-- ontap-version-exempt-file: this is a measurement plan for Amazon S3 Files standalone, not a
     record of what was measured, and not about ONTAP. -->

**この文書に測定値はない。** Amazon S3 Files を**ファイルシステムとして**測るとき、何を固定して
何を動かすか、そのために何が必要か、そして既存の S3 Files 測定では答えにならない理由を書く。
実行後に結果を別の記録として追加する。

既に測った反映の速さと意味論は[実測記録](s3files-measured.md)に、この構成との比較は
[比較検証](s3files-vs-flexcache.md)にある。**この計画はその続きで、反映ではなくスループット・
IOPS・並列度・台数を測る。** 他のファイルプロトコル（NFS / SMB / EFS）側で確立した手法を
S3 Files に適用する（[プロトコル別測定の結果](perf-matrix-results.md)、
[スループット / IOPS / 並列度の実測](throughput-iops-concurrency.md)）。

パターン記号は **S** で、A / D / E / E1 / E2 / F / G と重ならない。

## この計画が答えないこと

先に範囲を切る。登壇や記事で「速い / 遅い」を言うための材料ではない。

- **どちらが速いかの判定ではない。** S3 Files とこの構成は設計点が違う。並べるのは
  [比較検証](s3files-vs-flexcache.md)の役割で、この計画は S3 Files 単体の性能を測る。
- **サイジングの式ではない。** 出すのは、ファイルシステムらしい負荷（小ファイル・大ファイル・
  並列・多数クライアント）で S3 Files がどこで頭打ちになり、何がその位置を決めるか。
- **反映の速さではない。** それは[実測記録](s3files-measured.md)で測り済み。この計画は
  再測しない。

## なぜ測るか — 既存の S3 Files 測定が持たない面

[実測記録](s3files-measured.md)の「読み取れないこと」が挙げているとおり、S3 Files は**反映の
意味論しか測っていない**。一方、ファイルプロトコル側（NFS / SMB / EFS）では
スループット曲線・IOPS 掃引・キャッシュ温度の分離・台数試験の手法が確立している。
**公式が S3 Files に与える価値（AI / ML のデータ準備、多数の小ファイル、協調ワークロード、
集約 4 TB/s+）は、いずれもこの面の裏取りを必要とする。**

| 公式が挙げる価値 | 裏取りに要る測定 | いまの状態 |
|---|---|---|
| 多数の小ファイルを扱う ML / AI のデータ準備 | 4 KiB / 64 KiB の IOPS を並列度で掃引 | **未測定**（レイテンシ 1 点のみ） |
| 集約読み取り 4 TB/s+ | 大ファイルのスループット曲線、台数で積み上げ | **未測定**（約 450 MB/s の 1 点のみ） |
| 作業セットだけ低遅延 | 高性能ストレージ上を warm / cold で分離 | **未分離**（経路差 5.1 倍は測ったが温度は振っていない） |
| 最大 25,000 の同時接続で協調 | クライアント 1 → N 台で共有 / 非共有 | **未測定** |

出どころ: [Amazon S3 Files features](https://aws.amazon.com/s3/features/files/)、
[What's New](https://aws.amazon.com/about-aws/whats-new/2026/04/amazon-s3-files/)。

## 測定パターン

| ID | 何を動かすか | 何を固定するか | 何を確かめるか | 状態 |
|---|---|---|---|---|
| **S-1** | ブロックサイズ 4 KiB / 64 KiB / 1 MiB / 4 MiB、並列度 1 / 16 / 64 / 256 | 取り込みしきい値、保持窓、ホスト、データの非圧縮性 | 小ファイルの IOPS がどこで頭打ちか。サイズと並列度のどちらが効くか | **実施済み**（2026-10-10、[結果](s3files-throughput-measured.md)。512 スレッドで実施、並列度掃引は未実施） |
| **S-2** | ブロックサイズを大きい側へ（1 MiB / 4 MiB / 16 MiB）、ストリーム 1 / 4 / 8 / 16 | 同上 | 大ファイルのスループット曲線と頭打ちの位置。1 MiB 以上がバケット直読に落ちる境界 | **実施済み**（同上。頭打ちは efs-proxy の 1 コアと確定。4 MiB / 16 MiB の曲線は未実施） |
| **S-3** | 読み取り対象の**キャッシュ温度**（warm = 載った直後 / cold = 保持窓を跨いだ or しきい値超過） | ブロックサイズ、並列度、ホスト | 「作業セットだけ低遅延」の実体。warm と cold の差 | **一部実施・clean な比較は未完了**（2026-10-10、[結果](s3files-throughput-measured.md#s-3--s3-files-のキャッシュ温度高性能ストレージ-と-バケット直読方法の限界つき)。しきい値フリップ方式が無効と判明。真の cold は初回アクセス前にしきい値を分けて作り直す必要がある） |
| **S-4** | クライアント台数 1 / 2 / 4 / 8、全台同一データ / 重ならない領域 | 1 台あたりの並列度 | 共有で N 台を満たせるか、クライアント単位で頭打ちか | **実施済み**（2026-10-10、[結果](s3files-throughput-measured.md#s-4--クライアント台数の集約1--8-台)。8 台で 8.01x の線形、1 台あたり一定。same/disjoint とも線形） |
| **S-5** | FSx for ONTAP S3 AP で読む対象の階層（SSD / キャパシティプール = Tiering All） | ファイルシステム・サイズ・ツール・並列度 | cold（キャパシティプール）読み取りの SSD に対するレイテンシ差と、1 回の `GetObject` が発生させるキャパシティプール読み取りリクエスト数 | **実施済み**（2026-10-10、[結果](s3files-throughput-measured.md#s-5--fsx-for-ontap-s3-access-point-の階層別読み取りssd-と-capacity-pool)。レイテンシ差は検証済み、リクエスト数は Cost Explorer 反映待ちで未確認） |

**S-5 は S3 Files ではなく FSx for ONTAP S3 Access Point の読み取りだが、階層とコストの話が
S3 Files のコスト並置と地続きなのでこの計画に含める。** 対照は同一ファイルシステム・同一サイズ・
同一ツールで、階層ポリシー None（または書いた直後の SSD）と ALL を並べ、**階層だけを動かす。**
Tiering All は即時に階層化される（冷却期間の 24〜48 時間は AUTO / Snapshot-only の話）ので、
移動完了を階層別の容量メトリクスか ONTAP のフットプリントで確認してから測る。発生した
キャパシティプール読み取りリクエスト数は Cost Explorer の usagetype `CPoolStdRd`（反映に数日）か
メトリクスで確認し、分からなければ「確認できなかった」と書く。

**S-1 が最優先である。** 公式が真っ先に挙げる ML / AI のデータ準備は小ファイルの集合で、
いまそこに実測が IOPS でなくレイテンシ 1 点しかない。**効いても効かなくても所見になる。**

**S-3 はこのリポジトリで最も高くついた教訓の再適用である。** ファイルプロトコル側では、同一設定で
キャッシュ温度だけが違い 45% 動いた。S3 Files の高性能ストレージも同じ性質を持つはずで、
**温度を制御しない測定は「作業セットだけ低遅延」を数値で言えない。**

## 既存の S3 Files 測定でこの比較が成立していない理由

[実測記録](s3files-measured.md)に性能に触れる数値はあるが、**ファイルシステム性能の測定として
成立していない。**

1. **並列度 1・逐次 1 件ずつ。** スループットも IOPS も、並列度を上げない構成では測れない。
2. **経路差とサイズ差が分離済みなのは読み取りレイテンシだけ。** スループット側（約 450 MB/s）は
   8 ストリームの 1 点で、曲線になっていない。頭打ちが `efs-proxy` の CPU だと分かったのは
   収穫だが、「どのブロックサイズ・どの並列度で何 MB/s」は空いたまま。
3. **キャッシュ温度を振っていない。** 経路（高性能ストレージ / バケット直読）は振ったが、
   高性能ストレージ上のデータを warm と cold で分けていない。

## 合意済みの設計判断

**測ってから決めると出た数値に都合のよい形を選べるので、先に確定させる。**

| 論点 | 確定した形 | 理由 |
|---|---|---|
| データの圧縮性 | **非圧縮に固定**（AES-CTR ブロック） | ファイルプロトコル側で、ゼロ埋めデータが上限の 4 倍を返した。S3 Files の背後も EFS なので同じ轍を踏みうる |
| 代表値 | **定常窓の中央値・窓長・10 秒区間の最小 / 最大・同一条件 2 回の幅** | 最大単独は最も再現しない統計。ファイルプロトコル側で実証済み |
| 頭打ちの帰属 | **判定できないときは「判定できない」と書く** | S3 Files は実装基盤が EFS なので、頭打ちがクライアント単位クォータ・プロキシ CPU・取り込み経路のどれかを切り分けないと「S3 Files が遅い」と誤読される |
| ホスト | **帯域が保証値のインスタンス 1 種に固定**（c5n.9xlarge 級） | 「Up to」表記では、詰まったのがストレージかクライアントか切り分けられない |

### 頭打ちの帰属に要る対照

S3 Files はファイルプロトコル側より切り分けが 1 段難しい。**背後が Amazon EFS で、EFS には
クライアント単位のスループットクォータが文書化されている**（素マウント 500 MiBps、Elastic +
`amazon-efs-utils` 2.0 以降で 1,500 MiBps。[Amazon EFS quotas](https://docs.aws.amazon.com/efs/latest/ug/limits.html)）。
S3 Files のマウントヘルパーは `efs-proxy --tls` をローカルに挟むので、頭打ちの候補が 3 つある。

| 候補 | 切り分けの手段 |
|---|---|
| ローカルの `efs-proxy` CPU | 負荷中の `efs-proxy` の CPU を記録する（既に約 450 MB/s でこれが効いていた） |
| EFS 由来のクライアント単位クォータ | 実測値を 500 / 1,500 MiBps と突き合わせる。台数（S-4）で 1 台あたりが不変かを見る |
| 取り込み経路 / しきい値 | しきい値の両側で測る。1 MiB 以上はバケット直読に落ちる |

**3 つが揃わない run は「判定できない」と書く。** 空欄にも 0 にもしない。

### キャッシュ温度をどう作るか（S-3）

S3 Files は「設定したサイズしきい値未満」かつ「保持窓（既定 30 日、1〜365 日）内にアクセスされた」
データを高性能ストレージに載せる（[features](https://aws.amazon.com/s3/features/files/)）。
温度を振る手段が 2 つある。

| 温度 | 作り方 |
|---|---|
| warm | しきい値未満のオブジェクトを読み、高性能ストレージに載せた直後に測る |
| cold（経路） | しきい値を下げ、同じサイズをバケット直読の経路に落として測る（経路差。[実測記録](s3files-measured.md)で実施済みの手法） |
| cold（保持窓） | 保持窓を最短（1 日）に設定し、窓を跨いで高性能ストレージから落ちた後に読む |

**保持窓を跨ぐ cold は時間がかかる（最短 1 日）。** 計画では経路 cold を主とし、保持窓 cold は
「できれば」とする。どちらで測ったかを必ず書く。

## 使うツール

### ファイルプロトコル側 — auto_vdbench

ファイルプロトコル側の測定と同じく VDBENCH を使う
（[測定環境](../../../environments/perf-matrix/README.md)）。マウントされたパスに対して動くので、
S3 Files のマウントポイントをそのまま測れる。**IOPS を振りながらレイテンシを追えるので、
「頭打ちがどこか」ではなく「どのレイテンシまでなら何 IOPS 出るか」が出る。**

S3 Files のマウントは `environments/s3files-compare/mount-s3files.sh` が作る。VDBENCH の
`testfile_dir` にそのマウントポイントを渡す。**S3 Files では ONTAP 側カウンタ（`storage_type`
`NetApp_ONTAP`）は使えない。** 背後は EFS なので、サービス側メトリクスは CloudWatch の
`AWS/S3/Files` と `AWS/EFS` から読む。

### 既に動く計測スクリプト

反映と意味論は測定済みだが、スループット側は VDBENCH が主になる。既存スクリプトの役割を
混同しないよう整理する。

| 測る対象 | ツール | 出る単位 | この計画での用途 |
|---|---|---|---|
| S3 Files のファイル経路のスループット / IOPS | auto_vdbench（VDBENCH） | IOPS、レイテンシ、スループット | S-1〜S-4 の本体 |
| 反映の速さ・意味論 | `scripts/measure_s3files_visibility.py` / `measure_s3files_semantics.py` | p50 / p90 / max | 測定済み。再測しない |
| S3 API 経路のスループット | `scripts/measure_s3_throughput.py` | スループット、req/s | S3 Files を経由しない経路の対照 |

## 必要な環境

**未デプロイである。** S3 Files の作成・マウント・破棄の手順は
[S3 Files 検証環境セットアップ](../deployment/aws-s3files-compare.md)にあり、以下はこの計画に
固有の要件である。いずれも課金される。

| 要素 | 条件 | 理由 |
|---|---|---|
| S3 Files ファイルシステム | 汎用バケット全体、バージョニング必須、SSE-S3 か SSE-KMS | S3 Files の前提（[セットアップ](../deployment/aws-s3files-compare.md#前提条件)） |
| アクセスポイント | POSIX uid/gid + root ディレクトリ | 非 root の `mkdir` 拒否を避ける（[セットアップ](../deployment/aws-s3files-compare.md#実機で追加が必要だったもの)） |
| ホストロールの CloudWatch 権限 | `logs:CreateLogGroup` / `CreateLogStream` / `PutLogEvents`、`cloudwatch:PutMetricData` | **無いとマウントが無言でハングする。** マウントヘルパーが NFS 接続前に `/aws/efs/utils` を作る（[マウントの落とし穴](s3files-mount-pitfalls.md)） |
| botocore | dnf で導入（`pip3` 不可） | 無いと `access denied` かメトリクス不可（同上） |
| 取り込みしきい値 | 既定 131,072 B と、S-3 用に小さい値 | 経路を振るため。測定後に API で既定へ戻し、出力でなく API で確認する |
| 保持窓 | 既定 30 日。保持窓 cold を測るなら 1 日 | S-3。短くすると cold を作れるが待ち時間が増える |
| Linux クライアント | c5n.9xlarge ×1（S-1〜S-3）、c5n.2xlarge ×8（S-4） | 帯域が保証値でないと頭打ちの原因を切り分けられない |
| 非圧縮テストデータ | AES-CTR ブロック。高性能ストレージ量を超える大きさ | ゼロ埋めだと上限超えの偽値が返る |
| VDBENCH + Java | Oracle のサイトから取得 | auto_vdbench の前提 |

**S3 Files は 1 VPC 1 ファイルシステムで、マウントターゲットは AZ ごとに 1 つ。** 台数試験
（S-4）のクライアントは全台を同じ AZ に置き、AZ を跨ぐホップを値に混ぜない。

## 測定を無効にしうる既定値（S3 Files 固有）

ファイルプロトコル側の「測定を無効にする 4 つの既定値」に加え、S3 Files 固有のものがある。

| 既定値 | 何が起きるか | 気づき方 | 対処 |
|---|---|---|---|
| 取り込みしきい値 `SizeLessThan` 131,072 B | **単位はバイト。** `128` と書くとほぼ何も載らず、全読み取りがバケット直読になる | 高性能ストレージの `StorageBytes` がほぼ 0 | バイトで指定し、API で確認 |
| `efs-proxy --tls` がローカルに挟まる | 単一ストリームが遅く、頭打ちがプロキシ CPU で決まる | マウント先が `127.0.0.1`、`efs-proxy` の CPU が高い | ホストを太くする（マウントオプションでは外せない） |
| `nconnect` 非対応 | 指定するとマウントがハング（90 秒でタイムアウト） | マウントが返らない | 指定しない。`timeout` を付けて試す |
| 1 MiB 以上の読み取りはバケット直読 | 高性能ストレージに載っていても、大きい読み取りはバケットから | 大ブロックだけレイテンシが跳ねる | 経路の違いとして記録する（S-2 の論点そのもの） |

**共通するのは「もっともらしい数値が出る」こと。** ファイルプロトコル側と同じく、実測値は
公称上限（4 TB/s+ は集約値、クライアント単位は EFS クォータ）に対する割合として書き、
100% を大きく外れたら測定を疑う。

## 不可逆操作と破棄の順序

**この計画に不可逆な機能（S3 Object Lock、保持設定、Vault Lock）は入れない。** 入れる場合は
保持値を名指しした明示の指示が要る（AGENTS.md の不可逆操作の節）。S3 Files 固有の破棄順を
守る（[実測記録](s3files-measured.md#落とし穴)で実際に詰まった）。

| 順序 | 操作 | 理由 |
|---|---|---|
| 1 | アンマウント | — |
| 2 | **エクスポート待ちが捌けるまで待つ** | 待ちがあると `delete-file-system` が `ConflictException` で拒否。`PendingExports` はゲートに使えないので `ExportAge` を見る |
| 3 | ファイルシステム / マウントターゲット / アクセスポイントの削除 | — |
| 4 | バケットのバージョンと削除マーカーを全削除 | バージョニング必須なので現行バージョン削除だけでは空にならない |
| 5 | バケットの削除 | **ファイルシステムが付いたバケットは削除できない**。FS を先に消す |

**成功レスポンスは成功の証拠ではない。** 削除は戻り値でなく一覧 API の件数で判定する
（[`teardown.sh`](../../../environments/s3files-compare/teardown.sh) がそうしている）。

## 記録する項目

**1 つ欠けると引用できない。** 一覧は[性能検証の考慮点](../reference/performance-testing-guide.md#記録に必ず添える項目)にあり、
この計画に固有のものは次のとおり。

- 測定日、リージョン、S3 Files の取り込みしきい値と保持窓、暗号化方式
- マウントの**実効オプション**（`findmnt` の出力。`actimeo` でなく `acregmin` を見る）、NFS バージョン
- ブロックサイズ、並列度 / ストリーム数、読み書き比、逐次 / ランダム
- **キャッシュ温度**（warm / 経路 cold / 保持窓 cold のどれか）と、作業セットと高性能ストレージ量の比
- クライアントのインスタンス型と、ネットワーク帯域が保証値かバーストか
- **定常窓の中央値、窓長、10 秒区間の最小 / 最大、同一条件 2 回の幅**
- **頭打ちの帰属**（`efs-proxy` CPU / EFS クォータ / 取り込み経路）、または「判定できない」
- データの非圧縮性の確認（gzip 比）
