# ブロックプロトコルのスループット測定計画

**この文書に測定値はない。** iSCSI と NVMe/TCP を何のために・どう測るか、そのために既存の測定環境へ
何を足すか、そして**既存のファイルプロトコルの表と並べたときにどこが揃わないか**を書く。実行後に
結果を[プロトコル別測定の結果](perf-matrix-results.md)へ追加する。

**この計画は単独で環境を立てるためのものではない。** 依頼元も「perf-matrix が別の理由で立つときに
一緒に測る」という前提を置いている。単独で立てた場合の額は[費用と所要時間](#費用と所要時間)に
別立てで書いた。

ファイルプロトコル側の計画は[プロトコル別スループットの測定計画](throughput-protocol-matrix-plan.md)に
あり、パターン記号（A / D / E / E1 / E2）はそちらと通し番号である。この文書は **F** を担当する。

## 測定パターン

| ID | 対象 | セッション数 | シナリオ | 何を確かめるか | 状態 |
|---|---|---|---|---|---|
| **F-1** | iSCSI（LUN、raw device） | **1 と 8** | 1 MiB 逐次読み / 書き、64 KiB 逐次読み、4 KiB ランダム読み | **「必要帯域 ÷ 625 MBps = セッション数」が成り立つか。** 1 セッションの実測が 625 MBps に一致するか、それより低いか | 未実施 |
| **F-2** | NVMe/TCP（namespace、raw device） | F-1 と同じ | F-1 と同じ | **同じセッション数で iSCSI と並ぶか。** 差があるなら、プロトコル選択を性能で語らない現状の書き方に注記が要る | 未実施 |
| **F-3** | F-1 で速かった側 | F-1 の上側 | 1 MiB 逐次読み | **キャッシュ常駐と非常駐で 2 つの上限に分かれるか。** ファイル側では 0.18 倍になった | 未実施 |

**F-1 と F-2 は同じ LUN / namespace のサイズ・同じボリューム・同じ充填データで行う。** 作り直すと、
比較しているものがデータの配置差を含む。

**F-3 は F-1 と F-2 のうち速かった側だけで行う。** 2 つの上限に分かれるかどうかは経路の性質の問いで、
プロトコルごとに 2 回測っても答えが 2 つになるだけである。

### F-1 が答える問いの現状

**依頼元は「625 MBps という除数は推論であって実測ではない」と書いている。この前提は正確ではない。**
除数そのものには出典がある。

| 主張 | 段階 | 出典 |
|---|---|---|
| EC2 の 1 クライアントあたりの上限が 5 Gbps（約 625 MBps）であること | **documented** | [Provisioning iSCSI for Linux](https://docs.aws.amazon.com/fsx/latest/ONTAPGuide/mount-iscsi-luns-linux.html) と [Provisioning NVMe/TCP for Linux](https://docs.aws.amazon.com/fsx/latest/ONTAPGuide/provision-nvme-linux.html) が、セッションを増やす手順の前置きとしてこの値を書いている |
| 単一フローが 5 Gbps で止まること（配置グループ外） | **documented** | [Amazon EC2 instance network bandwidth](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/ec2-instance-network-bandwidth.html) |
| **その上限に対する iSCSI / NVMe/TCP の実測** | **未測定** | — |
| **ファイルプロトコルでの同じ位置の実測** | **検証済み。ただし 625 MBps ではない** | NFSv4.1 単一接続 591.62 MB/s、SMB 3.1.1 単一チャネル 574.24 MB/s（[結果](perf-matrix-results.md#同一パラメータでの横並びvdbench-直接300-秒--ウォームアップ-60-秒)） |

**したがって F-1 が確かめるのは「除数の出典があるか」ではなく「除数が実測と何%ずれるか」である。**
ファイル側の実測は 625 MBps の **94.7%**（NFS）と **91.9%**（SMB）だった。同じずれがブロックにも
出るなら、必要帯域を 625 で割ったセッション数は**足りない**方向に外れる。ブロックで 625 に一致するなら、
ファイル側とブロック側で 1 フローに乗る量が違うことになり、それ自体が所見である。

### 「1 セッション」が単一フローではないこと

**F-1 を素直に実行すると、単一接続の比較にならない。** ファイル側の 1 接続の行は
**1 ノードへの TCP 1 本**だが、iSCSI の既定のログインは**両ノードへ 1 本ずつ、計 2 本**を張る。

| 手順 | 何が起きるか | 出典 |
|---|---|---|
| `iscsiadm --mode discovery` | **`iscsi_1` と `iscsi_2` の 2 ポータルが返る**（別ノード） | [Provisioning iSCSI for Linux](https://docs.aws.amazon.com/fsx/latest/ONTAPGuide/mount-iscsi-luns-linux.html) |
| `nr_sessions` の意味 | **イニシエーターあたり ONTAP ノードあたり**のセッション数 | 同上 |
| `--login`（ポータル指定なし） | 発見した全ポータルへログインする。AWS 自身が「各ファイルサーバの各セッションについて 1 つずつ応答が出る」と書いている | 同上 |

**つまり `nr_sessions=1` でも TCP は 2 本になる。** この値をファイル側の 1 接続の行に並べると、
**iSCSI が約 2 倍に見え、その差はプロトコルではなく経路の本数である。**

**したがって F-1 は 1 セッションの点を 2 通り測る。**

| 点 | 手順 | 何と比べられるか |
|---|---|---|
| **単一フロー** | `--login` に**ポータルを 1 つだけ指定**する（`-p <iscsi_1 の IP>:3260`） | **ファイル側の 1 接続の行と並べられる。** これが 4 行目の候補 |
| 既定（両ポータル） | ポータルを指定せずログインする | **並べられない。** ブロック側の表に別行として置く |

**どちらか片方だけでは足りない。** 単一フローだけでは既定構成の値が無く、既定だけでは
ファイル側と比較できない。**そして単一ポータルでのログインが実際に TCP 1 本になったかは、
`ss` で数えて確認する**（`nconnect` と SMB Multichannel の両方で、指定しただけでは
本数が期待どおりにならなかった）。

### セッション数の意味の曖昧さ

**先に決めておく必要がある。** AWS の手順は次のコマンドを示し、これを「アベイラビリティーゾーンごとに
イニシエーターあたり ONTAP ノードあたり 8 セッション」と説明したうえで、**合計 40 Gbps（5,000 MBps）**
に達すると書いている。

```bash
iscsiadm --mode node -T <target_iqn> --op update -n node.session.nr_sessions -v 8
```

**`nr_sessions=8` は 1 ノードあたり 8 である。** この SVM は両ノードに iSCSI LIF を持つので、
**張られる TCP は 16 本になる。** 一方で AWS が併記する 40 Gbps は 8 × 5 Gbps であって 16 × 5 Gbps では
ない。**「8 セッション」がどちらを指すかは、この記述からは決まらない。**

**測定側の対処は、指定値ではなく実際に張られた TCP を数えることである。** ファイル側で
`nconnect` の実効値だけを読んで足りなかったのと同じ問題で、この環境では
[EFS の `nconnect` が実効値には現れるのに I/O が停滞した](perf-matrix-results.md#amazon-efs-と-nconnect)。
記録には `nr_sessions` の指定値と、**両 LIF アドレスへの確立済み TCP の実数**を並べて書く。

### NVMe/TCP 側で「1 セッション」と呼ぶもの

**iSCSI の `nr_sessions` に対応するものが NVMe/TCP に無い。** NVMe/TCP は 1 コントローラあたり
複数の I/O キューを持ち、**キューごとに TCP 接続を張る。** 既定のキュー数はホストの CPU 数に
追随するので、`nvme connect` を 1 回実行しただけで **1 接続にはならない。**

**したがって単一フローの点は、キュー数を明示的に 1 に絞って取る。**

| この計画での呼び方 | 手順 | 期待する TCP 本数 | 何と比べられるか |
|---|---|---|---|
| **single** | 片方の LIF に `nvme connect --nr-io-queues=1` | **1 + admin queue** | **iSCSI の single、およびファイル側の 1 接続の行** |
| default | 片方の LIF に `nvme connect`（キュー数を指定しない） | 未知。**数える** | iSCSI の default とは比べられない（下） |
| multi | 両方の LIF に `nvme connect`（キュー数を指定しない） | 未知。**数える** | iSCSI の multi とも比べられない（下） |

**default と multi を iSCSI の同名と並べてはいけない。** iSCSI の default は「両ポータルに
1 セッションずつ」で本数が構成から決まるが、NVMe/TCP の default は**ホストの CPU 数で決まる。**
同じ語を使っているだけで、変えている量が違う。

> **admin queue の分を数に入れるかは、実測して決めない。** `--nr-io-queues=1` で確立済み TCP が
> 1 本か 2 本かは環境で違いうるので、**両方の数を記録し、比較には I/O を運ぶキューの数を使う。**
> 「1 セッション」と書くときは、その隣に数えた本数を必ず置く。

**この定義は測定前に決めた。** 出た数値を見てから「1 セッション」の意味を選べる状態にしておくと、
どの定義でも都合のよい行が作れてしまう。

## 既存の測定との比較可能性

**揃うものと揃わないものを先に分ける。** 揃わない項目を書かずに同じ表へ入れると、そこが
プロトコル差として読まれる。

| 条件 | ファイル側（実施済み） | ブロック側（この計画） | 揃うか |
|---|---|---|---|
| ファイルシステム | 第二世代 SINGLE_AZ_2、6,144 MBps ×1 HA ペア、SSD 4,096 GiB、プロビジョンド 200,000 IOPS | 同一 | 揃う |
| NVMe リードキャッシュ | 無効（両ノードで読み直して確認） | 同一手順で無効 | 揃う |
| クライアント | c5n.9xlarge、ネットワーク 50 Gbps は保証値、配置グループなし | 同一 | 揃う |
| 測定器 | VDBENCH 5.04.07 直接、`iorate=max`、ウォームアップ 60 秒 + 300 秒 | 同一 | 揃う |
| 並列度 | 512 スレッド | 同一 | 揃う |
| ワークロード定義 | `vdbench/workloads-common.txt` | **同じファイルを include する** | 揃う |
| テストデータ | 非圧縮、効率化なし | 同一 | 揃う |
| **データ LIF の本数と載っているノード** | **1 本、`-01` の `e0e` だけ**（`-02` は 0 バイト） | **2 本、`-01` と `-02` の `e0e`** | **揃わない** |
| **クライアント側の I/O 経路** | カーネルの NFS / SMB クライアント | **dm-multipath（iSCSI）または ANA（NVMe/TCP）** | **揃わない** |
| **キャッシュ回避のフラグ** | `o_direct`（Linux）/ `directio`（Windows） | `o_direct`。**ただしファイルシステム層が無い** | **揃わない** |
| **アクセス先の形** | ボリューム上のファイル 1 つ | **LUN / namespace（raw device）** | **揃わない** |

### 揃わない 4 つが結果に効く形

**LIF の本数がいちばん大きい。** ファイル側の測定は、単一クライアントの 3,551 MB/s も台数試験の
12,173 MiB/s も、**すべて `-01` の 1 ポートを通っていた**（`-02:e0e` は 0 だった）。iSCSI と NVMe/TCP は
`iscsi_1` / `iscsi_2` を使い、**この 2 本は別ノードの別ポートに載っている**。この環境で実測した
LIF の配置がそれである（[指定値との差](perf-matrix-results.md#指定値との差)）。

つまり**ブロック側は既定で 2 ノードへ分散し、ファイル側は 1 ノードに集まっていた。**
ブロックの数値がファイルより高く出たとき、それはプロトコルの差ではなく**経路の本数の差**でありうる。
**ポートの累積カウンタを両ノードで差分し、どちらに何バイト流れたかを結果に併記する。**
`ladder.sh` が既に `nic_common` の `transmit_bytes` を差分しているので、読む対象を 2 ノードに広げる。

**ファイルシステム層の不在は、有利にも不利にも働く。** raw device への `o_direct` はページキャッシュも
ファイルシステムのメタデータ更新も通らない。ファイル側の数値にはそれが含まれている。
**「ブロックの方が速い」を書くときは、この層の差を条件として添える。**

**そして raw device は VDBENCH の書き込みで壊れる。** ファイル側は 1 つのファイルを上書きしていたが、
ブロック側は**デバイス全体が書き込み対象になる**。これは測定の性質ではなく事故の性質なので、
[環境テンプレートに対する差分](#環境テンプレートに対する差分)に検査として書いた。

## 使うツール

### ブロック側は VDBENCH 直接のみ

**auto_vdbench は raw device を駆動できない。** 設定ファイルの項目を確認した結果ではなく、
生成されるパラメータファイルとヘルパースクリプトの実装がそうなっている。

| 確認した箇所 | 内容 |
|---|---|
| `auto_vdbench.py` の SD 生成 | `sd=sd{i}-1,host=hd{i},lun={testfile_dir}/file1` を書き出す。**`/file1` は固定で、設定から外せない**。`testfile_dir` に `/dev` を入れても `/dev/file1` になる |
| `conf/storages.template` | `sd=default,openflag=o_direct,size=${size}g`。**`size=` が必ず入る。** raw device に対してデバイス長と違う `size=` を与えると測定の意味が変わる |
| `shell/make_testfile.sh` | `rm -f $TESTFILE_PATH` を実行し、その後 `stat -c %s` が `testfile_size` に達するまで待つ。**デバイスノードに対して `stat -c %s` は 0 を返すのでこのループは終わらない。** そして先行する `rm -f` は root で走るので、**デバイスノードそのものを消す** |

**したがってブロックは VDBENCH を直接実行する。** これは SMB で既に採った形と同じで、理由も同じ系統
（auto_vdbench が駆動できない対象がある）である。

**auto_vdbench の設定ファイルで渡せるもの / 渡せないもの**（ブロック測定に関係する範囲）。

| 設定 | ブロック測定で使えるか |
|---|---|
| `server_list` / `server_threads` | 使える。ただし SD の宛先が固定なので台数試験には別の形が要る |
| `testfile_dir` | **使えない。** 末尾に `/file1` が付く |
| `testfile_size` | **使えない。** raw device では長さはデバイスが持つ |
| `storage_type` / `ontap_*` | 使える。ONTAP 側のカウンタ取得はブロックでも成立する |
| `random_blocksize_list` / `sequential_blocksize_list` / `read_ratio_list` | 使える（`wd=` の生成に使われる） |
| `inc_iops_start` / `inc_iops_step` / `cutoff_latency` | 使える。**レイテンシ曲線が要るならここだが、SD の宛先を変えられないので raw では届かない** |
| `openflag` | **渡せない。** テンプレートで `o_direct` に固定されている（raw では望ましい値なので支障はない） |

**レイテンシ曲線をブロックで採る手はある。** LUN の上に xfs を作れば auto_vdbench の `testfile_dir` が
使える。**ただしそれは別の測定である** — ファイルシステム層が経路に入るので、F-1 の raw device の
値とは並べられない。今回の計画には入れない。

### パラメータファイルの構成

`vdbench/` に 2 つ足す。**ワークロード定義は既存の `workloads-common.txt` をそのまま include する。**

| ファイル | 中身 |
|---|---|
| `vdbench/vdbench-linux-iscsi.txt` | `hd=` と `sd=`（`lun=/dev/mapper/<friendly-name>`）のみ |
| `vdbench/vdbench-linux-nvmetcp.txt` | `hd=` と `sd=`（`lun=/dev/<namespace-device>`）のみ |

**2 つの diff が 2 つの実行の差の全部になる。** 差は `lun=` の 1 行だけである。ファイル側の
NFS / SMB の対で差が 3 つあったのに対し、ここは 1 つで済む。**同じホスト・同じ OS・
同じ `openflag` で 2 つのプロトコルを比べられるのは、ファイル側では得られなかった条件である。**

**`size=` は書かない。** raw device の長さは LUN / namespace が決める。**`size=` を書いてデバイスより
大きければ範囲外を読み、小さければ作業セットを取り違える。** VDBENCH がデバイス長を自力で読むかは
**未確認**なので、[検査フェーズ](#環境テンプレートに対する差分)で 1 回空回しして確認する。

## 必要な環境

**未デプロイである。** ファイル側の測定環境をそのまま使い、**足りないのは下の 5 つだけである。**

| 要素 | 条件 | 理由 |
|---|---|---|
| FSx for ONTAP 第二世代 | **既存の E パターンと同一構成**（SINGLE_AZ_2、6,144 MBps ×1 HA ペア、SSD 4,096 GiB、200,000 IOPS） | 構成を変えると既存の表と並べられない |
| ブロック用ボリューム | 900 GiB / UNIX、階層化なし・インライン効率化なし、**NFS 用とは別のボリューム** | LUN を NFS のテストファイルと同居させると、片方の測定が他方の配置を動かす |
| LUN と igroup（iSCSI） | LUN 600 GiB、igroup にクライアントの IQN | 600 GiB はインメモリキャッシュ 256 GB の 2 倍超。ファイル側と同じ理由・同じ大きさ |
| namespace と subsystem（NVMe/TCP） | namespace 600 GiB、subsystem にクライアントの NQN | 同上 |
| クライアント側のパッケージ | `iscsi-initiator-utils`、`device-mapper-multipath`、`nvme-cli` | AL2023 のリポジトリは S3 経由で到達する（実測済み）。**インターネット経由の取得は要らない** |

**AD・Windows クライアント・EFS はいずれも要らない。** ブロックは SMB を含まず、EFS にブロック
プロトコルが無い。**E パターンより構成が小さく、費用も安い。**

**SVM は NFS 用のものを使う。** この環境の NFS 用 SVM には `iscsi_1` / `iscsi_2` が
サービスポリシー `default-data-iscsi` で既に存在した（実測。[指定値との差](perf-matrix-results.md#指定値との差)）。
**LUN を置いても CIFS は有効にならないので、SMB のときのようにドメインコントローラが
経路に入る問題は起きない。** SVM を増やす理由がない。

### 対応状況の確認（測る前に落ちる条件）

| 項目 | 状態 | 出典 |
|---|---|---|
| iSCSI は HA ペア 6 以下のファイルシステムで使える | documented | [Creating an iSCSI LUN](https://docs.aws.amazon.com/fsx/latest/ONTAPGuide/create-iscsi-lun.html) |
| **NVMe/TCP は第二世代かつ HA ペア 6 以下** | documented | [Provisioning NVMe/TCP for Linux](https://docs.aws.amazon.com/fsx/latest/ONTAPGuide/provision-nvme-linux.html) |
| 両プロトコルが SVM の iSCSI LIF を共用すること | documented | 同上（`iscsi_1` は iSCSI と NVMe/TCP の両方に使われる、と明記） |
| **第一世代で NVMe/TCP が使えないこと** | documented（上の裏返し） | 同上。**E1 の世代差にブロックを足せないのはこのため** |
| AL2023 で `nvme-tcp` モジュールと `nvme-cli` が揃うこと | **未確認** | AWS の手順は RHEL 9.3 を前提に書かれている。**この環境のクライアントは AL2023 である** |

**最後の 1 行は着手前に潰す。** モジュールが無ければ F-2 は測れず、その事実は
クライアントを起動してから分かる。**`dnf install` と `modprobe` が通るかだけの確認なので、
ファイルシステムを立てる前にできる。**

## 環境テンプレートに対する差分

**以下は提案であって、適用済みではない。** 実装するときは、この節をそのまま作業単位として使える。

### template-fsxn-gen2.yaml

**足すのは 3 つの ingress 規則だけである。** クライアント側のセキュリティグループは
egress を `0.0.0.0/0` で持っているので、**クライアント側の変更は要らない。**

| プロトコル | ポート | 用途 |
|---|---|---|
| tcp | **3260** | iSCSI |
| tcp | **4420** | NVMe/TCP のデータ |
| tcp | **8009** | NVMe/TCP の discovery |

**SMB を足したときと同じ形にする。** つまり `SecurityGroupIngress` のリストへ追記するのではなく、
条件付きの `AWS::EC2::SecurityGroupIngress` を 3 つ足し、`EnableBlockProtocols` パラメータで切る。
**そうすればブロックを使わないデプロイが、以前と正確に同じ規則を作る。** この方針はこの
テンプレートが SMB のときに既に採ったもので、理由もそこに書いてある。

**ファイルシステム側の egress は増やさない。** ブロックは外向きの通信を必要としない。
既存の `127.0.0.1/32` プレースホルダをそのまま残す。

### 新しいボリューム

`AWS::FSx::Volume` を 1 つ足す。**NFS 用ボリュームの設定をそのまま複製する**
（`SecurityStyle: UNIX`、`TieringPolicy: NONE`、`StorageEfficiencyEnabled: false`、
`SnapshotPolicy: none`）。`JunctionPath` は要らない — LUN はジャンクション経由で読まれない。

**LUN はここには書けない。** 次の節がその理由である。

### LUN・igroup・namespace・subsystem は CloudFormation で作れない

**`AWS::FSx::Volume` に LUN のプロパティは無く、FSx の API にも無い。** AWS の手順はすべて
ONTAP CLI（`lun create` / `lun igroup create` / `lun mapping create` /
`vserver nvme namespace create` / `vserver nvme subsystem create`）で書かれている。

**したがって runbook のフェーズになる。** この環境には既に ONTAP の REST を叩く仕組みがあり
（`runbook.sh nvme-cache` と `nfs-xfer-size` が使っている `ontap_rest_on_client`）、
**パスワードはクライアント上で Secrets Manager から読むのでコマンド履歴に残らない。** 同じ経路を使う。

| 新しいフェーズ | やること |
|---|---|
| `block-provision iscsi` | ボリューム上に LUN を作り、クライアントの IQN で igroup を作り、マッピングする。**`serial-hex` を読んで返す**（下） |
| `block-provision nvme` | namespace と subsystem を作り、マッピングし、クライアントの NQN を追加する |
| `block-sessions <n>` | `nr_sessions` を設定して再ログインし、**両 LIF への確立済み TCP を数えて表示する** |
| `block-preflight` | 下の検査を全部走らせる |
| `block-fill` | デバイス全体に非圧縮データを 1 回書く（下） |

### デバイスの取り違えによるクライアントのルートボリュームの破壊

**これが最も危険な差分である。** VDBENCH は `lun=` に与えられたデバイスへ**書く**。
そしてこのクライアントの**ルート EBS ボリュームは `/dev/nvme0n1` として見える。**
AWS の手順の出力例そのものが、`nvme0n1` に `Amazon Elastic Block Store`、
`nvme2n1` に `NetApp ONTAP Controller` を並べている。

**デバイス番号でパラメータファイルを書いてはいけない。** 番号は起動順とアタッチ順で動く。

| プロトコル | 何で解決するか |
|---|---|
| iSCSI | `lun show -fields serial-hex` で読んだシリアルから `/dev/mapper/<friendly-name>` を作り、**その名前で指定する** |
| NVMe/TCP | `nvme netapp ontapdevices` が返す namespace パスとデバイスの対応で解決する。**`nvme list` の並び順に依存しない** |

**`block-preflight` は、パラメータファイルの `lun=` が指すデバイスが ONTAP のものであることを
確認してから通す。** ここを人の目視に任せると、失敗の代償が測定のやり直しではなく
クライアントの再作成になる。

### 検査フェーズで確認すること

**どれも「設定した」ではなく「効いている」を見る。** ファイル側で `nconnect` と
SMB Multichannel の両方が、指定しただけでは増えなかった。

| 確認 | 通っている状態 |
|---|---|
| `lun=` が指すデバイスの正体 | ONTAP の LUN / namespace であること（上） |
| iSCSI の multipath | `multipath -ll` が 1 つの LUN を複数パスで示し、**`active` と `enabled` の数が等しい** |
| NVMe の multipath | `/sys/module/nvme_core/parameters/multipath` が `Y` |
| NVMe の負荷分散 | 該当 subsystem の `iopolicy` が `round-robin` |
| NVMe のパス状態 | 2 パスが `live` で、片方が `optimized`、もう片方が `non-optimized` |
| **実際に張られたセッション数** | 両 LIF アドレス宛ての確立済み TCP を数えた値。**指定値ではない** |
| NVMe リードキャッシュ | 両ノードで `is_enabled: false`（既存の `nvme-cache off` を流用） |
| VDBENCH が読んだデバイス長 | 1 回空回しして、LUN / namespace のサイズと一致すること |

**`optimized` と `non-optimized` が出ることは、それ自体が測定条件である。** ANA は namespace を
持つノードを優先するので、**2 パスが対称ではない。** iSCSI の dm-multipath とは分散の形が違い、
**これが F-2 の差の候補になる。** 結果には両方の分散設定を書く。

### 充填を先に行う理由

**書いていないブロックの読み取りは、ディスクに到達しない。** シンプロビジョニングされた LUN の
未書き込み領域はゼロを返すので、**読み取りの測定にならない。**

**したがって測定の前にデバイス全体を 1 回書く。** ファイル側では `format=yes` の充填が
キュー深度 2 に固定されて 165 MB/s しか出なかったが、**raw device なら通常の
`rd=`（`rdpct=0`、512 スレッド）で書けるので、その制約は入らない。** 見込みは
ファイル側の書き込み実測（900 秒定常で 2,063.00 MB/s）と同じ範囲だが、**これは予測である。**
実際の充填速度は測ってから書く。

### teardown.sh の追加分

**順序がある。** 使用中の LUN は削除できない。

1. クライアント側で `iscsiadm --logout` と `nvme disconnect-all`
2. LUN のマッピング解除 → LUN 削除 → igroup 削除
3. subsystem のマッピング解除 → subsystem 削除 → namespace 削除
4. ブロック用ボリューム削除
5. 以降は既存の順序どおり

**そして既存の検証行はこの追加分を見ない。** 「nothing tagged for deletion remains」は
タグの範囲でしか成立せず、**LUN も igroup も namespace も subsystem も AWS のリソースではないので
タグを持たない。** ファイルシステムを消せば道連れになるが、**ファイルシステムを残して
ブロックだけ畳む場合は、ONTAP 側を列挙して読む行が要る。**

## 測定条件

**既存の測定と揃えるものは[比較可能性](#既存の測定との比較可能性)の表にある。** ここはブロック固有の
項目である。

| 項目 | 値 |
|---|---|
| ブロックサイズ | 4 KiB / 64 KiB / 1 MiB（`workloads-common.txt` の定義をそのまま） |
| 読み書き比 | 100% read、100% write |
| アクセスパターン | 逐次、ランダム |
| `openflag` | `o_direct` |
| 並列度 | 512 スレッド |
| 窓 | ウォームアップ 60 秒 + 300 秒、`interval=1` |
| **繰り返し** | **同一条件を 2 回。1 点で報告しない**（下） |
| セッション数 | `nr_sessions` の指定値と、確立済み TCP の実数の両方 |
| multipath | iSCSI は `path_grouping_policy` と `path_selector`、NVMe は `iopolicy` と各パスの ANA 状態 |
| LUN / namespace の長さ | 600 GiB。**ボリュームは 900 GiB**（AWS は LUN より 5% 以上大きいボリュームを推奨） |
| 充填 | デバイス全体を 1 回書いた後。充填の実測速度も記録する |

### 1 点で報告しない理由

**同一構成・同一パラメータファイル・同一測定器で 2 回測って 45% 違った記録がある**
（3,551.18 と 5,148.56 MB/s。[キャッシュの温まり方だけで 45% 違った件](perf-matrix-results.md#キャッシュの温まり方だけで-45-違った件)）。
違いは直前に何を読んだかだけだった。

**したがってブロックでも同一条件を 2 回回し、幅で報告する。** そして**2 回の間でキャッシュの状態を
どう扱ったかを書く** — 毎回冷やすのか、毎回同じ手順で温めるのか。ファイル側はそこを揃えて
いなかったので、複数接続の行に 45% の幅が付いている。

**冷やす手段は F-3 の作業セットで作れる。** 600 GiB はインメモリキャッシュ 256 GB の 2.3 倍なので、
デバイス全体を通読すればキャッシュの中身は入れ替わる。**その通読を各測定の前に入れれば、
「毎回同じ手順で温める」側に揃う。**

## 結果の書き方

- **ブロックの行をファイルの横並び表に足さない。** 別の表にし、[並べてよい表](#並べてよい表と並べてはいけない表)の
  判定を守る。
- **数値には条件を全項目併記する。** 測定日、リージョン、ONTAP バージョン、世代、
  スループットキャパシティ、SSD 容量、プロビジョンド IOPS、NVMe リードキャッシュの状態、
  クライアントの型と**帯域が保証値かバーストか**、並列度、ブロックサイズ、セッション数（指定値と実数）、
  multipath の設定、LUN / namespace の長さ、充填済みかどうか、繰り返し回数。
  **1 つでも欠けた数値は引用できない。**
- **2 ノードのポート実測を併記する。** クライアント側の合計は証拠にならない。
- **セッション数を「8」と書かない。** `nr_sessions=8` と、そのとき数えた TCP の本数を書く。
- **未測定は「できない」と書かない。**

### 単一接続の文の書き換え方の事前決定

**[プロトコル別測定の結果](perf-matrix-results.md)の 24 行目は外部から引用されている。**

> 単一接続の 3 行は 500〜592 MB/s に収まる。しかし当たっている上限は 2 製品で別物である。

Adoption Playbook がこの文の `500〜592 MB/s に収まる` を `reread` として登録している。**発火は
「該当節を読み直せ」の合図で、撤回の検出には使われていない。** つまり**実測に合わせて書き換えてよく、
文言を維持する義務はない。** そのうえで、書き換えの形を測る前に決めておく。**測ってから決めると、
出た数値に都合のよい書き方を選べてしまう。**

| F-1（単一フロー）の着地点 | 24 行目の書き換え | probe |
|---|---|---|
| 500〜592 の内側 | **「3 行」→「4 行」。範囲は変えない** | **発火しない** |
| 592 超 | 「4 行」にし、**範囲の上端を実測値へ**（`500〜<n> MB/s`） | 発火する |
| 500 未満 | 「4 行」にし、**範囲の下端を実測値へ**（`<n>〜592 MB/s`） | 発火する |
| **単一フローに張り付かない**（多重度が 1 にならない、または大きく外れる） | **行を足さない。** 「3 行」のまま残し、ブロックの表への参照を添える | **発火しない** |

**4 行目が足されない場合がある**ことを先に決めておく。単一ポータルでも TCP が 2 本になる、
あるいは値が 1 フローの上限とは無関係な位置に出るなら、**その行はこの表に属さない。**
無理に足せば、範囲は広がるが「似た値・別の上限」という文の主旨が崩れる。

**そして 4 通りのうち 2 通りで probe は沈黙する。** 上の 1 行目と 4 行目である。
**probe の沈黙は「F-1 が終わっていない」ことを意味しない。** 引用している側が完了を知る手段は
probe ではなく Issue で、これは測る前に伝える。

**この文の主旨は範囲ではなく「似た値が別の原因で出ている」ことである。** iSCSI が同じ範囲に入ったなら
原因が同じ（EC2 の 1 フロー上限）かどうかを確かめて書く。**範囲に入ったことを原因が同じ証拠にしない** —
それが[EFS で 1 度誤った形](perf-matrix-results.md#この測定でいちばん効いた要因)である。

### 625 MBps の除数への報告

**F-1 が済んだら、結果がどちらに出ても依頼元へ通知する。** 破れた場合だけ知らせるのでは、
「まだ測っていない」と「測って一致した」が区別できない。

| F-1 の結果 | 報告する内容 |
|---|---|
| 1 セッションが 625 MBps に一致 | 除数は妥当。**ただしファイル側の 591.62 / 574.24 とは一致しないので、ファイルとブロックで 1 フローに乗る量が違うという所見になる** |
| 1 セッションが 591 MB/s 前後 | **除数を実測より高く見積もっている。** 必要帯域 ÷ 625 は必要セッション数を 5% 少なく出す |
| 8 セッションが 8 倍に届かない | **線形の前提が破れる。** 除算でセッション数を出す形そのものに上限の注記が要る |

## 費用と所要時間

**単価は[検証パターンごとの費用構造](../reference/comparison/finops-performance-test-patterns.md)から
取った ap-northeast-1 の On-Demand 値で、実際の請求ではない。** 所要時間は VDBENCH の窓長
（60 + 300 秒）と既存の測定で実測した構築時間から積んだ**見積りであって、実測ではない。**

### 時間あたりの課金

| リソース | 時間あたり | 停止で止まるか |
|---|---|---|
| FSx for ONTAP 第二世代 6,144 MBps + 200,000 IOPS + SSD 4,096 GiB | **$23.03** | 止まらない |
| c5n.9xlarge ×1（Linux） | $2.45 | 止まる |
| **合計** | **約 $25.48** | — |

**E パターンとの差は、要らないものの分だけ安い。** Managed AD（$0.146/時）、Windows クライアント
（$2.45/時）、EFS（Elastic は従量、Provisioned は $9/時）がいずれも不要である。

### 所要時間の内訳

| 段階 | 見積り | 根拠 |
|---|---|---|
| ブロックの provisioning（LUN / igroup / namespace / subsystem） | 0.75 h | REST 呼び出しは速い。**時間を食うのは検査**（multipath とセッション数の確認） |
| 充填（600 GiB を 1 回書く） | 0.5 h | 書き込み 2,000 MB/s 級なら 5 分。**残りは段取りの余白** |
| F-1（4 シナリオ × 2 セッション数 × 2 回 = 16 run） | 1.9 h | 1 run は 60 + 300 秒 + 間隔で約 7 分 |
| NVMe/TCP への切り替え | 0.3 h | namespace / subsystem の作成と検査 |
| F-2（同じく 16 run） | 1.9 h | 同上 |
| F-3（2 作業セット × 2 回 = 4 run） | 0.5 h | 同上 |
| **既存の測定に足す場合の追加時間** | **約 5.9 h** | — |

### 既存の測定に足す場合

**perf-matrix が別の理由で立っているなら、追加されるのは上の 5.9 h 分の窓の延長である。**

```text
5.9 h × $25.48/h ≒ $150
```

**ここに EFS や Windows クライアントの分は入らない。** それらを止めた状態で測れる。
**逆に、止めずに並走させると同じ 5.9 h に対してそれらの額が乗る** — そして
**2 つの SVM がスループットキャパシティを共有するので、並走は測定そのものも壊す。**
ブロックを測る間、ファイル側は idle にする。

**優先順 1 だけなら短い。** F-1 と、その前提の provisioning・充填・検査だけで
**約 3.2 h、$82** である。依頼元が最初に欲しいのはこの 1 点なので、時間が取れないなら
ここで切れる。

### 指定値のクールダウンがこの計画には効かない理由

**F は構成を作ったあと指定値を一切変えない。** スループットキャパシティ・SSD 容量・
プロビジョンド IOPS はすべて作成時の値で固定で、既存のファイル側の表と揃えるためにそうしている。

**したがって[変更のクールダウン 6 時間](../reference/comparison/finops-performance-test-patterns.md#変更のクールダウン-6-時間)は
この計画の所要時間に入らない。** 指定値を振る測定と同じ環境を共有する場合は入るので、
**順序で決まる。** 同じファイルシステムを使うなら、**指定値を振る側を先に、F を後にする。**
理由は 2 つある。

1. **F は 200,000 IOPS のために SSD 4,096 GiB を要求する。** 第一世代では SSD 容量を減らせないと
   明記されており、第二世代については記載が無い（未確認）。**先に大きく作ると、段ごとの既定 SSD へ
   戻す前提の測定ができなくなりうる。**
2. **F の構成は指定値を振る測定の最上段と同じ 6,144 MBps である。** 下から上げてくるなら、
   最後の段がそのまま F の構成になり、**変更が 1 回減る。**

**逆順にすると 6 時間の待ちが 1 回増え、その間も時間課金が続く。**

**依頼元は単独で立てることを求めていないが、額を先に出しておく。**

| 段階 | 時間 | 備考 |
|---|---|---|
| 第二世代ファイルシステムの作成 | 0.5 h | **待っている間も課金される** |
| クライアントと測定ツールの持ち込み | 0.75 h | S3 経由。VDBENCH は手元から置く |
| 事前確認（NVMe キャッシュ無効化、AL2023 のモジュール確認） | 0.25 h | |
| 測定（上の内訳） | 5.9 h | |
| 撤去と検証（バックアップの残骸確認まで） | 0.5 h | |
| **合計** | **約 7.9 h** | |

```text
7.9 h × $25.48/h ≒ $201
```

**約 $200 で、8 時間の窓である。** AD も EFS も Windows も要らないので、
[8 時間の測定 1 回の総額](../reference/comparison/finops-performance-test-patterns.md#8-時間の測定-1-回の総額)の
約 $729 より小さい。

**構成を安くすると比較が壊れる。** スループットキャパシティを 3,072 MBps へ落とせば
$11.51/時 になり総額はほぼ半分だが、**既存のファイル側の表と並べられなくなる。**
ブロックとファイルを比べることが目的なので、**この下げ方は選べない。**

### 消し忘れたときの額

**第二世代を消し忘れると月 $16,812 である。** ブロック固有の注意は、
[teardown の追加分](#teardownsh-の追加分)にある **LUN と namespace がタグを持たない**ことである。
ファイルシステムを消せば一緒に消えるが、**ファイルシステムを残す判断をしたときは
削除確認の網に入らない。**

## この計画が答えないこと

- **世代差は測れない。** NVMe/TCP は第二世代限定なので、E1 に相当するブロックの行は作れない。
  iSCSI だけなら第一世代でも測れるが、**第一世代のファイルシステムはこの環境が作ったものではない。**
- **台数を増やす試験は入っていない。** 1 つの LUN を複数ホストが同時に書くには、
  書き込みを調停する層が要る。**読み取り専用なら成立しうるが、それは別の設計である。**
- **HA ペアを増やしたときの分散は測らない。** 1 ペアで固定する。
- **ファイルシステム層を載せた場合の値は測らない。** raw device の値だけを出す。
  xfs を挟むと auto_vdbench の曲線が使えるようになるが、**F-1 の値とは並べられない。**
- **バーストとベースラインを分離しない。** 窓は 300 秒である。
  **上の数値をベースラインとして引用しない**という注記が、結果にも必要になる。
