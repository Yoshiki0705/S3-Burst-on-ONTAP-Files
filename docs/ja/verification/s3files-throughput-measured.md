# 検証記録 — Amazon S3 Files のファイルシステム性能（スループット / IOPS）

<!-- ontap-version-exempt-file: this record measures Amazon S3 Files standalone (built on Amazon
     EFS); ONTAP is not involved. -->

**この記録は Amazon S3 Files 単体のスループットと IOPS の実測である。** [測定計画](s3files-throughput-matrix-plan.md)
の S-1（小ファイル IOPS）と S-2（大ファイルスループット）を 1 台から、S-4（クライアント台数）を 1〜8 台から実行した結果と、S-3（キャッシュ温度、clean な比較は未完了）・S-5（FSx for ONTAP の階層別読み取り）の記録で、反映の速さと
意味論は別記録（[実測記録](s3files-measured.md)）にある。**マウントが通らず止まった切り分けは
[マウントの落とし穴](s3files-mount-pitfalls.md)にある。先にそちらを読むと、この環境を再現できる。**

S-1・S-2 の値は 1 台・単一マウントである。S-4 は 1〜8 台まで実施済み（S-4 の節）。S-3 は一部実施で、clean な warm / cold の比較は未完了（S-3 の節）。

## TL;DR

**S3 Files の単一マウントのスループットは `efs-proxy` の 1 コアで頭打ちになる。** c5n.9xlarge
（36 vCPU、50 Gbps 保証値）で 1 MiB 逐次読みが **1,104.9 MB/s**、そのとき `efs-proxy` プロセスの
CPU は **97〜98%**（1 コア飽和）で、vdbench と NFS クライアントはアイドルだった。**ホストを
太くすると上限は上がる**（c5n.2xlarge の約 450 MB/s → c5n.9xlarge の約 1,110 MB/s、別記録
[nconnect 非対応が持つ意味](s3files-vs-flexcache.md#nconnect-非対応が持つ意味)）**が、単一の
proxy プロセスが律速する構造は変わらない。** `nconnect` 非対応なのでマウント側で並列化できない。

**一方、クライアント台数を増やすと合計はほぼ線形に伸びる（S-4）。** c5n.2xlarge 8 台で
**8.01 倍**、1 台あたりは一定だった。単一マウントは proxy の 1 コアで頭打ちだが、**台数で
横に伸ばせる**。FSx for ONTAP の [S3 Access Points 経由（S3 API）の台数試験](throughput-iops-concurrency.md#クライアント台数を-1-から-4-まで上げたとき)
（書き込みは 4 台まで 1.01 倍、読み取りは 2 台以降 約 600 MB/s で平ら。128 MBps 構成）は逆の振る舞いで、
構成と経路が違うため同条件の比較ではない。

この記録の構成（1 台 1 回のサンプル。S-1/S-2 は単一ホスト、S-4 は 8 台、S-5 は FSx for ONTAP の
階層、S-3 は方法の限界つき）は各節の冒頭に書く。

## 頭打ちは efs-proxy の 1 コア（確定）

**1 MiB 逐次読みを 60 秒だけ再測しながら CPU を採った。** 定常状態の 3 サンプルで:

| サンプル | 再測スループット | `efs-proxy` プロセス CPU | vdbench / java |
|---|---|---|---|
| 1 | — | **96.8%** | ほぼ 0 |
| 2 | — | **97.4%** | ほぼ 0 |
| 3 | **1,109.4 MB/s** | **97.9%** | ほぼ 0 |

**36 vCPU のうち、単一の `efs-proxy` プロセスが 1 コアを使い切っている。** 再測値 1,109.4 は本測定の
1,104.9 と一致し、律速が CPU 側であることと整合する。

**これは S3 Files 固有の構造である。** マウントの相手は `127.0.0.1`（ローカルの efs-proxy）で、
proxy が TLS 終端と NFS 変換を 1 プロセスで行う。`nconnect` は非対応（指定するとマウントが
ハング、[全方向比較側の記録](s3files-vs-flexcache.md#nconnect-非対応が持つ意味)）なので、
マウントオプションで proxy への接続を増やせない。**単一マウントの上限を上げる手段はホストを
太くすること**で、c5n.2xlarge の約 450 MB/s から c5n.9xlarge の約 1,110 MB/s へ上がったのが
その実測である。ただし 36 vCPU でも 1 コアで止まるので、**ホストの総コア数ではなく単一コアの
速さが効く。**

## 読み取れること

**大きい逐次読みが最も速く、小さいランダム書きが最も遅い。** 1 MiB 逐次読み 1,104.9 MB/s に対し
4 KiB ランダム書き 14.4 MB/s で、約 77 倍の開きがある。ファイルシステムとしての素直な傾向だが、
**どのワークロードも単一マウントでは proxy CPU の下にある。**

**小ファイルのランダム読みは約 15,800 IOPS で頭打ち。** S3 Files の公式が挙げる「多数の小ファイルを
扱う ML / AI のデータ準備」に対する 1 マウント 1 ホストの実測の目安になる。公称の
「ファイルシステムごと 10M+ IOPS」は集約値で、**1 マウントの値ではない。**

**書き込みは読み取りより一貫して遅い。** 1 MiB で読み 1,105 対 書き 852（0.77 倍）、
64 KiB で読み 356 対 書き 110（0.31 倍）、4 KiB ランダムで読み 15,839 対 書き 3,688 IOPS（0.23 倍）。
S3 Files はファイル側の書き込みを約 60 秒まとめてから S3 へ出す設計なので、書き込み経路に
高性能ストレージへの同期が入る。

## 読み取れないこと

| 問い | この測定で答えられない理由 |
|---|---|
| warm と cold の差 | S-1・S-2 の測定では温度を振っていない。読みが高性能ストレージ由来かバケット直読かを分離していない（S-3 は一部実施で、clean な比較は未完了。S-3 の節） |
| 複数マウント・複数ホストの集約 | この表の S-1・S-2 は 1 台 1 マウントのみ。複数ホストの集約は S-4 の節（1〜8 台）にある。公式の表現（Performance specifications）の “up to terabytes per second” は集約値で、1 マウントの値ではない |
| 同一条件の再現性 | 各ワークロード 1 回。1 MiB 逐次読みだけ再測して 1,104.9 対 1,109.4（0.4% 差）を確認したが、他は 1 回 |
| 別インスタンス型での頭打ち | c5n.9xlarge のみ。c5n.2xlarge の約 450 MB/s は別記録の値 |
| `nodirects3read` を付けた場合 | 付けていない（ゲートウェイエンドポイントがあるため）。付けると大ファイル直読を失う |

## S-4 — クライアント台数の集約（1 → 8 台）

**S3 Files の集約スループットは台数にほぼ線形に伸び、1 台あたりは一定だった。** FSx for ONTAP の
[S3 Access Points 経由（S3 API）の台数試験](throughput-iops-concurrency.md#クライアント台数を-1-から-4-まで上げたとき)は
逆で、購入したスループットキャパシティを分け合うため、書き込みは 4 台まで 1.01 倍、読み取りは 2 台以降
約 600 MB/s で合計が増えなかった（128 MBps 構成）。FSx for ONTAP の NFS 経路の
[台数試験](perf-matrix-results.md#台数試験と2-つの上限)（第二世代 6,144 MBps、`nconnect=16`）では、
同じファイルを全台が読むと 1 → 8 台で 4.47 倍に伸び、1 ポートの上限で止まった。経路と構成が違うので
同条件の比較ではない。S3 Files は各ホストが独自の efs-proxy を持つ。公式が挙げる上限は、ファイルシステム
あたり 25,000 接続（Quotas）と、集約読み取りの “up to terabytes per second”（Performance specifications）で、
8 台はそのどちらにも届いていない。

### 検証環境

| 項目 | 値 |
|---|---|
| 計測日 | 2026-10-10（UTC） |
| S3 Files | 専用 VPC の 1 ファイルシステム、Internet 不要（VPC 内）、取り込みしきい値は既定 |
| クライアント | **c5n.2xlarge ×8**、Amazon Linux 2023、各ホストが S3 Files を個別にマウント（efs-proxy はホストごと） |
| ツール | VDBENCH、1 MiB 逐次読み、`o_direct`、1 台あたり 64 スレッド固定（台数だけを振る）、共有エポックで同時起動、warmup 60 s + elapsed 180 s |
| 共有の形 | same（全台が同じ 600 GiB ファイル）と disjoint（各台が重ならない範囲）の 2 通り |
| 検算 | クライアント合計を CloudWatch `AWS/S3/Files DataReadBytes` と突き合わせる設計（当日はメトリクス反映が疎で窓に乗らず） |

### 結果 — same（全台が同じファイル）

| 台数 | 合計スループット | 1 台あたり | 1 台比 |
|---|---|---|---|
| 1 | 784.4 MB/s | 784.4 | — |
| 2 | 1,604.5 MB/s | 802.2 | 2.05x |
| 4 | 3,148.4 MB/s | 787.1 | 4.01x |
| 8 | **6,282.6 MB/s** | 785.3 | **8.01x** |

**8 台で 8.01 倍、1 台あたりは 785〜802 MB/s でほぼ一定。** 台数に対して合計が線形に伸びる。

### 結果 — disjoint（各台が重ならない範囲、8 台）

| 台数 | 合計スループット | 1 台あたり |
|---|---|---|
| 8（重ならない範囲） | **7,210.0 MB/s** | 901.3（770〜1,332 のばらつき） |

**データを共有しなくても線形は崩れない。** むしろ合計は same（6,283）より高い（7,210）。
これで「same の線形はサービス側のキャッシュから配っていただけ」ではないと言える。
disjoint は各台が別のデータを読むので、サービス側の共有キャッシュでは説明できない。

### 読み取れること

**S3 Files は読み手を増やすと合計が増える。** 容量計画はクライアント側の帯域で行う形で、
[FSx for ONTAP の S3 Access Points 経由（S3 API）](s3files-vs-flexcache.md#上限の種別が違うことが動作として出る箇所)が
ファイルシステム単位で容量を買う形とは逆である。**同じ「読み手が増える」という変化が、
S3 Files では合計の増加、FSx for ONTAP 側では 1 台あたりの減少になる。**

### 読み取れないこと

| 問い | 理由 |
|---|---|
| CloudWatch との突き合わせ | 当日はメトリクス反映が疎で測定窓に `DataReadBytes` が乗らなかった。クライアント合計のみ |
| 8 台を超えたときの頭打ち | 8 台まで線形。頭打ちの位置は測っていない。公式が挙げる上限は、ファイルシステムあたり 25,000 接続（Quotas）と、集約読み取りの “up to terabytes per second”（Performance specifications）で、8 台（合計 6,282.6 MB/s）はどちらにも届いていない |
| 1 台あたり 785 MB/s の頭打ちの帰属 | c5n.2xlarge の efs-proxy CPU とホスト帯域のどちらが先かは S-4 では切り分けていない（S-1/S-2 の proxy CPU 飽和と整合する） |

## S-3 — S3 Files のキャッシュ温度（高性能ストレージ と バケット直読）、方法の限界つき

**S-3 は「clean な warm / cold 比較」を取れなかった。** 取れなかったこと自体が、同じ測定をする人が
踏む落とし穴なので記録する。測ったのは 64 KiB、O_DIRECT、n=30、c5n.9xlarge、2026-10-10。

### 3 つの読み取りと、その意味

| 読み方 | p50 | 有効な測定か |
|---|---|---|
| 高性能ストレージ（しきい値 131072、64 KiB 取り込み済み、O_DIRECT） | 5.33 ms | 有効 |
| しきい値を 1024 に下げた後に**同じ**ファイルを読む | 2.94 ms | **無効**（下記） |
| しきい値 1024 のまま**新規**に作った 64 KiB を読む（真のバケット直読） | 4.05 ms | 有効 |

### しきい値を下げても、既に載ったデータは追い出されない（方法の落とし穴）

**最初、しきい値を下げてから同じファイルを読めば cold になると考えたが、ならなかった。**
`sizeLessThan` は**次にディレクトリへ初回アクセスしたときに何を取り込むか**を決める設定で、
**既に高性能ストレージに載っているデータを追い出さない。** CloudWatch の `DataReadBytes`
（高性能ストレージの読み取り）が「cold」のつもりの窓でも立っており、実際には両方とも
高性能ストレージから読んでいた。2.94 ms が 5.33 ms より速かったのは、cold だったからではなく、
**両方 warm で、実行ごとのばらつき + 再マウントの差**だった。

**真の cold を測るには、しきい値を下げた後に取り込まれていない新規ファイルを読む。** それが
3 行目で、4.05 ms だった。[実測記録 s3files-measured.md](s3files-measured.md) が
サイズ固定で経路を振ったときは、**しきい値を初回アクセスの前に設定していた**ので有効だった。

### 読み取れること

**c5n.9xlarge では、高性能ストレージ（5.33 ms）とバケット直読（4.05 ms）の差は小さく、
実行ごとのばらつきの範囲に収まる。** [s3files-measured.md](s3files-measured.md) の
t3.small での 5.1 倍差（高性能ストレージ 10.8 ms 対 バケット直読 55.0 ms）は再現しなかった。
**ホストが太いと 1 リクエストあたりの固定費が相対的に小さくなり、経路差が埋もれる**と読めるが、
これは 2 つの別環境・別方法の突き合わせであり、同一環境で経路だけを振った clean な比較ではない。
**S-3 の clean な warm/cold 比較は未完了とする。**

### 読み取れないこと

| 問い | 理由 |
|---|---|
| 同一環境・同一方法での warm/cold の clean な差 | しきい値フリップ方式が無効だったため未取得。初回アクセス前にしきい値を分けて作り直す必要がある。別設計の測定は[測定記録](s3files-warm-cold-latency-measured.md)にあるが、`DataReadBytes` が初回と再読みを区別せず、経路は区別できていない |
| 保持窓（30 日）を跨いだ失効後の cold | 時間がかかるため未実施 |
| 並列度を上げたときの経路差 | 並列度 1（逐次 pread）のみ |

## S-5 — FSx for ONTAP S3 Access Point の階層別読み取り（SSD と capacity pool）

**これは S3 Files ではなく FSx for ONTAP S3 Access Point の読み取りだが、階層とコストの話が
S3 Files のコスト並置と地続きなので同じ記録に置く。** Observability 側の依頼
（[コスト並置](../reference/comparison/finops-s3-vs-s3ap.md#階層化を踏まえた-s3-access-point-読み取りのコスト並置)の
空欄を埋める）。「SSD 上のデータの方が capacity pool より速いのではないか」という予想を測った。
結果は、方向は予想と一致したが、capacity pool から読んだ遅れとしては読めない。理由は、cold の窓の読み取りが
capacity pool に届いていなかったことと、測定の設計が対称でなかったことにある（下の「結果」「リクエスト数」）。
1 回の測定である。

### 検証環境

| 項目 | 値 |
|---|---|
| 計測日 | 2026-10-10（UTC） |
| ファイルシステム | 既存の検証用 FSx for ONTAP（SINGLE_AZ_1、128 MBps、SSD 1024 GiB）に測定用ボリューム 1 つを間借り |
| ONTAP バージョン | 測定時の版は特定できず（版を記録できていない）。この記録の初版は 9.18.1P6 と書いたが、その値を 2026-10-10 に読んだ記録は、手元の測定データに残っていない。隣接リポジトリの記録には、同型のファイルシステム（SINGLE_AZ_1、128 MBps、SSD 1024 GiB）について、2026-10-06 に REST で読んだ 9.18.1P6 と、2026-10-11 に読んだ 9.19.1P2 があり、変更の日付は不明で、測定日の版は分からないと書かれている（[環境の表](https://github.com/Yoshiki0705/FSx-for-ONTAP-Observability-integrations/blob/main/docs/ja/s3ap-throughput-benchmark.md#テスト環境)）。この記録の版も、どちらとも断定しない |
| ボリューム | 1 GiB、UNIX、ストレージ効率オフ、SnapLock なし。tiering NONE で作成し、SSD 側の測定の後に ALL へ変更した（CloudTrail: 作成 09:11:18Z、ALL への変更 09:17:39Z）。測定後に削除（残存 0 件を確認） |
| S3 Access Point | **Internet origin**（`-ext-s3alias`）、UNIX root 識別情報 |
| クライアント | **AWS 外のローカル端末からインターネット経由**。並列度 1、逐次 |
| ツール | SSD 側は `scripts/measure_s3_throughput.py`。cold 側は別の読み取りループで、スクリプトを保存していない。パーセンタイルの定義も SSD 側と違う（n=10 で p90 が最大値より小さい）ので、同手法ではない |
| オブジェクト | 64 KiB / 1 MiB / 5 MiB、各 10 本。読み取り用の中身は同一バイトの繰り返し（`b"r" * size`）。ツールの `--body random` が効くのは書き込み相だけで、読んだオブジェクトには効いていない。ストレージ効率はオフなので、中身の違いは結果に影響しないと見ているが、測っていない |
| 測定の順序 | SSD 側を一括で測り（09:14:48Z〜09:17:24Z）、ALL への変更の後、8 分 22 秒空けて cold 側を一括で測った（09:26:01Z〜09:26:06Z）。交互ではない。各条件 1 回 |
| サンプル数 | SSD 側: 10 本を順番に繰り返し読み、計測窓の 20 秒で 64 KiB が 407 回、1 MiB が 318 回、5 MiB が 166 回（1 本あたり約 17〜41 回。ウォームアップ 5 秒を含めると、1 本あたり約 21〜51 回で、`DataReadOperations` からの導出値）。p50 は計測窓の全リクエストから出している。cold 側: サイズごとに n=10（内訳は記録なし）。リクエストごとの生のサンプルは両方とも保存していない（保存したのは集計値だけ） |
| 階層の確認 | CloudWatch `StorageUsed` の `StorageTier` ディメンション（ボリューム別）で、ALL 適用後に capacity pool が 0 → 63.65 MB、SSD が 85.54 → 21.32 MB（18:19 JST の 1 分）になった。シード 30 本の合計 63.57 MB と一致する。cold の測定は 18:26 JST で、その間 capacity pool の値は変化していない |

> **測定位置の注記**: クライアントが AWS 外なので、**全数値にインターネット往復が含まれる**。
> 同一条件で測った SSD と cold の比較には使えるが、ストレージ側の応答時間としては読めない。
> VPC 内から測った値ではない。

### 結果（GET の p50、ミリ秒、並列度 1。SSD は 166〜407 リクエスト、cold は n=10）

| オブジェクトサイズ | SSD 側（tiering NONE） | ALL への変更後（capacity pool に配置） | p50 の差 |
|---|---|---|---|
| 64 KiB | 46.5 ms（p90 52.3、n=407） | 56.4 ms（p90 62.1、最大 65.9、n=10） | +9.9 ms |
| 1 MiB | 58.6 ms（p90 71.7、n=318） | 74.0 ms（p90 84.9、最大 91.7、n=10） | +15.4 ms |
| 5 MiB | 116.0 ms（p90 125.0、n=166） | 121.3 ms（p90 125.6、最大 126.1、n=10） | +5.3 ms |

1 回の測定で、方向は予想（SSD の方が速い）と一致した。ただし、この差を「capacity pool から
読んだ遅れ」とは読めない。次の理由による。

- cold の読み取りは capacity pool に届いていない。ボリューム別の CloudWatch で、cold の窓
  （18:26 JST）の `DataReadOperations` は 33 回（11 回 × 3 サイズ。バイト数からこの分割に一意に
  決まる）で、同じ窓の `CapacityPoolReadOperations` は 0 回だった（下の小節）。
- 5 MiB の差（+5.3 ms）は、1 回の中でも区別できない。SSD 側の p50 から p90 までの幅（9.0 ms）
  より小さい。64 KiB と 1 MiB は、SSD の p90（52.3、71.7）が ALL 変更後の p50（56.4、74.0）より
  小さく、この 1 回の中では分かれている。
- 測定の設計が対称でない。SSD 側を一括で測り、8 分 22 秒空けて cold 側を一括で測った（交互でない）。
  サンプル数が違い（407 / 318 / 166 対 10）、cold 側のスクリプトとパーセンタイルの定義が違う。
  SSD 側は同じ 10 本を階層化の前に約 21〜51 回（ウォームアップ込み、導出）読んでいる。
- ウォームアップ込みでは 1 本の接続で、SSD 側が 64 KiB で約 507 回、1 MiB で約 401 回、5 MiB で
  約 208 回のリクエストを発行している（`DataReadOperations` から導出）。接続あたり 100 回で
  切り替わる事象が、SSD 側にだけ含まれうる。p50 への影響は小さいと見るが、p99 と mean には効く。
  これらは公開していない。

SSD 側の値を、別のクライアントの値で裏づけたとは言えない。Observability 側の SSD の値
（1 MB で p50 48.5〜60.4 ms、5 MB で 106.9〜119.8 ms）は、こちらの SSD（1 MiB 58.6、5 MiB 116.0）と
近い範囲に収まった。ただし、クライアントがこちらはローカル端末、あちらは同一リージョンの Lambda で、
条件が違う。独立な検証ではなく、「近い範囲に収まった」までしか言えない。

### capacity pool 読み取りリクエスト数（確認できなかった）

**1 回の `GetObject` が capacity pool に何回の読み取りリクエストを発生させるかは、この測定では
確認できなかった。** cold の窓の読み取りが capacity pool に届いていなかったためである。

当初は Cost Explorer の usagetype `APN1-Requests.SAZ_2N:CPoolStdRd` を測定当日に引き、0 だった。
その後、ボリューム別の CloudWatch 指標（`CapacityPoolReadOperations` / `CapacityPoolReadBytes`、
[ボリュームの指標](https://docs.aws.amazon.com/fsx/latest/ONTAPGuide/volume-metrics.html)）が
あることを確認し、削除済みのボリュームの系列を 1 分粒度で読み直した。**初版の「メトリクス側でも
内訳は取れていない」は、この一覧を確認せずに書いた誤りだった。**

測定用ボリュームの 1 分ごとの値（JST のラベル。AWS CLI v2 は時刻を JST で返す）:

| 時刻（JST） | `DataReadOperations` | `CapacityPoolReadOperations` | `CapacityPoolReadBytes` | `CapacityPoolWriteOperations` | `CapacityPoolWriteBytes` |
|---|---|---|---|---|---|
| 18:16〜18:18（SSD 側の読み取り） | 589 / 437 / 90 | 0 | 0 | 0 | 0 |
| 18:19（ALL への変更の後の階層化） | 0 | 15 | 61,440 | 15 | 938,816 |
| 18:26（cold の読み取り） | 33 | 0 | 0 | 0 | 0 |
| 18:20〜19:11（削除まで、18:26 以外） | 0 | 0 | 0 | 0 | 0 |

- 系列は 18:13 から 19:11 まで欠測がなく（59 点）、18:26 の 0 は報告された値。
- 18:19 の 15 回の読み取り（1 回 4,096 B）は、階層化の直後に ONTAP が書き込んだオブジェクトを
  読み戻したもの（AWS の指標の定義: 書き込み直後に capacity pool を読む）。cold の読み取りではない。
- CloudWatch のラベルは、クライアントの実時刻より約 47 秒遅いと導出できる（2 つの事象から、仮説）。
  18:19 のラベルは、実時刻では 18:18 台。
- 階層化の書き込みは、論理サイズ 63,569,920 B に対して 938,816 B だった（約 1/67.7）。内容が
  同一バイトの繰り返しだったことと整合する可能性があるが、機構は未特定（`hypothesis`）。

**S-5 の cold は、「capacity pool に載っている」状態を指し、「capacity pool から読んだ」状態を指さない。**
このボリュームは tiering NONE で作り、SSD 側の測定の後に ALL へ変更した（上の表）。この経路と、
cold の窓の 0 との関係は、この測定からは特定できない。

[コスト並置](../reference/comparison/finops-s3-vs-s3ap.md#階層化を踏まえた-s3-access-point-読み取りのコスト並置)の
該当行は、回数を入れず、この測定では出なかったと書く。

### 隣接リポジトリの測定との関係

S-5 の 0 の原因を、別の測定で調べた記録が、隣接リポジトリ（FSx for ONTAP のモニタリング連携）にある。
同型のファイルシステム（SINGLE_AZ_1、128 MBps、SSD 1024 GiB）で、2026-10-11 の 1 日に、ボリューム 13 本を
VPC 外の Lambda から読んだ。**S-5 のデータは、その記録に載っていない。条件（クライアント、読み方、サイズの構成、ONTAP の版）
も違うので、S-5 の結果とは直接比べない。** ここでは、その記録が裏づけている範囲だけを引く
（[階層化の経路](https://github.com/Yoshiki0705/FSx-for-ONTAP-Observability-integrations/blob/main/docs/ja/s3ap-throughput-benchmark.md#階層化の経路-直接-all-と-none-から-all-への切り替え2026-10-11)、[裏づけられる範囲と裏づけられない範囲](https://github.com/Yoshiki0705/FSx-for-ONTAP-Observability-integrations/blob/main/docs/ja/s3ap-throughput-benchmark.md#経路の比較で裏付けられる範囲と裏付けられない範囲)、[根拠区分](https://github.com/Yoshiki0705/FSx-for-ONTAP-Observability-integrations/blob/main/docs/ja/s3ap-throughput-benchmark.md#階層化の経路に関する主張の根拠区分)）。

- ALL で作成して直接書いた 8 本のうち、6 本は最初の読み取りで capacity pool の読み取りが立ち、2 本（別々の実験の DIR）は立たなかった。
  立たなかった DIR は、2 本とも、capacity pool に入ってから 5〜16 分後の読み取り（各 2 回）のどちらでも 0 だった。NONE で作って ALL に変えた 5 本
  （最長 60 分後まで）は、すべて立たなかった。**書き方は、立つための十分条件ではない。必要条件かは示されていない。**
- 最初の読み取りまでの経過時間は、片側だけの閾値では説明できない。経過時間が関与するか、他の要因と合わせて関与するかは未検討（`open`）。
- 切り替え前の読み取りは、その記録の範囲（32 回の読み取りと 0 回の 1 組。S2 と S4）では、結果を分けなかった。
  読み取りの回数は振っておらず、S-5 の約 21〜51 回についてまでは言えない。
- 直接 ALL で立った場合の `CapacityPoolReadOperations` は、1 オブジェクトあたり 1 MiB で約 5.4〜5.6、5 MiB で約 29.8〜33.2、
  64 KiB では 0 だった（B の 3 回、[呼び出しごとの読み取り](https://github.com/Yoshiki0705/FSx-for-ONTAP-Observability-integrations/blob/main/docs/ja/s3ap-throughput-benchmark.md#呼び出しごとのキャパシティプール読み取り導出値)）。この操作数と、請求される読み取りの件数の関係は、その記録でも未確認（`open`）。
- 同一バイトの内容は、階層化時の書き込みバイトを論理サイズの約 1/74 にした（ランダムは約 1）。S-5 の約 1/67.7 と近い桁だが、
  条件が違うので、同じ現象だとは書かない。

その記録が裏づけないこととして、引用しないものがある。「ALL に変えたボリュームは capacity pool から読まない」という一般化（5 本、1 ファイルシステム、1 日）、
書き方・経過時間・他のボリュームの読み取りのいずれかが原因であること、機構（ONTAP のキャッシュなど）、
2026-10-10 の表（S-5 を含む）との比較である。したがって、**S-5 の 0 は、「切り替え経路で起きる現象の一例」とは書かない。**

### 読み取れないこと

| 問い | この測定で答えられない理由 |
|---|---|
| 1 回の `GetObject` が発生させる capacity pool 読み取りリクエスト数 | cold の窓の読み取り 33 回で、`CapacityPoolReadOperations` が 0 回だった。分子が 0 なので回数が出ない。後の測定で CloudWatch の操作数は測れた（[測定記録](fsx-ontap-cpool-read-operations-measured.md)）が、請求される件数との対応は未確認 |
| cold の 0 の原因 | この測定では切り分けていない。同型のファイルシステムでの隣接リポジトリの測定（別の日、別のボリューム）では、ALL で作成して直接書いたボリュームに、最初の読み取りで capacity pool の読み取りが立つ例と立たない例があり、NONE から ALL に変えたボリュームには立たなかった例だけがあった（下の「隣接リポジトリの測定との関係」）。S-5 自身の 0 の原因は、そこからも特定できない |
| capacity pool から実際に読んだ読み取りの遅れ | cold の窓の読み取りが capacity pool に届いていないため、この測定では測れていない |
| 差の再現 | 1 回の測定。交互でなく、n が非対称で、cold 側のスクリプトと生のサンプルが残っていない |
| VPC 内（往復遅延なし）での階層差 | AWS 外のローカルから測った。往復が全数値に乗る。VPC 内の EC2 からの測定は[測定記録](fsx-ontap-tier-latency-in-vpc-measured.md)にある |
| 並列度を上げたときの階層差 | 並列度 1 のみ |
| 繰り返し読んだときの昇格の有無 | 測っていない。cold の窓の後に SSD の使用量を再確認していない |
| 往復遅延の大きさ | 測っていない。64 KiB の SSD 読み取りの p50（46.5 ms）が往復遅延の上限になる（半数の読み取りが 46.5 ms 以内に終わっており、どの読み取りも往復遅延以上の時間がかかるので、往復遅延は 46.5 ms 以下） |
