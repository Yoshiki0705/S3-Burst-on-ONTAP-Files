# 検証記録 — Amazon S3 Files のファイルシステム性能（スループット / IOPS）

<!-- ontap-version-exempt-file: this record measures Amazon S3 Files standalone (built on Amazon
     EFS); ONTAP is not involved. -->

**この記録は Amazon S3 Files 単体のスループットと IOPS の実測である。** [測定計画](s3files-throughput-matrix-plan.md)
の S-1（小ファイル IOPS）と S-2（大ファイルスループット）を 1 台から実行した結果で、反映の速さと
意味論は別記録（[実測記録](s3files-measured.md)）にある。**マウントが通らず止まった切り分けは
[マウントの落とし穴](s3files-mount-pitfalls.md)にある。先にそちらを読むと、この環境を再現できる。**

S-3（キャッシュ温度）と S-4（台数）は未実施。この記録は 1 台・単一マウントの値である。

## TL;DR

**S3 Files の単一マウントのスループットは `efs-proxy` の 1 コアで頭打ちになる。** c5n.9xlarge
（36 vCPU、50 Gbps 保証値）で 1 MiB 逐次読みが **1,104.9 MB/s**、そのとき `efs-proxy` プロセスの
CPU は **97〜98%**（1 コア飽和）で、vdbench と NFS クライアントはアイドルだった。**ホストを
太くすると上限は上がる**（c5n.2xlarge の約 450 MB/s → c5n.9xlarge の約 1,110 MB/s、別記録
[nconnect 非対応が持つ意味](s3files-vs-flexcache.md#nconnect-非対応が持つ意味)）**が、単一の
proxy プロセスが律速する構造は変わらない。** `nconnect` 非対応なのでマウント側で並列化できない。

**一方、クライアント台数を増やすと合計はほぼ線形に伸びる（S-4）。** c5n.2xlarge 8 台で
**8.01 倍**、1 台あたりは一定だった。単一マウントは proxy の 1 コアで頭打ちだが、**台数で
横に伸ばせる**。これは [S3 AP + FlexCache 側の台数試験](perf-matrix-results.md#台数試験と2-つの上限)
（購入容量を分け合うため台数で合計が増えない）とは逆の振る舞いである。

この記録の構成（1 台 1 回のサンプル。S-1/S-2 は単一ホスト、S-4 は 8 台、S-5 は FSx for ONTAP の
階層、S-3 は方法の限界つき）は各節の冒頭に書く。

## 測定環境

| 項目 | 値 |
|---|---|
| 計測日 | 2026-10-10（UTC） |
| リージョン | ap-northeast-1、単一 AZ（ap-northeast-1a） |
| ネットワーク | 測定専用に新規作成した VPC（IGW + パブリックサブネット + S3 ゲートウェイエンドポイント） |
| S3 Files | 汎用バケット全体、バージョニング有効、SSE-S3、取り込みしきい値は既定（`sizeLessThan 131072`） |
| マウント | `mount -t s3files -o accesspoint=...`。実効 `nfs4 vers=4.2 rsize=wsize=1048576 hard timeo=600 retrans=2 noresvport`、相手は `127.0.0.1`（efs-proxy 経由、tls + iam 常時） |
| クライアント | **c5n.9xlarge**（36 vCPU、ネットワーク 50 Gbps は保証値）、Amazon Linux 2023 |
| クライアント側の版 | `amazon-efs-utils` 3.3.2、java-17、python3-botocore 1.40.31 |
| テストデータ | **非圧縮**（AES-CTR ブロック、600 GiB 単一ファイル）。gzip 比を確認（128 MiB の gzip が 134,238,853 B ≈ 原寸） |
| 測定器 | VDBENCH 5.04.07、`openflag=o_direct`、512 スレッド、各ワークロード warmup 60 s + elapsed 300 s、`iorate=max` |
| ワークロード定義 | 他プロトコルと共有の [`workloads-common.txt`](../../../environments/perf-matrix/vdbench/workloads-common.txt) |

**ホストは専用 VPC に 1 台。** 測定後、ファイルシステム・マウントターゲット・アクセスポイント・
バケット・ホスト・VPC 一式を破棄し、残存 0 件を一覧 API の件数で確認済み。

## 測定結果（S-1 + S-2、1 台、n=512 スレッド）

VDBENCH の `avg_61-360`（warmup 後の定常窓）。スループットは 1 行あたり単一値（1 回の実行）で、
同一条件 2 回の幅は取っていない（1 台 1 回のサンプル実行）。

| # | ワークロード | スループット | IOPS | 平均応答 ms | ブロック | 読み書き |
|---|---|---|---|---|---|---|
| 1 | **1 MiB 逐次読み** | **1,104.9 MB/s** | 1,105 | 463.4 | 1 MiB | read |
| 2 | 64 KiB 逐次読み | 355.6 MB/s | 5,690 | 90.0 | 64 KiB | read |
| 3 | 1 MiB 逐次書き | 852.0 MB/s | 852 | 600.9 | 1 MiB | write |
| 4 | 64 KiB 逐次書き | 110.2 MB/s | 1,763 | 290.5 | 64 KiB | write |
| 5 | 4 KiB ランダム読み | 61.9 MB/s | **15,839** | 32.3 | 4 KiB | read |
| 6 | 4 KiB ランダム書き | 14.4 MB/s | 3,688 | 138.8 | 4 KiB | write |
| 7 | 64 KiB ランダム読み | 522.1 MB/s | 8,354 | 61.3 | 64 KiB | read |

**サービス側の対照（CloudWatch `AWS/S3/Files`、測定窓）**: `DataReadBytes` 約 135 GB、
`DataWriteBytes` 約 22 GB、`StorageBytes` peak 644 GB（= 書いた 600 GiB ファイル）。
**データ経路が実際に動いた裏付け**であり、読みがバケット直読と高性能ストレージのどちらから
来たかの内訳は、この記録では分離していない（S-3 の論点）。

## 頭打ちは efs-proxy の 1 コア（確定）

**1 MiB 逐次読みを 60 秒だけ再測しながら CPU を採った。** 定常状態の 3 サンプルで:

| サンプル | 再測スループット | `efs-proxy` プロセス CPU | vdbench / java |
|---|---|---|---|
| 1 | — | **96.8%** | ほぼ 0 |
| 2 | — | **97.4%** | ほぼ 0 |
| 3 | **1,109.4 MB/s** | **97.9%** | ほぼ 0 |

**36 vCPU のうち、単一の `efs-proxy` プロセスが 1 コアを使い切っている。** 再測値 1,109.4 は本測定の
1,104.9 と一致し、律速が CPU 側であることと整合する。

**これは S3 Files 固有の構造である。** マウントの相手は `127.0.0.1`（ローカルの efs-proxy）で、
proxy が TLS 終端と NFS 変換を 1 プロセスで行う。`nconnect` は非対応（指定するとマウントが
ハング、[全方向比較側の記録](s3files-vs-flexcache.md#nconnect-非対応が持つ意味)）なので、
マウントオプションで proxy への接続を増やせない。**単一マウントの上限を上げる手段はホストを
太くすること**で、c5n.2xlarge の約 450 MB/s から c5n.9xlarge の約 1,110 MB/s へ上がったのが
その実測である。ただし 36 vCPU でも 1 コアで止まるので、**ホストの総コア数ではなく単一コアの
速さが効く。**

## 読み取れること

**大きい逐次読みが最も速く、小さいランダム書きが最も遅い。** 1 MiB 逐次読み 1,104.9 MB/s に対し
4 KiB ランダム書き 14.4 MB/s で、約 77 倍の開きがある。ファイルシステムとしての素直な傾向だが、
**どのワークロードも単一マウントでは proxy CPU の下にある。**

**小ファイルのランダム読みは約 15,800 IOPS で頭打ち。** S3 Files の公式が挙げる「多数の小ファイルを
扱う ML / AI のデータ準備」に対する 1 マウント 1 ホストの実測の目安になる。公称の
「ファイルシステムごと 10M+ IOPS」は集約値で、**1 マウントの値ではない。**

**書き込みは読み取りより一貫して遅い。** 1 MiB で読み 1,105 対 書き 852（0.77 倍）、
64 KiB で読み 356 対 書き 110（0.31 倍）、4 KiB ランダムで読み 15,839 対 書き 3,688 IOPS（0.23 倍）。
S3 Files はファイル側の書き込みを約 60 秒まとめてから S3 へ出す設計なので、書き込み経路に
高性能ストレージへの同期が入る。

## 読み取れないこと

| 問い | この測定で答えられない理由 |
|---|---|
| warm と cold の差 | 温度を振っていない（S-3 未実施）。読みが高性能ストレージ由来かバケット直読かを分離していない |
| 複数マウント・複数ホストの集約 | 1 台 1 マウントのみ（S-4 未実施）。公称 4 TB/s+ は集約値で、1 マウントの値ではない |
| 同一条件の再現性 | 各ワークロード 1 回。1 MiB 逐次読みだけ再測して 1,104.9 対 1,109.4（0.4% 差）を確認したが、他は 1 回 |
| 別インスタンス型での頭打ち | c5n.9xlarge のみ。c5n.2xlarge の約 450 MB/s は別記録の値 |
| `nodirects3read` を付けた場合 | 付けていない（ゲートウェイエンドポイントがあるため）。付けると大ファイル直読を失う |

## S-4 — クライアント台数の集約（1 → 8 台）

**S3 Files の集約スループットは台数にほぼ線形に伸び、1 台あたりは一定だった。** これは
[S3 AP + FlexCache 側の台数試験](perf-matrix-results.md#台数試験と2-つの上限)と**逆**で、
あちらは購入した容量を分け合うため台数を増やしても合計が増えなかった。S3 Files は各ホストが
独自の efs-proxy を持ち、公称「最大 25,000 接続・集約 4 TB/s+」と整合する。

### 検証環境

| 項目 | 値 |
|---|---|
| 計測日 | 2026-10-10（UTC） |
| S3 Files | 専用 VPC の 1 ファイルシステム、Internet 不要（VPC 内）、取り込みしきい値は既定 |
| クライアント | **c5n.2xlarge ×8**、Amazon Linux 2023、各ホストが S3 Files を個別にマウント（efs-proxy はホストごと） |
| ツール | VDBENCH、1 MiB 逐次読み、`o_direct`、1 台あたり 64 スレッド固定（台数だけを振る）、共有エポックで同時起動、warmup 60 s + elapsed 180 s |
| 共有の形 | same（全台が同じ 600 GiB ファイル）と disjoint（各台が重ならない範囲）の 2 通り |
| 検算 | クライアント合計を CloudWatch `AWS/S3/Files DataReadBytes` と突き合わせる設計（当日はメトリクス反映が疎で窓に乗らず） |

### 結果 — same（全台が同じファイル）

| 台数 | 合計スループット | 1 台あたり | 1 台比 |
|---|---|---|---|
| 1 | 784.4 MB/s | 784.4 | — |
| 2 | 1,604.5 MB/s | 802.2 | 2.05x |
| 4 | 3,148.4 MB/s | 787.1 | 4.01x |
| 8 | **6,282.6 MB/s** | 785.3 | **8.01x** |

**8 台で 8.01 倍、1 台あたりは 785〜802 MB/s でほぼ一定。** 台数に対して合計が線形に伸びる。

### 結果 — disjoint（各台が重ならない範囲、8 台）

| 台数 | 合計スループット | 1 台あたり |
|---|---|---|
| 8（重ならない範囲） | **7,210.0 MB/s** | 901.3（770〜1,332 のばらつき） |

**データを共有しなくても線形は崩れない。** むしろ合計は same（6,283）より高い（7,210）。
これで「same の線形はサービス側のキャッシュから配っていただけ」ではないと言える。
disjoint は各台が別のデータを読むので、サービス側の共有キャッシュでは説明できない。

### 読み取れること

**S3 Files は読み手を増やすと合計が増える。** 容量計画はクライアント側の帯域で行う形で、
[S3 AP + FlexCache 側](s3files-vs-flexcache.md#上限の種別が違うことが動作として出る箇所)が
ファイルシステム単位で容量を買う形とは逆である。**同じ「読み手が増える」という変化が、
S3 Files では合計の増加、FSx for ONTAP 側では 1 台あたりの減少になる。**

### 読み取れないこと

| 問い | 理由 |
|---|---|
| CloudWatch との突き合わせ | 当日はメトリクス反映が疎で測定窓に `DataReadBytes` が乗らなかった。クライアント合計のみ |
| 8 台を超えたときの頭打ち | 8 台まで線形。頭打ちの位置（25,000 接続や 4 TB/s+ の公称まで）は測っていない |
| 1 台あたり 785 MB/s の頭打ちの帰属 | c5n.2xlarge の efs-proxy CP+ ホスト帯域のどちらが先かは S-4 では切り分けていない（S-1/S-2 の proxy CPU 飽和と整合する） |

## S-3 — S3 Files のキャッシュ温度（高性能ストレージ と バケット直読）、方法の限界つき

**S-3 は「clean な warm / cold 比較」を取れなかった。** 取れなかったこと自体が、同じ測定をする人が
踏む落とし穴なので記録する。測ったのは 64 KiB、O_DIRECT、n=30、c5n.9xlarge、2026-10-10。

### 3 つの読み取りと、その意味

| 読み方 | p50 | 有効な測定か |
|---|---|---|
| 高性能ストレージ（しきい値 131072、64 KiB 取り込み済み、O_DIRECT） | 5.33 ms | 有効 |
| しきい値を 1024 に下げた後に**同じ**ファイルを読む | 2.94 ms | **無効**（下記） |
| しきい値 1024 のまま**新規**に作った 64 KiB を読む（真のバケット直読） | 4.05 ms | 有効 |

### しきい値を下げても、既に載ったデータは追い出されない（方法の落とし穴）

**最初、しきい値を下げてから同じファイルを読めば cold になると考えたが、ならなかった。**
`sizeLessThan` は**次にディレクトリへ初回アクセスしたときに何を取り込むか**を決める設定で、
**既に高性能ストレージに載っているデータを追い出さない。** CloudWatch の `DataReadBytes`
（高性能ストレージの読み取り）が「cold」のつもりの窓でも立っており、実際には両方とも
高性能ストレージから読んでいた。2.94 ms が 5.33 ms より速かったのは、cold だったからではなく、
**両方 warm で、実行ごとのばらつき + 再マウントの差**だった。

**真の cold を測るには、しきい値を下げた後に取り込まれていない新規ファイルを読む。** それが
3 行目で、4.05 ms だった。[実測記録 s3files-measured.md](s3files-measured.md) が
サイズ固定で経路を振ったときは、**しきい値を初回アクセスの前に設定していた**ので有効だった。

### 読み取れること

**c5n.9xlarge では、高性能ストレージ（5.33 ms）とバケット直読（4.05 ms）の差は小さく、
実行ごとのばらつきの範囲に収まる。** [s3files-measured.md](s3files-measured.md) の
t3.small での 5.1 倍差（高性能ストレージ 10.8 ms 対 バケット直読 55.0 ms）は再現しなかった。
**ホストが太いと 1 リクエストあたりの固定費が相対的に小さくなり、経路差が埋もれる**と読めるが、
これは 2 つの別環境・別方法の突き合わせであり、同一環境で経路だけを振った clean な比較ではない。
**S-3 の clean な warm/cold 比較は未完了とする。**

### 読み取れないこと

| 問い | 理由 |
|---|---|
| 同一環境・同一方法での warm/cold の clean な差 | しきい値フリップ方式が無効だったため未取得。初回アクセス前にしきい値を分けて作り直す必要がある |
| 保持窓（30 日）を跨いだ失効後の cold | 時間がかかるため未実施 |
| 並列度を上げたときの経路差 | 並列度 1（逐次 pread）のみ |

## S-5 — FSx for ONTAP S3 Access Point の階層別読み取り（SSD と capacity pool）

**これは S3 Files ではなく FSx for ONTAP S3 Access Point の読み取りだが、階層とコストの話が
S3 Files のコスト並置と地続きなので同じ記録に置く。** Observability 側の依頼
（[コスト並置](../reference/comparison/finops-s3-vs-s3ap.md#階層化を踏まえた-s3-access-point-読み取りのコスト並置)の
空欄を埋める）。「SSD 上のデータの方が capacity pool より速いのではないか」という予想を測った。

### 検証環境

| 項目 | 値 |
|---|---|
| 計測日 | 2026-10-10（UTC） |
| ファイルシステム | 既存の検証用 FSx for ONTAP（SINGLE_AZ_1、128 MBps、SSD 1024 GiB、ONTAP 9.18.1P6）に測定用ボリューム 1 つを間借り |
| ボリューム | 1 GiB、UNIX、ストレージ効率オフ、SnapLock なし。測定後に削除（残存 0 件を確認） |
| S3 Access Point | **Internet origin**（`-ext-s3alias`）、UNIX root 識別情報 |
| クライアント | **AWS 外のローカル端末からインターネット経由**。並列度 1、逐次 |
| ツール | SSD 側は `scripts/measure_s3_throughput.py`、cold 側は同手法の読み取りループ（既存オブジェクトを再書き込みせず読む） |
| オブジェクト | 非圧縮（`--body random`）、64 KiB / 1 MiB / 5 MiB、各 10 本、n=10 |
| 階層の確認 | CloudWatch `StorageUsed` の `StorageTier` ディメンションで、ALL 適用後に capacity pool が 0 → 約 63.6 MB、SSD が約 85.5 → 約 19 MB（メタデータは SSD 残留）になったことを確認してから cold を測定 |

> **測定位置の注記**: クライアントが AWS 外なので、**全数値にインターネット往復が含まれる**。
> 同一条件で測った SSD と cold の比較には使えるが、ストレージ側の応答時間としては読めない。
> VPC 内から測った値ではない。

### 結果（GET の p50、ミリ秒、並列度 1、n=10）

| オブジェクトサイズ | SSD（hot、tiering NONE） | capacity pool（cold、tiering ALL） | 差 |
|---|---|---|---|
| 64 KiB | 46.5 ms | 56.4 ms | +9.9 ms（1.21x） |
| 1 MiB | 58.6 ms | 74.0 ms | +15.4 ms（1.26x） |
| 5 MiB | 116.0 ms | 121.3 ms | +5.3 ms（1.05x） |

**予想（SSD の方が速い）は成立した。** cold は 5〜15 ms 遅く、相対差は 1 MiB で最大（1.26x）。
ただし差は小さく、5 MiB では 1.05x に縮む（転送時間が階層取得の遅延を上回るため）。

**SSD 側はクロスチェックが取れている。** 同じ内容を測った Observability 側の SSD の値（1 MB で
p50 48.5〜60.4 ms、5 MB で 106.9〜119.8 ms）と、こちらの SSD（1 MiB 58.6、5 MiB 116.0）は
同じ範囲に収まる。

### capacity pool 読み取りリクエスト数（確認できなかった）

**1 回の `GetObject` が capacity pool に何回の読み取りリクエストを発生させるかは、この測定では
確認できなかった。** Cost Explorer の usagetype `APN1-Requests.SAZ_2N:CPoolStdRd` は測定当日は
0（請求データの反映が遅れるため）。**数日後に再確認が要る。** メトリクス側でもリクエスト数の
内訳は取れていない。[コスト並置](../reference/comparison/finops-s3-vs-s3ap.md#階層化を踏まえた-s3-access-point-読み取りのコスト並置)の
該当行は「測定が必要」のままとする。

### 読み取れないこと

| 問い | この測定で答えられない理由 |
|---|---|
| capacity pool 読み取りリクエスト数 | Cost Explorer の反映待ち。当日は 0。数日後の再確認が必要 |
| VPC 内（往復遅延なし）での階層差 | AWS 外のローカルから測った。往復が全数値に乗る |
| 並列度を上げたときの階層差 | 並列度 1 のみ |
| 繰り返し読んだときの昇格の有無 | ALL は昇格しないはず（予想）。読み直しによる SSD への書き戻しは測っていない |
