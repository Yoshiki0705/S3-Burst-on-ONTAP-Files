# 検証記録 — S3 Access Point と NFS の相互可視性（同一ボリューム）
<!-- lang-switcher:start -->
🌐 [日本語](s3ap-nfs-visibility.md) | [English](../../en/verification/s3ap-nfs-visibility.md) | [🏠 リポジトリトップ](../../../README.md)
<!-- lang-switcher:end -->

**この記録は FlexCache の検証ではありません。** 測ったのは 1 つのボリュームに対して
S3 Access Point とNFS の両方からアクセスしたときの可視性です。
S3 Access Point 経由で書いたものが **FlexCache の Cache ボリューム**でいつ見えるかは
依然として未検証です（[検証状況](../verification-status.md)）。

この 2 つを混ぜないことが、この記録でいちばん重要な点です。前者は後者の前提条件ですが、
前者の数値を後者の答えとして引用することはできません。

## 検証環境

| 項目 | 値 |
|---|---|
| 計測日 | 2026-08-09（UTC） |
| リージョン | ap-northeast-1 |
| デプロイタイプ | SINGLE_AZ_1、HA ペア 1 組 |
| スループット | 128 MBps（確保値） |
| SSD 容量 | 1024 GiB、`AUTOMATIC` 3072 IOPS |
| ボリューム | 1228 MB、セキュリティスタイル UNIX、ティアリング `AUTO`（31 日）、ストレージ効率 有効 |
| S3 Access Point | ファイルシステム識別情報 UNIX（root）、`NetworkOrigin` は Internet |
| クライアント | 同一 VPC・同一サブネットの EC2、カーネル 6.1.161-183.298.amzn2023、nfs-utils 2.5.4 |
| プロトコル | NFSv3 |
| オブジェクトサイズ | 64 B / 1 MiB / 8 MiB |
| 並列度 | 1 |
| 測定方法 | 書き込みと読み取りを**同一ホスト・同一クロック**で実行 |
| **ONTAP バージョン** | **特定できず**（下記） |

> **識別情報についての注記**: この測定はアクセスポイントの識別情報を UNIX の root で行っています。アクセスポイント経由の全リクエストがこの 1 つの識別情報で認可されるため、root を指定するとファイル権限による絞り込みが効きません（[実測](https://github.com/Yoshiki0705/FSx-for-ONTAP-Adoption-Playbook/blob/main/docs/ja/domains/security-governance/notes/access-point-authorization-layers.md#layer-2--絞り込みを担うファイルシステム側の権限)）。測定条件としてそのまま記録しますが、推奨構成ではありません。書き込みに必要な権限だけを持つ専用ユーザーを使い、用途ごとにアクセスポイントを分けてください（`FileSystemIdentity` は作成後に変更できません）。

### ONTAP バージョンを併記できていない理由

このリポジトリは測定値に ONTAP バージョンの併記を求めています。この測定については
併記できていません。理由は 2 つあり、どちらも回避できませんでした。

- FSx for ONTAP の `DescribeFileSystems` が、この既存ファイルシステムに対して
  `FileSystemTypeVersion` を返しませんでした（フィールドそのものが応答に含まれません）
- ONTAP の REST API は資格情報なしではバージョンを返しません（`401`）。
  この検証で使える `fsxadmin` 資格情報がありませんでした

したがって**この数値は、そのバージョン未知という一点において再現性が不完全です。**
新しく作った環境ではこの穴が塞がるように、
[収集側のテンプレート](../../../environments/aws-origin/template.yaml)は資格情報を
ファイルシステムと同時に作り、ONTAP へ到達する経路を用意しています。

## 測定結果

### S3 PutObject → NFS で読めるまで

マウントは `actimeo=0`。クライアントのキャッシュ期限ではなく、サーバ側の反映を測るためです。

| オブジェクトサイズ | n | min | p50 | p90 | p99 | max |
|---|---|---|---|---|---|---|
| 64 B | 30 | 7 ms | 9 ms | 11 ms | 15 ms | 15 ms |

### NFS 書き込み → S3 Access Point 経由で読めるまで

> **訂正**: この表の値は `aws s3api get-object` コマンドを毎回起動する方法で測定したもので、
> CLI のプロセス起動 + TLS ハンドシェイクが毎回含まれています。boto3 の persistent session を
> 使った再測定では **p50 44 ms** でした。873 ms の大部分は CLI 起動コストであり、
> ストレージの反映遅延ではありません。正しい値と全方向の比較は
> [全方向比較記録](cross-protocol-directions.md)にあります。

| オブジェクトサイズ | n | min | p50 | p90 | p99 | max |
|---|---|---|---|---|---|---|
| 64 B | 30 | 679 ms | 873 ms | 1,165 ms | 1,439 ms | 1,439 ms |
| 1 MiB | 30 | 700 ms | 904 ms | 1,423 ms | 1,650 ms | 1,650 ms |
| 8 MiB | 10 | 993 ms | 1,169 ms | 1,444 ms | 1,928 ms | 1,928 ms |

### 削除の反映（S3 DeleteObject → NFS から消えるまで）

| マウントオプション | 所要 |
|---|---|
| `actimeo=0` | 7 ms |
| 既定 | 2,171 ms |

### マルチパートアップロード中の可視性

| 時点 | NFS 側 |
|---|---|
| パート 1 アップロード後、`CompleteMultipartUpload` 前 | **見えない** |
| `CompleteMultipartUpload` 後（`actimeo=0`） | 見える（6,291,456 バイト） |
| `CompleteMultipartUpload` 後（既定マウント、3 秒後） | まだ見えない |

## 読み取れること

**方向によって約 2 桁違います。** S3 → NFS は 1 桁 ms、NFS → S3 は 1 秒前後です。
同じデータ、同じボリューム、同じホストでこの差が出ます。

**遅い方向は S3 API のオーバーヘッドが支配しています。** boto3 persistent session を使った
再測定では p50 44 ms に低下しました。以下の表に記載した値は CLI 起動コストを含むものとして
参考値にとどめ、正しい比較は[全方向比較](cross-protocol-directions.md)を参照してください。

**部分的なオブジェクトはファイル側に現れません。** マルチパートアップロードは
`CompleteMultipartUpload` まで NFS 側に見えませんでした。
中途半端なファイルを読んでしまう心配はしなくてよい、という結果です。

**クライアントのマウントオプションが結果を左右します。** これは実装の話ではなく運用の話です。
Linux の既定は `acdirmin=30` / `acdirmax=60` なので、クライアントが既に一覧を取得した
ディレクトリに現れたファイルは、ストレージ側と無関係に最大 1 分見えないことがあります。
削除の反映で 7 ms 対 2,171 ms という差が出たのはこれです。完了したマルチパートの
オブジェクトが既定マウントで 3 秒後にまだ見えなかったのも同じ理由です。

## 読み取れないこと

| 問い | この測定では答えられない理由 |
|---|---|
| FlexCache の Cache 側でいつ見えるか | FlexCache を経由していません。同一ボリュームの測定です |
| スループットはどれくらいか | 並列度 1、最大 8 MiB、確保スループット 128 MBps の環境です。スループットを測る構成ではありません |
| 別のスループット設定・別の世代でどうなるか | 1 構成しか測っていません |
| 大量の小ファイルでどうなるか | 逐次 1 件ずつです。並列や大量投入は測っていません |
| SMB でも同じか | NFSv3 のみです |
| NTFS セキュリティスタイルでも同じか | UNIX のみです |
| どのバージョンの ONTAP での値か | 上記のとおり特定できていません |

## 再現手順

1. [収集側](../deployment/aws-cloudformation.md)をデプロイし、Origin ボリュームに
   S3 Access Point を接続する
2. 検証ホストに `actimeo=0` と既定の 2 つでマウントする
3. **書き込みと読み取りを同じホストで行う。** 2 ホストに分けるとクロックの比較になり、
   ミリ秒スケールでは測定になりません
4. 1 回ではなく 30 回程度繰り返し、分布で見る
5. 環境情報（上の表の全項目）を数値と一緒に記録する

## 後片付け

この測定で作ったオブジェクトとマウントはすべて削除しました
（対象プレフィックスの残存オブジェクト 0、マウント解除済み）。
既存のボリュームを借りて実施したため、測定用のプレフィックスの外には触れていません。
