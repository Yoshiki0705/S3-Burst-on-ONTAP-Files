# 測る前に読む性能の期待値

**この構成で何がどれだけ出るかを、測らずに読み取れる形にまとめたページです。**
数値はすべてこのリポジトリの実測で、**条件を外すと当てはまりません。**
条件も一緒に置いてあるのは、そこが移植できるかどうかの判断材料だからです。

**このページの使い方は 2 通りです。**

| したいこと | 読む場所 |
|---|---|
| 自分の構成で何が上限になるかを知る | 下の[上限の種別](#上限の種別と実際に効いた順序)から順に |
| 数値を引いて設計に使う | [層ごとの期待値](#層ごとの期待値)。**条件の列を落とさないこと** |
| 自分の環境で測り直す | [再現の手引き](verification/reproduction-guide.md)。問いごとに環境と合格条件がある |
| 測る前の落とし穴を知る | [性能検証の考慮点](reference/performance-testing-guide.md) |
| 検証環境の費用を見る | [検証パターンごとの費用構造](reference/comparison/finops-performance-test-patterns.md) |

> **このページに新しい数値はありません。** 出典はすべて実測記録側にあり、リンクを張っています。
> **記録の側が正で、ここは索引です。** 食い違っていたら記録を信じてください。

## 上限の種別と、実際に効いた順序

**スループットの数値を比べる前に、その数値がどの種類の上限に当たっているかを確かめてください。**
種類が違うものを同じ列に並べると、比較の形をした表ができあがります。

| 種別 | 何で決まるか | 増やす手段 | この構成での例 |
|---|---|---|---|
| **買った上限** | ファイルシステムに指定したスループットキャパシティ | 指定値を上げる（時間課金） | S3 API 経路の書き込み。クライアントを増やしても合計は増えない（4 台で 1.01 倍） |
| **ディスク経路の上限** | プロビジョンドした SSD IOPS | IOPS を上げる（$0.0204/IOPS-月） | 第一世代 2048 の冷えた読み。3,072 で 256.47 MB/s、`DiskIopsUtilization` 112% で飽和 |
| **HA ペアの上限** | 世代と構成 | HA ペアを増やす | 第一世代 Single-AZ の書き込み 750 MBps |
| **クライアント側の帯域** | インスタンスタイプ | 台数を増やす | Amazon S3 の 1 台あたり約 500 MB/s。8 台で 8.04〜8.23 倍に伸びる |
| **クライアント上のプロセス** | vCPU | クライアントを大きくする | Amazon S3 Files の読み約 450 MB/s（`efs-proxy` の CPU） |
| **単一フローの上限** | プロトコルの接続本数 | `nconnect` / セッション追加 | NFS 既定マウントの約 590 MB/s。`nconnect=16` で 4.95 倍 |
| **キャッシュから返る割合** | 作業セットと読む領域の重なり | ワークロード側で決まる | 同一構成・同一接続数で **5.5 倍**動く（11,916.29 対 2,173.37 MB/s） |

**実測で最も多く効いていたのは、上の表の下 3 つです。** 「ストレージの上限を測った」と書く前に、
**クライアントを増やしてみてください。** 増やして合計が伸びるなら、測っていたのはクライアントの
上限です。**スレッドを増やしても分かりません** — 飽和している側ではスループットが動かず、
応答時間だけが比例します（実測: 512 → 2,048 スレッドでスループット 0.07%、応答 216.6 → 860.3 ms）。

## 層ごとの期待値

### 収集側（S3 API で書く）

| 構成 | 実測 | 効いていた上限 | 条件 |
|---|---|---|---|
| 第一世代 128 MBps | 書き 133.4 MB/s（指定値の **104%**） | 指定したスループットキャパシティ | 8 MiB、並列 64、非圧縮 |
| 第一世代 2048 MBps | 書き 415 MB/s（HA ペア上限 750 の **55%**） | HA ペアの書き込み上限 | 同上。**残り 45% の行き先は特定できていない** |
| 第一世代 128 MBps | 読み 579.3 MB/s（指定値の **4.5 倍**） | 特定できていない | 8 MiB、並列 16 |
| 小さいオブジェクト | 279〜605 req/s | S3 Access Point のリクエスト経路 | 4 KiB / 64 KiB、並列 64・256。**スループット 16 倍・IOPS 13 倍にしても増えない** |

**書き込み側で見た上限を読み取りの見積りに使わないでください。** 同じ構成で 4.5 倍違います。
出典は[スループット実測記録](verification/throughput-iops-concurrency.md)。

### 配布側（NFS / SMB で読む）

| 構成 | 実測 | 効いていた上限 | 条件 |
|---|---|---|---|
| 第一世代 2048、SSD IOPS 3,072 | 256.47 MB/s | **SSD IOPS**（利用率 112%） | 512 GiB を 1 回、1 MiB 逐次、8 ストリーム、`o_direct` |
| 第一世代 2048、SSD IOPS 40,000 | **1,246.67 MB/s** | **クライアント側の設定**（ディスク 67% / IOPS 43% / ネットワーク 43% で未飽和） | 同上、NVMe キャッシュ無効、**`rsize` 64 KiB・8 スレッド** |
| 同構成、クライアント 2 台（重ならない 300 GiB ずつ） | 合計 **1,901.48 MB/s**（982 + 920） | **ファイルシステムのディスク経路**（使用率 102〜103%、バースト） | 1 MiB、8 ストリーム/台、NVMe キャッシュ無効 |
| 同構成、**クライアント 1 台で `rsize` 1 MiB・16 スレッド** | **1,646.17 MB/s** | **ファイルシステムのディスク経路**（使用率 **102.6%**、バースト） | **1 台でも 2 台と同じ上限に達する。** 8 スレッドでは 1,446.66（使用率 77.2%）、32 と 64 では 1,647〜1,649 で平ら（応答だけ倍々） |
| 第二世代 2048、SSD IOPS 3,072、転送 1 MiB | 300.95 MB/s | **SSD IOPS**（利用率 103%） | 512 GiB を 1 回、`rsize=wsize=1048576`、8 ストリーム |
| 第二世代 2048、SSD IOPS 40,000、転送 1 MiB | **1,215.06 MB/s** | **未特定**（IOPS 34%） | 同上。**転送サイズを 16 倍にしても倍率は 4.04 倍で動かない** |
| 第二世代 1,536 | 読み 2,882 MB/s が 27 分、そのあと 1,439 | ネットワークのベースライン（指定値の約 2 倍） | 1 MiB 逐次 |
| 第二世代 6,144、8 台 | 同じ領域 **11,916.29** / 重ならない **2,173.37** | 前者はメモリ、後者はディスク経路 | 128 接続、作業セット 600 GiB 一定 |
| 第二世代 6,144、SMB 8 台 | 同じ範囲 **10,721.19** / 1/8 ずつ **4,225.31** | 同上 | Multichannel 4 チャネル |
| FlexCache 経由（cache 128 / origin 2048） | 初回 **207.53** / 常駐 **210.59** | **cache 自身の指定値**（バースト中） | 100 GiB を 1 回、1 MiB、8 ストリーム |
| 同じ構成で origin を直読み（対照） | **1,706.67** | origin のメモリ（`DiskReadBytes` 0） | 同上 |

**同じファイルシステム・同じ接続数で 5.5 倍動きます。** 決めているのは**各クライアントが読む領域が
重なるかどうか**です。**台数を数える前にそこを決めてください。**

出典は[プロトコル別測定の結果](verification/perf-matrix-results.md)と
[指定値・バースト・ベースライン](verification/throughput-capacity-burst-and-baseline.md)。

### 持続書き込み（減衰するか）

| 構成 | 定常窓 | 公表値に対して | 窓の中の減衰 |
|---|---|---|---|
| 第二世代 1,536（NFS） | **1,333 MB/s** | 一般則の 512 に対し **2.60 倍** | 観測されず |
| 第二世代 6,144（NFS） | **2,063 / 2,097 MB/s** | 例外表の 1,024 に対し **2.05 倍** | 観測されず（900 秒・1,800 秒の 2 回） |
| 第二世代 6,144（SMB） | **1,488.03 MB/s** | — | 観測されず。ただし 300 秒窓の 1,698.42 より 12.4% 低い |

**設計上の効き方は過小ではなく過大です。** 公表値から逆算すると必要以上の指定値を買うことになります
（第二世代の指定値は $2.013/MBps-月、ap-northeast-1、2026-09-04 取得）。
**この乖離は AWS に提出済みで、回答が来たら記録を更新します。**

### ブロック（iSCSI / NVMe/TCP）

| 測定点 | 実測 | 注意 |
|---|---|---|
| iSCSI、数えた TCP 1 本 | 1,135.18 MB/s | 2 本にしても**同じ値**。1 本で当たっている上限はフローの容量ではない |
| iSCSI、16 本 | 1,970.43 MB/s | 「必要帯域 ÷ 625 MBps」の見積りは 1 本で 1.82 倍、16 本で 0.20 倍に外れる |
| NVMe/TCP、I/O キュー 1 | 591.64 MB/s | — |
| NVMe/TCP、手順どおり | **1,288.87〜3,407.60 MB/s** | **3 デプロイで 2.64 倍ぶれる。1 点でサイジングできない** |
| 同一デプロイ、配置を戻す前後 | 1,239.15 → **2,298.54** | **1.85 倍。** 崩すのは小さいランダム書きだけで、逐次書き 300 秒では 0.03% |
| 4 KiB ランダム読み | 指定 SSD IOPS の約 **66%** | 4 点で同じ比。**逐次読みは指定 IOPS に依存しない** |

**この幅の理由はディスク上の配置です。** 4 KiB ランダム書きを 300 秒挟むと、ディスク側 1 回の
読みが 87〜89 KiB から 11.7 KiB になり、ディスク IOPS が 7.3 倍で飽和します。
**30 秒では崩れず、300 秒で崩れます。** 出典は[プロトコル別測定の結果](verification/perf-matrix-results.md)。

### 比較対象（同じホストから測った他の選択肢）

| 経路 | 実測 | ボトルネックの場所 |
|---|---|---|
| FSx for ONTAP S3 Access Point | 書き 133.4 / 415 MB/s | **指定したスループットキャパシティ**（全クライアントで共有） |
| Amazon S3 | 8 台で 書き 4,783.2 / 読み 3,992.2 MB/s | **クライアント側の帯域**（1 台あたり約 500 MB/s、8 台で 8 倍） |
| Amazon S3 Files | 読み約 450 MB/s | **クライアント上の `efs-proxy` の CPU**。`nconnect` 非対応は原因ではない |

**3 つとも別の場所で頭打ちになります。** 上限の値より、何がボトルネックかのほうが設計に効きます。

## 移植できない値

**次の数値は、条件を変えると当てはまりません。引用するなら条件ごと引いてください。**

| 数値 | 移植できない理由 |
|---|---|
| ブロックの逐次読み 1 点 | **同じ構成が環境をまたいで 2.64 倍ぶれる。** 1 点でサイジングできない |
| `iorate=max` で測った値 | **飽和点であって動作点ではない。** 同じ 2,364 MB/s が 216 ms の点にも 860 ms の点にもある。目標 **4,400** IOPS を与えると 4,406 MB/s・8.86 ms、無制限では 4,204 MB/s・121.79 ms |
| 300 秒以下の窓の値 | **バーストを含む。** 第二世代 1,536 は 27 分だけ 2,882 MB/s を出し、そのあと 1,439 に落ちる |
| 第一世代の表の読み方 | **第二世代では指定値の意味が違う**（ディスクのベースラインで、ネットワークはその約 2 倍）。持ち込むと読み取りを 2 倍外す |
| FlexCache の「2.31 倍」 | **origin と cache の両方が 128 MBps での値。** origin だけ 2048 MBps に上げると**逆転して origin が 8.1 倍速い**（2026-09-18 実測）。**この比は両側の指定値の組み合わせで決まるので、片方だけを引用しないこと** |
| Rocky Linux で測った逐次書き | **RHEL 本体と一致しない。** 中央値が 7.0% 違い、幅は Rocky 29.6% 対 RHEL 2.1%。読みと 4 KiB ランダム書きは 0.1% / 0.3% で一致する |
| NFS の値を SMB に | **測っていない。** 多重度の出どころが違う（クライアントが指定する接続数 対 ネゴシエートされたチャネル数） |

## 引用のときに落とさないこと

**数値だけを取り出すと、その数値が何の上限かが消えます。** 一緒に運ぶ項目です。

1. **世代と指定値**（第一世代 128 / 2048、第二世代 1,536 / 6,144 のどれか）
2. **SSD 容量とプロビジョンド IOPS**（`AUTOMATIC` か、いくらか）
3. **NVMe リードキャッシュの有無**（第一世代 Single-AZ の 2 GBps 以上には既定で付く）
4. **作業セットとインメモリキャッシュの比**（超えていないなら、それはキャッシュの値）
5. **窓の長さ**（300 秒以下ならバーストを含む）
6. **目標値を与えたか、`iorate=max` か**
7. **並列度・接続数・`nconnect`・チャネル数**
8. **ペイロードが非圧縮か**（ゼロブロックはディスクに行かず、上限の 4 倍で返る）
9. **ONTAP の版**（`FileSystemTypeVersion` は FSx for ONTAP では `null` を返す。クラスタ API から読む）

**9 番目は 2 回続けて記録し忘れました。** そのため
`environments/perf-matrix/runbook.sh preflight` が版を読み、読めなければ止まるようにしてあります。

## 未解明のまま残しているもの

**「できない」ではなく、測っていない・説明できていないという意味です。**

| 項目 | 状態 |
|---|---|
| 40,000 IOPS 側の約 1,250 MB/s の天井 | **特定した（2026-09-19/20）。資源ではなく設定 2 つ。** `rsize` 64 KiB（1 MiB にして +21%）と多重度 8（16 にして +14%、以降は平ら）。**その先で飽和するのはファイルシステム側**（使用率 102.6%）で、**1 台でも 2 台と同じ上限に達する。** 飽和したクライアント側の装置は無い |
| 第一世代 128 の約 300 MB/s | ディスク・ネットワークのバースト上限に届いておらず、残枠も枯渇していない |
| 第一世代 2048 の書き込みが HA ペア上限の 55% で止まる理由 | 候補 2 つ（書き込みの 2 倍のネットワーク消費、リクエストあたりの固定費）を切り分けていない |
| ブロックの増幅率が 0.8 と 1.5 に分かれる理由 | 配置でも書き込み履歴でもない。**残る候補の片方（ONTAP のパッチ版）は FSx for ONTAP では選べないので対照実験が組めない** |
| SMB の 300 秒と 900 秒の 12.4% 差 | **窓長を振る測定は実施したが、単一チャネルの経路で測ってしまった**（2026-09-18、ばらつき 0.07% で平ら）。**差が出た 4 チャネル側は未測定。** 残る候補は「測定中にチャネル数が減った」で、これは仮説 |

段階の定義と全項目は[検証状況](verification-status.md)にあります。
