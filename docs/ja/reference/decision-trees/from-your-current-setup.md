# いまの構成から読む

🌐 [日本語](from-your-current-setup.md) | [English](../../../en/reference/decision-trees/from-your-current-setup.md) | [🏠 リポジトリトップ](../../../../README.md)
<!-- lang-switcher:end -->

**この構成が自分に当てはまるかは、製品名では決まりません。** 決まるのは、いまデータが
どこに入ってどこから読まれているか、その間を何が運んでいるかです。

以下は**構成の形**を 5 つ並べたものです。製品名を挙げていないのは、同じ形が複数の製品で
成り立つからで、**どれを使っているかより、どの形にいるかのほうが判断に効きます。**
形が分かったら[選び方](choosing-this-architecture.md)の分岐に入ってください。

**この構成の除外条件も各行に書いてあります。** 片側だけ書くと選べません。

## 形 1 — オブジェクトへの収集と、コピーを挟んだ読み取り

**いまの形。** アプリや機器がオブジェクトストレージへ書き、読む側はファイルで欲しいので、
転送ジョブか同期処理でファイルストレージへコピーしている。**コピーの完了を待ってから読む。**

| 項目 | 内容 |
|---|---|
| この構成で置き換わるもの | **コピーの工程そのもの。** 収集は S3 API のまま、読み取りは FlexCache 経由の NFS / SMB になり、その間にジョブが入りません |
| 置き換わらないもの | **オブジェクトストレージ側の機能。** バージョニング、ライフサイクル、イベント通知は S3 Access Point 経路では使えません。**イベント駆動は ONTAP 側でも代替できません**（FPolicy はこの経路で発火しない） |
| 先に確かめること | オブジェクト名が NAS で表現できるか（255 文字、階層、使えない文字） |
| 向かない条件 | **収集が小さいオブジェクトの大量書き込み**。実測で書き込み約 420 req/s、読み取り約 600 req/s で頭打ちになります（[検証状況](../../verification-status.md)） |

**この形からの移行がいちばん素直です。** 失うのは S3 固有機能で、得るのはコピー工程の消滅です。

## 形 2 — 拠点ごとのファイルストレージと、全量の複製

**いまの形。** 読む場所ごとにファイルストレージがあり、レプリケーションか転送で同じ内容を
配っている。**全量を持つので、読まない分も置き場と転送量を使う。**

| 項目 | 内容 |
|---|---|
| この構成で置き換わるもの | **全量の複製。** FlexCache は**実際に読まれた分だけ**を持ちます。拠点の容量は作業セットに比例します |
| 置き換わらないもの | **正本の可用性。** Cache は復旧単位ではありません。Origin が失われれば Cache は答えられません（[構成](../../architecture.md)） |
| 先に確かめること | **クラスタピアリングと SVM ピアリング。** この構成の前提で、[Terraform 側では作りません](../../deployment/onprem-terraform.md)。**FlexCache 作成が失敗する原因として最も多いのがこれです** |
| 向かない条件 | **拠点側で大量に書く**なら向きません。書き込みは Origin へ戻るので、書き主体の拠点は別の設計（拠点を正本にする、双方向のレプリケーション）が合います |

**初回読み取りは遅くなります。** 同じ環境の実測で、キャッシュに無いデータの読み取りは
**2.88 分の 1** でした（[構成](../../architecture.md)）。**1 度しか読まないデータでは、この
コストが償却されません。**

## 形 3 — ファイルストレージを正本とし、オブジェクトを後段に置く構成

**いまの形。** 正本は NAS で、分析や配布のためにオブジェクトストレージへ出している。

| 項目 | 内容 |
|---|---|
| この構成が向くか | **向きません。** この構成は S3 API で入ってファイルで出る向きです。逆向きなら、ONTAP の S3 対応や階層化のほうが素直です |
| ただし使える部分 | **拠点への読み取り配布だけを FlexCache にする**のは成立します。収集側を S3 Access Point にする必要はありません |
| 先に確かめること | 読む側が本当に遠隔にあるか。**Origin と同じ場所なら FlexCache の SSD とピアリングの運用が戻りのない費用になります** |

## 形 4 — 転送・同期サービスによるスケジュール実行

**いまの形。** 転送サービスがスケジュールで走り、オブジェクトとファイルの間を運んでいる。

| 項目 | 内容 |
|---|---|
| この構成で置き換わるもの | **スケジュールという概念。** コピーが無いので、待ち時間はスケジュール間隔ではなく初回読み取りのキャッシュ充填になります |
| 置き換わらないもの | **転送サービスが持つ機能。** 帯域制御、検証、フィルタ、レポートは FlexCache にありません |
| 判断の分かれ目 | **鮮度要件をスケジュール間隔で満たせるかどうか。** 満たせるなら転送のままで足ります。**「日次で足りるなら転送」という線引きは、このリポジトリが測った値ではありません** — いま使っているサービスの最小間隔で判断してください |
| 向かない条件 | **収集と配布が同じ場所**にあるなら、この構成の配布層は要りません |

## 形 5 — 利用側からのブロックストレージの要求

**いまの形。** 読む側が iSCSI や NVMe/TCP でブロックデバイスを要求している。

| 項目 | 内容 |
|---|---|
| この構成が向くか | **対象外です。** FlexCache が配るのはボリュームで、**LUN や namespace は配りません** |
| このリポジトリにあるもの | ブロックの実測はあります（[F-1 / F-2 / F-3](../../verification/perf-matrix-results.md#f-1-iscsi-の実測)）。ただし**同じファイルシステムに直結したクライアントの値**で、拠点への配布ではありません |
| 読むときの注意 | raw device の値で、**ファイルシステムを載せた構成の値ではありません。** 窓は 300 秒でバーストを含みます。**同じ構成でもデプロイをまたぐと 2.64 倍ぶれた実測があります** |

## どの形にも共通して先に決めること

**利用拠点で NFS を使うのか SMB を使うのか。** Origin のセキュリティスタイル（UNIX / NTFS）と
対応し、**Origin ボリュームを作る前に決めます。**

**Cache は Origin から継承します。実測しました**
（[継承の検証記録](../../verification/flexcache-security-style-inheritance.md)、両側 FSx for ONTAP）。
**そして Cache 側で選び直す経路がありません** — 作成時に渡す引数が無く、作成後の変更は ONTAP が
拒否します。**つまり先に決める理由は「念のため」ではなく、あとから直せないことです。**
詳細は[最初に決めること](../../design-first-decisions.md)にあります。
