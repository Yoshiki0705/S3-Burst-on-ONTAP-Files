# 代替案との比較

S3 とファイルストレージの両方が必要なとき、実務では概ね次のいずれかに落ちる。
どれも合理的な選択であり、問題は選択そのものではなく**代償が見えにくいこと**にある。

向く条件と向かない条件を同じ粒度で書く。この構成自身の向かない条件も同じ列に書く。

| 方式 | 向く条件 | 向かない条件 |
|---|---|---|
| S3 単独 | 新規アプリ、フラットな名前空間、S3 の機能（バージョニング・ライフサイクル・イベント通知）が要る | 既存の NFS / SMB アプリや装置を変更できない、POSIX セマンティクスが要る |
| ファイル単独 | プロトコルが固定で、収集側も同じネットワークにいる | 収集側が S3 API 前提、外部サービスに書かせたい |
| ファイル → S3 コピー | 対象が確定していて、鮮度要件が緩い（日次で足りる） | 鮮度が要る、容量が大きい、削除の伝播が要る |
| S3 → ファイルゲートウェイ / FUSE | 読み取り中心で、S3 を正典にする方針が確定している | ロックや原子的 rename が要る、メタデータ操作が多い |
| 二重管理 | 用途が完全に分離していて、突き合わせの必要がない | 監査対応が要る、コスト削減が要る |
| SnapMirror で拠点へ複製 | 拠点で全量が必要、書き込みも拠点で行う | 全量転送を避けたい、拠点数が多い |
| **S3 で収集 → FlexCache で NFS / SMB に配布（この構成）** | 収集は S3、利用は既存のファイルプロトコル。利用は読み取り中心。必要な範囲だけ拠点に置きたい | S3 固有機能が要る、NAS フレンドリでない名前を多用する、拠点で大量に書き込む、Cache 側でも S3 で読みたい |

## それぞれの代償

### ファイルを正典にし、分析や配布のために S3 へコピーする

NAS 上のデータを DataSync / rsync / robocopy / 自作 ETL で S3 に複製する。

| 代償 | 内容 |
|---|---|
| 鮮度 | 下流が見るのは常に「コピーした時点」のもの。ジョブ間隔がそのまま遅延になる |
| 二重容量 | 同じバイト列に 2 系統の課金。削除の伝播が漏れると差は開き続ける |
| 権限の分岐 | ファイル側は POSIX / NTFS ACL、S3 側は IAM とバケットポリシー。監査で「誰が読めるか」を 1 つの答えで示せない |
| 運用 | 同期の失敗検知、部分失敗の再実行、リネーム・削除の伝播が恒久的な運用項目になる |

### S3 を正典にし、ファイルアクセスをゲートウェイや FUSE で代替する

| 代償 | 内容 |
|---|---|
| セマンティクスの差 | ロック、`rename` の原子性、部分更新、`stat` の頻度など、POSIX / SMB の期待とオブジェクトの実体が一致しない |
| メタデータ性能 | 小ファイル多数・ディレクトリ走査が多いワークロードで劣化しやすい |
| 認証・監査の分断 | AD 統合や既存 ACL をそのまま持ち込めない場合、権限モデルの再設計が必要になる |
| 障害面の追加 | ゲートウェイ層が新しい単一障害点と運用対象になる |

### 両方を正典として二重管理する

| 代償 | 内容 |
|---|---|
| 正典の不在 | 差分が出たときに、どちらが正しいかを決める規則が組織に存在しないことが多い |
| 説明可能性 | 保持期間・改ざん防止・監査ログをどちら側で担保するかが曖昧になり、監査で説明できない |
| コスト | 容量・転送・API リクエストが二重に発生し、削減余地が見えない |

### S3 で収集 → FlexCache で配布（この構成）

| 代償 | 内容 |
|---|---|
| 対応オペレーション | S3 の全機能は使えない。イベント通知・ライフサイクル・バージョニングは対象外 |
| 名前空間 | オブジェクト名に制約がある。NAS フレンドリでない名前を多用するワークロードには向かない |
| 書き込み経路 | 拠点側から大量に書く用途は想定していない。書き込みは Origin 側に集約する |
| Cache 側のオブジェクトアクセス | 提供しない。拠点で S3 API が必要なら別の構成を検討する |
| 前提となるバージョン | 収集層に ONTAP 9.17.1 以降が必要。既存クラスタが下回る場合は先にアップグレードの検討が要る |
| 未検証の中核 | 書いたものが Cache 側で読めるまでの挙動は未検証（[検証状況](../../verification-status.md)） |
| 設計の前後関係 | 利用側のプロトコルを Origin 作成前に決める必要がある（[最初に決めること](../../design-first-decisions.md)） |

## 課題を軸で分解する

どの方式を採っても、次の軸のどこかに代償が現れる。
この構成が扱うのは主に 1 から 4 で、5 と 6 の一部は扱わない。

| # | 軸 | 具体的に何が起きるか |
|---|---|---|
| 1 | 一貫性・鮮度 | コピー遅延、部分同期、削除の非伝播。「配布先のデータはいつのものか」を答えられない |
| 2 | 権限の単一起点 | 2 つの権限体系。棚卸しのたびに両方を突き合わせる工数が発生する |
| 3 | 容量とコスト | 同一データの二重計上。転送とリクエスト課金。アイドル時も動くゲートウェイ |
| 4 | 運用負荷 | 同期ジョブの監視・再実行が定常業務化する。障害時に「どちらを直すか」の判断が要る |
| 5 | 性能特性の不一致 | オブジェクトは大きい順次読み出しに強く、NAS はメタデータ操作とランダムアクセスに強い。片方に寄せると他方が劣化する |
| 6 | 移植性 | クラウド固有 API に寄せた設計は、オンプレミスや他クラウドで同じ形にならない |

## 誰が何を求めているか

役割ベースの整理である。実在の個人や組織への取材に基づくものではない。

| 役割 | 要求 | 譲れない制約 |
|---|---|---|
| データ / AI エンジニア | S3 API で書き込みたい。収集側のツールとサービスが S3 を前提にしている | 収集の受け口を作り直す予算がない |
| 現場の検証設備・制作・CAE / EDA・医療画像 | NFS / SMB を変更できない。装置もアプリも既存のまま動かす | プロトコルの差し替えは選択肢に入らない |
| セキュリティ / 監査 | 「誰がどのデータを読めるか」を単一の根拠で示したい | 権限モデルが 2 つある構成は説明コストが高い |
| コスト管理 | 二重容量をやめたい。増分を予測可能にしたい | 削減が測れない改善は稟議に載らない |
| インフラ / アーキテクト | 同じ設計をオンプレミスと複数クラウドで使い回したい | 単一クラウド専用の設計は標準化できない |

「収集は S3、利用は NFS / SMB」という要求の分岐が、この構成が対象とする状況そのものである。
