# FinOps — S3 標準バケットと FSx for ONTAP S3 Access Point の費用構造

<!-- lang-switcher:start -->
🌐 [日本語](finops-s3-vs-s3ap.md) | [English](../../../en/reference/comparison/finops-s3-vs-s3ap.md) | [🏠 リポジトリトップ](../../../../README.md)
<!-- lang-switcher:end -->

費用が問題になる典型は 2 つある。

1 つは**読み取り側**である。S3 に置いたデータを、AWS の外にいる利用側が S3 API で読む。同じファイルを何度も読むと、リージョンから出たバイト数に対してデータ転送料金がかかり、読んだ回数だけ倍になる。GET リクエストも回数に比例する。
この構成が解こうとしているのはここである。

もう 1 つは**収集側**で、受け口を S3 バケットにするか FSx for ONTAP S3 AP にするかでリクエスト単価と保存単価の出方が変わる。

このドキュメントは両方を課金次元に分解し、複数の構成で試算する。読み取り側が先に来るのは、そちらの金額が大きくなりやすいからである。

安いほうを選ぶための表ではない。FinOps の判断に必要なのは、
どの次元に費用が乗るか、その次元が周辺のワークロードに何を強いるか、
そして構成を選び直すときに何が固定されるか、である。

数値の扱いを先に決めておく。**単価は AWS Price List API から取得した実際の値**で、
リージョンと適用開始日を併記する。**使用量は仮定**であり、そこから出る月額は試算である。
試算を実測として扱わないために、両者を同じ表に混ぜない。

## 結論

| 状況 | 費用面で向く選択 | 理由 |
|---|---|---|
| 同じデータを AWS の外から繰り返し読む | FSx for ONTAP + FlexCache | 転送料金は読んだバイト数にかかる。キャッシュは作業セットを 1 回運ぶだけで済む |
| AWS の外から読むが、各データを 1 回しか読まない | S3 を直接読む | 運ぶ量が同じで、ファイルシステムの固定費を負う理由がない |
| 利用側を AWS へ移せる | まず移設を検討する | 同一リージョン内の転送は無料。ストレージ層の選択で動く額より大きい |
| 利用側が AWS 上の Linux で、S3 を正本にしたまま POSIX が要る | S3 Files | 大きいオブジェクトなら直接読む場合との差が小さい。NFSv3 と SMB は対象外 |
| 利用側が S3 API を話せて、ファイルプロトコルが不要 | S3 バケット単独 | FSx for ONTAP の固定費を負う理由がない |
| 小さいオブジェクトを高頻度で書く | FSx for ONTAP S3 AP | リクエスト単価が支配項になり、差が大きく出る。閾値は[算定](#算定)で計算する |
| 大きいオブジェクトを低頻度で扱い、利用側が NFS / SMB を要求する | 費用差は小さい | 選ぶ理由は費用ではなく、同期ジョブを持つかどうかになる |
| 既に FSx for ONTAP がある | FSx for ONTAP S3 AP | 比較が増分になる。固定費は既存ワークロードが負っている |
| 新規に FSx for ONTAP を建てる必要があり、データ量も要求も小さい | S3 バケット単独、または要件の再確認 | 月額下限を回収できる理由が要る |
| 長期保持が中心で、読み出しが稀 | S3 の Glacier 系ストレージクラス | FSx for ONTAP に同等の取り出し課金モデルはない |
| 配布側が必要とするのは全データではなく作業セット | FlexCache の Cache ボリューム | 疎なキャッシュなので、Origin の 1 割程度の SSD で足りる |
| 利用側が AWS 上の Linux コンピュートで、マウントヘルパーを入れられる | S3 Files | FSx for ONTAP の固定費がかからない。大きいオブジェクトではとくに安い |
| 利用側が構成を変えられない装置、SMB、または AWS 外 | FSx for ONTAP S3 AP + FlexCache | S3 Files は EC2 / Lambda / EKS / ECS の Linux 向けで、SMB を提供しない |
| 配布側で全データを常時ローカルに置く必要がある | 全量コピー (SnapMirror など) | Cache は階層化できないため、全量を載せるとコピーより高くつく |

費用の前に絞り込みが効く軸が 2 つある。利用側が話せるプロトコルと、書き込みの経路である。

- [対応プロトコルとバージョンの対比](#対応プロトコルとバージョンの対比) — NFSv3 で固定された装置や SMB を使う工程があるかどうかで、選択肢が先に絞られる
- [配布側での書き込み](#配布側での書き込み--flexcache-の-2-つのモード) — Cache は書き込み可能で、既定の write-around と非同期の write-back で鮮度と遅延の出方が違う

## 課金次元の対応

同じ「オブジェクトを置いて読む」でも、課金される軸が違う。
片方にあって他方にない項目が、そのまま設計上の制約になる。

| 次元 | S3 バケット | FSx for ONTAP + S3 AP |
|---|---|---|
| 保存 | ストレージクラス別の GB-Mo。使用量で段階が下がる | SSD の GB-Mo と キャパシティプールの GB-Mo |
| 保存の下限 | なし | SSD 1 TiB |
| 帯域 | 事前のプロビジョニングは不要 | スループットキャパシティを MBps-Mo で事前に選ぶ |
| IOPS | 課金項目にない | SSD 1 GiB あたり 3 IOPS が込み。超過分を IOPS-Mo で |
| リクエスト | Tier1 / Tier2。ストレージクラスごとに単価が違う | S3 AP 経由の Tier1 / Tier2 (専用単価) と、キャパシティプールの読み書き |
| 取り出し | 低頻度アクセス層と Glacier 系は GB あたりの取り出し料金 | 取り出し料金という項目はない。キャパシティプールはリクエスト課金 |
| 最小保存期間 | 低頻度アクセス層は 30 日、Glacier 系はさらに長い | なし |
| 最小課金オブジェクトサイズ | Standard-IA は 128 KB | なし |
| 階層化 | ライフサイクルの遷移にリクエスト課金 | 自動階層化。遷移そのものへの課金項目はない |
| バックアップ | バージョニングとレプリケーションは容量課金 | バックアップストレージの GB-Mo |
| データ転送 | 標準の S3 データ転送料金 | S3 AP 経由も標準の S3 データ転送料金と同じ扱い |
| コンプライアンス保持 | Object Lock (追加課金なし) | SnapLock (独立したライセンス項目) |
| ソフトウェアライセンス | なし | ONTAP のデータ管理機能は追加ライセンス不要。SnapLock は別 |
| ファイルプロトコルでの読み出し | S3 Files を併用すると、正本のバケット料金に加えて高性能ストレージと読み書きの課金が載る | FlexCache の Cache ボリューム。階層化できないため全量 SSD |

## 3 つの構造的な違い

### 1. 固定費の有無

S3 バケットは使った分だけで、下限がない。FSx for ONTAP は SSD 1 TiB と
スループットキャパシティ 1 つが最小構成で、使用量に関わらず毎月かかる。
新規に建てるなら、この下限を回収できる理由が要る。既にあるなら、この項は比較から外れる。

### 2. リクエスト単価の非対称

同じ `PutObject` でも、宛先が S3 バケットか FSx for ONTAP ボリュームかで単価が違う。
FSx for ONTAP 宛のほうが安い。差は PUT で 4 倍強、GET で 12 倍強ある。

### 3. 保存単価の非対称と、キャパシティプールでの逆転

SSD は S3 Standard より高い。一方でキャパシティプールは S3 Standard を下回る。
どちらに寄るかは階層化の割合とストレージ効率で決まるので、
「FSx for ONTAP の保存は高い」とも「安い」とも一律には言えない。

## S3 側でストレージクラスを下げるときの制約

保存単価を下げる目的で階層を落とすと、別の次元で戻ってくる。
小さいオブジェクトを高頻度で書く収集系では、この戻りが効きやすい。

| 制約 | 内容 | 出典 |
|---|---|---|
| 最小課金オブジェクトサイズ | Standard-IA は 128 KB。6 KB のオブジェクトも 128 KB として課金される | [S3 FAQ](https://aws.amazon.com/s3/faqs/) |
| 最小保存期間 | Standard-IA と One Zone-IA は 30 日、Glacier Flexible Retrieval は 90 日、Glacier Deep Archive は 180 日 | [ライフサイクルの考慮事項](https://docs.aws.amazon.com/AmazonS3/latest/userguide/lifecycle-expire-general-considerations.html) |
| 遷移リクエスト | PUT / COPY / ライフサイクルでデータを移すときにリクエスト課金がかかる | [S3 料金](https://aws.amazon.com/s3/pricing/) |
| 取り出し料金 | Standard-IA と Glacier 系は GB あたりの取り出し料金が加わる | Price List API (下の単価表) |
| リクエスト単価の上昇 | 階層を下げると Tier1 / Tier2 の単価が上がる | Price List API (下の単価表) |
| Intelligent-Tiering の対象外 | 128 KB 未満は自動階層化の対象にならず、頻繁アクセス層の単価で課金され続ける | [S3 料金](https://aws.amazon.com/s3/pricing/) |

最後の 1 行は小オブジェクト主体の収集に直接効く。
平均 64 KiB のテレメトリを Intelligent-Tiering に置いても、階層化による削減は発生しない。
128 KB 未満のオブジェクトは頻繁アクセス層のまま課金され続ける。

## FSx for ONTAP 側で構成を選ぶときの制約

| 制約 | 内容 |
|---|---|
| デプロイタイプは変更できない | 世代と AZ 構成は作成後に変えられない。移行はバックアップからの復元、SnapMirror、DataSync のいずれかになる |
| Multi-AZ は SSD 単価が 2 倍 | AZ 障害への耐性が要件かどうかで決める。AZ 間レプリケーションの転送料金はスループット料金に含まれる |
| Single-AZ の AZ 跨ぎアクセス | ファイルシステムの優先 AZ 以外から読み書きすると各方向 $0.01/GB。2022-02-23 以降に作成した Multi-AZ では発生しない |
| スループットは刻みで上がる | 連続値ではなく選択肢から選ぶ。1 つ上げると費用も刻みで上がる。**買った指定値がそのまま出るとは限らない**（下の節） |
| 第二世代の下限は 384 MBps | 第一世代の 128 MBps より 3 つ上の指定値。上限 (SSD 512 TiB、200,000 IOPS、Single-AZ で最大 12 HA ペア) に用がなければ、使わない余力に払うことになる |
| Cache ボリュームは階層化できない | FabricPool の Origin を Cache することはできるが、Cache ボリューム自体は階層化されない ([対応機能一覧](https://docs.netapp.com/us-en/ontap/flexcache/supported-unsupported-features-concept.html))。配布側は全量が SSD に載る |
| Cache のサイジングが費用を決める | Origin の全量ではなく作業セットで足りる。NetApp のサイジング指針は最低 10%、作成時の既定値も 10% ([サイジング指針](https://docs.netapp.com/us-en/ontap/flexcache/sizing-concept.html)) |

出典は[可用性とデプロイオプション](https://docs.aws.amazon.com/fsx/latest/ONTAPGuide/high-availability-AZ.html)と
[FSx for ONTAP 料金](https://aws.amazon.com/fsx/netapp-ontap/pricing/)。

### 買った指定値と出る値の差

**スループットキャパシティは課金の単位であって、達成値の保証ではありません。** サイジングを
指定値で行うと、払った分に届かないことがあります。

[スループット実測記録](../../verification/throughput-iops-concurrency.md)で 2 つの指定値を測りました
（2026-09-01、ap-northeast-1、SINGLE_AZ_1、8 MiB、S3 API 経由の書き込み、並列度 64）。

| 購入した指定値 | 指定値の月額（$0.906/MBps-Mo） | 実測の書き込み | 実際に効いた上限 |
|---|---|---|---|
| 128 MBps | 約 $116 | 129.5 MB/s | 購入した指定値（128 MBps） |
| 2048 MBps | 約 $1,855 | 497.1 MB/s | **書き込み上限 750 MBps**（指定値ではない） |

**費用は 16 倍、得られた書き込みは 3.8 倍**でした。理由は指定値を使い切れなかったからではなく、
**2048 MBps の構成では購入した指定値がそもそも書き込みの上限ではないから**です。

### 効く上限は 3 つあり、実際の上限はその最小値

[性能仕様](https://docs.aws.amazon.com/fsx/latest/ONTAPGuide/performance.html)に 3 つ書かれて
います。ap-northeast-1 の第一世代 Single-AZ の場合は次のとおりです。

| 上限 | 値 |
|---|---|
| 購入した throughput capacity（ディスクスループット） | 指定値（128 / 256 / … / 2,048 MBps） |
| **SSD 側から来るディスクスループット** | **768 MBps / TiB**（SSD IOPS が `AUTOMATIC` のとき） |
| **HA ペアあたりの書き込み上限** | **750 MBps**（読み取りは 2,048 MBps） |

**費用設計で見落としやすいのは 2 つめです。** SSD 1 TiB で SSD IOPS が既定（`AUTOMATIC`）の
ファイルシステムでは、throughput capacity をいくら上げてもディスクスループットは 768 MBps で
止まります。

**外す方法は 2 つあり、単価が 1 桁違います。**

| 方法 | 課金項目 | 1 TiB・40,000 IOPS 相当での月額目安 |
|---|---|---|
| SSD 容量を 2.67 TiB 以上にする | SSD ストレージ $0.15/GB-Mo | 追加 1.67 TiB で **約 $257** |
| **SSD IOPS を `USER_PROVISIONED` にする** | プロビジョンド SSD IOPS $0.0204/IOPS-Mo | 追加 36,928 IOPS で **約 $753** |

> **コストに関する補足。** 容量側の方が安く見えますが、増やした容量はそのまま使えるので、
> 実際には「その容量が要るか」で選ぶことになります。容量が不要なのに天井だけ外したい場合は
> IOPS 側になります。

**IOPS 側は実測しました。** SSD IOPS を 3,072 から 40,000 に上げて他を一切変えずに測ると、
280 GiB の読み取りが **286.1 → 2042.1 MB/s（7.14 倍）**になりました。**768 MBps は容量が決める
天井ではなく、既定の IOPS 水準を MB/s で言い直したものです。**

> **費用判断に使う前の注意。この 7.14 倍は観測であって、機構は特定できていません。** 後日
> CloudWatch を見ると、速い側の読み取りは**バイトの 98.5〜99.9% がディスクに行っていません。**
> 280 GiB はこの構成のキャッシュ 238 GiB を 18% 超えただけでした。再測でも 2042.1 は 2667.2 に
> なり、「指定値の 99.7%」という一致は再現しません。**プロビジョンド IOPS に月 $753 を払う前に、
> 自環境で `DiskReadBytes` ÷ `DataReadBytes` を見て、読み取りが本当にディスクから来ているかを
> 確かめてください。** キャッシュから返っているなら、IOPS を買っても効きません。

つまり**指定値を上げるだけでは性能は買えません。** 上の実測では、指定値に月 $1,739 追加して
（$116 → $1,855）書き込みは 129.5 → 497.1 MB/s でした。指定値だけを上げた場合の書き込み上限は
750 MBps なので、それ以上を求めるなら別の項目も同時に上げることになります。

**そして最初に確認するのは無料の側です。** クライアントの NFS マウントは既定で TCP 接続を
1 本しか張らず、この環境では約 590 MB/s で止まりました。`nconnect=16` を付けるだけで同じ測定が
2000 MB/s 級になります。**課金項目を増やす前にここを見てください。**

### 費用設計への含意

- **指定値を上げる前に、どの上限に当たっているかを確認します。** 指定値に当たっているなら指定値を上げれば
  伸びます。SSD IOPS 側や書き込み上限に当たっているなら、指定値を上げても払うだけになります。
  **クライアントのマウントに当たっている場合は、何を買っても動きません。**
- **読み取りにはこの構成はほぼ効きません。** 128 MBps のファイルシステムで読み取りは
  579.3 MB/s、指定値を 16 倍にして 654.8 MB/s（1.13 倍）でした。読み取り上限は 2,048 MBps で
  指定値とは別に決まっているためです。**読み取り主体のワークロードで指定値を上げるのは、費用に対して
  得られるものが小さい選択です。**
- **並列度が足りないと指定値は使い切れません。** 1 リクエストあたり約 330 ms の固定費があります
  （[設計ガイド](../limits/s3ap-design-guide.md#並行度の決め方)）。
- **指定値の変更はオンラインですが即時ではありません。** 128 → 2048 の更新に 24 分かかりました。
  検証で一時的に上げる場合、上げ下げの往復で 1 時間近く上位の指定値の課金を見込みます。

**実測値は 1 環境・1 回のものです。** 上限の値は公式表からの引用で、実測は「128 の構成では指定値が
上限として効き、2048 の構成では効かなかった」ことの確認です。

### SSD IOPS を追加しても S3 経由のリクエストレートは上がらない

SSD IOPS の追加プロビジョニングは $0.0204/IOPS-Mo の課金項目です。**S3 Access Point 経由の
ワークロードでは、これを増やしても効きません。**

4 KiB と 64 KiB のオブジェクトで実測した結果、リクエストレートは**書き込み約 420 req/s、
読み取り約 600 req/s で頭打ち**になり、SSD IOPS 3,072 の 14〜20% にしか届きませんでした
（[実測記録](../../verification/throughput-iops-concurrency.md#小さいオブジェクトの-iops)）。
律速は S3 API のリクエスト経路です。

**小さいオブジェクトを大量に扱う見積りで IOPS 課金を積む前に、経路がどちらで詰まっているかを
確認してください。** ファイル経路（NFS/SMB）主体なら SSD IOPS は効きますが、S3 経由の部分には
効きません。

### 2 つの側で逆になる容量計画の単位

**同じ「MB/s」でも、クライアントを増やしたときの振る舞いが逆です。** 1 台と 2 台同時で測りました
（8 MiB、並列度 16）。

| 対象 | 1 台 | 2 台の合計 | 意味 |
|---|---|---|---|
| FSx for ONTAP S3 AP 読み取り | 585.3 | **592.5** | 購入した容量を分け合う |
| Amazon S3 読み取り | 649.3 | **1308.9** | クライアント側が上限だった |

単位 MB/s。費用設計への含意は次のとおりです。

- **FSx for ONTAP 側**: 読み手が増えても総量は増えません。**費用はファイルシステム単位で決まり、
  クライアントを増やすことは容量を買うことではありません。** 総量を上げるには指定値か SSD 容量を
  上げます（上の 3 つの上限を参照）。
- **Amazon S3 側**: 総量はクライアント数でほぼ線形に増え、ストレージ側に追加費用は発生しません。
  **費用はリクエスト数とデータ量で決まり、帯域を買う項目がありません。**

つまり**「並列に読む利用者が増える」という同じ変化が、一方では容量追加の検討につながり、
他方ではリクエスト課金の増加にしかなりません。** 見積りのときに取り違えやすい箇所です。

## ストレージ効率の扱い

試算の金額はストレージ効率の仮定で大きく動く。
どこから持ってきた数字かを先に示す。

AWS はワークロード別の典型的な削減率を公表している ([ストレージ容量の管理](https://docs.aws.amazon.com/fsx/latest/ONTAPGuide/managing-storage-capacity.html))。

| ワークロード | 圧縮のみ | 重複排除のみ | 圧縮 + 重複排除 |
|---|---|---|---|
| 汎用ファイル共有 | 50% | 30% | 65% |
| 仮想サーバーとデスクトップ | 55% | 70% | 70% |
| データベース | 65-70% | 0% | 65-70% |
| エンジニアリングデータ | 55% | 30% | 75% |
| 地震探査データ | 40% | 3% | 40% |

各シナリオの SSD 層の効率は、この表から最も近いワークロードを当てている。
当てた根拠はシナリオごとの前提表に書いてある。

### 階層化による効率の前提の変化

**階層化されたデータには背景の効率化処理が動かない。**
SSD にいる間に適用された削減だけがプールへ引き継がれ、
効率化が走る前に階層化されたブロックは削減なしのままプールに残る。

| 出典 | 記述 |
|---|---|
| [FSx for ONTAP のドキュメント](https://docs.aws.amazon.com/fsx/latest/ONTAPGuide/manage-vol-SE.html) | キャパシティプールへ階層化された後のデータに対して背景の効率化は実行されない。ただし SSD にいる間の削減はプールへ引き継がれる |
| [NetApp KB](https://kb.netapp.com/Advice_and_Troubleshooting/Data_Storage_Software/ONTAP_OS/Does_ONTAP_apply_efficiencies_to_blocks_that_are_tiered-out_to_Fabricpool%3F) | 効率化が適用される前に階層化されたブロックは、効率化が適用されない状態でキャパシティ層に残る |

このため、キャパシティプール層の効率を SSD 層と同じ値で置くことはできない。
本文の試算はプール層を **SSD 層の 50%** と仮定している。これは仮定であり、出典のある値ではない。
cooling period が短い構成や `All` ポリシーでは 0% に寄る。
`AUTO` で 31 日の既定値なら、階層化までに効率化が走る余地はある。

階層化を有効にした環境で 40% を超える削減を前提に置くのは慎重に扱う。
前提を楽観的にすると、この構成が実際より安く見える方向に働く
（S3 を保管に使う選択肢では ONTAP の効率が効かないため、金額が動かない）。
影響の大きさは[算定](#算定)の感度表で確認できる。

### FlexClone は 3 つめの効率化機構

重複排除と圧縮は同じバイト列を 1 つに寄せる。FlexClone は**同じバイト列を指す参照を増やす**。
試算のモデルには入れていないが、収集したデータの複製を作る運用があるなら、これが金額を動かす。

実測（2026-08-26、ap-northeast-1、ONTAP 9.18.1P3D1、S3 Access Point を取り付けた UNIX ボリューム）:

| 時点 | 論理使用量 | 物理使用量 |
|---|---|---|
| 256 MiB のファイルを S3 経由で 1 本 PUT した直後 | — | 253,534,208 B |
| そのファイルをファイル単位 FlexClone で 4 本複製した後 | 1,350,942,720 B | 277,200,896 B |

論理は 5 本分になり、物理は約 23 MB 増えた。**FSx for ONTAP の課金はプロビジョニングした SSD
容量にかかるので、複製の本数だけ容量を積む必要がない。**

同じことを S3 側で行うと `CopyObject` が必要で、複製したオブジェクトには保管料金がそのままかかり、
コピーのリクエスト料金も加わる。**この差は構造の差であり、単価では埋まらない。**

裏返しも同じ粒度で書く。

| 制約 | 内容 |
|---|---|
| クローンに書き込んだ変更の分は共有されない | NetApp は「変更がコピーに書き込まれるまで、メタデータに必要な分を除いてストレージを消費しない」と記載している（[FlexClone volumes, files, and LUNs](https://docs.netapp.com/us-en/ontap/concepts/flexclone-volumes-files-luns-concept.html)）。書き込んだ変更の分だけ新しいブロックを消費する。新規作成時のメタデータは公称サイズの約 0.5%（[使用スペースの確認](https://docs.netapp.com/ja-jp/ontap/volumes/determine-space-used-flexclone-task.html)） |
| スプリットすると共有が終わる | クローンを通常の FlexVol にする明示の操作（`volume clone split start`）。**ONTAP 9.4 以降、ボリュームギャランティが `none` の AFF システムでは物理ブロックを共有したままデータをコピーせず、ストレージ効率も維持される。** ただしスプリット後は親とクローンの両方が、それぞれのボリュームギャランティに基づく完全なスペース割り当てを必要とする。所要スペースは `volume clone show -estimate` で事前に確認する（[スプリットの手順](https://docs.netapp.com/ja-jp/ontap/volumes/split-flexclone-from-parent-task.html)）。**この構成では未測定**（ドキュメント記載） |
| 参照されているブロックは解放されない | 親のデータを削除しても、クローンやスナップショットが参照している間は容量が戻らない |
| プロビジョニングを下げなければ請求は変わらない | 節約が金額に出るのは、積まずに済んだ容量の分だけ。すでに余裕を持って確保している構成では請求は動かない |
| 削除の順序が増える | クローンを消してから親を消す。ONTAP の volume recovery queue に残っている間は親側の `clone.has_flexclone` が `true` のままで、AWS 側の `delete-volume` が無言で戻る（[相互運用性](../limits/s3ap-interoperability.md)） |
| ボリューム単位のクローンは利用開始までに待ちがある | クローン自身にアクセスポイントを取り付けるには `fsvol-` ID が必要で、ONTAP API で作ったボリュームが AWS 側に現れるまで実測で 599〜1,177 秒かかった。ファイル単位のクローンは同じボリュームに入るため、この待ちが無い |

#### 支配項ごとの打ち手

| 支配項 | 症状 | 効く手 | 効かない手 |
|---|---|---|---|
| 転送 | 同じデータを何度も読む。オブジェクトは数 MiB 以上 | 作業セットだけを運ぶ (FlexCache)、利用側の移設、Direct Connect で単価を下げる | オブジェクトをまとめる。回数は減っても運ぶバイト数は変わらない |
| リクエスト | オブジェクトが一桁 KiB で、読み出し回数が非常に多い | オブジェクトをまとめて大きくする、S3 API を経由しない読み出し経路にする | 転送単価の交渉。金額の大半がリクエスト側にある |
| 両方 | 小さいオブジェクトを繰り返し読む | まとめる (リクエスト) とキャッシュする (転送) の併用。片方だけでは残る | 片方だけの対処 |
| どちらも小さい | 読み取り回数が少ない。ファイルプロトコルの要件もない | S3 を直接読む。ファイルシステムの固定費を負わない | キャッシュの導入。固定費のほうが大きい |

この構成の列がサイズと回数でほとんど動かないのは、読み出しが S3 API を経由せず、運ぶのが作業セットに限られるためである。**そのぶん固定費が先に立つ**ので、読み取りが少ない領域では不利になる。表の「直接読むほうが安い」行がその領域である。

### 配布側 — フル SSD の Cache ボリューム

ここまでの試算は収集側 (Origin) だけを見ている。この構成は配布側に FlexCache の Cache ボリュームを置くので、その分が別に載る。

Cache ボリュームには階層化ができない。ONTAP の仕様として、FabricPool の Origin を Cache することはできるが**Cache ボリューム自体は階層化されない** ([対応機能一覧](https://docs.netapp.com/us-en/ontap/flexcache/supported-unsupported-features-concept.html))。したがって Cache は全量が SSD に載る。

それが成立するのは Cache が疎だからである。FlexCache は Origin の全データを複製せず、実際に読まれたブロックだけを保持する。NetApp のサイジング指針は Origin の**最低 10%**を推奨し、作成時の既定値も 10% である ([サイジング指針](https://docs.netapp.com/us-en/ontap/flexcache/sizing-concept.html))。読み取り中心のワークロードでは 5〜15% に収める運用が一般的で、この帯であれば全量 SSD でも費用が成り立つ。

以下は Cache 比率を 10% に置いた場合の配布側の月額と、同じ場所に全量コピーを置いた場合の比較である。全量コピーは通常のボリュームなので階層化できるものとして計算している。全量 SSD として計算すれば差はさらに開くが、それは比較として不当なので採らない。

| ワークロード | Origin 論理 | Cache SSD (効率適用後、10%) | Cache 10% の月額 | Cache 20% の月額 | 全量コピーの月額 | コピーが何倍か |
|---|---|---|---|---|---|---|
| HiL テストベンチ | 39,062 GiB | 2,813 GiB | $537.92 | $959.72 | $3,292.29 | 6.1 倍 |
| EDA / CAE | 43,945 GiB | 1,319 GiB | $313.82 | $511.52 | $1,564.09 | 5.0 倍 |
| メディア / レンダリング | 73,242 GiB | 8,790 GiB | $1,550.44 | $2,868.79 | $4,263.32 | 2.7 倍 |
| ゲノム解析 | 93,750 GiB | 6,750 GiB | $1,128.47 | $2,140.97 | $4,402.97 | 3.9 倍 |

差が小さく出るのは、Origin の階層化割合が大きいワークロードである。コピー側もキャパシティプールに落とせるため、SSD 単価の差が効きにくくなる。逆にホットなデータが多いワークロードでは、コピー側も SSD に置くことになり差が開く。

Cache 比率を動かしたときの月額を、Origin 論理が最大の「ゲノム解析」(93,750 GiB) で示す。

| Cache 比率 | Cache SSD | Cache の月額 | 備考 |
|---|---|---|---|
| 10% | 6,750 GiB | $1,128.47 | サイジング指針の下限、かつ作成時の既定値 |
| 15% | 10,125 GiB | $1,634.72 |  |
| 20% | 13,500 GiB | $2,140.97 | 作業セットが読みきれないときの比較用 |
| 25% | 16,875 GiB | $2,647.22 |  |
| 50% | 33,750 GiB | $5,178.47 |  |
| 100% | 67,500 GiB | $10,240.97 | 実質的にコピー。階層化できないぶんコピーより高い |

比率 100% は成立しない選択である。階層化できない Cache に全量を置くと、階層化できる通常のボリュームに全量コピーを置くより高くつく。Cache を「コピーの代わり」として全量でサイジングすると、この領域に入る。

### 3 つの選択肢を並べる — 収集と利用が同じ場所の場合

ここでは配布側を足さない。**バケットから DataSync で FSx for ONTAP にコピーすれば、その FSx for ONTAP 自体が NFS / SMB で読み書きできるので、Cache を置く理由がない。**Cache が費用に見合うのは、利用側がファイルシステムと別の場所にいる場合だけである。その場合の比較は Cache と全量コピーの対比（上の表）になる。この表は 3 案がいずれもファイルシステム 1 つ、または 0 つで済む単一サイトの比較である。

この表は「利用側にファイルとして配る」ことを前提にした比較である。利用側が S3 API で足りるなら配布層そのものが不要で、各ワークロードの試算にある S3 単独の金額が下限になる。

3 列目の S3 Files は、S3 バケットをファイルシステムとしてマウントする選択肢である。FSx for ONTAP を持たないため固定費の下限がなく、正本はバケットに残る。対応プロトコルは NFSv4.1 と NFSv4.2 で、**NFSv3 と SMB は対象外**である ([非対応事項とクォータ](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-files-quotas.html))。EC2 では S3 Files のマウントヘルパー (`amazon-efs-utils` に含まれる) が必要で、`s3files` というファイルシステムタイプでマウントする ([マウント手順](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-files-mounting.html))。対応するコンピュートは EC2、Lambda、EKS、ECS である ([S3 Files の概要](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-files.html))。費用だけでは決められない仕様上の制約が複数あるので、この表の金額は後述の[S3 Files を選ぶ場合の仕様](#s3-files-を選ぶ場合の仕様)と併せて読む。

| ワークロード | 平均オブジェクト | S3 + DataSync + FSx for ONTAP | FSx for ONTAP S3 AP (この構成) | S3 + S3 Files |
|---|---|---|---|---|
| 車載 / IoT テレメトリ | 64 KiB | $3,629.75 | $2,088.02 | $10,756.38 |
| HiL テストベンチ | 1,024 KiB | $3,763.33 | $3,317.22 | 要件を満たさない |
| EDA / CAE | 256 KiB | $2,835.78 | $2,321.44 | $1,522.08 |
| メディア / レンダリング | 512,000 KiB | $4,721.38 | $4,263.42 | $1,809.34 |
| ゲノム解析 | 8,192 KiB | $4,707.12 | $4,406.16 | $2,313.22 |

オブジェクトサイズで結果が反転する。S3 Files は既定のしきい値 (128 KiB) を超えるファイルを高性能ストレージに載せず、バケットから直接ストリームする。ストレージ課金が発生しないので、大きいオブジェクトを読むワークロードでは安い。しきい値以下のファイルは高性能ストレージに取り込まれ、$0.36 / GB-Mo が効くので、小さいオブジェクトでは高くつく。

大きいオブジェクトの行で S3 Files の金額がほぼ S3 Standard の保存料金に見えるのは、計上漏れではなく設計どおりである。1 MiB 以上の読み出しは高性能ストレージを経由せずバケットから直接ストリームされ、ファイルシステム側のデータ課金が発生しない。残るのは S3 の GET リクエストと 4 KiB のメタデータ読み取りだけで、オブジェクトが大きければ回数が少ないため金額に出ない。S3 の GET と PUT はどの行でも計上している。

**配布サイトを増やしたときの増え方は 3 案で違う。**この構成は Origin 1 つに対してサイトごとに Cache を足すので、1 サイトあたり Origin 論理の 1 割程度で増える。DataSync 方式はサイトごとに全量コピーを置くので、1 サイトあたり全量で増える。S3 Files はファイルシステムあたり 1 VPC なのでサイトごとにファイルシステムを作るが、同じバケットに複数のファイルシステムを付けられ、課金されるのは各ファイルシステムが実際に使った分だけである。サイト数が増えるほど全量コピー方式が不利になる。

S3 Files が安く出るワークロードで、それでもこの構成を選ぶ理由は費用ではない。利用側が構成を変えられない装置である、SMB が要る、AWS 外にいる、ONTAP のデータ管理機能を収集直後のデータに効かせたい、といった要件の側にある。費用だけで選ぶなら、その要件がない限り S3 Files のほうが合う場面がある。

#### 大きいオブジェクトで S3 Files が安くなる理由

「ゲノム解析」の内訳を並べると理由が 1 行で出る。S3 Files は**しきい値を超えるファイルのデータを高性能ストレージに載せない**ので、保管の課金は S3 Standard の単価だけになる。FSx for ONTAP は作業セット相当を SSD に置く。

| 比較項目 | 値 |
|---|---|
| 論理データ量 | 93,750 GiB |
| S3 Files の保管 (論理全量を S3 Standard に) | $2,301.20 |
| この構成の SSD 分のみ (20,250 GiB × $0.15) | $3,037.50 |
| SSD 分が S3 Standard 全量の何倍か | 1.32 倍 |

論理データの 30% を SSD に置くだけで、論理全量を S3 Standard に置いた金額を上回る。さらにスループットキャパシティの固定費が乗る。S3 Files にはその項目がない。

引き換えになっているものも同じ表から読める。S3 Files でしきい値を超えるファイルは、読み出しのたびにバケットから取得される。低レイテンシが要るならしきい値を上げることになり、上げた分は $0.36 / GB-Mo の課金対象になる。この安さは、読み出しが S3 のレイテンシで行われることと引き換えである。

効率の仮定は、この文書で最も金額を動かす仮定である。「ゲノム解析」で SSD 層の効率を振ると次のようになる（キャパシティプール層は常にその半分と仮定）。

| SSD 層の効率 | プール層の効率 | この構成の月額 | S3 + S3 Files の月額 | 備考 |
|---|---|---|---|---|
| 0% | 0% | $6,743.54 | $2,313.22 |  |
| 20% | 10% | $5,575.00 | $2,313.22 |  |
| 40% | 20% | $4,406.16 | $2,313.22 | AWS 公表値の地震探査データ |
| 60% | 30% | $3,237.63 | $2,313.22 |  |
| 75% | 38% | $2,361.04 | $2,313.22 | AWS 公表値のエンジニアリングデータ |

**S3 Files の列は動かない。** ONTAP の重複排除と圧縮は S3 の保管料金に効かないので、効率をどう仮定しても S3 Files 側の金額は変わらない。つまり効率の仮定は、この構成に有利な方向にしか働かない。楽観的な効率を置くと、この構成が実際より良く見える。

階層化を有効にしている環境で高い効率を期待するのは慎重に扱う。**階層化されたデータには背景の効率化処理が動かない**。SSD にいる間に適用された分だけが保持され、効率化が走る前に階層化されたブロックは削減なしでプールに残る ([FSx for ONTAP のドキュメント](https://docs.aws.amazon.com/fsx/latest/ONTAPGuide/manage-vol-SE.html)、[NetApp KB](https://kb.netapp.com/Advice_and_Troubleshooting/Data_Storage_Software/ONTAP_OS/Does_ONTAP_apply_efficiencies_to_blocks_that_are_tiered-out_to_Fabricpool%3F))。cooling period が短い構成や `All` ポリシーでは、プール層の効率は 0% に寄る。

小さいオブジェクトの場合、高性能ストレージの有効期限が最大のレバーになる。「車載 / IoT テレメトリ」で期限を振ると次のようになる(既定は 30 日、設定可能な範囲は 1 日から 365 日)。

| 有効期限 | アクティブ割合 | S3 + S3 Files の月額 | 備考 |
|---|---|---|---|
| 1 日 | 3% | $4,384.31 |  |
| 3 日 | 10% | $4,823.76 |  |
| 7 日 | 23% | $5,702.67 |  |
| 30 日 | 100% | $10,756.38 | 既定値 |
| 90 日 | 100% | $10,756.38 |  |

期限を詰めれば下がるが、期限外のファイルを読むとバケットからの取り込みが再度発生する。読み取りの時間的な偏りが小さいワークロードでは、期限を詰めても取り込みの往復で戻ってくる。

しきい値のほうも同じ構造を持つ。しきい値を上げれば小さくないファイルも低レイテンシで読めるが、その分が高性能ストレージの課金対象になる。この列の安さは、しきい値を超えるファイルが S3 のレイテンシで読まれることと引き換えである。

### 既に FSx for ONTAP がある場合の増分

この構成が対象とする状況では、利用側が NFS / SMB を要求するため FSx for ONTAP は既にある。そこに S3 の受け口を足すときの比較は、グリーンフィールドの「S3 か FSx for ONTAP か」ではなく「増分としてどちらが安いか」になる。

前提は上の「車載 / IoT テレメトリ — 小オブジェクト高頻度」と同じ (3 億オブジェクト / 月、64 KiB)。SSD とスループットは既存ワークロードのために既に払っているものとして、増分だけを並べる。

| 増分 | 内訳 | 月額 |
|---|---|---|
| S3 AP を足す | S3 AP 経由 PUT のみ | $324.00 |
| S3 バケットと同期ジョブを足す | S3 保存 + S3 PUT + 同期の読み出し GET + DataSync 転送 | $1,865.73 |
| 差 |  | **$1,541.73** |

S3 AP はアクセスポイント自体に時間課金がないため、増分はリクエスト課金に集約される。同期ジョブ側の増分には、同じバイト列を 2 系統で持つ保存料金が含まれる。この差は容量が増えても縮まらない。

## 費用に現れない価値と、その裏返し

FinOps の判断は請求書の金額だけでは閉じない。
同じ金額でも得られるものが違うなら、比較は金額だけでは足りない。
得るものと引き換えに手放すものを同じ粒度で並べる。

| 得るもの | 内容 | 費用への効き方 |
|---|---|---|
| 鮮度 | 書いた時点でボリューム上にある。同期ジョブの周期がそのまま遅延になる構造がなくなる | 金額には出ない。要件として鮮度がある場合、代替案は周期を短くする必要があり、その分だけ転送とリクエストが増える |
| 単一の正本 | 同じバイト列を 2 系統で持たない。削除は 1 回で済む | 二重容量が消える。差分が開き続ける構造そのものがなくなる |
| 書き込み経路の集約 | 書き込みが Origin 側の S3 Access Point に集約される。認可は AWS 側と ONTAP 側の両方が許可する形になる | 棚卸しの工数。請求書には出ない。**監査ログに記録されるのはアクセスポイントに固定した識別情報で、呼び出し元の IAM プリンシパルではない。** 主体別の追跡が要件なら、アクセスポイントの分割か AWS CloudTrail との突き合わせを見積りに含める |
| 運用対象の削減 | 同期の失敗検知、部分失敗の再実行、リネームと削除の伝播確認が定常業務から外れる | 請求書には出ない。人的コストと障害時の判断コスト |
| ONTAP のデータ管理機能が収集直後のデータに効く | 収集したデータをそのまま Snapshot で保護し、FlexClone で検証用に複製し、SnapMirror で複製できる | 追加ライセンスなし。同等のことを S3 側の機構で組むと別の課金項目になる |
| 検証用の複製が容量を積まずに作れて、しかも S3 から読める | ファイル単位クローンは同じアクセスポイントに新しいキーとして現れ、ボリューム単位クローンは自分のアクセスポイント・自分のポリシーを持てる。**どちらもブロックを共有する**（実測: 論理 1,350,942,720 B / 物理 277,200,896 B） | 複製の本数だけ容量を積まない。S3 側で同じことをすると複製ごとに保管料金とコピーのリクエスト料金がかかる。詳細は[FlexClone は 3 つめの効率化機構](#flexclone-は-3-つめの効率化機構) |
| 複製に別の認可境界を与えられる | ボリューム単位クローンには別のアクセスポイントを取り付けられるので、識別情報とポリシーを親と分けられる。クローンへの書き込みは親に現れない（実測） | 請求書には出ない。同じ分離を S3 側で作ると、別バケットか別プレフィックスに実体をコピーすることになる |
| 配布量の抑制 | FlexCache は要求されたブロックだけを Origin から引く。全量を拠点へ置かない | 配布側の SSD が Origin の 1 割程度で足りる。全量コピーとの差は[算定](#算定)の配布側の表にある |

| 手放すもの | 内容 |
|---|---|
| S3 固有機能 | イベント通知、ライフサイクル、バージョニングは対象外。ポーリングか ONTAP ネイティブ監査ログで代替を設計する。**FPolicy は代替にならない**（AP 経由の書き込みは通知されない。実測 2026-08-26） |
| フラットな名前空間の自由度 | オブジェクト名に制約がある。NAS フレンドリでない名前を多用するワークロードには向かない |
| 帯域の弾力性 | スループットキャパシティを事前に選ぶ。S3 のように要求に応じて伸びるわけではない |
| ストレージクラスの選択肢 | 取り出し課金と引き換えに保存単価を大きく下げるモデルはない。階層はキャパシティプールの 1 つだけ |
| 配布側でのオブジェクトアクセス | Cache 側で S3 API は提供しない |
| Cache 側での階層化 | Cache ボリュームは階層化できない。作業セットが膨らむとそのまま SSD の費用になる |
| キャッシュミスの局所性 | ミスは Origin まで取りに行く。Origin のスループットと、AZ やリージョンを跨ぐ場合の転送料金を消費する |

前半 4 行はいずれも請求書に出ない。
費用だけで比較すると、大きいオブジェクトを低頻度で扱うワークロードでは差が小さく見える。
その場合に選ぶ根拠は後半の表と前半の表の突き合わせにある。

## S3 Files を選ぶ場合の仕様

前節の試算で S3 Files が安く出るワークロードがある。
金額だけで選ぶと判断を誤るので、費用に現れない仕様上の制約をここに集める。
以下はすべて AWS のドキュメント記載であり、この構成での実測ではない。

### 対応プロトコルとバージョンの対比

ファイルで配る設計では、利用側が話せる NFS のバージョンが選択肢を決める。
3 つの選択肢で対応範囲が違う。

| 選択肢 | 対応プロトコル | 出典 |
|---|---|---|
| FSx for ONTAP (Origin / Cache) | NFS v3、v4.0、v4.1、v4.2 と SMB。NVMe と iSCSI も使える | [FSx for ONTAP の仕組み](https://docs.aws.amazon.com/fsx/latest/ONTAPGuide/how-it-works-fsx-ontap.html) |
| S3 Files | NFSv4.1 と NFSv4.2。**NFSv3 と SMB は対象外** | [非対応事項とクォータ](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-files-quotas.html) |
| Amazon EFS (S3 Files の基盤) | NFSv4.0 と NFSv4.1 | [EFS とは](https://docs.aws.amazon.com/efs/latest/ug/whatisefs.html) |

S3 Files は EFS を基盤にしているが、対応バージョンは一致しない。
EFS が持つ v4.0 は対象外で、代わりに v4.2 が入っている。
基盤が同じだからといってバージョンを推測せず、それぞれのドキュメントで確認する。

NFSv3 で固定された装置がある場合、この差がそのまま選択肢の絞り込みになる。
SMB を使う工程がある場合も同様で、FSx for ONTAP 以外は候補から外れる。

### プロトコルと利用側の前提

| 項目 | 内容 | 出典 |
|---|---|---|
| 対応プロトコル | NFSv4.1 と NFSv4.2。**NFSv3 と SMB は対象外** | [非対応事項とクォータ](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-files-quotas.html) |
| ロック | すべて advisory。mandatory locking と deny share は非対応 | 同上 |
| NFS ACL | 非対応。POSIX 権限ビットは対応する | 同上 |
| Kerberos | 非対応。AD 統合を前提とした認証は持ち込めない | 同上 |
| `nconnect` | 非対応。マウントオプションでの多重接続チューニングができない | 同上 |
| マウント方法 | EC2 ではマウントヘルパー (`amazon-efs-utils`) が必要。`s3files` タイプでマウントする | [マウント手順](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-files-mounting.html) |
| 対応コンピュート | EC2、Lambda、EKS、ECS | [S3 Files の概要](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-files.html) |
| VPC | ファイルシステムあたり 1 VPC、AZ あたりマウントターゲット 1 つ | [非対応事項とクォータ](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-files-quotas.html) |

SMB と NFSv3 が対象外である点は、この構成が対象とする状況に直接効く。
既存の Windows 工程や、NFSv3 で固定された装置は利用側になれない。

### 同期の遅延

| 方向 | 挙動 | 出典 |
|---|---|---|
| バケット → ファイルシステム | S3 イベント通知を監視し、**通常は数秒**で反映される。ただし反映されるのは高性能ストレージに現在データがあるファイルに限る。期限切れで追い出されたファイルは、次にアクセスするまで更新されない | [同期の仕組み](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-files-synchronization.html) |
| ファイルシステム → バケット | 書き込みが止まってから **約 60 秒**待って、まとめてエクスポートする | [性能仕様](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-files-performance.html) |

エクスポート側の 60 秒は待ち時間ではなく**書き込みの無活動時間**である。
ドキュメントの例では、30 秒ごとに 5 分間追記し続けるアプリケーションのエクスポートは 6 分目に始まる。
追記が続いている間はバケットに出ない。ログのように書き込みが途切れないファイルでは、
S3 API 側から見た鮮度がこの分だけ遅れる。

収集を S3 API で行い、利用側が読み取りだけを行うのであれば、効くのはインポート側の数秒である。
利用側が書き戻す設計にすると、エクスポート側の 60 秒が下流の鮮度になる。

| 同期のレート上限 | 値 | 出典 |
|---|---|---|
| インポート | 1 ファイルシステムあたり 2,400 オブジェクト/秒、700 MB/秒 | [性能仕様](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-files-performance.html) |
| エクスポート | 1 ファイルシステムあたり 800 ファイル/秒、2,700 MB/秒 | 同上 |

変更が同期レートを超えると、キューに積まれて順に処理される。
`PendingExports` の増加がその状態を示す ([ベストプラクティス](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-files-best-practices.html))。

### 計上している項目

S3 Files の金額が保存料金だけに見えることがあるので、内訳を明示する。
オブジェクトが大きいと**リクエスト回数が少ないため金額に出ない**が、計上はしている。

| 項目 | しきい値以下のファイル | しきい値を超えるファイル |
|---|---|---|
| S3 Standard の保存 (正本はバケットに残る) | 計上 | 計上 |
| S3 の PUT (収集) | 計上 | 計上 |
| S3 の GET | 計上。初回読み出しはバケットからストリームされ、これが取り込みの契機になる | 計上。すべての読み出しがバケットからのストリーム |
| S3 Files 高性能ストレージ | 計上。アクティブ分のみ | 発生しない。データは載らない |
| S3 Files 書き込み | 計上。取り込み（データ + メタデータ） | 計上。メタデータのみ |
| S3 Files 読み取り | 計上。取り込み後の読み出しとメタデータ | 計上。メタデータのみ |

1 MiB 以上の読み出しは、データが高性能ストレージにあっても
バケットから直接ストリームされ、ファイルシステム側のデータ課金は発生しない ([計測の仕組み](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-files-metering.html))。
大きいオブジェクトの試算が保存料金に寄るのはこの仕様による。

**計上していないもの**があるので、そのまま見積りに使わない。

| 未計上の項目 | 内容 |
|---|---|
| メタデータの保管 | ファイルのメタデータは高性能ストレージ上に置かれ、データが期限切れになっても消えない ([同期の仕組み](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-files-synchronization.html))。オブジェクト数に比例して積み上がる。1 件 4 KiB として 3 億件なら約 1,144 GiB、最小課金サイズ 10 KiB が適用されるなら約 2,861 GiB に相当する。どちらの基準で課金されるかはドキュメントに明記されていないため、金額を断定せず項目として示す |
| 非現行バージョンの保管 | S3 バージョニングが必須なため積み上がる。ライフサイクルでの失効設計が別に必要 |
| 大きい読み出しの分割 | 1 回の読み出しが内部で複数の GET に分かれる場合、GET 回数は試算より増える。分割の粒度はドキュメントに記載がない |
| リージョン間のデータ転送 | 同一リージョンを前提にしている |

### 一貫性と競合

| 項目 | 内容 | 出典 |
|---|---|---|
| 競合時の正本 | バケットが正本。ファイルシステム側とバケット側が同じファイルを同時に変更すると、ファイルシステム側は lost and found ディレクトリに移される | [ベストプラクティス](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-files-best-practices.html) |
| 推奨 | 書き込み経路をファイルシステムかバケットの片方に固定する | 同上 |
| バージョニング | リンクするバケットで **S3 バージョニングが必須**。ファイルシステム側の変更は新しいバージョンとして書かれる | [同期の仕組み](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-files-synchronization.html) |

バージョニングが必須である点はコストに関わる。
非現行バージョンの保管料金が積み上がるため、ライフサイクルでの失効設計が必要になる。
`chmod` や `chown` も新しいバージョンを作る。本文の試算にはこの分を含めていない。

### 名前空間と構造の制約

この構成の[S3 AP 設計ガイド](../limits/s3ap-design-guide.md)で扱っている論点と重なる。

| 項目 | 値 | 出典 |
|---|---|---|
| パス構成要素 | ディレクトリ名・ファイル名は 255 バイトまで | [非対応事項とクォータ](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-files-quotas.html) |
| オブジェクトキー | 全体で 1,024 バイトを超えるとエクスポートできない | 同上 |
| POSIX にできないキー名 | `foo//bar`、`foo/./bar`、`foo/../bar`、ヌルバイトを含むキーはアクセスできない | 同上 |
| ハードリンク | 非対応 | 同上 |
| ディレクトリ深さ | 1,000 段まで | 同上 |
| リネームと移動 | S3 にリネームがないため、プレフィックス配下の全オブジェクトをコピーして削除する。10 万ファイルのディレクトリのリネームはバケットに反映されるまで数分かかる | [同期の仕組み](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-files-synchronization.html) |
| 大きなプレフィックス | リネームに最大 4 時間かかる規模 (約 1,200 万オブジェクト) のプレフィックスを指定するとエラーになる。`--AcceptBucketWarning` で回避する | 同上 |

同じフォルダーに大量のオブジェクトを平置きすると、リネームと初回一覧が重くなる。
これは受け口を S3 AP にする場合と同じ論点で、どちらを選んでもディレクトリ設計は必要になる。

### ストレージクラスとの関係

| 項目 | 内容 | 出典 |
|---|---|---|
| アーカイブ系 | S3 Glacier Flexible Retrieval、S3 Glacier Deep Archive、Intelligent-Tiering のアーカイブ層とディープアーカイブ層のオブジェクトは、**ファイルシステムから読めない**。先に S3 API で復元する必要がある | [非対応事項とクォータ](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-files-quotas.html) |
| S3 ACL | ファイルシステム側で変更すると保持されない | 同上 |

アーカイブ系が読めない点は、費用設計の自由度に効く。
保存単価を下げるためにアーカイブ層へ落とすと、ファイルとしては読めなくなる。
S3 Files を配布経路にする場合、ファイルで読ませたいデータは Standard 系に置き続けることになる。

### この構成側の対応する制約

比較を片側だけ厳しく書かないために、同じ粒度でこちらの制約も挙げる。

| 項目 | 内容 |
|---|---|
| 収集層の対応オペレーション | S3 の全機能は使えない。イベント通知・ライフサイクル・バージョニングは対象外 ([上限値](../limits/s3-access-point.md)) |
| 配布層の書き込み | Cache は書き込み可能。既定の write-around は Origin 確定後に応答するため遅延が大きい。write-back は非同期で速いが上の条件が付く |
| 配布層の階層化 | Cache ボリュームは階層化できない |
| 配布層でのオブジェクトアクセス | Cache 側で S3 API は提供しない |
| 収集層の前提バージョン | ONTAP 9.17.1 以降 |
| 固定費 | スループットキャパシティと SSD の下限を毎月負う |

## 配布側での書き込み — FlexCache の 2 つのモード

Cache ボリュームは読み取り専用ではない。書き込みができる。
モードが 2 つあり、既定と選択肢で鮮度と遅延の出方が変わる。

| モード | 挙動 | 出典 |
|---|---|---|
| write-around (既定) | 書き込みは Cache から Origin へ転送される。Origin がストレージに確定して応答を返すまでクライアントに応答しない。ネットワークを往復するため write-back より遅延が大きい | [FlexCache での複製](https://docs.aws.amazon.com/fsx/latest/ONTAPGuide/using-flexcache.html) |
| write-back (ONTAP 9.15.1 以降) | 書き込みを Cache 側で確定してクライアントに即座に応答し、Origin へは**非同期**に書く。ローカルに近い速度で書ける | 同上 |

AWS のドキュメントは、書き込みが多く低遅延が要るワークロードには write-back、
読み取り中心で遅延に敏感でない場合や Origin ボリュームが 10 を超える場合には write-around を挙げている。
作成時に `-is-writeback-enabled true` を指定するか、
`volume flexcache config modify -is-writeback-enabled` で後から変更する
(advanced 権限が必要) ([FlexCache の作成](https://docs.aws.amazon.com/fsx/latest/ONTAPGuide/create-flexcache.html))。

鮮度の観点では、既定の write-around が持つ性質が重要である。
Origin が確定してから応答するため、**Cache 側の書き込みが Origin に無い時間帯が生じない**。
非同期のバッチを待つ構造ではないので、正本側から見た遅れが発生しない。
遅延と引き換えに鮮度を取る設計である。

### write-back を使う場合の条件

有効にすると条件が増える。費用ではなく設計の制約なのでここに集める。

| 項目 | 内容 | 出典 |
|---|---|---|
| ONTAP バージョン | 9.15.1 以降で利用可能。ただし 9.17.1P1 で重要な改善が入っており、Origin と Cache の両方でそれ以降を強く推奨。9.15.1 は本番向けに推奨されない | [write-back のガイドライン](https://docs.netapp.com/us-en/ontap/flexcache-writeback/flexcache-write-back-guidelines.html) |
| 構成 | Cache ボリューム全体を単一コンスティチュエントで構成することが推奨。マルチコンスティチュエントは意図しない退避を招く | 同上 |
| 検証済みの範囲 | 100 GB 未満のファイルと、Cache と Origin 間の WAN 往復 200 ms 以内でテストされている | 同上 |
| リネーム | ファイルのリネームは Cache から退避される。ダーティデータを Origin へ流し切るまで他の操作ができない | 同上 |
| 変更できる属性 | Cache 側で設定できるのはタイムスタンプ、モードビット、NT ACL、所有者、グループ、サイズ。それ以外は Origin へ転送され、退避を招く場合がある | 同上 |
| Origin のスナップショット | Origin でスナップショットを取ると、関連する全 write-back Cache から未処理のダーティデータを回収する。書き込みが多いと複数回の再試行が必要になる | 同上 |
| SMB | write-back 有効の Cache では、書き込みの SMB Opportunistic Lock (oplock) が非対応 | 同上 |
| Origin の空き容量 | Origin ボリュームの空きが 20% 以下になると自動的に write-around へ切り替わる。閾値は Origin の報告値とアグリゲートの物理空き容量の両方で評価されるため、オーバープロビジョニングしていると想定より早く切り替わる | 同上 |
| ネットワーク | 帯域が細い、あるいはロスのあるクラスタ間ネットワークは write-back 性能に強く影響する | 同上 |
| Origin 側のリソース | Origin の各ノードに 128 GB RAM と 20 CPU 以上が強く推奨される。FSx for ONTAP のスケールアップ構成では SSD 1,024 GiB 以上が基準として挙げられている | [TCO 事例](https://aws.amazon.com/blogs/storage/how-a-customer-reduced-storage-tco-by-28-with-amazon-fsx-for-netapp-ontap/) |
| ライセンス | write-back を含め FlexCache に追加ライセンスは不要 | 同上 |
| ピアリング | Origin と Cache のクラスタ間ピアリングと、FlexCache オプション付きの SVM ピアリングが必要 | 同上 |

この構成が収集を S3 AP で Origin に集約し、配布側を読み取り中心として説明しているのは、
Cache に書き込み機能がないからではない。上の条件を負わずに済むからである。
配布側で書き込みが多い要件があるなら write-back は選択肢に入る。
その場合はバージョン要件と Origin 側のリソースを見積りに含める。

## 周辺ワークロードへの影響

収集の受け口を足すことは、既存の NFS / SMB ワークロードに影響する。
費用はこの影響を吸収するために動くので、リクエスト単価だけを見ると判断を誤る。

| 影響 | 内容 | 費用への出方 |
|---|---|---|
| スループットキャパシティの共有 | S3 AP のリクエストも NFS / SMB のトラフィックも、同じファイルシステムのスループットキャパシティから出る | ヘッドルームが足りなくなると 1 つ上げることになる。Single-AZ 第一世代で 128 から 256 MBps へ上げると月額 +$115.97 |
| 並行度の上げすぎ | 姉妹リポジトリの実測では 128 MBps のファイルシステムに対して並行度 25 で P99 894 ms、並行度 50 で P99 1,703 ms まで伸びた | 遅延は同じファイルシステムを使うファイルクライアントにも及ぶ。並行度を上げて解決しようとすると逆方向に働く |
| IOPS の共有 | SSD 1 GiB あたり 3 IOPS が込み。小さいオブジェクトを大量に書く収集は IOPS を消費する | 込みの範囲を超えると追加 IOPS の課金が発生する |
| 階層化と読み出しの衝突 | キャパシティプールの読み取りリクエストは S3 AP 経由の GET より単価が高い | 保存料金を下げるために積極的に階層化すると、読み出しが多いデータではリクエスト側で戻る |
| 配布側 (FlexCache) の費用 | Cache は別のファイルシステム、または別プラットフォーム。階層化できないため全量 SSD | AWS 内に置くなら固定費の下限がもう 1 つ増える。小さい Origin では Cache が SSD 1 TiB の下限に張り付く。オンプレミスならそのプラットフォームの費用になる |
| キャッシュミスが Origin に返る | Cache に無いブロックの読み出しは Origin へ行く | Origin のスループットを消費する。作業セットに対して Cache が小さすぎると、ミス率が上がって Origin 側の増強につながる |
| バックアップ容量 | 収集量が増えればバックアップ対象も増える | バックアップストレージの GB-Mo が連動して増える |
| スナップショット | 高頻度の書き込みと削除はスナップショットが保持するブロックを増やす | SSD の消費が増え、SSD のプロビジョニング量に跳ね返る |

最初の 2 行が実務でいちばん効く。収集を足した結果として配布側の遅延が悪化し、
その対処としてスループットを 1 つ上げると、リクエスト単価で得た差が相殺されることがある。
収集と配布を同じファイルシステムに載せる設計では、
スループットのヘッドルームを費用項目として最初から見積りに入れる。

## ライセンス

| 項目 | 扱い | 出典 |
|---|---|---|
| ONTAP のデータ管理機能 | FlexCache、SnapMirror、Snapshot、FlexClone、重複排除と圧縮は FSx for ONTAP の料金に含まれる。別途のライセンス調達はない | FlexCache については AWS Storage Blog が「included with your ONTAP purchase ... No extra license is required」と記載 ([出典](https://aws.amazon.com/blogs/storage/how-a-customer-reduced-storage-tco-by-28-with-amazon-fsx-for-netapp-ontap/)) |
| SnapLock | 独立したライセンス項目。AWS Storage Blog はコスト構成要素を「SSD storage, SSD IOPS, Capacity Pool usage, throughput capacity, backups, and SnapLock licensing」と列挙し、請求レポートにも SnapLock usage が GB-Month で現れる | [サイジング](https://aws.amazon.com/blogs/storage/how-to-size-an-amazon-fsx-for-netapp-ontap-file-system/) と [請求レポート](https://docs.aws.amazon.com/fsx/latest/ONTAPGuide/FSxONTAP-Billing.html) |
| S3 AP そのもの | アクセスポイント単位の時間課金はない。課金はリクエストとデータ転送 | [FSx for ONTAP 料金](https://aws.amazon.com/fsx/netapp-ontap/pricing/) |
| 配布側が FSx for ONTAP 以外の場合 | オンプレミス ONTAP などに Cache を置くなら、そのプラットフォームのライセンスと保守が別に載る | [移植性](../../portability.md) |

コンプライアンス保持が要件なら、SnapLock を独立した項目として見積もる。
本文の試算には含めていない。東京リージョンの単価は Price List API から取得できなかったため、
数値を書かずに項目の存在だけを示す。

固定費の置き場所は方式ごとに違う。ゲートウェイや FUSE を挟む方式では、
ソフトウェアのライセンスと常時稼働のインスタンスが恒久的な費用になる。
この構成では、スループットキャパシティを事前に確定させることが同じ役割を果たす。
どちらも固定費を持たずに済む方式ではなく、置き場所が違うだけである。

## コストの可視化

Cost Explorer で追うときの usage type を挙げる。プレフィックスは東京リージョンの `APN1-` で、
他リージョンでは変わる。

| 見たいもの | サービス | usage type |
|---|---|---|
| SSD ストレージ (Single-AZ 第一世代) | FSx for ONTAP | `APN1-Storage.SAZ_2N:SSD` |
| SSD ストレージ (Single-AZ 第二世代) | FSx for ONTAP | `APN1-Storage.SAZ_2N2:SSD` |
| SSD ストレージ (Multi-AZ 第一 / 第二世代) | FSx for ONTAP | `APN1-Storage.MAZ:SSD` / `APN1-Storage.MAZ2:SSD` |
| スループットキャパシティ (Single-AZ 第一 / 第二世代) | FSx for ONTAP | `APN1-ThroughputCapacity.SAZ_2N` / `APN1-ThroughputCapacity.SAZ_2N2` |
| 追加 SSD IOPS (Single-AZ 第一世代) | FSx for ONTAP | `APN1-ProvisionedSSDIOPS.SAZ_2N` |
| キャパシティプールストレージ | FSx for ONTAP | `APN1-Storage.SAZ_2N:CPoolStd` |
| キャパシティプールの読み / 書き | FSx for ONTAP | `APN1-Requests.SAZ_2N:CPoolStdRd` / `APN1-Requests.SAZ_2N:CPoolStdWr` |
| バックアップ | FSx for ONTAP | `APN1-BackupUsage` |
| **S3 AP 経由の PUT / COPY / POST / LIST** | **S3** | `APN1-Requests-FSXONTAP-Tier1` |
| **S3 AP 経由の GET およびその他** | **S3** | `APN1-Requests-FSXONTAP-Tier2` |

太字の 2 行に注意が要る。S3 AP 経由のリクエストは FSx for ONTAP ボリューム宛でありながら
**Amazon S3 の請求として計上される**。サービスを FSx for ONTAP だけに絞ったレポートでは、
収集経路の費用が抜け落ちる。収集の費用を追うには、FSx for ONTAP の usage type と
S3 側の `FSXONTAP` を含む usage type を同じレポートに入れる。

## 削減レバー

| レバー | 効く条件 | 副作用 |
|---|---|---|
| オブジェクトをまとめて大きくする | リクエスト課金が保存料金を上回っている | 利用側の読み出し単位と合わなくなる。粒度を落としすぎると再取得が増える |
| 階層化の閾値を下げる | 読み出しが稀なデータの割合が大きい | キャパシティプールの読み取りリクエストが増える。読み出しが多いデータでは逆効果 |
| スループットを実測で右サイズする | 過剰にプロビジョニングしている | 刻みで下がるので、下げすぎると既存の NFS / SMB が影響を受ける |
| ストレージ効率を有効にする | 圧縮と重複排除が効くデータ | 既に圧縮された素材では効果がない |
| 保持期間を短くする | 保持要件に余地がある | 監査要件と衝突しうる |
| Single-AZ を選ぶ | 可用性要件が単一 AZ で足りる | AZ 障害で停止する。DR は別に設計する。優先 AZ 以外からのアクセスに転送料金がかかる |
| 第一世代を選ぶ | 第二世代の上限に用がない | デプロイタイプは変更できないため、後から上限が必要になると移行作業が発生する |
| 収集を S3 AP に寄せて同期ジョブを畳む | 同期ジョブが定常運用にある | S3 固有機能を使っていた場合は代替が要る |
| Cache を作業セットでサイジングする | 配布側が全データを必要としていない | 小さすぎるとミス率が上がり、Origin のスループットを消費する |
| Cache 側を Single-AZ にする | Cache は Origin から再構築できる | 再構築の間は配布が止まる。復旧手順を用意する |
| Cache 側のバックアップを取らない | Cache が正本ではない | Origin 側のバックアップ設計が前提になる |

最後のレバーには費用に現れない分もある。同期ジョブの監視、部分失敗の再実行、
削除の伝播の確認が運用項目から消える。この分は請求書に出ないが、
FinOps の対象は請求書だけではない。

## この構成が費用面で向かない条件

| 条件 | 理由 |
|---|---|
| 平均オブジェクトサイズが大きく、リクエストが少ない | リクエスト単価の差が効かない。費用差は小さく、選ぶ根拠は運用面に移る |
| 利用側が S3 API で足りる | FSx for ONTAP の固定費を負う理由がない |
| 長期保持が中心で読み出しが稀 | Glacier 系の保存単価と取り出し課金のモデルのほうが合う |
| データ量が小さい | 月額下限を回収できない |
| S3 固有機能が要る | イベント通知、ライフサイクル、バージョニングは対象外 ([上限値](../limits/s3-access-point.md)) |
| 配布側で S3 API が要る | この構成は提供しない ([代替案との比較](alternatives.md)) |
| 利用側が AWS 上の Linux コンピュートに限られ、大きいオブジェクトを読む | S3 Files のほうが安く出る。固定費の下限がなく、しきい値超のファイルはバケットから直接ストリームされるため |

## 前提と限界

| 項目 | 内容 |
|---|---|
| 単価の範囲 | 東京リージョン、オンデマンド、税別。Savings Plans、私的価格、無料利用枠は含まない |
| 単価の取得元 | AWS Price List API。適用開始日は単価表の `effective` 列 |
| 使用量 | すべて仮定。試算であって実測ではない |
| ストレージ効率 | SSD 層は AWS 公表のワークロード別の値を当てている。キャパシティプール層は SSD 層の 50% と仮定しており、これは出典のある値ではない（[ストレージ効率の扱い](#ストレージ効率の扱い)） |
| Cache 比率 | Origin 論理データに対する割合として仮定。既定は 10% で、NetApp のサイジング指針の下限と作成時の既定値に合わせている。比較用に 20% も併記する |
| S3 Files のしきい値と有効期限 | 既定値 (128 KiB、30 日) を仮定。どちらも設定可能で、費用とレイテンシの両方を動かす |
| S3 Files のバージョニング | 必須だが、非現行バージョンの保管料金は試算に含めていない |
| S3 Files のメタデータ保管 | 高性能ストレージ上に残り続けるが、課金の基準がドキュメントに明記されていないため試算に含めていない。オブジェクト数が多い構成では無視できない |
| S3 Files の利用可否 | 利用側が AWS 上の Linux コンピュートでマウントヘルパーを入れられるかどうかで、ワークロードごとに判断している |
| Cache の可用性構成 | Single-AZ を仮定。Cache は Origin から再構築できるという前提に基づく |
| 試算に含めない項目 | SnapLock、追加 SSD IOPS、スナップショット予約、リージョン間データ転送、Direct Connect のポート料金、オンプレミス側の機器とライセンス |
| データ転送 | 読み取り側の試算には含めている。単価はインターネット向けの段階単価で、Direct Connect の場合は定額。オンプレミス側の回線費用は含まない |
| キャッシュの再取得率 | 作業セットに対する割合として仮定。読み取り中心の参照系では妥当な範囲として扱っているが、実機で測った値ではない。実際の値は変更頻度と退避の設定で決まる |
| 作業セットの割合 | データセット全体の 1 割として仮定。同じく妥当な範囲として扱っているが実測ではない。この割合が大きくなるほどキャッシュの利点は薄れ、全量コピーとの差が縮む |
| 遅延の値 | 姉妹リポジトリ [FSx-for-ONTAP-S3AccessPoints-Serverless-Patterns](https://github.com/Yoshiki0705/FSx-for-ONTAP-S3AccessPoints-Serverless-Patterns) の実測。環境が違えば変わる |
| 再計算 | `make finops-write`（`python3 tools/finops_model.py --write`） |

単価は変わる。この文書の数値をそのまま見積りに使う前に、
`python3 tools/finops_model.py --show-prices` で現在の想定を確認し、
Price List API と突き合わせる。
