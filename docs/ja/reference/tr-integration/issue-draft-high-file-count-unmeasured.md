## 起票タイトル案

`[measurement] 高ファイル数ワークロードのメタデータ・列挙・FlexCache 複製コストの計測`

## 本文案

### 背景

NetApp ONTAP の High File Count NAS Workloads の Technical Report は、inode 容量や単一ディレクトリの
最大サイズが列挙コストに関わることを示唆している。一方、この構成
（S3 API 収集 → Amazon FSx for NetApp ONTAP（以降 FSx for ONTAP）の origin ボリューム → FlexCache で NFS / SMB 配布）で
公開済みのスループット測定は、スループット・IOPS・並列度を対象としており、ファイル数が多いときの挙動とは
別の軸である。この Issue は、その未計測の軸を追跡する。

### 計測対象

| # | 計測対象 |
|---|---|
| 1 | 高ファイル数時のメタデータ操作（大量ファイルの生成・列挙・stat）の性能 |
| 2 | 大量のファイルを含むディレクトリの列挙（`ListObjectsV2`、NFS / SMB のディレクトリ走査）にかかる時間 |
| 3 | 高ファイル数時の FlexCache のメタデータ複製コスト（origin からキャッシュへメタデータが複製される際のコストがファイル数にどう比例するか） |

### 未計測の理由

公開済みの Part 2 ブログおよびこの repo の検証記録は、スループット・IOPS・並列度を対象に測定した
ものであり、高ファイル数のメタデータ操作・列挙・FlexCache メタデータ複製コストは測定対象に含めて
いない。これらは throughput 測定とは直交する軸であり、実測値が存在しない。実測値がないため、
性能主張としては記述せず、未計測事項として追跡する。

### 将来の計測条件（計測を実施できると判断する前提条件）

| 前提条件 |
|---|
| 十分なファイル数を持つ origin ボリュームを用意できること（高ファイル数の負荷を再現できる規模） |
| その origin 上でメタデータ操作（生成・列挙・stat）を計測する環境を構築できること |
| FlexCache の origin / cache 間でメタデータ複製コストを観測できる計測手段があること |
| 測定時に環境 7 項目（測定日・リージョン・ONTAP バージョン・ファイルシステム構成・オブジェクトサイズ・並列度・測定対象）を記録できること |

これらの前提が満たされた時点で計測を実施し、結果が得られたら「## まだ測っていないこと」節の該当
項目を実測値へ更新する。
