# いま動いているものからの移り方（3 つの出発点）

**置き換えの話ではありません。** すでに動いているものを止めずに、**どこだけを足すと
「収集は S3、利用は NFS / SMB」が成立するか**を書きます。

3 つの出発点を扱います。どれも実在する構成で、**それぞれに「足さないほうがよい条件」を
最後に書いてあります**。そこに当てはまるなら、いまの構成のままがよい選択です。

| 出発点 | いちばん効く差 | 足さないほうがよい条件 |
|---|---|---|
| [ファイル → S3 のコピージョブがある](#1-ファイル--s3-のコピージョブがある構成) | コピージョブが要らなくなる（**データの移動自体は残る**） | 鮮度がジョブ間隔で足りていて、二重容量が問題になっていない |
| [Amazon EFS で NFS を提供している](#2-amazon-efs-で-nfs-を提供している構成) | 収集を S3 API で受けられる。SMB と NFSv3 が使える | 利用側が AWS 上の Linux だけで、NFSv4 で足りている |
| [S3 を正本にしたパイプラインがある](#3-s3-を正本にしたパイプラインがある構成) | 既存の NAS 前提のアプリと装置を変えずに読める | 読み手も S3 API に寄せられる。または利用側が AWS 上の Linux に限られる |

## 1. ファイル → S3 のコピージョブがある構成

NAS が正本で、分析や配布のために AWS DataSync・rsync・robocopy・自作 ETL で S3 へ複製している
構成です。**この構成の代償は 4 つに分解できます** — 鮮度がジョブ間隔に固定される、同じバイト列に
2 系統の課金、権限が POSIX / NTFS ACL と IAM に分岐する、そして同期の失敗検知と再実行が
恒久的な運用項目になること。

**変わらないもの**: 利用側のアプリと装置。プロトコルも、マウントパスも、権限の見え方も
そのままです。**収集側の受け口が S3 API に変わるだけ**で、利用側からは同じファイルに見えます。

**足すもの**:

| 足すもの | 役割 |
|---|---|
| FSx for ONTAP の Origin ボリューム | 正本。ここに S3 Access Point を付ける |
| S3 Access Point | 収集の受け口。**S3 API で書く側の変更はここだけ** |
| FlexCache（利用拠点ごと） | 読み手の近くに、**読まれた分だけ**置く |

**コピージョブは無くなります。データの移動は無くなりません。** FlexCache は読まれたブロックを
Origin から引くので、**初回の読み取りには代価があります**（実測で常駐時の 2.88 分の 1。
ただし Cache 側の指定値が天井になる構成ではこの差が +1.5% まで縮みました）。
「コピーが消える」ことと「転送が消える」ことは別です。

**足さないほうがよい条件**:

- **鮮度がジョブ間隔で足りている。** DataSync のスケジュールは 1 時間より短くできませんが、
  それで困っていないなら、この構成に移る理由は鮮度からは出ません
- **二重容量が問題になっていない。** 対象が小さい、または片方を短期で捨てているなら
  費用面の動機も弱いです
- **収集側が S3 API に寄せられない。** 書く側を変えられないなら、受け口を S3 にする前提が崩れます
- **権限を単一の根拠で示したい。** **この構成でも解決しません。** 2 系統（コピー元とコピー先）が
  2 層（AWS 側とファイルシステム側）に変わるだけです

## 2. Amazon EFS で NFS を提供している構成

利用側が AWS 上の Linux で、マネージドな NFS を使っている構成です。**運用の手間は少なく、
容量は自動で伸びます。** 効いている制約は別のところにあります。

**変わらないもの**: NFS で読むという形。**利用側が AWS 上の Linux で NFSv4 で足りているなら、
そのままでよい構成です。**

**足すもの**（当てはまる制約がある場合）:

| 制約 | この構成でどうなるか |
|---|---|
| **SMB が必要** | Origin の security style を NTFS にして SMB で配布できる。**ただし Origin 作成前に決める必要があります** |
| **NFSv3 固定の装置がある** | NFSv3 で配布できる |
| **Windows クライアントがある** | SMB 経由で読める |
| **AWS の外に利用側がある** | 拠点側 ONTAP を Cache にできる（**このリポジトリでは未検証**） |
| **収集を S3 API で受けたい** | Origin に S3 Access Point を付けて受けられる |

**この構成の代償も対称に書きます。** 指定値（throughput capacity）を購入する形なので、
**使わなくても課金されます**。容量も**プロビジョニングした分**に課金され、自動では伸びません。
ONTAP 9.17.1 以降が収集層に必要で、FlexCache の作成にはクラスタ / SVM ピアリングという
**このリポジトリが作らない前提**が要ります。

**足さないほうがよい条件**:

- **利用側が AWS 上の Linux だけで、NFSv4 で足りている。** 上の制約に 1 つも当たらないなら、
  運用の手間が増えるだけです
- **容量の変動が大きく、自動で伸びてほしい。** 指定値を先に買う形は向きません
- **ONTAP の運用経験がない。** FlexCache とピアリングは AWS API では扱えず、
  **ONTAP 側の管理面を触ることになります**

## 3. S3 を正本にしたパイプラインがある構成

収集も処理も S3 中心で、**ファイルとして読みたい要求が後から出てきた**構成です。
選択肢は複数あり、**どれが向くかは利用側の形で決まります。**

| 方法 | 向く条件 | 向かない条件 |
|---|---|---|
| S3 のまま、アプリを S3 API に合わせる | 読み手を変えられる | 既存の NAS 前提アプリや装置がある |
| S3 をファイルシステムとしてマウントする（Amazon S3 Files など） | 利用側が AWS 上の Linux コンピュートで、マウントヘルパーを入れられる。**S3 を正本に保てる** | 構成を変えられない装置、SMB、NFSv3、AWS 外の利用側 |
| ゲートウェイ / FUSE | 読み取り中心で、セマンティクスの差を許容できる | ロックや原子的 rename が要る、メタデータ操作が多い |
| **この構成**（S3 で収集 → FlexCache で配布） | **既存の NFS / SMB のまま読みたい。** 必要な範囲だけ拠点に置きたい | S3 固有機能（イベント通知・ライフサイクル・バージョニング）が要る、Cache 側でも S3 API で読みたい |

**「S3 を正本にしたまま」が要件なら、この構成は当てはまりません。** この構成の正本は
FSx for ONTAP の Origin ボリュームで、S3 Access Point はその入り口です。**S3 バケットが
正本である必要があるなら、上の 2 行目か 3 行目を先に検討してください。**

**変わらないもの**: S3 API で書くという形。**書く側のコードは変わりません**（宛先が
アクセスポイントの ARN になります）。

**足すもの**: Origin ボリュームと S3 Access Point、利用拠点ごとの FlexCache。

**足さないほうがよい条件**:

- **S3 のイベント通知・ライフサイクル・バージョニングを使っている。** この経路の外です
- **オブジェクト名が NAS フレンドリでない。** 名前空間に制約があります
- **Cache 側でも S3 API で読みたい。** この構成は提供しません
- **読み手が AWS 上の Linux だけ。** それなら S3 をファイルシステムとしてマウントする方法が、
  大きいオブジェクトでは安く出る場合があります（[費用比較](../comparison/finops-s3-vs-s3ap.md)）

## 選び方の順序

**3 つの出発点のどれでも、判断の順序は同じです。**

1. **利用側のプロトコルを確定する。** NFS なら UNIX、SMB なら NTFS。
   **Origin ボリュームを作る前に決めます**（[最初に決めること](../../design-first-decisions.md)）
2. **利用側が読む範囲を見る。** 全量が要るなら FlexCache の前提（読まれた分だけ置く）が
   合いません。SnapMirror での複製のほうが向きます
3. **Cache 側の指定値を先に決める。** **消費側が見る性能は Cache 側で決まり、Origin を上げても
   変わりません**（実測）
4. **S3 固有機能の要否を確認する。** 要るなら、この構成の外で受けることになります

判断を表から落とすフローチャートは
[この構成を採るかの判断](../decision-trees/choosing-this-architecture.md)、
方式ごとの向く条件・向かない条件の一覧は[代替案との比較](../comparison/alternatives.md)にあります。
