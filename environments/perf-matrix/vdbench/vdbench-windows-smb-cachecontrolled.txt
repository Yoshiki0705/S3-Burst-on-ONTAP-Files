**********************************************************************
* The SMB shapes with the cache-hit ratio controlled.
*
* NOT YET EXECUTED. Two attempts have ended before the first measured
* number, and both are worth reading before a third:
*
*   1. The NFS counterpart filled the volume and was abandoned. Automatic
*      daily backups were on, the backup snapshot held the pre-overwrite
*      blocks, and the volume went 88% -> 100% full. That is closed in
*      template-fsxn-gen2.yaml (AutomaticBackupRetentionDays: 0).
*   2. This file stalled on its own fill. `size=2600g` was declared against
*      an existing 600 GB file, which VDBENCH refuses rather than extends
*      ("Insufficient amount of lun size specified"), and once the fill was
*      moved to `format=yes` it ran at 165 MB/s -- because format ignores
*      the run's `xfersize` and `threads` and writes 128 KiB at queue depth
*      2. `formatxfersize=1m` lifted it to 315 MB/s and left the depth at 2,
*      which is a fifth of what the same file reaches when overwritten.
*
* The account is in docs/ja/verification/perf-matrix-results.md. Read it:
* the same shape of failure has more than one cause.
*
* WHY CONTROLLING THE RATIO IS THE ONLY HANDLE
*
* On the same file system, at the same connection count, the NFS ladder
* moved 5.5x depending on whether the hosts read overlapping regions:
* 11,916.29 MB/s sharing one file against 2,173.37 MB/s on disjoint ones.
* SSD IOPS are consumed only for data in neither the in-memory nor the NVMe
* cache, so how much comes back from cache decides which ceiling applies.
*
* There is no documented way to disable the in-memory cache or to set its
* size (**unconfirmed** -- no statement found, which is not the same as no
* such control existing). So the ratio is controlled from the workload
* side, by choosing which region each shape reads.
*
*   cd C:\bench
*   C:\bench\vdbench50407\vdbench.bat -f vdbench-windows-smb-cachecontrolled.txt -o C:\bench\out-cc
**********************************************************************
* Every shape reads its own region, and no two shapes share one. A shape
* therefore starts with the cache holding the *previous* shape's region,
* which is disjoint from its own, so it begins close to cold without any
* cache-flush step.
*
* Two constraints set the region size:
*
*   1. A region has to be larger than the cache. In-memory read cache here
*      is 256 GB = 238 GiB. At 371 GiB per region, a shape that wrapped
*      inside its own region would still not find all of it resident.
*   2. A region has to be larger than what its window can consume, or the
*      shape wraps and starts reading what it just pulled in.
*
* ONE FILE PER REGION, WHICH REVERSES WHAT THIS FILE USED TO SAY.
*
* The earlier version pointed seven SDs at ranges of one 2,600 GB file and
* gave the reason as format volume: separate files would make VDBENCH format
* each one, "5,197 GiB of formatting before any measurement started". That
* figure counted the whole-file fill SD *and* the seven ranges. Dropping the
* fill SD -- the regions are what needs data, and together they are the file
* -- makes the two layouts format the same 2,597 GiB.
*
* At equal volume, separate files are the better shape for two reasons:
*
*   - **Format runs per SD, so seven files format concurrently.** One file
*      formats at a single queue depth of 2. Whether that actually multiplies
*      the rate is **a prediction, not a result** -- see below.
*   - Several SDs on one file is a shape this project has already recorded as
*      a mistake, under "同じファイルに複数の SD を向けない". Keeping it here
*      while calling it out there is how the wrong one gets copied.
*
* WHAT TO RECORD, WHICHEVER WAY IT GOES
*
* The fill rate. If seven-way format reaches roughly 7 x 315 MB/s, the queue
* depth of 2 was the constraint and this layout removed it. **If it does not,
* the constraint is somewhere else and the paragraph above is withdrawn** --
* write the measured rate either way. A prediction left in place without its
* result reads, to the next person, as a procedure that was verified.
*
* Region 1 is measured first, and the fill leaves the cache holding the last
* region formatted, so the first shape does not start warm. With concurrent
* format that ordering is weaker than it was with one sequential pass: seven
* streams finish at about the same time, so the cache holds a slice of each.
* **Record the disk-to-data ratio of the first shape** rather than assuming
* the ordering did the work.
**********************************************************************
hd=default,shell=vdbench,jvms=16
hd=hd1,system=localhost

* 371 GiB per SD, seven of them, 2,597 GiB in total. The volume has to hold
* it with headroom: at 100% full, writes fall by roughly a factor of eight
* before failing, and the run reports that as a measurement.
*
* `openflag=directio` (Windows). The NFS side uses `o_direct`.
*
* Both SVMs share the file system's throughput capacity. Run this while the
* NFS side is idle, and record that it was.

**********************************************************************
* The fill is a phase of the run, not a preparation step to be skipped: the
* regions have to contain data before a read of one means anything.
*
* `format=yes` creates each file at `size=` and writes it. `formatxfersize=1m`
* is required: without it format writes 128 KiB regardless of the xfersize
* above, and that alone cost a factor of two last time.
*
* elapsed=3600 is a ceiling, not a target -- format ends when the files are
* written. At 2,000 MB/s a 2,597 GiB fill takes about 22 minutes, which at
* $23.03/hour is roughly $8.50 of file system time before the first measured
* number. That is the price of controlling the ratio and it belongs in the
* cost record. **At 315 MB/s it is 2.3 hours and $53**, which is why the fill
* rate is the first thing to read in the output rather than the last.
*
* interval=30 during the fill: nothing about it is being measured, and
* per-second rows for 22 minutes bury the shapes that follow.
**********************************************************************
