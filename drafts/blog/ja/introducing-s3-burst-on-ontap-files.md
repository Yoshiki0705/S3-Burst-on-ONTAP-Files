## TL;DR

- 収集は S3 API、利用は NFS / SMB。その間にコピージョブを置かない構成を、実装とテンプレートで
  まとめたリポジトリを公開しました → [s3-burst-on-ontap-files](https://github.com/Yoshiki0705/s3-burst-on-ontap-files)
- S3 Access Point は **Origin ボリュームにだけ**付けます。Cache 側には S3 を出しません
- 同一ボリュームに対する両プロトコルの可視性を実測しました。**S3 → NFS は p50 9 ms、
  NFS → S3 は p50 873 ms。方向で約 2 桁違います**
- **この構成の中核はまだ未検証です。** FlexCache の Cache ボリューム側での可視性は測れていません。
  未検証を検証済みのように書かないことを、リポジトリの検査で機械的に強制しています
- クライアントのマウントオプションが、ストレージより結果を左右する場面があります

## 想定読者

- 既存の NFS / SMB ワークロードを持ちながら、収集側は S3 API で受けたい方
- 読み取りを複数拠点に配りたいが、全量転送は避けたい方
- Amazon FSx for NetApp ONTAP の S3 Access Point と FlexCache を組み合わせる構成を検討中の方

ONTAP の運用経験は前提にしていません。用語は都度説明します。

## 何が困るのか

S3 とファイルストレージの両方が必要になったとき、実務では概ね次のどれかに落ちます。

1. ファイルを正典にして、分析のために S3 へコピーする
2. S3 を正典にして、既存アプリにはゲートウェイや FUSE を挟む
3. 両方を正典として二重管理する

どれも合理的な選択です。問題は選択そのものではなく、**代償が見えにくいこと**にあります。

1 なら、下流が見るのは常に「コピーした時点」のものです。ジョブ間隔がそのまま遅延になり、
同じバイト列に 2 系統の課金が発生し、削除の伝播が漏れると差は開き続けます。
権限もファイル側は POSIX / NTFS ACL、S3 側は IAM とバケットポリシーに分かれるので、
監査で「誰が読めるか」を 1 つの答えで示せません。

2 なら、ロック、`rename` の原子性、部分更新といった POSIX / SMB の期待と、
オブジェクトの実体が一致しません。ゲートウェイ層が新しい単一障害点にもなります。

3 なら、差分が出たときにどちらが正しいかを決める規則が、組織に存在しないことが多いです。

## 構成

やっていることは単純です。

| 層 | 何を使うか | プロトコル |
|---|---|---|
| 収集（書き込み） | FSx for ONTAP の S3 Access Point。**Origin ボリュームにだけ付ける** | S3 API |
| 正典 | FSx for ONTAP の Origin ボリューム | — |
| 配布 | FlexCache | ONTAP 間のクラスタ / SVM ピアリング |
| 利用（読み取り） | ファンアウト先の Cache ボリューム | NFS / SMB のみ |

リポジトリ名の `burst` は、集めたデータをファイルプロトコル側へ吹き出すことを指します。
FSx for ONTAP のスループットのバーストクレジットとは関係ありません。同じ語なので、
README の 1 文目でこれを断っています。

### なぜ Cache 側に S3 を出さないのか

**書き込み経路が 1 本になります。** 正典は Origin で、書き込みは常に AWS 側の
S3 Access Point を通ります。Cache 側からの書き戻し（write-back / write-around）の
設計判断が主題から外れ、Cache は読み取り中心という FlexCache 本来の適性に収まります。

**ファンアウト先に S3 の実装差を持ち込みません。** 「ファイルを S3 で見せる」機能は、
プラットフォームごとに別の名前と別の実装を持ちます。この構成ではその機能を Origin 側の
1 か所だけで使うので、Cache 側に要求するのは FlexCache と NFS / SMB だけになります。

### 混同しやすい 2 つの機構

ここは丁寧に分けます。名前が近く、どちらも「ONTAP のボリュームに S3 でアクセスする」と
要約できてしまうためです。

| 呼び名 | 実装元 | 何をするか | 最小要件 |
|---|---|---|---|
| S3 Access Point（FSx for ONTAP に接続） | AWS | AWS 側のエンドポイントを ONTAP ボリュームに接続する | ONTAP 9.17.1 以降 |
| FlexCache duality | NetApp | **Cache ボリューム**に ONTAP 自身の S3 アクセスを許可する | ONTAP 9.18.1 以降 |

**この 2 つは別の機構です。** 実装元も有効化方法も最小バージョンも違います。
そのため、duality と S3 Access Point の接続は別の機構であり、「duality が 9.18.1 で
使えるようになったから Cache ボリュームにも接続できる」という推論は成り立ちません。
否定の方向にも使えません。

この構成はどちらも使いません。それでもこの区別を書いているのは、**両者を混ぜた記述が
実際に出回っているから**です。片方の対応状況をもう片方の根拠として引用してしまうと、
読者は存在しない前提で設計します。

リポジトリでは、この混同を**機械的に**防いでいます。`make audit` は、1 行の中で
duality と S3 Access Point の両方に触れていながら「別の機構」と書いていない行を拒否します。
正しく書いてあればマーカーは不要で、うっかり混ぜたときだけ落ちます。

## 実測したこと

Amazon FSx for NetApp ONTAP 上で、**同一ボリューム**に対して S3 Access Point と NFS の
両方からアクセスしたときの可視性を測りました。

### 測定条件

| 項目 | 値 |
|---|---|
| 計測日 | 2026-08-09（UTC） |
| リージョン | ap-northeast-1 |
| デプロイタイプ | SINGLE_AZ_1、HA ペア 1 組 |
| スループット | 128 MBps（確保値） |
| ボリューム | セキュリティスタイル UNIX、ティアリング AUTO |
| クライアント | 同一サブネットの EC2、NFSv3 |
| 並列度 | 1 |
| 測定方法 | 書き込みと読み取りを**同一ホスト・同一クロック**で実行 |
| ONTAP バージョン | **特定できず**（後述） |

### 結果

**S3 PutObject → NFS で読めるまで**（64 B、`actimeo=0`、n=30）

| min | p50 | p90 | p99 |
|---|---|---|---|
| 7 ms | 9 ms | 11 ms | 15 ms |

**NFS 書き込み → S3 Access Point 経由で読めるまで**（`actimeo=0`）

| サイズ | n | min | p50 | p90 | p99 |
|---|---|---|---|---|---|
| 64 B | 30 | 679 ms | 873 ms | 1,165 ms | 1,439 ms |
| 1 MiB | 30 | 700 ms | 904 ms | 1,423 ms | 1,650 ms |
| 8 MiB | 10 | 993 ms | 1,169 ms | 1,444 ms | 1,928 ms |

### ここから言えること

**方向によって約 2 桁違います。** 同じデータ、同じボリューム、同じホストで、
S3 → NFS は 1 桁 ms、NFS → S3 は 1 秒前後です。

**遅い方向は固定的な成分が支配しています。** オブジェクトを 64 B から 8 MiB まで
12 万倍にしても、p50 は 873 ms から 1,169 ms しか動きません。下限も 679 ms から 993 ms です。
データ量に比例する成分は 8 MiB でようやく見える程度で、大半は**サイズに依存しない待ち**です。
データ移動ではなく、反映の周期的な性質を示唆します。

「示唆します」と書いているのは、周期そのものを観測していないからです。内部実装を
確認したわけではなく、外から見た振る舞いがそう見える、という段階です。

**部分的なオブジェクトはファイル側に現れません。** マルチパートアップロードは
`CompleteMultipartUpload` まで NFS 側に見えませんでした。中途半端なファイルを
読んでしまう心配はしなくてよい、という結果です。

### いちばん実用的だったのは、実はストレージの話ではありませんでした

削除の反映を測ったところ、こうなりました。

| マウントオプション | S3 で削除 → NFS から消えるまで |
|---|---|
| `actimeo=0` | 7 ms |
| Linux 既定 | 2,171 ms |

**300 倍以上違います。** 原因はストレージ側ではなく、NFS クライアントの属性・
ディレクトリキャッシュです。Linux の既定は `acdirmin=30` / `acdirmax=60` なので、
クライアントが既に一覧を取得したディレクトリに現れたファイルは、
最大 1 分見えないことがあります。実際、完了したマルチパートのオブジェクトが
既定マウントでは 3 秒後にまだ見えませんでした。

**「書いたのに見えない」の多くは、ここを見れば説明がつきます。** 測るときと鮮度が要るときは
`actimeo=0`、同じファイルを繰り返し読むときは既定値、という使い分けになります。

## 測れなかったこと

ここが本題の半分です。

**この構成の中核、つまり S3 Access Point 経由で書いたオブジェクトが FlexCache の
Cache ボリューム側でいつ見えるかは、未検証です。** 上の測定は同一ボリュームに対するもので、
FlexCache を経由していません。前者は後者の前提条件ですが、前者の数値を後者の答えとして
引用することはできません。

理由は環境側の制約でした。検証に使えるクラスタ管理の資格情報が用意できず、
FlexCache の作成には AWS の API がなく ONTAP 経由しかないためです。
2 つのファイルシステムの間にネットワーク経路もありませんでした。

**ONTAP のバージョンも特定できませんでした。** FSx for ONTAP の `DescribeFileSystems` が
対象の既存ファイルシステムに対して `FileSystemTypeVersion` を返さず、ONTAP の REST API は
資格情報なしにバージョンを返しません。したがって上の数値は、**バージョン未知という一点において
再現性が不完全**です。

書かないという選択もありましたが、条件を明記した測定値には価値があると判断しました。
代わりに、リポジトリの検証記録に「何が言えて何が言えないか」の表を置いています。

## デプロイテンプレート

同じ測定を自分の環境で再現できるように、環境を 2 つに分けて用意しました。

| 対象 | ツール | 中身 |
|---|---|---|
| 収集側（Origin） | CloudFormation | ファイルシステム、SVM、Origin ボリューム、**VPC 内の検証ホスト**、生成される `fsxadmin` 資格情報 |
| 配布側（Cache） | Terraform（ONTAP プロバイダ） | FlexCache ボリューム、読み取り専用の NFS エクスポート |

ツールが 2 つなのは、**配布側が AWS の外にあり得るから**です。ファンアウト先は
オンプレミスの ONTAP、ONTAP Select、あるいは別リージョンの FSx for ONTAP です。
ONTAP を相手にする以上、AWS のコントロールプレーンでは記述できません。

### 検証ホストをテンプレートに含めた理由

飾りではありません。2 つあります。

**ONTAP の管理エンドポイントは VPC 内からしか到達しません。** そして FlexCache には
AWS の API がありません。つまり VPC 内のホストがないと、配布側は作れません。

**可視性の測定には、書き込みと読み取りが同一クロックである必要があります。**
2 ホストに分けると 2 つのクロックの比較になり、ミリ秒スケールでは測定になりません。

### あえて含めなかったもの

| 項目 | 理由 |
|---|---|
| クラスタピア / SVM ピア | 2 クラスタの intercluster LIF 間の IP 到達性が前提で、VPC 間なら VPC ピアリングとルートが必要です。ネットワーク構成をテンプレートが黙って変えるほうが害が大きいと判断しました。**FlexCache 作成の失敗原因として最も多いのがこれ**なので、ガイド側で最初に確認するよう書いています |
| S3 Access Point | CloudFormation に FSx for ONTAP のボリュームへ接続するリソースがありません。CLI で作ります。1 回の API 呼び出しのために Lambda をデプロイの信頼経路に入れるのは割に合いません |
| 不可逆な機能 | SnapLock と改ざん防止 Snapshot は**一切入れていません**。有効化するとボリューム・SVM・ファイルシステム全体が保持期間中削除できなくなります。検証環境はそれを置く場所として最悪です |

最後の点は、テストで機械的に守っています。どちらのテンプレートにも
不可逆機能のパラメータ名が出現しないことを検査しています。

## 未検証を検証済みのように書かないために

このリポジトリでいちばん手をかけたのは、実は文章の検査です。
未検証の主張が動作保証として読まれると、読者は存在しない前提で設計します。

段階を 4 つに分け、語を 1 対 1 で対応させています。

| 段階 | 意味 |
|---|---|
| 検証済み | 実環境で再現した。環境を併記する |
| ドキュメント記載 | 記載はあるが実機では確かめていない |
| 未検証 | 確かめていない |
| 未確認 | 公開ドキュメントに記載を見つけられていない。**「できない」ではない** |

そのうえで、次を機械的に拒否しています。

- 2 つの機構を同じ行で扱いながら「別の機構」と書いていない記述
- 各方式の適用外条件を同じ粒度で書かずに優劣を述べる語
- 本文に書いたパターン数がファイルシステムと食い違っている状態
  （数はディレクトリから数え直します。ゼロが返ったら「まだ無い」ではなく
  「読み取り側が壊れた」として報告します）

## 次に確かめること

順序は費用ではなく、**答えが出ないと設計が書けない順**にしています。

1. S3 Access Point で書いたものが Cache 側で読めるか、どれくらいで読めるか（**最優先・未検証**）
2. FSx for ONTAP Origin からオンプレミス ONTAP Cache への FlexCache（対応構成として
   明記されているが実機未検証）
3. ファンアウト数を増やしたときの挙動
4. 他プラットフォームを Cache にできるか（**未確認**）

なお、AWS が明記している FSx for ONTAP の FlexCache 対応構成は 3 通りだけで、
FSx for ONTAP を Origin とする場合の Cache は**オンプレミス ONTAP と FSx for ONTAP のみ**です。
それ以外は未確認として扱っています。「ONTAP ベースだから動く」とはまとめません。

## FAQ

**Q. S3 の全機能が使えますか。**
使えません。対応オペレーションが限られ、イベント通知・ライフサイクル・バージョニングは対象外です。

**Q. 任意のオブジェクト名が使えますか。**
使えません。S3 名は 1024 バイト、ファイル / ディレクトリ名は 255 文字までです。
スラッシュを含まない名前はすべてルートディレクトリに集まるので、数が多いと性能問題になります。

**Q. Cache 側にも書けますか。**
この構成では想定していません。書き込みは Origin 側の S3 Access Point に集約します。

**Q. 最初に決めるべきことは。**
**利用拠点で NFS を使うのか SMB を使うのか**です。Origin のセキュリティスタイルがこれに関わり、
Cache 作成時に継承される項目として扱われるため、**Origin ボリュームを作る前に**決める必要があります。
この根拠は Azure NetApp Files のキャッシュボリューム要件で、本構成の主経路で同じ規則が
成り立つかは未確認です。それでも先に決める価値があります。成り立っていた場合の手戻りが
大きく、成り立っていなかった場合に失うものがないためです。

**Q. どこから読めばいいですか。**
[構成の形](https://github.com/Yoshiki0705/s3-burst-on-ontap-files/blob/main/docs/ja/architecture.md)
→ [選び方](https://github.com/Yoshiki0705/s3-burst-on-ontap-files/blob/main/docs/ja/reference/decision-trees/choosing-this-architecture.md)
→ [検証状況](https://github.com/Yoshiki0705/s3-burst-on-ontap-files/blob/main/docs/ja/verification-status.md)
の順がおすすめです。採らない判断を早くできることを重視しています。

## おわりに

この構成が向かないケースも書いてあります。S3 固有機能が要る、NAS フレンドリでない名前を
多用する、拠点で大量に書き込む、Cache 側でも S3 で読みたい、のいずれかなら別の方式が適します。

いちばん歓迎する貢献は**検証結果**です。**否定的な結果も同じ価値があります。**
「この組み合わせは動かない」は「未確認」より強く、得るのが難しい情報です。
